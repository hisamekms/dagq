# Who may run what, and how it is recorded

Read this when the binary refuses a command, or before doing on a person's word something your role may not do.

## The check

Every command that changes the queue is checked against a default-deny policy first, for the role `DAGQ_ROLE` names (none is the person, `user`) or, in client mode (below), for the token's principal. A refusal (`<role> may not ...`) changes nothing and is recorded with you as its actor.

Take a refusal as the answer: never retry it under another `DAGQ_ROLE`, without it, through a path to the binary or a script, or in the database. Hand it to the role that has it (below), or tell the person.

## Client mode: a worker's and a job's dagq

A worker, a job and the observer get the queue service's address and a token, never the queue's path: their `dagq` sends each command to the service, which checks it for the token's principal whatever `DAGQ_ROLE` says. A refusal names a code:

- `no_use_case`: the service does not serve the command; `control_side_command`: `doctor`, `service status` or `queue-broker status`, which a person or the inbox runs on the host; `queue_named`: it names a queue (`--db`). Never add `--db` to reach the queue; hand the step on.
- `authorization_denied`: refused for your principal, as in "The check".
- `unreachable`, `unauthenticated`, `no_credential`, `client_misconfigured`: no service, token or usable address. Do not work around it (the client never opens the queue instead): try again later, or write it in the receipt.
- `response_too_large`: the answer is too long to print. Do not retry the same read: narrow it as the message says (a smaller window or limit, the next page) and run it again.
- `request_too_large`: the request is too large to send, and your `dagq` did not send it. Do not retry the same command: make it smaller (a shorter text, fewer items) or split it into several commands and run them.
- `bad_request`, `failed`, `api_version_mismatch`: read the message.

## What each role is refused

`judge-follow-up` (`follow_up.judge`) is granted only to the person (`user`), inbox and runtime planner, for follow_up tasks in any state; it moves membership only in `draft` / `ready`. Workers, jobs and the supervisor may not judge.

`agent eval <agent>` asks the supervisor for one round of an agent's eval: nobody runs the agent's LLM CLI for it. A `dev` round (`eval.request`) is the person's, the inbox's, a planner's and a worker's (of its own run only); `--split holdout|production` (`eval.request_held_out`) is the person's, the inbox's and a planner's; `--rerun` (`eval.rerun`) only the person's and the inbox's. `agent results` / `agent result` (`eval.read`) read the rounds: a worker only its own run's. `agent cases` and `agent decide` (`eval.cases`) are the person's, the inbox's and a planner's only; `agent sets` / `agent set` (`eval.read`) read the sets.

`replan request --run RUN` (`replan.request`) asks the runtime to replan a long-running run: only the person and the inbox. `replan propose --run RUN` (`replan.propose`) is a worker's proposal on its own run only. `replan resolve ID` (`replan.resolve`) decides on an operation held `blocked` (continue, withdraw or plan again): only the person and the inbox. Parking a run and applying its replacement (`replan.park`, `replan.apply`) are the supervisor's alone, with no command. While a run's replanning holds its task, changing it, landing it and resuming it are refused for every role, the person's included. Each role's part in a replanning: `reference/replan.md`.

`hold TASK|RUN --reason '...'` and `release TASK|RUN` (`task.hold`) hold a task and let it go: only the person and the inbox (what a hold does: the `dagq-recover` skill's `reference/hold.md`).

`setup-review` (`review.setup`, `reference/review-setup.md`): only the person and the inbox. Approving beforehand with `--yes` (`review.setup_approve`) is the person's alone. Its job (`setup-review-job`) may only read the queue.

`edit` may not replace a title, description or acceptance with an empty or whitespace-only value, for any role, the person's included: the blank check refuses it and leaves the task and `task_edited` unchanged (the authorization check comes first, and its refusal is recorded as `authorization_denied` as always). To drop a draft, `cancel` it.

`revisit` (a draft's revisit time) is a planning command (`task.write`): the person, the inbox and a planner may set, change or clear it on a `draft`; a planner may not give one to a draft whose runtime planners are used up (only the person or the inbox does).

- **worker**: `supervise`, `plan`, `up` / `down` / `inbox` / `install` / `auto-update`, `queue-broker start` / `stop` (`service.lifecycle`, as `up`), `init` / `migrate`, `session` (its own run's is the wrapper's), `watch` (in client mode: `no_use_case`); `integrate`, `review`, `observe`, `throughput-review`, `setup-review` (through the queue broker, from a container: `control_side_command`), `ready` (with or without `--inherit`), `cancel`, `add` / `edit` / `submit` / `judge-follow-up` / `revisit` and every other planning command, `goal ...` (but `goal list` / `goal show`), `request add` / `request decline`, `mark`, `answer`, `ask close`, `replan request` / `replan resolve`, `hold` / `release`, `recover`, `rebind`, a session's screen and log, `planner request`, `report` / `graph --out`, `ci failures` (`ci.read`), `finding ...`, and `ask`, `note` and `replan propose` on anything but its own run or task (`authorization_denied`); `agent eval` with `--split holdout|production`, `--set` or `--rerun`, `agent cases` / `agent decide` / `agent sets` / `agent set`, or `agent result` of another run's round (`authorization_denied`). It opens only `worker_question` asks.
A priority a person set (on a goal, or on what a task takes) only the person and the inbox change. Any other actor's `set-priority` (`--inherit` too) and `goal edit --priority` of it, and a `goal add` / `add` priority other than the request's, are refused (`authorization_denied`, `a person's priority`). A move by another actor (`set-goal`, a follow_up's `out_of_scope`) is not refused for it; a person's priority of the task's own stays on any move.

- **planner**: `ready` (with or without `--bypass-review` or `--inherit`), `goal ready`, `goal review`, `integrate`, `review`, `recover`, `supervise`, `observe`, `answer`, `ask close`, `finding record`, `request add` (the inbox's and the person's), `setup-review`, `replan request` / `replan propose` / `replan resolve`, `hold` / `release`, `request decline` and `ask --kind planner_question --request N` of a request it was not opened for (only the request's own planner declines it or asks on it; another planner, of another request, a draft or a finding, is refused with `authorization_denied` and no ask opens), a session's screen and log (`run screen` / `run log` / `run send`, `planner screen` / `planner log` / `planner send` / `planner request`), `session` / `planner-session` (the wrappers' own, by the tokens the runtime issues them), `run close-workspaces`; any ask on a run (it opens only `planner_question`, on a task, a finding or its own request); changing or canceling a task once it is `in_progress` (except recording a follow_up membership judgement with `judge-follow-up`); `revisit` of a task that is not a `draft`, or of a draft whose runtime planners are used up; withdrawing another planner's proposal; changing or canceling (`edit`, `set-goal`, `set-paths`, `set-priority`, `revisit`, `draft`, `dependency`, `cancel`) a task of a `revising` proposal another planner owns, or of one whose owner is unrecorded or only a role's name (the planner the revise went to owns it; a submitted proposal's task stays any planner's); `agent eval --rerun`; changing a person's priority (above); moving a goal review's `goal_gap` draft out of its goal with `set-goal` (to another goal or `--none`; `task.write`, the rule in `register.md`, "A follow_up's membership"). On a run it may only write a `note`.
- **review, recovery, plan review, goal review, throughput review and setup-review jobs**: every command that changes state (`setup-review` too) (in client mode: `no_use_case`, and `authorization_denied` for `integrate`, `review`, `observe`, `throughput-review`, `setup-review`, `note`, `ask`, finding writes, the planning commands, `request add` / `request decline`, `mark`, `answer`, `ask close`, `ready --inherit`, `hold` / `release`, `replan request` / `replan resolve`, `recover`, `rebind`, a session's screen and log, `planner request`, `report` / `graph --out` and `agent eval`, `results`, `result`, `cases`, `decide`, `sets` and `set`), and `ci failures` (`ci.read`, `authorization_denied`). Their verdict is data the supervisor applies; the setup-review job's files are data `setup-review` checks before showing them.
- **observer**: every state change but `finding record`, `finding resolve` and `ask --kind blocked --finding ID` (in client mode: `integrate`, `review`, `observe`, `throughput-review`, `setup-review`, `finding dismiss`, `note`, other asks, the planning commands, `request add` / `request decline`, `mark`, the dialogue and operations the person and the inbox run (`answer`, `hold`, `recover`, `report`, ...), `agent eval`, `agent cases` and `agent decide` are `authorization_denied`; its reads, `ci failures` (`ci.read`), `agent results` / `agent result` and `agent sets` / `agent set` are answered, the rest `no_use_case`).
- **executor-telemetry** (no `DAGQ_ROLE`: a queue service principal the control side issues a token of, for one run or one target of no run, to the process that runs an agent, never to the agent): every use case but `telemetry_report`, a read included, and `telemetry_report` of any target but its token's or of a session the control side did not register to that target (`authorization_denied`).
- **inbox**: nothing a person may do (it acts on the person's word) but `setup-review --yes` and the queue broker's records (`queue_broker.record`, no command: the broker records its refusals and its sweeps of the verifications' tokens as the person, a supervisor may record its sweeps, and every AI actor is refused it with `authorization_denied`); landing and pushing themselves are the integrator's, reached through `integrate`. It registers no work itself: a plan the person asks for goes to a runtime planner as a request (`request add`, `skills/dagq-inbox/reference/requests.md`).

`telemetry_report` (`telemetry.report`) has no command: the worker's, every job's, the observer's and a planner's tokens are refused it (`authorization_denied`), and no command makes a telemetry token.
No command makes any other token either (`token.issue`): the queue service issues a principal's token at its parent's request (the person's, the supervisor's; the person's and the inbox's job only one within their own capabilities, as a command of theirs starts, and that job's executor's telemetry), refuses an AI actor's request for any other (`authorization_denied`), replaces a job's token only at the request of the parent that asked for it once the process that asked has ended (another parent's issue of it is `authorization_denied`, and so is its revocation while that process runs; one with no parent it can tell, as an older binary left, only once the queue records that its job ended or, keeping no record of it, no process that may have asked for it runs), and issues the integrator's only with the supervisor's landing slot, for that run's landing.

`plan` opens no planner for anyone: people no longer open planners, and it fails with a pointer to the inbox's request. A person at a terminal without `DAGQ_ROLE` may still `request add` and run the planning commands directly.

## The inbox acts on the person's behalf, and the record says so

The inbox acts on the person's word (answers, requests, `dagq-recover`), and the record keeps what it did apart from what the person did themselves. A `!` command in the inbox's terminal is the inbox's; to record an action as the person's own, the person types it in a terminal without `DAGQ_ROLE`.

## Advisory, not a sandbox

Everything runs as one user on the host (a worker put in a container never falls back to the host). The check stops mistakes and records who did what, but a process faking the environment or opening the database gets past it: so never work around a refusal.
