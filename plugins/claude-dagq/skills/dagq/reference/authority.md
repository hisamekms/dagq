# Who may run what, and how it is recorded

Read this when the binary refuses a command with `<role> may not <capability> (<reason>)` or with a `queue_service` code (`{"error": ..., "queue_service": {"code": ...}}`, a worker's or a job's `dagq` in client mode), or before doing on a person's word something your role may not do.

## The check

Every command that changes the queue names its caller from the environment (`DAGQ_ROLE`, `DAGQ_ACTOR_ID`, `DAGQ_RUN_ID`, `DAGQ_TASK_ID`; no `DAGQ_ROLE` is the person, `user`) and is checked against a fixed, default-deny policy before it changes anything. An unknown `DAGQ_ROLE` stops every command. A refusal changes nothing, is recorded as an `authorization_denied` event with you as its actor, and prints `{"error": "<role> may not <capability> (<reason>)", "denied": {"role", "capability", "reason"}}` (a job: `reviewer may not change queue state`; the observer: `observer may not change queue state`). Reasons: `not granted` (the role never has it), `not on this resource` (not your run, task, planner or proposal, or a task already started), `not of this kind` (an ask kind your role does not open), `reserved`.

Take a refusal as the answer: never retry it under another `DAGQ_ROLE`, without it, through a path to the binary or a script, or in the database. Hand the step to the role that has it (below), or tell the person.

## Client mode: a worker's and a job's dagq

The runtime gives the worker (and its resume), the review, recovery, plan review, goal review, throughput review and setup-review jobs and the observer the queue service's socket (`DAGQ_SERVICE_SOCKET`; in a run's container, the queue broker's URL `DAGQ_SERVICE_URL` instead) and a token's file (`DAGQ_SERVICE_CREDENTIAL_FILE`), never the queue's path. Their `dagq` then opens no queue: it sends each command to the service, which checks it against the same policy for the token's principal (the run's worker, the job), whatever `DAGQ_ROLE` says. A refusal exits 1 and prints `{"error": "<message>", "queue_service": {"code": "<code>"}}`:

- `no_use_case`: the command is none of the service's use cases (`init`, `add`, `edit`, `submit`, `ready`, `cancel`, `goal add`, `integrate`, `answer`, `ask close`, `mark`, `recover`, `review`, `up`, `watch`, `report`, `doctor`, `ci failures`, ...). Refused by the client; nothing is recorded.
- `queue_named`: the command names a queue (`--db`). Refused by the client; nothing is recorded. Never add `--db` to reach the queue.
- `authorization_denied`: the service refused it for your principal (a `note` or `ask` outside your run and task, a finding write that is not your role's); the message is `<role> may not <capability> (<reason>)`, and it is recorded as `authorization_denied` with you as its actor.
- `unauthenticated`: no token, one never issued or revoked, or its run has ended; recorded as `queue_service_unauthenticated`. `no_credential`: the token's file does not read; nothing is recorded.
- `unreachable`: no service answers on the socket (or no broker at the URL); nothing is recorded, and the client does not open the queue instead. Do not work around it: wait and try again later, or write it in the receipt.
- `client_misconfigured`: the environment names both a socket and a URL, a URL that does not read, or (with a URL) a `DAGQ_RUN_ID` that holds a control character; nothing is sent. Write it in the receipt.
- `bad_request`, `failed`, `api_version_mismatch`: the params do not read, the use case failed (a missing task, ...), or the service speaks another API version.

`locate` (the launcher's `--resolve`) answers `client_mode: true` with the `socket` (in a run's container, the queue broker's address as `broker` instead) and no `db`. Reads (`show`, `list`, `events`, `stats`, `kpi`, ...) print what the command line prints.

## What each role is refused

`judge-follow-up` (`follow_up.judge`) is granted only to the person (`user`), inbox and runtime planner, for follow_up tasks in any state. It moves membership only in `draft` / `ready`; workers, jobs and the supervisor may not judge. Judgement and movement grant no adoption and preserve source task/run/goal and depth.

`agent eval <agent>` asks the supervisor for one round of an agent's eval, which it runs itself: nobody runs the agent's LLM CLI for it. A `dev` round (`eval.request`) is the person's, the inbox's, a planner's and a worker's (of its own run only); `--split holdout|production` (`eval.request_held_out`) is the person's, the inbox's and a planner's; `--rerun` of a held-out set already run (`eval.rerun`) only the person's and the inbox's. `--set ID` runs a production set of the queue's side whole as production, never with `--cases`. `agent results` / `agent result` (`eval.read`) read the rounds: a worker only its own run's. The supervisor runs rounds and asks for none.

`agent cases <agent>` asks the supervisor to make a production set of the agent's cases from its production reviews, labeled by another provider's job, and `agent decide` records a person's label of a disputed case (`eval.cases`): the person's, the inbox's and a planner's only. `agent sets` / `agent set` (`eval.read`) read the sets. The supervisor makes the sets it is asked for and asks for none.

`replan request --run RUN` (`replan.request`) asks the runtime to replan a long-running run: only the person and the inbox. `replan propose --run RUN` (`replan.propose`) is a worker's proposal on its own run only, through the queue service in client mode; it stops and changes nothing. Parking a run and applying its replacement (`replan.park`, `replan.apply`) are the supervisor's alone, with no command. While a run's replanning holds its task, `ready`, `edit`, `cancel`, dependency changes, `integrate` and a resume of it are refused for every role, the person's included.

`hold TASK|RUN --reason '...'` and `release TASK|RUN` (`task.hold`; a run's ID names its task) hold a task so that the runtime neither claims it nor resumes or recovers its run, and let it go: only the person and the inbox. A held task keeps its status, and a turn already going is not stopped.

`setup-review` (`review.setup`) has a coding agent generate the review's settings in a temporary checkout and writes them to the working tree only at the person's approval (`reference/review-setup.md`): only the person and the inbox. Approving beforehand with `--yes` (`review.setup_approve`) is the person's alone: the inbox and every other actor are refused it. Its job (`setup-review-job`) may only read the queue: every command that changes state is refused.

`revisit` (a draft's revisit time) is a planning command (`task.write`): the person, the inbox and a planner may set, change or clear it on a `draft`; a planner may not give one to a draft whose runtime planners are used up (only the person or the inbox does).

- **worker**: `integrate`, `answer`, `ask close`, `ready`, `cancel`, `add` / `edit` / `submit` / `judge-follow-up` / `revisit` and every other planning command, `goal ...` (but `goal list` / `goal show`), `request add` / `request decline`, `replan request`, `hold` / `release`, `recover`, `review`, `supervise`, `observe`, `plan`, `up` / `down` / `inbox` / `install` / `auto-update`, `init` / `migrate` / `rebind`, `setup-review`, `mark`, `session`, `ci failures` (`ci.read`) (in client mode: `no_use_case`); `finding ...`, and `ask`, `note` and `replan propose` on any run or task but its own (`authorization_denied`); `agent eval` with `--split holdout|production`, `--set` or `--rerun`, `agent cases` / `agent decide`, or `agent result` of another run's round (`authorization_denied`). It opens only `worker_question` asks.
A priority a person set (`priority_by: human` on a goal, or on what a task takes) only the person and the inbox change. Any other actor's `set-priority` (`--inherit` too) and `goal edit --priority` of it, and a `goal add` / `add` priority other than the request's, are refused with the person's value and recorded as `authorization_denied` (`a person's priority`); plan review leaves its `lower_priority` unapplied. A move by another actor (`set-goal`, a follow_up's `out_of_scope`) is not refused. With `set-goal` the task keeps the value as its own, a person's, unless the new goal has the same value as a person's. A follow_up moved by its `out_of_scope` judgement takes the new goal's instead of a value it only took from its old goal (recorded as `dropped_on_move` in `task_priority_changed`); a person's priority of the task's own stays on any move.

- **planner**: `ready` (with or without `--bypass-review` or `--inherit`), `goal ready`, `goal review`, `integrate`, `review`, `recover`, `supervise`, `observe`, `answer`, `ask close`, `finding record`, `request add` (the inbox's and the person's), `setup-review`, `replan request` / `replan propose`, `hold` / `release`, `request decline` and `ask --kind planner_question --request N` of a request it was not opened for (only the request's own planner declines it or asks on it; another planner, of another request, a draft or a finding, is refused with `authorization_denied` and no ask opens), a session's screen and log (`run screen` / `run log` / `run send`, `planner screen` / `planner log` / `planner send` / `planner request`), `session` / `session-event` of a run; any ask on a run (it opens only `planner_question`, on a task, a finding or its own request); changing or canceling a task once it is `in_progress` (except recording a follow_up membership judgement with `judge-follow-up`); `revisit` of a task that is not a `draft`, or of a draft whose runtime planners are used up; withdrawing another planner's proposal; `agent eval --rerun`; changing a person's priority (above). On a run it may only write a `note`.
- **review, recovery, plan review, goal review, throughput review and setup-review jobs**: every command that changes state (`setup-review` too), and `ci failures` (`ci.read`) (in client mode: `no_use_case`, and `authorization_denied` for `note`, `ask`, finding writes and `agent eval`, `results`, `result`, `cases` and `decide`). Their verdict is data the supervisor applies; the setup-review job's files are data `setup-review` checks before showing them.
- **observer**: every state change but `finding record`, `finding resolve` and `ask --kind blocked --finding ID` (in client mode: `finding dismiss`, `note`, other asks, `agent eval`, `agent cases` and `agent decide` are `authorization_denied`, the rest `no_use_case`). It holds `ci failures` (`ci.read`), which is not a queue service use case, so in client mode it is `no_use_case` too.
- **inbox**: nothing a person may do (it acts on the person's word) but `setup-review --yes`; landing and pushing themselves are the integrator's, reached through `integrate`. It registers no work itself: a plan the person asks for goes to a runtime planner as a request (`request add`, `skills/dagq-inbox/reference/requests.md`).

`plan` opens no planner for anyone: people no longer open planners, and it fails with a pointer to the inbox's request. A person at a terminal without `DAGQ_ROLE` may still `request add` and run the planning commands directly.

## The inbox acts on the person's behalf, and the record says so

The inbox may answer every ask, record a planning request (`request add`), hand an open planner a follow-up (`planner request`) and carry out `dagq-recover` (`integrate`, `recover`, `review`, `ready --bypass-review`, `ready --inherit`, `cancel`, `up` / `down` / `install`, ...) on the person's word. The record keeps it apart from the person's own action:

- each event's `actor` (`events --full`, `show --full`) has role `inbox` for what the inbox did and `user` for what the person typed; a landing it asked for has `requested_by: inbox`
- an answer's `authority` (`ask_answered`) is `delegated` from the inbox, `user` from the person, `runtime` when the runtime closed it; `approval: true` marks an answer that approves (landing, plan, goal, update, a `decide`, a finding's `propose` / `dismiss`)

A `!` command typed in the inbox's terminal inherits `DAGQ_ROLE=inbox` and is recorded as delegated. To record an action as the person's own, the person types it in a terminal without `DAGQ_ROLE`.

## Advisory, not a sandbox

Everything runs as one user on the host (`status` and `doctor` show `actors` with `backend: host`, `enforcement: advisory`, `sandboxed: false`; once a supervisor can run Codex, the worker row's `providers` shows the Codex worker `confined`: its OS sandbox stops writes and signals, but it is not isolated). The exception is a worker the repository's settings put in a container: its row says so (`status`'s and `doctor`'s `runtimes` show where the worker and the verification of `integrate` run), and while that container cannot be used the worker does not run at all, never on the host instead. The check stops mistakes and records who did what; a process that fakes the environment or opens the database gets past it. That is why working around a refusal is never allowed: it is not isolated, only trusted to hold.
