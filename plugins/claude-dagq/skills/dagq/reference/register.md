# Registering goals and tasks: the details

What `SKILL.md` section 2 names in short. `DAGQ="${CLAUDE_PLUGIN_ROOT}/bin/dagq"`.

## Goal fields and states

Collect, asking only for what is missing: title (the problem, one line), description (what is wrong today and what the repository looks like when solved), acceptance (how the whole goal is judged after every task landed), constraints (naming, boundaries, what not to do, shared by every task), doc (a committed document, relative to the repository root), priority and tags.

- `--priority LEVEL` (default `normal`; the levels of "Priority" below): the source of its tasks' priority. Its tasks without one of their own inherit it ("Priority"). `goal edit ID --priority LEVEL` changes it while the goal is draft or open.
- `--tag TAG` (repeatable): what the goal is about, a lowercase label like a task's `--change`. When the repository's `dagq.toml` lists `[goals] tags`, give tags from it: `goal add` / `goal edit` refuse another, and `lint` reports (`missing_goal_tag`, `goal_tag_outside_set`) and `submit` refuses (`GoalTagMissing`, `GoalTagNotInSet`) the task of an unclosed draft goal with no tag or one outside the list. Without the list only the form is checked. `goal edit ID --tag T...` replaces them all, `--no-tags` removes them. `goal list --tag T` narrows to them.

The planner registering a goal gives it both: tags from the vocabulary for what it touches, and a priority by what waiting for the whole goal costs (the levels below), or as the person's words or the repository's rules say.

A goal has no verification commands; a goal-level check is a final task depending on the others. It is draft or open: the tasks of a `goal add --draft` goal are never claimed, even when `ready`. Adopt it by submitting it (`submit --goal ID`; a `pass` lifts the draft), or reject it with `goal close ID --verdict abandoned`. The observer's findings, and how they become proposals: `reference/observer.md`.

## Task fields

Split the goal into tasks, each one session in one worktree. A task's prompt shows its goal, its dependencies' receipts and siblings in progress, so siblings agree on names. Collect per task:

- title (one line)
- description (what to change and where; for a task without `--paths`, the files it mainly touches). A task that changes behavior or a specification names here or in `--context` the related documents (repository-relative path and section) and why each needs updating
- acceptance (how a reviewer decides it is done). Split it into numbered items a reviewer can check one by one: the worker maps each item to what meets it before its receipt. For a behavior change, make the changed behavior and its related documents checkable for agreement. For a measuring task, state the number of rounds (and whether they alternate), the table's columns, the formula of each value (what is divided by what, which interval of waiting is subtracted), and where the evidence lives (a document section, CSV, script, the command and its time bounds such as `--since` / `--until`); for one that does not fit (rounds of a one-time read), say why. A criterion widened to "anything of the same form" names the grep or list that bounds it. A worker cannot create or drive a throwaway queue (`init`, `add`, `up`, or `doctor` / `stats` / `kpi` run by hand against a real scratch queue): authorization gives it no `queue.admin`, and its state-changing commands reach only its own run and task. So write no such hand steps into a worker's acceptance: make the check a test (an integration test fixture or e2e), or keep it outside the task as a check for the person or the inbox.
- verification commands (run by `integrate` after its rebase; repeat `--verify`)
- dependencies (tasks that must be `completed` first, repeat `--depends-on`; to wait for another goal, `--depends-on-goal ID`: claimed only once that goal is closed `achieved`, `reference/inspect.md`)
- `add --wait-for-build`; `edit TASK --wait-for-build` / `--no-wait-for-build` (draft / submitted): declare or withdraw waiting until the supervisor's build commit contains every direct dependency's landed commit before claiming the task.
- `--context` (why it exists, what to read first)
- `--evidence` (receipt checks to report `passed` with evidence: `tests`, `subagent_review`; a missing one parks the run, `evidence_missing`). `e2e` is not a receipt check (ADR-t1233-2): no worker runs it, and `--evidence e2e` makes the runtime run the e2e on the host after the review passes, whatever the diff. When `dagq.toml` has `[e2e] paths`, a run whose diff touches them gets that e2e too, so a task needs `--evidence e2e` only when the real cmux must check it whatever its diff (`reference/scope.md`).
- `--paths GLOB` (repeatable) limits what a task may change: a run changing more parks (`scope_violation`). Include the documents it needs, but it is an allowance, not a list of documents that must change: do not narrow the code it may change to fit the document list.
- `--change CHANGE`: the kind of change the task makes (a lowercase label, ADR-t980-1). When the repository's `dagq.toml` lists `[tasks] changes`, give one of them: `add` / `edit` refuse another value, and `lint` (`missing_change`) and `submit` refuse a task without one. Without the list it is optional.

Pick `--verify`, `--paths`, `--evidence`, `--change` and the files named per `reference/scope.md`. The task's `--kind` was removed (ADR-t980-1): `--change` and the area (read from the landed diff) replace it, and `add` / `edit` refuse `--kind`.

## From draft to ready

A one-shot task omits `--goal`. `add` makes a `draft`, never claimed. `submit` (refusing what `lint` rejects) makes the tasks `submitted`, never claimed, in one proposal owned by this session. Plan review checks each proposal in turn:

- `pass` makes its tasks `ready`.
- `revise` returns them to `draft` with reasons for their planner to fix and `submit --proposal ID` again.
- `concern` asks the person through the inbox.

`proposal list` / `proposal show ID` read proposals. Its planner withdraws one with `proposal withdraw ID` (a dropped plan, or `EmptyProposal`): it ends `canceled`, its submitted tasks `draft` (`reference/inspect.md`). Only plan review readies a task; `ready --bypass-review` skips it on a person's explicit word. `candidates` lists claimable ready tasks; a ready one missing from it is blocked (`show ID`).

## Changing a registered task

`edit` changes a draft or submitted task, `draft ID` takes a ready or submitted task back, `cancel ID` drops it (`--duplicate-of X` for a duplicate), `dependency add|remove TASK PREDECESSOR` (or `--goal ID`) changes prerequisites. `set-goal`, `goal edit`, `edit`: `reference/inspect.md`; `set-paths`: `reference/scope.md`.

## Priority

Five levels order claiming:

- `interrupt`: a rare cut-in, never routine
- `urgent`: a defect stopping operation
- `high`: a prerequisite of other work
- `normal`
- `low`: deferred

The goal's priority is the source (ADR-t1639-1). A task's priority is its own when it has one, else its goal's, else `normal` (no goal); `priority_source` says which (`task`, `goal`, `default`). `add --priority LEVEL` gives a task its own (omit it to inherit), `set-priority TASK LEVEL` sets it and `set-priority TASK --inherit` clears it, both while `draft`, `submitted` or `ready`. A task's own priority is for raising or lowering a few tasks of a goal; otherwise change the goal's (`goal edit ID --priority LEVEL`). Its tasks without their own follow the goal's current priority in every status; it changes the order only at a `ready` task's next claim and never stops a running run. A task without its own priority moved to another goal inherits that goal's. Claim order, and urgency without drafting or bending dependencies: `reference/inspect.md`.

## For a planner: checks, traffic control, revise, requests and runtime planners

What the `dagq-planner` skill's sections 1 to 3 name in short.

**Wait for the installed build.** In a queue whose installed dagq binary must contain a prerequisite's landing before a task can run, register it with `--wait-for-build` and `--depends-on ID`, repeating the dependencies as needed. Use this declaration rather than a handwritten build gate in `--verify`, which runs after claiming. Declare it only when the installed binary understands the flag; older binaries reject it. A queue running a build without a commit identifier cannot judge ancestry and claims with a warning. Do not declare it just to wait for documentation-only landings: they do not trigger an automatic build update.

**Before and after `add`.** Name in the description of a task without `--paths` the files it mainly touches: a forecast plan review and `related` match, not a limit, never `--paths` (`reference/scope.md`). To wait for another goal, depend on the goal (`--depends-on-goal ID`), not its last task, which follow-up drafts outlive; inside a goal, task dependencies (`reference/inspect.md`). A task needing paths outside its `--paths` (a `failed` receipt names them): `set-paths` before a claim, else add it again wider. Before each `add`, `"$DAGQ" search` the problem's file and test names and title words; after it, `"$DAGQ" related ID`, reading only the top candidates in full (`show ID --full`). Cancel a duplicate or work already done: `"$DAGQ" cancel ID --duplicate-of X`.

**Traffic control is plan review's.** It checks the proposal against other proposals and ready tasks (duplicates, done work, conflicts, same-file dependencies) and adds dependencies, lowers priorities or cancels an obvious duplicate itself. Beyond `search` / `related`, a planner does not take stock of other drafts, or re-wire or park other tasks. Give a task its own priority only when the person says it goes first or can wait (`add --priority`, `set-priority`); otherwise it inherits its goal's. The goal's priority and tags are given by the planner registering the goal ("Goal fields and states"). Never draft other tasks or bend dependencies to hurry one.

**A revise.** "Plan review sent proposal N back" with the reasons reaches the proposal's planner: typed into its terminal or handed as its next turn while it is open, or in the initial prompt of a runtime planner opened for it once it is gone. The proposal's drafts are `draft` again (tasks plan review reopened stay `submitted` and go again as they are). Fix what the reasons point at with `edit`, `dependency`, `add` or `cancel`, `lint --proposal N`, then `"$DAGQ" submit --proposal N`. If that fails with `EmptyProposal` (a bypass or `cancel` left no draft), or the plan is dropped: `"$DAGQ" proposal withdraw N` (it ends `canceled`, its `submitted` tasks `draft`). A fix the reasons name is made as they say, without asking (the `dagq-planner` skill's Basic policy, ADR-t451-1). A fix that changes the plan's intent (acceptance, scope, the relation to the goal) goes up only when the queue, the repository, the ADRs and the person's precedents cannot settle it:

`"$DAGQ" ask --task ID --kind planner_question --because scope --question '...'` (everything the person needs, the recommendation), report and stop. The answer arrives as `answer to ask <id>: ...`; apply it. A revise left unanswered is told to the inbox (`check the planner`).

People no longer open planners (ADR-t1394-1: `dagq plan` is refused). A person's planner opened before keeps running until it ends: once its agent has exited (`/exit`, or `planner send --key exit`), the supervisor closes the workspace and its record 60 seconds later, recorded as `planner_closed` (ADR-t1300-1).

A ready task plan review must change is moved back to `submitted` (never claimed) into a proposal of its own for a runtime planner, with the reasons: fix it and `submit --proposal N`. A person's concern (`approve_plan`) goes to the inbox, never to a planner; its `send_back` returns as a revise.

**A runtime planner for a draft** first runs `related ID` on it (and `search`), judges a follow_up's membership ("A follow_up's membership" below), then does one of what its prompt lists: adopt (complete it with `edit`, `lint`, `submit`), drop (`cancel` and `note`; `cancel --duplicate-of X` when a candidate already covers it), or ask (`planner_question` with `adopt` / `cancel` / `keep_draft` and its recommendation) only for what the Basic policy raises: a person's `scope` or `discard` it cannot settle, a call it is not confident of, or a follow_up past ADR-t808-1's limit (depth 3 or more; a missing, closed or unknown source goal at registration; or no current goal or a closed current goal), which always waits for the person's adopt. `set-goal` and `judge-follow-up` keep registration facts and depth, and never count as adoption. An existing person's adopt remains valid. Record why it adopted or dropped in a `note` or the task's `context`. It reports briefly and stops; the runtime ends the session. A draft kept with `keep_draft` or left undecided (`request a plan for the draft`) stays a draft until the inbox, on the person's word, records a planning request that names it (`request add --ref task:N`), or until its revisit time comes ("A draft's revisit time" below); that request's runtime planner decides it the same way, asking the person only what the Basic policy raises. The person may instead decide it in their own terminal (no `DAGQ_ROLE`).

**A draft's revisit time.** When a draft cannot be decided yet but you know when it can (after a task lands, after a period to measure), keep it with a time instead: `"$DAGQ" revisit ID --at <RFC 3339 time> --note '<what to look at then>'`. A runtime planner sets it as it keeps the draft, after a `keep_draft` answer or, when keeping it is its own recommendation, without asking; the person and the inbox set, change (`--at` again) or clear (`--clear`) it too. Once the time comes the runtime opens a planner for the draft again, even one kept by `keep_draft` or one a person added, as a bundle of its own, with the time, the note and the last decision (its `planner_question`s and its notes) in the prompt. The time is used once: a planner that keeps it again sets a new one. That planner counts toward the draft's planners; a draft whose planners are used up takes a revisit time only from the person or the inbox (one planner past the limit). A draft an open planning request names waits for that request's planner first. Without a time, a kept draft waits for a request as above. `show ID` gives the time (`revisit`); setting, changing, clearing and its coming are events (`draft_revisit_set`, `draft_revisit_cleared`, `draft_revisit_due`) with their actor. Only a `draft` takes one; workers, jobs and the observer are refused.

**A follow_up's membership** (ADR-t1504-1, ADR-t1504-2). A follow_up draft whose source goal is not `none` (`show ID`: the material's `source_goal_id` and `source_goal_state`, `unknown` included) is judged against that source goal's acceptance, not its current goal's, before you adopt or ask (a drop may skip it, step 5). Membership, adoption and priority are three separate calls:

1. **Start from the worker's proposal.** The material's `membership_proposal` (classification, acceptance items, reason; may be null) is where you start, not a judgement. Read the source goal's acceptance (`goal show SOURCE`), the source receipt and what it points at, and earlier judgements (`show ID`'s `membership_judgements`; one that still holds is not recorded again).
2. **Ask one question:** could the source goal's acceptance be said to be met without this follow-up? No: `required` (it stays in, or goes back to, the source goal). Yes: `out_of_scope` (it goes to another goal). Size, priority, relatedness and the worker's `category` do not decide it. When you cannot tell, look for grounds (the acceptance, the receipt, the source, the ADRs) and decide; ask (`planner_question --because scope`, the membership question in it) only when the goal's intent is needed. `undecided` records why it could not be settled, not a place to park it: `submit` refuses it and the source goal cannot close; after the answer, record `required` or `out_of_scope`.
3. **Record it before you adopt or ask:** `"$DAGQ" judge-follow-up ID --classification required|out_of_scope|undecided --acceptance-item '<the item>' --reason '<why the acceptance can or cannot be met without it>' --evidence '<receipt of run R, commit, document section or task>'` (repeat `--acceptance-item` and `--evidence`; `required` needs an item, `required` and `out_of_scope` need evidence). `out_of_scope` adds `--destination-goal G`; an `unknown` source adds `--source-goal G`, the goal you judged against, with evidence. A draft or ready task moves with it in the same transaction (not a `required` one whose source goal is closed; a later state records the judgement only).
4. **The destination of `out_of_scope`:** `search` and `goal list` for an existing open goal whose problem it belongs to first. If a candidate goal's acceptance does not need the improvement and its priority is higher than the same-tag deferral goal's, choose that deferral goal instead. A fitting existing goal with a lower or equal priority may still be chosen even when its acceptance does not need the improvement. This keeps deferred improvements from running at an inherited higher priority (ADR-t1639-2 decisions 1 and 2). When none fits and the source goal has tags, it goes to the **deferral goal** of the source goal's tag (ADR-t1639-2): one goal per tag, `low`, carrying that tag, holding the theme's improvements no goal's acceptance needs. Find it with `goal list --tag T`; when there is none, create it (`goal add --draft --priority low --tag T`, its acceptance saying it collects deferred improvements of that theme). For a goal with several tags, pick its main tag. Never create a leftover goal per source goal, and never put it in an unrelated large maintenance goal. A goal without tags: create a fitting goal (`goal add --draft`) only when none fits.
5. **Then decide adoption.** A move out of scope is neither adoption nor priority. Adopt it (`edit`, `lint`, `submit`), drop it (`cancel` with a `note` giving the grounds: a duplicate with `--duplicate-of X`, done already, not needed; a canceled follow-up holds no goal, so a drop may skip a judgement that would need a new goal), or ask per the Basic policy. Priority follows "Priority" above, not membership. Source task, run, goal and depth stay, and ADR-t808-1's limit still applies after any move.
6. **Correcting it.** Between `required` and `out_of_scope` give `--corrects <latest judgement id>` and a reason naming what was wrong; never back to `undecided`. `set-goal` to a goal other than the judgement's is refused: record a correction instead. A correction is yours; after an achieved close it may also open a person's ask (`reference/goal-close.md`, "After an achieved close").
7. **Acceptance is the person's.** Never weaken a goal's acceptance (remove or loosen an item) to put a follow-up out of scope: that changes the scope, so ask (`planner_question --because scope`). Once a goal's acceptance changes (`goal edit --acceptance`, any acceptance version bump), each judgement made against the older version is `needs_recheck` (`goal show ID`'s `follow_up_memberships`): read it against the new text and record it again (the same classification is a recheck) before the goal can close or the draft be submitted.

**Deferring what an acceptance does not need** (ADR-t1639-2). Apply the same question to a goal's remaining tasks, not only to follow-ups, when a goal (above all a `high` or higher one) holds work its acceptance does not need: what it needs stays and inherits the goal's priority; an improvement it does not need leaves for a fitting goal or the tag's deferral goal (step 4). When moving one, clear its own priority (`set-priority TASK --inherit`) so it takes the deferral goal's `low`, or write in its `context` why it keeps one. Only a `draft` or `ready` task moves; a `submitted` or later one stays in its goal (a follow-up's judgement is recorded all the same). A follow-up moves with `judge-follow-up --classification out_of_scope --destination-goal G` (step 3); a task that is not a follow-up moves with `set-goal TASK G`, its grounds (the acceptance items it does not serve, and why) in the proposal or its `context`. A deferred follow-up arriving after its source goal closed goes to the same tag's deferral goal; it still waits for the person's adopt when ADR-t808-1's limit applies (a closed source goal at registration), and the move does not lift that. One found required after an achieved close is not deferred: it takes the correction path (`reference/goal-close.md`, "After an achieved close"). A move to the deferral goal is neither adoption nor priority (step 5); drop what is not needed with `cancel` and a `note`.

`goal_gap` and `reopened` drafts are not judged; a `goal_gap` draft is required by birth, so do not move it out of its goal (`set-goal`); only the next goal review or the person's `approve_goal` decides it is not needed (cancel a duplicate or done one; the next goal review checks). Plan review starts from your judgement: it checks the item, the reason and the evidence, reads the surrounding evidence when they look doubtful (no acceptance item named, evidence that disagrees with the receipt or diff, an unrelated catch-all goal, a weakened acceptance, a version mismatch), sends a fixable mapping back as `revise` and a weakened acceptance as `concern`. So write the mapping someone can check without redoing your investigation.

**A runtime planner for a request** (the person's words the inbox recorded with `request add`, ADR-t1394-1) reads the words, the inbox's note, what they refer to (asks, tasks, runs, events, findings, goals) and the goals they lead to, looks for work that already covers them, and does one: plans it, declines it (`request decline N --reason '<why>'`: done already, a duplicate in flight, or not plannable as asked), or asks (`ask --request N --kind planner_question` with `plan` / `decline` and its recommendation) only for what the Basic policy raises. Up to 3 planners are opened for a request before it is `exhausted`; the inbox tells the person each outcome (`skills/dagq-inbox/reference/requests.md`).

To plan it (the `dagq-planner` skill's section 1): a goal (`goal add --draft` with its `--priority` and `--tag`, "Goal fields and states") unless it is a one-shot task or fits an open goal, and tasks with `add --goal`: acceptance, verification, dependencies, `--context` beginning `from request N`, `--paths`, `--evidence` and `--change` per the repository's rules (`reference/scope.md`), `e2e` from the diff and `[e2e] paths`, not a blanket `--evidence e2e` (above), and no throwaway-queue hand steps in a worker's acceptance ("Task fields"). After each `add`, `"$DAGQ" related ID`, cancelling a duplicate with `cancel ID --duplicate-of X`. Check the order with `"$DAGQ" graph --goal ID`, then `lint` and `submit`: `submit` refuses what `lint` rejects and makes the planner the proposal's owner, its tasks `submitted` and the request `proposed`, with no person's approval needed, even for a new goal. Report the proposal ID. The worker's provider and route: no flag (Claude headless) unless the person's words ask for `--provider codex` or `--interactive` (`reference/provider.md`, "Which to choose").

**A runtime planner for a finding** (a `kpi` one too: tasks `normal` or lower) checks `search` / `related` first, then does one: `submit ... --finding N` of tasks on an open goal or a new draft goal (no person's approval needed); `finding dismiss N --reason`; or, only for what a person must decide, `ask --finding N --kind planner_question` (`reference/observer.md`).

**A `ci_failure` finding** is the supervisor's: the CI of the watched branch turned red with new failures (`[ci_watch]` of `dagq.toml`). Its `detail` is one JSON object: `tests` (the new failing tests, or `job:<job>/step:<step>` when no test name is known), `failed_jobs`, `range` (`from` the last green commit, `to` the red one, `commits` between), `url` of the CI run, `binary_contains` (`all`, `some`, `none` or `unknown`: whether the supervisor's build contains that range) with `binary_commit`, and `run`. Copy each item into the fix task's `--description` and give the task `--priority normal`. First look for an open task that already fixes the same tests (`search`, `related`, `ci failures`); if one does, add no task: `"$DAGQ" finding dismiss N --covered-by TASK --reason '<why>'`. `--covered-by` takes only a `ci_failure` finding and a task that is not `completed` or `canceled`; `ci failures --task TASK` then lists the finding's tests under `kept_for_task`. When every test of the finding passes on the branch, the runtime resolves it while no planner is open for it.
