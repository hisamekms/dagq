# Registering goals and tasks: the details

What `SKILL.md` section 2 names in short. `DAGQ="${CLAUDE_PLUGIN_ROOT}/bin/dagq"`. Each command's flags and values: `"$DAGQ" <command> --help`.

## Goal fields and states

Collect, asking only for what is missing: title (the problem, one line), description (what is wrong today and what the repository looks like when solved), acceptance (how the whole goal is judged after every task landed), constraints (naming, boundaries, what not to do, shared by every task), doc (a committed document, relative to the repository root), priority and tags.

- `--priority LEVEL`: the source of its tasks' priority ("Priority"). A goal a request's planner adds for a request with a priority takes that value from the runtime as the person's: leave `--priority` out; another value is refused.
- `--tag TAG` (repeatable): what the goal is about. When the repository's `dagq.toml` lists `[goals] tags`, give tags from it; `lint` reports and `submit` refuses a draft goal's task whose goal has none or one outside the list.

The planner registering a goal gives it both: tags from the vocabulary for what it touches, and a priority: the request's, which the runtime gives; else by what waiting for the whole goal costs (the levels below) or as the repository's rules say. Never copy a priority out of the request's words or a `context`: the person's reaches the queue only through the request's field, or the person or the inbox setting it.

A goal has no verification commands; a goal-level check is a final task depending on the others. It is draft or open: the tasks of a `goal add --draft` goal are never claimed, even when `ready`. Adopt it by submitting it (`submit --goal ID`; a `pass` lifts the draft), or reject it with `goal close ID --verdict abandoned`. The observer's findings, and how they become proposals: `reference/observer.md`.

## Task fields

Split the goal into tasks, each one session in one worktree. Collect per task:

- title (one line). When the repository's `dagq.toml` lists `[tasks] title_prefixes`, start it with one of them (`feat(cli): ...`); `lint` and `submit` refuse another, so fix a draft's title with `edit TASK --title` before `submit`.
- description (what to change and where; for a task without `--paths`, the files it mainly touches). A task that changes behavior or a specification names here or in `--context` the related documents (repository-relative path and section) and why each needs updating
- acceptance (how a reviewer decides it is done), in numbered items a reviewer can check one by one: the worker maps each to what meets it. For a behavior change, make the changed behavior and its related documents checkable for agreement. For a measuring task, state the rounds (and whether they alternate), the table's columns, each value's formula (what is divided by what, which waiting is subtracted) and where the evidence lives (a document section, CSV, script, the command and its `--since` / `--until`), or why that does not fit. A criterion widened to "anything of the same form" names the grep or list that bounds it. A worker cannot create or drive a throwaway queue (`init`, `add`, `up`, or `doctor` / `stats` / `kpi` by hand): write no such hand steps into its acceptance; make the check a test (an integration test fixture or e2e), or a check for the person or the inbox outside the task.
- verification commands (`--verify`, run by `integrate` after its rebase)
- dependencies (`--depends-on`; to wait for another goal, `--depends-on-goal ID`, `reference/inspect.md`)
- `--context` (why it exists, what to read first)
- `--evidence` (receipt checks to report `passed` with evidence). No worker runs the e2e: `--evidence e2e` has the runtime run it on the host whatever the diff, and a diff touching `dagq.toml`'s `[e2e] paths` gets it anyway, so give `--evidence e2e` only when the real processes must check it whatever its diff (`reference/scope.md`).
- `--paths GLOB` limits what a task may change. Include the documents it needs, but it is an allowance, not a list of documents that must change: do not narrow the code it may change to fit the document list.
- `--change CHANGE`: the kind of change the task makes. When the repository's `dagq.toml` lists `[tasks] changes`, give one of them.
- `--execution-class spike`: the run investigates a premise of the plan by experiment, prototype, build or measurement instead of implementing (omitted: `implementation`). Independent of `--change`, and changed with `edit` only while the task is `draft` or `submitted`. A Spike's description holds its question, impact, method, limit, evidence and what each verdict leads to; its acceptance is a verdict with grounds, and its receipt's `spike_result` carries it (`reference/spike.md`).

Pick `--verify`, `--paths`, `--evidence`, `--change` and the files named per `reference/scope.md`. `--kind` is refused.

## From draft to ready

A one-shot task omits `--goal`. `add` makes a `draft`, never claimed. `submit` (refusing what `lint` rejects) makes the tasks `submitted`, never claimed, in one proposal owned by this session. Plan review checks each proposal in turn: `pass` makes its tasks `ready`; `revise` returns them to `draft` with reasons for their planner to fix and `submit --proposal ID` again; `concern` asks the person through the inbox.

Its planner withdraws a proposal with `proposal withdraw ID` (a dropped plan, or `EmptyProposal`; `reference/inspect.md`). Only plan review readies a task; `ready --bypass-review` skips it on a person's explicit word. `candidates` lists claimable ready tasks and the deferred ones with their reason; a ready one missing from it is blocked (`show ID`).

## Changing a registered task

`edit` changes a draft or submitted task, `draft ID` takes a ready or submitted task back, `cancel ID` drops it with its reason ("Cancel reasons" below), `dependency add|remove TASK PREDECESSOR` (or `--goal ID`) changes prerequisites. `set-goal`, `goal edit`, `edit`: `reference/inspect.md`; `set-paths`: `reference/scope.md`.

## Cancel reasons

`cancel ID` needs `--reason CODE` or `--duplicate-of X`. Choose by where the task's content is now, when you decide the cancel. When another task X holds it, name X: `--duplicate-of X` alone for an open duplicate (`duplicate`) or work X already landed (`already_done`), `--reason absorbed --duplicate-of X` when X took the content, `--reason re_registered --duplicate-of X` when X replaces it under a new ID. Otherwise: `superseded` (a decision changed; name it in `--note`, and X if a successor exists), `not_worth` (right, but not worth its change and checks), `decision_moot` (a question already answered or no longer asked), `not_repo_work` (work or observation outside the repository, for a person or the inbox), `stale` (its premise is gone, with no successor), `other` (none fits; `--note` says why). `answered_cancel` (an ask's `cancel` the runtime applies) and `unrecorded` (how statistics count a cancel without a reason) are the runtime's own; a person's `cancel` you carry out takes the code that fits it. A code not listed is recorded as it is. Only `duplicate` and `already_done` make X's pair a duplicate for `related`, `search` and `stats`.

## Priority

Five levels order claiming:

- `interrupt`: a rare cut-in, never routine
- `urgent`: a defect stopping operation
- `high`: a prerequisite of other work
- `normal`
- `low`: deferred

The goal's priority is the source: a task without its own takes its goal's and follows its changes; a change never stops a running run. Give a task its own (`add --priority`, `set-priority TASK LEVEL`; `set-priority TASK --inherit` clears it) only to raise or lower a few tasks of a goal; otherwise change the goal's (`goal edit ID --priority LEVEL`). A task without its own moved to another goal inherits that goal's, unless an actor other than the person or the inbox moves it while it takes a priority a person set: it then keeps that value as its own, still the person's, unless the new goal has the same value set by a person. A follow_up moved by its `out_of_scope` membership judgement is the exception: it takes the new goal's, the person's value being for the old goal's acceptance it was judged outside of. A priority of a task's own that a person set stays on any move. Claim order, and urgency without drafting or bending dependencies: `reference/inspect.md`.

**By where a task or goal comes from**. The runtime records each goal's and task's origin when it is made, and nothing changes it later: human-made for what a request's planner makes (a planner revising a request's proposal included) or what the person or the inbox adds; AI-made for what a finding's, a follow_up's, a goal gap's or a draft's planner or the runtime makes; `unknown` (an old row) counts as human-made. A `context` or description (`from request N` included) is not its origin.

- Plan review does not change a priority a person set, nor the priorities or goals of human-made work itself: it raises a `concern`. The CLI refuses any other actor's change of a priority a person set; a planner that doubts one asks a `planner_question` and does not work around the refusal.
- A new goal of a request without a priority, and an AI-made new goal, take one from the repository's guide (say so in the description); plan review sends it back (`revise`) when it is off and does not change it itself.
- An AI-made task takes no priority of its own (one a person set stays), and goes into an existing goal only when that goal's acceptance needs it, else into a new goal or none; plan review sends an unrelated one back (`revise`). A follow_up with a source goal goes by "A follow_up's membership" below; a move to a deferral goal ("Deferring what an acceptance does not need") stays.
- When an inherited priority looks too high, fix the membership or the goal's priority, not the task's.

## For a planner: checks, traffic control, revise, requests and runtime planners

What the `dagq-planner` skill's sections 1 to 3 name in short.

**Premises and Spikes.** Before you split the work, settle the unconfirmed premises a short read answers, move only those needing an experiment into Spikes, submit the Spikes alone and stop; a Spike's completion records a planning request the runtime gives a new planner, which decides the next step and submits the implementation for plan review again (`reference/spike.md`).

**Wait for the installed build.** When a task needs the installed binary to contain a prerequisite's landing, use `--wait-for-build` with `--depends-on ID`, not a build gate in `--verify` (it runs after claiming). Do not declare it just to wait for documentation-only landings: they trigger no build update.

**Before and after `add`.** The files a task without `--paths` mainly touches, named in its description, are a forecast plan review and `related` match, not a limit (`reference/scope.md`). Depend only on a content prerequisite: work that must land before this task can be done. Never add a dependency, or ask, only to keep tasks that touch the same files apart: the claim deferral holds a task back from hot files, and rebase or the landing resolves the rest. Record each dependency's kind (content prerequisite or conflict avoidance) and reason in a `note` or `context`. To wait for another goal, depend on the goal (`--depends-on-goal ID`), not its last task, which follow-up drafts outlive. A task needing paths outside its `--paths` (a `failed` receipt names them): `set-paths` before a claim, else add it again wider. Before each `add`, `"$DAGQ" search` the problem's file and test names and title words; after it, `"$DAGQ" related ID`, reading only the top candidates in full (`show ID --full`). Cancel a duplicate or done work: `cancel ID --duplicate-of X`.

**Traffic control is plan review's.** It checks the proposal against other proposals and ready tasks (duplicates, done work, overlaps, content prerequisites) and adds only a dependency a content prerequisite needs, or cancels an obvious duplicate, itself; tasks touching the same files it leaves to the claim deferral. It sends back as `revise` a dependency from a higher-priority goal's task onto a lower-priority goal's task whose only reason is avoiding a conflict, or one with no kind and reason recorded. It lowers only a priority an AI set on an AI-made task, by clearing it; for human-made work it raises a `concern` ("Priority"). Beyond `search` / `related`, a planner does not take stock of other drafts, or re-wire or park other tasks. Give a task its own priority only when the request has none and the person's words say it goes first or can wait; never for an AI-made task. Never draft other tasks or bend dependencies to hurry one. A content prerequisite that lifts a lower-priority goal's task by inheritance (its effective priority) is yours to solve by reordering, moving the task into the goal or splitting it; only when none of these works, raise a `planner_question` (`--because scope`): "bring the lower goal's task forward with its priority, or does the higher goal wait?"

**A revise.** "Plan review sent proposal N back" with the reasons reaches the proposal's planner; its drafts are `draft` again. Fix what the reasons point at with `edit`, `dependency`, `add` or `cancel`, `lint --proposal N`, then `"$DAGQ" submit --proposal N`; on `EmptyProposal`, or when the plan is dropped, `"$DAGQ" proposal withdraw N`. A fix the reasons name is made as they say, without asking (the `dagq-planner` skill's Basic policy). A fix that changes the plan's intent (acceptance, scope, the relation to the goal) goes up only when the queue, the repository, the decision records and the person's precedents cannot settle it: `"$DAGQ" ask --task ID --kind planner_question --because scope --question '...'` (everything the person needs, the recommendation), after making and saving every fix the answer does not touch ("Before stopping at a question" below); report and stop. The answer comes as `answer to ask <id>: ...`; apply it.

People no longer open planners (`dagq plan` is refused). A ready task plan review must change comes back `submitted` in a proposal of its own, with the reasons: fix it and `submit --proposal N`. A person's concern (`approve_plan`) goes to the inbox, never to a planner; its `send_back` returns as a revise.

**A runtime planner for a draft** first runs `related ID` on it (and `search`), judges a follow_up's membership ("A follow_up's membership" below), then does one of what its prompt lists: adopt (`edit`, `lint`, `submit`), drop (`cancel` with its reason and `note`, `--duplicate-of X` when a candidate covers it), or ask (`planner_question` with `adopt` / `cancel` / `keep_draft` and its recommendation) only for what the Basic policy raises, or for a follow_up past the follow_up limit (depth 3 or more; a source goal missing, closed or unknown at registration, even if found or reopened later; or no open current goal), which always waits for the person's adopt. `set-goal` and `judge-follow-up` are never adoption; a person's earlier adopt holds. Record why in a `note` or `context`. An adopted draft is AI-made ("Priority"); one a planning request names is planned as the person's ("A runtime planner for a request"). It reports briefly and stops. A kept or undecided draft waits for a planning request that names it (`request add --ref task:N`, the inbox on the person's word) or its revisit time ("A draft's revisit time" below), or the person decides it in their own terminal.

**Before stopping at a question (a runtime planner).** Decide first everything the answer does not touch (the other drafts of a bundle: adopt, drop, dependencies, what goes together; the fixes of a revise). Save draft edits with `edit`, and record with `"$DAGQ" note --task ID` (or `--goal ID`) what you decided, what you were about to decide, what is left open and why, and what the answer will decide. Then ask and stop: the runtime may end your session, and the planner the answer opens goes on from your notes and drafts without redoing what you decided.

**A draft's revisit time.** When a draft cannot be decided yet but you know when it can (after a task lands, after a period to measure), keep it with a time instead: `"$DAGQ" revisit ID --at <RFC 3339 time> --note '<what to look at then>'`. A runtime planner sets it as it keeps the draft (after a `keep_draft` answer, or without asking when keeping it is its own recommendation); the person and the inbox set, change or clear it too. A planner takes the draft up again then; the time is used once, so one that keeps it again sets a new one. A draft whose planners are used up takes a revisit time only from the person or the inbox. A draft an open planning request names waits for that request's planner first. Without a time, a kept draft waits for a request as above.

**A follow_up's membership**. A follow_up draft whose source goal is not `none` (`show ID`: the material's source goal and its state, `unknown` included) is judged against that source goal's acceptance, not its current goal's, before you adopt or ask (a drop may skip it, step 5). Membership, adoption and priority are three separate calls:

1. **Start from the worker's proposal** (in the material, if any), not a judgement. Read the source goal's acceptance (`goal show SOURCE`), the source receipt and what it points at, and earlier judgements (`show ID`; one that still holds is not recorded again).
2. **Ask one question:** could the source goal's acceptance be said to be met without this follow-up? No: `required` (it stays in, or goes back to, the source goal). Yes: `out_of_scope` (it goes to another goal). Size, priority, relatedness and the worker's `category` do not decide it. When you cannot tell, look for grounds (the acceptance, the receipt, the source, the decision records) and decide; ask (`planner_question --because scope`, the membership question in it) only when the goal's intent is needed. `undecided` records why it could not be settled, not a place to park it: `submit` refuses it and the source goal cannot close; after the answer, record `required` or `out_of_scope`.
3. **Record it before you adopt or ask:** `"$DAGQ" judge-follow-up ID --classification ... --acceptance-item '<the item>' --reason '<why the acceptance can or cannot be met without it>' --evidence '<receipt of run R, commit, document section or task>'` (what each needs: `judge-follow-up --help`). `out_of_scope` names `--destination-goal G`; an `unknown` source names `--source-goal G`, the goal you judged against. A draft or ready task moves with it, except a `required` one whose source goal is closed, which records the judgement only.
4. **The destination of `out_of_scope`:** first `search` and `goal list` for an open goal whose problem it belongs to. A candidate whose acceptance does not need it and whose priority is above the same-tag deferral goal's loses to that deferral goal (so a deferred improvement does not run at a higher inherited priority); one of lower or equal priority may still be chosen. When none fits and the source goal has tags, it goes to the **deferral goal** of the source goal's (main) tag: one `low` goal per tag holding the theme's improvements no acceptance needs. Find it with `goal list --tag T`, else create it (`goal add --draft --priority low --tag T`, its acceptance saying it collects them). Never a leftover goal per source goal, never an unrelated large maintenance goal. A goal without tags: create a fitting goal (`goal add --draft`) only when none fits.
5. **Then decide adoption.** A move out of scope is neither adoption nor priority. Adopt it (`edit`, `lint`, `submit`), drop it (`cancel` with its reason and a `note` giving the grounds: a duplicate with `--duplicate-of X`, done already, not needed; a canceled follow-up holds no goal, so a drop may skip a judgement that would need a new goal), or ask per the Basic policy. Priority follows "Priority" above, not membership. The follow_up limit ("A runtime planner for a draft" above) still applies after any move.
6. **Correcting it.** Between `required` and `out_of_scope` give `--corrects <latest judgement id>` and a reason naming what was wrong; never back to `undecided`. `set-goal` to a goal other than the judgement's is refused: record a correction instead. A correction is yours; after an achieved close it may also open a person's ask (`reference/goal-close.md`, "After an achieved close").
7. **Acceptance is the person's.** Never weaken a goal's acceptance (remove or loosen an item) to put a follow-up out of scope: that changes the scope, so ask (`planner_question --because scope`). Once a goal's acceptance changes, each judgement made against the older version needs a recheck (`goal show ID`): read it against the new text and record it again (the same classification is a recheck) before the goal can close or the draft be submitted.

**Deferring what an acceptance does not need**. Apply the same question to a goal's remaining tasks, not only to follow-ups, when a goal (above all a `high` or higher one) holds work its acceptance does not need: what it needs stays and inherits the goal's priority; an improvement it does not need leaves for a fitting goal or the tag's deferral goal (step 4). When moving one, clear its own priority (`set-priority TASK --inherit`), or write in its `context` why it keeps one; a person's priority stays and its clearing is refused: leave it, or ask a `planner_question`. Only a `draft` or `ready` task moves (a follow-up's judgement is recorded all the same). A follow-up moves by its judgement (step 3); another task with `set-goal TASK G`, its grounds (the acceptance items it does not serve, and why) in the proposal or its `context`. A deferred follow-up arriving after its source goal closed goes to the same tag's deferral goal and still waits for the person's adopt when the follow_up limit applies. One found required after an achieved close takes the correction path (`reference/goal-close.md`, "After an achieved close"). A move is neither adoption nor priority (step 5); drop what is not needed with `cancel` (its reason, "Cancel reasons") and a `note`.

Goal gap and reopened drafts are not judged; a goal gap draft is required by birth, so do not move it out of its goal (`set-goal`); only the next goal review or the person's `approve_goal` decides it is not needed (cancel a duplicate or done one). Other AI-made tasks record no judgement. Plan review checks the item, the reason and the evidence (doubting a missing item, evidence against the receipt, a catch-all goal, a stale version), sends a fixable mapping back as `revise` and a weakened acceptance as `concern`. So write the mapping someone can check without redoing your investigation.

**A runtime planner for a request** (the person's words the inbox recorded with `request add`) reads the words, the inbox's note, what they refer to and the goals they lead to, looks for work that already covers them, and does one: plans it, declines it (`request decline N --reason '<why>'`: done already, a duplicate in flight, or not plannable as asked), or asks (`ask --request N --kind planner_question` with `plan` / `decline` and its recommendation) only for what the Basic policy raises. What it plans is human-made ("Priority").

To plan it (the `dagq-planner` skill's section 1): a goal (`goal add --draft`, "Goal fields and states") unless it is a one-shot task or fits an open goal, and tasks with `add --goal` per "Task fields", `--context` beginning `from request N`, `--paths`, `--evidence` and `--change` per the repository's rules (`reference/scope.md`). After each `add`, `"$DAGQ" related ID`. Check the order with `"$DAGQ" graph --goal ID`, then `lint` and `submit` (no person's approval needed, even for a new goal). Report the proposal ID. The worker's provider: no flag unless the person's words ask for `--provider codex` (`reference/provider.md`, "Which to choose").

**A runtime planner for a finding** (a `kpi` one too) checks `search` / `related` first, then does one: `submit ... --finding N` of tasks on an open goal whose acceptance needs them, a new draft goal or no goal (AI-made, "Priority"; an improvement's tasks only in a goal of `normal` or lower or none); `finding dismiss N --reason`; or, only for what a person must decide, `ask --finding N --kind planner_question` (`reference/observer.md`).

**A `ci_failure` finding** says the CI of the watched branch turned red with new failures. Only the supervisor's CI watch records one: `finding record --kind ci_failure` is refused for every role, the person's and the supervisor's command line too. It names the failing tests, the commit range and whether the supervisor's build contains it. Copy them into the fix task's `--description`; the task takes no priority of its own ("Priority"). First look for an open task that already fixes the same tests (`search`, `related`, `ci failures`); if one does, add no task: `"$DAGQ" finding dismiss N --covered-by TASK --reason '<why>'` (only a `ci_failure` finding and an unfinished task). The runtime resolves the finding once its tests pass.
