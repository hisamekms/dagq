# Inspect commands and their fields

Read this when you need a field of `list`, `show`, `goal show`, `graph`, `search`, `related`, `findings`, `events`, `timeline`, `status`, `stats`, `doctor` or `ci failures`, the meaning of a task or run status, how to find a duplicate or work already done before submitting, how priority orders claiming, how to make a task wait for another goal, or how to edit a draft or submitted task.

Ordered unclosed goals (`open` and `draft`, a draft with no task included) first, then closed ones, each by `priority` highest first, then ID ascending. `--tag` (repeatable) keeps the goals with any of the tags; a tag not in the slug form is refused |

`list` answers "which tasks are moving or can move" and "how far is this goal". It prints `{"tasks": [...], "next": ID | null, "total": N}`:

- `tasks`: at most `--limit` (default 20) tasks in ID descending order (newest first). By default only unfinished ones (`draft`, `submitted`, `ready`, `in_progress`); `--status ready,in_progress` picks statuses (any of them; an unknown status exits 1 with an error), `--all` adds `completed` and `canceled`, `--goal ID` keeps one goal's tasks. `--status` / `--all` and `--goal` combine with AND.
- Each task has only `id`, `status`, `title`, `priority` (with `priority_source`: `task`, `goal` or `default`), `goal_id`, `dependencies` (predecessor IDs), `goal_dependencies` and `latest_run` (`{"id", "status"}` of the newest run, or null). `--full` adds `description`, `acceptance`, `context`, `verification_commands`, `required_evidence` (the `--evidence` checks), `paths` (the `--paths` globs; empty means unrestricted), `created_at`, `updated_at`; `effective_priority` is only in `graph` and `candidates`. Prefer `show ID` for one task.
- `next`: null means this page is the last one. Otherwise pass it as `--before NEXT` (with the same filters) for the following page; it is the ID of the first task of that page. Decide whether more pages exist from `next` alone — never by counting `tasks`.
- `total`: how many tasks match the filters across all pages.

`show`, `goal show` and `doctor` are compact by default so their size stays bounded by the number of runs or tasks: a long `description`, `acceptance`, `context` or `constraints` (and a run's `last_error`, an ask's `question` and `answer`) is cut to 300 characters ending in `…`, and the object that holds it carries `truncated: true`. Add `--full` only when you need the untruncated text, every run with all its fields, every event with its whole payload (a receipt), every ask, every process, or a run's `run_dir`.

The default compact `show ID` output has a top-level `claim_deferral` key only while the task's claim is deferred. It has the same shape as an element of `status`'s `claim_deferrals`: `{task_id, reason, since, files, runs, supervisor}`. When `reason` is `not_in_build`, `files` and `runs` are null, and it also has `build` (the supervisor's build identifier) and `missing` (`[{task_id, commit}]`, the dependencies' landings that build does not contain). `show --full` omits `claim_deferral`; read the deferral in its events of kinds `claim_deferred` and `claim_deferral_ended`.

A task that declares a build wait has `wait_for_build: true` in `task`; the field is omitted when it is not declared. This means the supervisor waits to claim it until its build contains the dependencies' landings.

Task `status`: `draft` → `submitted` (waiting for plan review; `submit` puts drafts in a proposal, never claimed) → `ready` → `in_progress` → `completed`, or `canceled`. Only plan review, `ready --bypass-review` and a retry of an `in_progress` task whose runs failed make a task `ready`. A task stays `in_progress` while any run is unfinished or awaiting integration.

Run `status` in `runs` (latest last): `claimed`, `starting`, `running`, `validating` are unfinished; `awaiting_integration` means the receipt passed validation (the verification commands have not run yet; `integrate` runs them after its rebase) and the run waits for `integrate` to land it on the resolved landing branch; `integrating` means an `integrate` process is landing it right now; `needs_session` means the landing hit a rebase conflict or a failed verification and the supervisor resumes the run's session to fix it, up to three times (`last_error` says what); `integrated` means the run was squashed onto the resolved landing branch (`result_commit` is the landed commit) and the task is `completed`; `failed` and `interrupted` keep their worktree and workspace for inspection, with the reason in `last_error`. Dependency-free tasks run in parallel (up to the supervisor's `--parallel`), each in its own workspace and worktree; a dependent task waits until every predecessor is `completed`.

Useful run fields: `branch` (`dagq/<run-id>`), `worktree_path`, `workspace_id` (cmux), `result_commit`, `last_error`, and with `show ID --full` also `run_dir` (prompt, logs, `receipt.json`, `integrate-<attempt>-verify-N.log`, one set per integrate attempt), `receipt_path`, `workspace_closed_at`.

## Runs waiting for a person (outside the slots)

A run whose live session only waits for a person (ADR-0071, which replaced ADR-0062) leaves its `--parallel` slot so another task is claimed: a `worker_question`, `answer_prompt` or `stalled` ask while the worker works, a `stuck_exit` or `answer_prompt` ask while its `/exit` waits after the receipt, and a `worker_question` or `answer_prompt` ask during a review's send-back or a resume. It keeps its lease, session and status.

- `status` `waiting`: one entry per such run, `run_id`, `task_id`, `asks` (`[{id, kind}]`), `phase` (`session` / `exit` / `revise` / `resume`), `status` (the run's), `state` (`waiting` for the person, or `returning`: the wait ended and the run waits for a free slot), `since`, `waited_secs`, and for `returning` also `ended_at` and `cause` (`answered` or `session_exited`; the other causes, `dialog_cleared`, `session_moved`, `queue_hold`, `wrapper_silent` and `phase_changed`, return the run to a slot in the same step, so such a run leaves `waiting` at once).
- Per supervisor, `slots.landing_queue` counts the runs that only wait for their landing turn (reviewed, e2e done, another run landing), up to `parallel`, and `slots.used` the other runs in slots. A heavy task, a resume or a returning run waits until `used + landing_queue` is under `parallel`; while only `used` is, the room takes only a task of `[supervisor] light_changes` that declares its `--paths` (none when `light_changes` is empty, the default). The landing queue is not a wait for a person: it is not in `waiting.count` and not bounded by `--max-waiting`. `waiting.count` is waiting plus returning runs, the number `supervise` / `up --max-waiting N` bounds (default 4; `0` keeps every run in its slot), `waiting.returning` how many of them are returning, and `waiting.limit` that flag (null for an older binary's registration). At the limit a new ask leaves its run in its slot (`run_waiting_deferred`, once per ask).
- An answer or the session's exit makes the run `returning`; it goes back to a slot when one is free, oldest first, before new claims. A dialog that went away or a session that moved on returns it at once, even beyond `--parallel`.
- `stats` `waiting`: `started` (waits started per ask kind), `waited` (per ask kind: `{count, total_secs, median_secs, max_secs}` of `run_waiting_ended`; `total_secs` is the slot time the waits would have held), `slot_wait` (the same shape for the time every run back in a slot waited for it, about 0 for one that returned at once), `over_parallel` (returns beyond `--parallel`) and `deferred` (asks `--max-waiting` kept in their slots), in the same window and `--goal` as `backend_failures`.

## Versions and load (`stats`)

Load bands are `0-4` / `4-8` / `8-16` / `16-32` / `32-64` / `64+` (1-minute load average, lower bound included).

- Per run: `dagq_version`, `claude_version`, `rustc_release`, `rustc_host`, `claim_parallel`, `claim_slots`, `claim_load_avg` (what its first `run_claimed` recorded; null for a manual `claim` or an older run); `load` (`{work, validate, verify}`, each `{mean, max, band}` with `band` of the mean, null when not recorded; `verify` is the `integrate` verification commands' load weighted by duration); `load_band` (`load.work.band`, else the band of `claim_load_avg`, else null).
- `versions` (`{dagq, claude, rustc}`): the runs per `dagq_version`, `claude_version` and `rustc` (`<rustc_release> <rustc_host>`), by name with `version: null` last, each `{version, runs, ...}` in the shape of `goals`. Compare before and after a binary or toolchain change.
- `load_bands`: the runs per `load_band`, lightest first and `band: null` last, each `{band, runs, ...}` in the shape of `goals`.
- `verification_commands`: `integrate`'s verification commands with a recorded duration, per command string: `{command, count, failed, total_secs, median_secs}` (`failed` exited non-zero), in the same window and `--goal` as `backend_failures`.
- `backend_failures.by_load_band`: `[{band, count}]` of failed cmux calls per band of their `load_avg`, lightest first (failures without one are not counted).

## Claude session time (`stats` `sessions`)

The runtime records each Claude session it uses as a span from open to close (ADR-0048): `worker` (a run's first session), `resume`, `revise` (a review's send-back), `review`, `triage` (the recovery job), `observer`, `plan_review`, `goal_review`, `throughput_review`, and, through the plugin's hooks, `inbox`, `planner` (one a person opened with `plan` before it was retired) and `runtime_planner` (a planner the supervisor opened; a headless one's span comes from its turns instead, with `route: headless`, and the hook records nothing for it). A span has two times: `open` (wall clock from open to close) and `active` (the time Claude spent on turns, from the session's transcript). `open` much longer than `active` means the session sat idle: waiting for a review, a person or `/exit`.

- `sessions` (the window): `{window: {after, upto}, by_kind, by_route}`, same window and `--goal` as `backend_failures`. `by_kind` always lists all twelve kinds, each `{count, open, active, active_ratio, open_now, inferred, active_unavailable, tokens, models}`: `open` and `active` are `{count, total, median, p90, max}` in seconds, cut to the window; `active_ratio` is active over open for the spans with an active time (null without one); `open_now` counts spans still open at the window's end, `inferred` spans closed without a seen end (e.g. the next session or job of that kind started, the run was recovered or triaged, or the workspace was gone), `active_unavailable` spans whose transcript could not be read, or an inbox or planner span closed by its hook whose transcript the supervisor has not taken in yet (up to its intake interval, about 10 minutes) (they have `open` but no `active`); `tokens` and `models` (`"<model> <effort>"` counts) cover the spans closed in the window. Use `--since` / `--until` for a period: `inbox`, `planner` and `runtime_planner` have no run, so they appear only here.
- `sessions.by_route`: `{<kind>: {<route>: <same shape as by_kind>}}` for the spans with a route (`interactive` / `headless`; a hook's span without one is `interactive`). Compare the interactive and headless `runtime_planner` here; `kpi`'s `session_*` KPIs carry the same split as `route=` strata.
- `planner_routes`: the runtime's planners per route, as `worker_routes` is the workers': `opened` (`revise` / `draft` / `finding` / `request`), seconds `revise_to_review`, `draft_settle`, `finding_settle` and `request_settle` (`{count, total, median, p90, max}`, counted when the end is in the window), `planner_questions`, the headless `turns` with `turn_outcomes` / `turn_failures`, and `tokens`. A planner with neither turns nor a hook span is `unknown`. `kpi` shows it in each period's `health.planner_routes`.
- Per run, `runs[].sessions`: `{<kind>: {count, open, active}}` with that run's total seconds (`active` null when not recorded), not cut to the window; kinds without a span are left out (`{}` for runs from before the recording).
- Per goal and overall, `goals[].sessions` and `overall.sessions`: `{<kind>: {count, open, active, active_ratio}}` with `open` and `active` as `{count, total, median}` over the spans of those runs.
- With `--goal ID`, `plan_review` and `runtime_planner` count the spans whose proposal touched that goal; `observer`, `inbox` and `planner` count 0.

## Find duplicates and work already done (`search`, `related`, `--duplicate-of`)

A queue with many tasks cannot be compared by reading every task in full. Take candidates from `search` and `related`, read only those in full (`show ID --full`), and judge only them (ADR-0063 decisions 6 and 7):

1. **Before `add`**: `search` the problem's words: the file names, test names, ADR numbers (`ADR-0041`) and the words of the title you are about to write. Look at hits in every status: a `completed` task or a landed `commit` means the work may already be done; an unfinished task may be the same work. Narrow with `--status` or `--kind` when the hits are many.
2. **After `add`, before `submit`**: `related ID` on each new draft. It takes its clues from the task as registered (declared `--paths`, the texts, the goal), so it cannot run before `add`; a draft is never claimed, so nothing duplicate runs meanwhile. Read the top few candidates' `clues`, then only their full text.
3. **A duplicate or work already done**: do not submit it; close it with `"$DAGQ" cancel ID --duplicate-of X`, where X is the task it duplicates (a `completed` X means "already implemented by X"). X must exist, differ from ID and not be `canceled`; if X was itself canceled as a duplicate, the error names X's target: use that. A plain `cancel` leaves no link, so use `--duplicate-of` whenever the reason is a duplicate. If the new task only overlaps X, keep it and narrow it (`edit`), or depend on X (`dependency add`).

`show ID` of a task canceled this way prints `duplicate_of`, `show X` lists `duplicates` (the tasks canceled as X's duplicates), `list` adds `duplicate_of` to a canceled row, `related` marks such a candidate with `duplicate_of`, and `stats` counts them in `duplicate_cancels` (`{count, tasks: [{task_id, duplicate_of}]}`, same window and `--goal` as the rest).

The same steps apply to every planner, including one the runtime opened for a draft from a receipt's `follow_ups` or from a finding: run `related` on the draft (and `search` before adding any task of your own) and close a duplicate with `--duplicate-of`. `search` and `related` change nothing, so any role may run them. Plan review does the same for each task of a proposal; it does not replace your own check, which catches the obvious cases before a review.

## Wait for another goal (goal dependencies)

A task can depend on a goal as well as on tasks (ADR-0038). It is not claimed until that goal is closed `achieved` (by its goal review job, or `goal close --verdict achieved`); whether the goal's tasks are all finished does not matter, since `integrate` may still add drafts from `follow_ups` and its goal review drafts for gaps until it is closed (`reference/goal-close.md`).

```sh
"$DAGQ" add "TITLE" --goal 2 --depends-on-goal 1 ...   # repeatable; combines with --depends-on
"$DAGQ" dependency add TASK --goal 1                    # or remove; instead of a PREDECESSOR
```

- **When to use which.** To wait for another goal's outcome, depend on that goal, not on its last task: a task dependency is met as soon as that task is `completed`, even while follow-up drafts added to the goal later are still unfinished. Order inside one goal stays task dependencies.
- **Rules.** Like task dependencies, only a `draft`, `submitted` or `ready` task gains or loses one. Refused: a dependency on the task's own goal (`OwnGoalDependency`), and any cycle through task dependencies, goal dependencies and goal membership (`GoalDependencyCycle`; `set-goal` into a goal the task waits on: `OwnGoalDependency` when it depends on it directly, else `GoalMembershipCycle`; a task dependency closing such a cycle: `DependencyCycle`). Events `goal_dependency_added` / `goal_dependency_removed` (`goal_id`).
- **Where it shows.** `show` and `list`: `goal_dependencies`. `goal show GOAL`: `dependents`, the unfinished tasks waiting on it. `graph`: `goal_dependencies`, `{"goal": ID}` in `ready_after` until the goal is closed as achieved, and the waiting tasks in `blocks` / `unblocks` of the open goal's unfinished tasks. A worker's prompt lists the goal's completed tasks and their receipts' summaries.
- **Abandoned.** A goal closed `abandoned` never releases its dependents: they stay in `ready_after` as `{"goal": ID}` until a planner removes the dependency (`dependency remove TASK --goal ID`), points it elsewhere or cancels the task, as the person's request says (`reference/goal-close.md`).

## Decide what to run first with `graph`

When planning a goal or deciding what to submit next, read `"$DAGQ" graph --goal ID` (or `graph` for the whole queue) instead of reading each task's `dependencies`:

1. `critical` is the chain that holds back the most work. Its first task should be `ready` and running; if it is `draft`, complete it and `submit` it for plan review before tasks with small `unblocks` (only plan review, or a person's explicit `ready --bypass-review`, makes it `ready`).
2. A task with a large `unblocks` that is not in `candidates` waits on its `ready_after`; those predecessors are what to finish (or to review and land) first. A ready task with an empty `ready_after` that is not in `candidates` is in `deferred`: the supervisor deferred its claim for the recorded `reason`.
3. When one task blocks many, consider splitting it or removing a dependency that is not real (`dependency remove`) so more tasks run in parallel.
4. `candidates` is the order the supervisor will claim in, as of its last judgment of the deferrals: a task it deferred (a hotspot, a provider it cannot use, a build that lacks a landing) stands in `deferred` instead, and what holds every claim stands in `held`. So there is no need to register or submit tasks in a particular order to get the releasing ones first. To put a task ahead of the others, give it a priority (below).

`graph [--goal ID] [--format json|d2|svg] [--out PATH]` keeps `json` as the default: the dependency graph above, with `candidates` and `deferred`. `d2` writes D2 source and `svg` writes the rendered SVG directly; with `--out` (only for `d2` / `svg`) it writes the file and returns its format, path and drawn task IDs as JSON. The diagram selects tasks that are in progress, have effective priority `high` or above, or lie on `critical`, plus one level of their unfinished task or goal prerequisites. With `--goal`, those first two roots stay inside the goal, while its critical chain and prerequisites may cross goal boundaries. D2 source needs no host tool; SVG needs executable `d2` and `d2plugin-tala` on PATH and fails with the reason if either is missing. `doctor`'s `d2` field shows both resolved paths.

## Priority and claim order

A goal and every task have one of five priorities. Pick it by what waiting costs, not by how much the work matters in general:

| Level | Use for | Example |
| --- | --- | --- |
| `interrupt` | An exceptional cut-in that must run before every other ready task. Not for routine use: when many tasks are `interrupt`, it orders nothing | A goal the person decided to put ahead of the whole queue |
| `urgent` | A defect that is stopping operation now | The supervisor or landing is broken |
| `high` | Work to do early, because other work builds on it | A cleanup or refactor several planned tasks assume |
| `normal` | Everything else (the default) | |
| `low` | Work that can wait | A conditional proposal, a remedy for a minor finding |

```sh
"$DAGQ" goal add "TITLE" --priority high ...       # the goal's; default normal; names only (no numbers)
"$DAGQ" goal edit GOAL --priority low               # a draft or open goal
"$DAGQ" add "TITLE" --goal 1 --priority high ...   # the task's own; omit it to inherit the goal's
"$DAGQ" set-priority TASK urgent                    # a draft, submitted, ready or in_progress task's own
"$DAGQ" set-priority TASK --inherit                 # clear it: inherit the goal's again
```

- **Where a task's priority comes from.** The goal's priority is the source: a task without its own takes its goal's, a task without a goal `normal`. `priority_source` (`task`, `goal`, `default`) in `show`, `list`, `goal show`, `graph` and `candidates` says which. A task's own priority raises or lowers a few tasks of a goal and does not follow the goal's changes; `set-priority TASK --inherit` gives the task back to the goal. A task without its own priority moved to another goal (`set-goal`) inherits the new goal's.
- **Claim order.** The supervisor, `candidates` and `graph`'s `candidates` all use one order: highest effective priority → most `unblocks` → lowest ID. Goals have no rank: order goals by their priority. `candidates` and `graph` leave out the tasks whose claim the supervisor last recorded as deferred (`candidates --ignore-deferrals` keeps them); the supervisor ends a deferral only when it judges the claims again, which it does not while its slots are full or a hold is on.
- **Slot order.** A free slot goes to one line of three kinds: the resume of a `needs_session` run, the recovery job of a `failed` or `interrupted` run, and the claim of a ready task. The line is sorted by the effective priority of each one's task, highest first; on the same priority a resume comes first, then a recovery job, then a claim; within a kind the order is that kind's own (resumes oldest first, claims in the claim order above). So a `high` ready task is claimed before a `normal` task's resume, and a `high` task's resume or recovery job starts before a `normal` claim. A kind that is held (for example claims held for the load, or recovery jobs held by a usage limit) only leaves the line; it keeps no slot free for itself.
- **Effective priority.** A task's priority (its own or its goal's), raised to the highest priority of the `ready` tasks that wait on it directly or transitively. So a `high` ready task pulls its unfinished predecessors ahead with it; there is no need to raise them one by one. An `in_progress` task has an effective priority the same way, which orders its next resume or recovery job. Only `ready` tasks outside a draft goal pass their priority on: an `in_progress`, `draft`, `canceled` or `completed` task, or a task in a draft goal, raises nothing (a draft set aside does not push its predecessors forward). A task in between does not stop it: a ready task's priority still reaches the predecessors beyond a draft one. `graph` shows both `priority` and `effective_priority`.
- **When it can change.** A task's own: while the task is `draft`, `submitted` or `ready`, and also while it is `in_progress` for the user and the inbox (a planner is refused there: it changes only tasks that have not started); `set-priority` on a finished (`completed`, `canceled`) task is refused. A change is recorded as a `task_priority_changed` event (`from`, `to`, `from_source`, `to_source`). A goal's: `goal edit --priority` on a draft or open goal (recorded in `goal_updated`); its tasks without their own show the new value in every status. Either takes effect at a `ready` task's next claim, or an `in_progress` task's next resume or recovery job, and never stops a run already running.
- **Putting parked work behind or ahead.** When many runs wait in `needs_session` and other work should go first, `set-priority TASK low` on the parked tasks (or `high` on the one to resume first) reorders the next resumes; `--inherit` gives the task back to its goal's priority. Canceling is the other way out for a parked run nobody needs.
- **Express urgency with priority only.** Do not move other tasks back to `draft`, and do not add or remove dependencies that are not real, to get one task claimed first; give it a higher priority instead.
- **No aging.** A `low` task waits as long as higher ones keep arriving; nothing raises it over time, and the same holds for a `low` task's resume. Check `graph` for ready tasks, and `list --status in_progress` for parked runs, that never reach the front and raise them by hand.

## Edit a draft or submitted task

Fix a draft or submitted task in place instead of canceling it and registering it again (that changes its ID and its dependents' edges):

```sh
"$DAGQ" edit TASK --description "..." --acceptance "..."   # also --title, --context
"$DAGQ" edit TASK --verify 'CHECK' --verify 'TEST'
"$DAGQ" edit TASK --evidence e2e --paths 'src/**'          # --no-verify / --no-evidence / --no-paths empty a list
"$DAGQ" edit TASK --change fix                              # one of dagq.toml's [tasks] changes (reference/scope.md)
```

- Each given field replaces the old value; a repeatable flag (`--verify`, `--evidence`, `--paths`) replaces the whole list, so pass every value it should keep. At least one field is required. The values follow the `add` rules (no blank title or command, valid globs).
- **When it can change.** Only a `draft` or `submitted` task. Editing a `submitted` task does not yet restart its plan review (ADR-0044 decision 9 is not implemented): a review already running may pass the old text, so fix a proposal while it is sent back (`draft`) rather than while it is `submitted`. A `ready` task is refused: it changes only through plan review, which moves it back to `submitted` for a planner (ADR-0044 decision 14), or by taking it back with `draft ID`, editing it and submitting it again. An `in_progress` task permits user or inbox to change only `--verify` / `--no-verify` when its latest run ended and no live run remains; a finished task is refused. The change is for a later `retry_inherit` and integration. A live run keeps its verification commands.
- The change is recorded as a `task_edited` event whose `from` and `to` hold only the fields that changed (under their task JSON names); `show ID` lists it with long texts cut to 300 characters, `show ID --full` has the whole values. Nothing changed, nothing recorded.
- Priority, goal and dependencies have their own commands: `set-priority`, `set-goal`, `dependency add|remove`.

## Withdraw a proposal (`proposal withdraw`)

```sh
"$DAGQ" proposal withdraw ID
```

Its planner (or a person) withdraws a `submitted` or `revising` proposal without plan review, in two cases:

- **A revising proposal that cannot be resubmitted.** Its drafts were all readied with `ready --bypass-review` or canceled, so `submit --proposal ID` fails with `EmptyProposal` ("a proposal needs at least one draft task") and the proposal would stay `revising` for good.
- **The plan is dropped or reshaped.** The person no longer wants it, or its tasks go into another proposal.

What it does, in one transaction: the proposal becomes `canceled` and its pending plan review and undelivered revise are dropped; its `submitted` tasks go back to `draft` (tasks already `ready`, `canceled` or claimed stay as they are); each member task and goal gets a `proposal_withdrawn` event (`proposal_id`, `from`); an `approve_plan` ask on it still open is closed (answered `withdrawn`, `runtime_closed: true`, when unanswered; an answer not yet applied is dropped), so no answer lands on the tasks' next proposal. The drafts are free: submit them in another proposal (`submit ID...`), `cancel` them, or leave them as drafts; a draft with an origin (`follow_up`, `goal_gap`) goes back to the runtime's planners. An `accepted` or `canceled` proposal is refused; the observer and the review jobs cannot run it.

## A run that needs paths outside its task

A task registered with `--paths` may change only what they match (`reference/scope.md`). Two signs say a run needed more:

- **`scope_violation`.** Validation parked the run as `needs_session` (`events --run RUN --kind scope_violation --full` has `paths`, the changed paths no glob matches, and `allowed`), or `integrate` deferred it (`integration_deferred` with `scope_violation`). The supervisor resumes the session to restore those paths; nothing is needed while the task's paths are right.
- **A `failed` receipt naming paths.** The worker found the task truly needs a path outside its globs and stopped; its `summary` names the path and the work.

Next: while the task is `draft`, `submitted` or `ready`, widen its globs with `set-paths TASK --paths ...` (every glob it should keep) or remove the limit with `--none`. A run already claimed keeps the paths it started with, so after a failed run register the task again with wider `--paths` and the verification those paths need (per the repository's rules: `reference/scope.md`).

## Change a goal or a task's goal


```sh
"$DAGQ" goal list [--tag TAG]             # every goal by priority with its tags and task counts by status
"$DAGQ" goal show ID                      # the goal, its tasks (id, title, status, priority), its latest events (--full: everything)
"$DAGQ" set-goal TASK GOAL                # move a draft or ready task into an open goal
"$DAGQ" set-goal TASK --none              # take a draft or ready task out of its goal
"$DAGQ" goal edit ID --constraints "..."  # replace one or more fields (--title, --description, --acceptance, --constraints, --doc, --priority, --tag; --doc "" clears it, --no-tags removes the tags)
"$DAGQ" goal close ID --verdict achieved  # or abandoned; see goal-close.md
"$DAGQ" goal review ID                     # rearm the goal review after `goal review by hand` or a keep_open answer (person or inbox)
```

`set-goal` follows the dependency rules: only a `draft` or `ready` task can be moved, and a closed goal accepts no task. Take an `in_progress` task back with `draft ID` only if its run is finished; a `completed` task keeps the goal it landed with. `goal edit` records the old and new fields in a `goal_updated` event; a run already claimed keeps the prompt it started with, and runs claimed afterwards see the new text. `goal edit --tag T` (repeatable) replaces every tag, from `[goals] tags` when `dagq.toml` lists them; a closed goal's tags and texts can still change, its priority cannot.
