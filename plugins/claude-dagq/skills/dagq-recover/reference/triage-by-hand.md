# Triage by hand, and recover by hand

Read this when the attention `triage by hand` or `recover by hand` reaches the person (the `dagq-recover` skill, section 4), or when a `decide` ask's run failed on a broken verify with its work committed. Act only on the person's word.

## `triage by hand`

Attention `triage by hand` (`kind` `triage_failed`): the recovery job of a `failed` / `interrupted` (or `resume_exhausted`) run could not start, timed out, printed no verdict, or its verdict could not be applied; the run stays as it is and is not tried again. A `triage_failed` with `provider_unusable` is not this attention: the job's provider could not be used (its `[roles.recovery]` names it), so the run stays `triaging (runtime)` and its next round starts on the other provider, or, with `[provider_fallback] jobs = false`, on the same provider once its hold ends. Under `--no-claude` with no provider left, that round fails with why (`provider_disabled`), and only then is it `triage by hand`. Read `last_error` and the run directory's `recovery-<alert>-<attempt>.prompt.txt`, `.out`, `.err`, and bring the choice to the person. On their answer: `"$DAGQ" ready ID` runs the task again as a new run from the current main (unchanged: no plan review), `ready ID --inherit` does so carrying the run's committed work over (below), `cancel ID` drops it. To change the work instead, cancel it and, on the person's word, record a planning request that names it (`"$DAGQ" request add --text '<their words>' --ref task:N`, `skills/dagq-inbox/reference/requests.md`), whose runtime planner plans it again; people no longer open planners. Its workspaces stay open until then, so read the screen first (`"$DAGQ" run screen RUN`); `"$DAGQ" run close-workspaces RUN --apply` closes its workspace once nothing lives behind it (never `cmux` itself).

## Carry a run's work over by hand

When the person wants an ended run's committed work carried over to a new run (for example they chose `retry_inherit` on a `decide` ask, but the answer did not match an option, or the job may not use its one automatic `retry_inherit` again): `"$DAGQ" ready ID --inherit --reason '<why, in the person's words>'`. Only user or inbox may run it, on the person's word.

- It applies to an `in_progress` task whose latest run is `failed` or `interrupted`, with no live process and no live lease, and whose branch holds commits on top of its base. Otherwise it is refused with the reason and changes nothing: with no commits of its own, use plain `ready ID`; while a recovery job's round holds the run (`triaging (runtime)`), wait for the round to end and try again.
- It keeps the run's head under `refs/dagq/runs/<run-id>`, makes the task `ready` without plan review, closes the run's open `decide` ask, and records `triage_finished` (`action: retry_inherit`, `by`, `reason`, `inherit`). The next run starts from that work (`run_inherited`, the prompt's `Carried over from run`).
- It does not use the task's one automatic `retry_inherit`, and works after it was used.
- If the verify is broken, `edit ID --verify` first (below), then carry the work over.

## `recover by hand`

Attention `recover by hand` (`kind` `recovery_failed`): a live run's recovery job failed under an older runtime, before a failed recovery job opened an ask (`last_error` its error); the session is untouched and the job does not retry that alert. The runtime now opens the alert's own ask instead (`stuck_exit`, `answer_prompt`, `stalled`, `reason_category` `recovery_failed`), carried out as that kind's answer. Read the screen with the person and carry out what they decide as in the skill's section 7 (`reference/session.md`, `reference/stalled.md`, `reference/stuck-exit.md`). It clears once the session exits.

## Broken verification command with committed work

First read `dagq show ID --full` and the run's `integrate-<attempt>-verify-N.log`. If the failed command itself is wrong (for example, it needs a tool or module the host lacks), ask the person for the corrected command. User or inbox may run `dagq edit ID --verify 'correct command'` on an `in_progress` task only after its latest run has ended and no live run remains. Repeat `--verify` for every command to keep; `--no-verify` clears all. Check the `task_edited` old/new values and actor with `show --full`, then answer the open `decide` ask with the exact option `edit the task's --verify, then retry_inherit`. The runtime offers it on every `decide` ask of a run whose integrate verification failed, including the ask that opens after the job's three tries are used up. This returns the run to the recovery job, with one more round even past those three tries because the verify was edited since the run began; it reads the corrected verify and chooses `retry_inherit`, retaining the branch's commits for the next integration. If you answer it without editing first, it counts like any other option, and once the tries are used up the same ask opens again: edit, then answer that one. Never use `retry` to discard committed work for this correction. The recovery job itself does not edit tasks.
