# needs_session runs: what the runtime's resume does

A run becomes `needs_session` only when its landing conflicted or its verification failed after the rebase, when validation found required evidence missing, or when a person answered `send_back` to the `approve_landing` ask of a review concern. A `revise` verdict goes to the still-open worker session without any resume.

Most landing conflicts never reach a resume either. Before it asks a run whose review passed to exit, the supervisor compares the run's head with the current resolved landing branch with `git merge-tree` (the worktree is not touched). When they conflict it records `conflict_precheck` (`main`, `head`, `conflicts`) and sends the same resolution request as a resume to the still-open session as its next turn (`run_dir` keeps it as `conflict-N.txt`); once the session has rebased, rewritten the receipt and gone idle (`conflict_resolved`), the run is validated, reviewed and prechecked again. The precheck counts its own requests and the run's resumes together: once they reach three, the session gets the exit request and the supervisor opens an `approve_landing` ask for the person instead. The resume's own limit still counts resumes only. Only a conflict that appears after the exit request (the landing branch moved while the run waited for the landing slot), or a failed verification after the rebase, parks the run as `needs_session`. Nothing here is yours: nothing is sent to the session by hand while it resolves the conflict.

The supervisor starts the run's own session again as a background process with no workspace (`run log` shows it) and gives it the fixed resolution request: the reason, the resolved landing branch to rebase onto, the tasks landed since the run's base, and the steps. `run_dir` keeps it as `resume-N.txt`.

Once the session has rewritten the receipt for the new head and gone idle:

- a run whose `integrate` was already called (`integration_approved`) gets the exit request and is landed by the runtime;
- any other run keeps the session open and goes through validation and the supervisor's review like the worker's (`reference/review-by-hand.md`).

A session that goes idle without resolving it, or runs past the resume timeout, gets the exit request (in `turns/`) and the supervisor stops what is left of its wrapper. Resumes for a rebase conflict alone, after the review passed, do not count toward the three (they stop at five of their own). Once the resumes are used up the supervisor stops resuming, and asks nobody yet: a run still parked only by conflicts is retried on its old branch once per task (`auto_repaired`, `repair: inherit_retry`: the task is `ready` again and the next run carries the commits over); any other run becomes `failed` (`last_error` says how often it was resumed, with the reason) with the `resume_exhausted` alert (`recovery_requested`), and the recovery job takes it like a failed run (`triaging (runtime)`; it can no longer choose `resume`). Only when the job escalates, is not sure or used its three tries does a `decide` ask with `retry` and `cancel` (and any option the job added) reach the inbox; the supervisor applies the answer: `retry` readies the task, `cancel` cancels it. Nothing is typed into a resumed session and no screen is read: a worker's answer reaches it as its next turn, and a `stalled` ask on it is answered as `reference/stalled.md` says. An `answer_prompt` ask with `input_not_ready` or a `stalled` ask with `reason: send_unconfirmed` on an older resume is a past record (`reference/session.md`).
