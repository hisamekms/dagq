# Updating the dagq binary: install, auto-update and the update asks

Read this when the person wants to update or roll back the `dagq` binary the queue runs on, turn on automatic updates, update to a new release from crates.io, or answer an `approve_release` / `update_failed` / `approve_update` ask. Everything here is typed from the inbox (or by the person in a terminal without `DAGQ_ROLE`), on the person's word; tell the person before a binary is replaced.

A binary names itself by its build identifier (`dagq --version`). A supervisor is replaced whenever that identifier differs, not only when the version is higher.

## install

```sh
"$DAGQ" install --from PATH        # a binary file, or a checkout of dagq's source (built)
"$DAGQ" install                    # in dagq's source repository only: build the queue's main checkout
"$DAGQ" install --release [VERSION]  # a release from crates.io (X.Y.Z; the newest without VERSION)
"$DAGQ" install --rollback         # go back to <binary>.previous
```

When it builds a checkout of dagq's source (the main checkout, or `--from <dir>`), `install` first runs the whole e2e suite (`cargo test --locked --test e2e -- --ignored`, same target; when cmux does not answer `cmux ping`, the e2e that need it are left out and the result's `e2e.skipped` names them and why) and, if a test fails or it times out, stops replacing nothing, with an error naming the failed tests and the e2e log. Only on the person's explicit word, when it cannot wait, `--skip-e2e` skips it (the result's `e2e` says `skipped`); a binary file, `--rollback` and `--release` have no gate. Then `install` checks the new binary (`--version`, and `init` + `list` on a throwaway queue), applies the compatible migrations, puts it in place with a rename (the one it replaced stays as `<binary>.previous`), and hands every live supervisor over to it: each supervisor execs the new binary under its own pid and token at its next short step, so the sessions and runs in flight go on and nothing waits for them. Then it watches them for up to 60 seconds: it succeeds only once each one handed over heartbeats on under the new build (`"outcome": "installed"` with `version`, `previous_version`, `migrated`, `supervisors`, and `watch`, one entry per supervisor). If none takes it (it fails the handoff, or dies or hangs right after it registered), `install` puts the previous binary back when `.previous` is the build it replaced (otherwise it leaves it and says why) and starts each failed supervisor again (one started by hand, with no mode, is not). If only some fail, the new binary stays for the ones that run it (`"kept": true`) and only the failed ones are brought back. Either way `install` exits non-zero, prints the failure (`"outcome": "failed"`, `"source": "install"`, `stage`, `restored`, `kept`, each supervisor's state) instead of its result, and opens an `update_failed` ask for the inbox (below). The drain of `--allow-breaking` is not watched: its own `up` starts the supervisor. `--to PATH` replaces another file than the running `dagq`. Never replace the file with `cp`: on macOS that can kill the processes running it, and it leaves no `.previous` to go back to.

- A supervisor listed under `not_handed_off` (a binary from before the handoff, or a launchd agent whose plist names another path) is replaced by the next `up`, which drains it.
- `install` stops, replacing nothing, when a supervisor is live and the new binary itself predates the handoff (a `--rollback` to such a binary too): then `down --wait`, the same `install` (with no supervisor it replaces the file and applies the compatible migrations), and `up`.
- **A breaking migration** (the error names it; `"$DAGQ" migrate --check` lists each with `compatible`): `install` refuses unless `--allow-breaking`, which drains: it stops the supervisor with `down --wait` (it waits for its runs, and for runs waiting on an ask, so show the person the open asks first), copies the queue to `backups/`, migrates, replaces the binary and starts the supervisor again with `up` under launchd (without `--in-cmux`, even when the drained one was a registered in-cmux supervisor). Pass what that `up` needs: `--claude EXE`, `--codex EXE` (the Codex workers' CLI, fixed like `--claude`), `--cmux EXE`, and `--plugin-dir PATH` only when the repository's instructions name one (never `$CLAUDE_PLUGIN_ROOT`, a per-version cache). That `up` carries the drained supervisor's `--auto-update` and `--max-waiting` over, so no second `up` is needed. A `--rollback` past a breaking migration is refused; the error names the backup.
- **`--release [VERSION]`** (not with `--from` or `--rollback`): runs `cargo install --locked dagq@VERSION` into `<queue dir>/update/release`, with its log in `<queue dir>/logs/install-release-VERSION.log`, and then goes on as above (check, compatible migrations, rename, handoff). `VERSION` is a plain `X.Y.Z`; without it, the newest release that is not yanked or a pre-release. If the binary in place already is that version, it does not run cargo and only hands over. If cargo is missing, fails or leaves no binary, nothing is replaced and the error says which (a failed cargo names the log). Use it when no supervisor serves the queue, when the person does not want to wait for the ask, or to carry out an `approve_release` answer no supervisor applied. It does not update the plugin: after it, run `claude plugin marketplace update dagq` and `claude plugin update claude-dagq@dagq`, then reopen the inbox and planner sessions.
- `unsupported queue schema version ... install a newer dagq`: the queue was migrated past this binary; use the newer binary. `run dagq migrate`: the binary has migrations the queue lacks; `install` or `up` applies the compatible ones, a breaking one goes as above.

## Automatic updates (`up --auto-update`)

```sh
"$DAGQ" up --auto-update   # with the same other flags as always
```

`--auto-update` is written on the registration of the supervisor `up` starts or reuses, so turning it on needs no restart: an `up` whose build matches the running one answers `reused` and sets it. An `up` without the flag turns it off again, so every later `up` (including the `restart supervisor` one) must carry it. `status` shows `auto_update` (`enabled`, `state`, the last step) and each `supervisors[].auto_update`.

While it is on, each landing on the resolved landing branch that changes `src/`, `migrations/`, `Cargo.toml`, `Cargo.lock` or `build.rs` is built under the queue's directory (not in the person's checkout), the whole e2e suite runs in that checkout (`status` shows `auto_update.state` `testing`; a failure replaces nothing, stages no breaking build and opens `update_failed` with `stage: e2e`), then it is checked, installed like `install`, and the supervisor hands itself over; a watch puts the previous binary back if no handed-over supervisor heartbeats on the new one within 60 seconds (when only some fail, the new binary stays and only the failed ones are started again: launchd restarts a launchd one by itself; a registered in-cmux one that is gone has its workspace closed and is started under launchd with `up`, with `--auto-update` only when it had it; that `up` runs outside cmux's process tree and cmux can refuse it, and a failed close is not reported, so then the `update_failed` ask and `supervisor_stopped` say so: run `down --wait`, then `up` without `--in-cmux`). Each step is a queue event (`"$DAGQ" events --kind update_installed`, `update_failed`, ...); `update_installed` reaches the inbox as `report the update`.

## Release updates (`approve_release`)

A supervisor whose build identifier is a plain release `X.Y.Z` (installed with `cargo install`) checks crates.io about once a day (`check_interval_secs`, default 86400 seconds), and at its first pass after it starts as a new build. A build with a pre-release or build metadata (`X.Y.Z-dev+...`) never does; `up --auto-update` covers dagq's source repository instead. The host's `host.toml` chooses the behavior: `<queue dir>/host.toml`, or else `~/.config/dagq/host.toml` (`$XDG_CONFIG_HOME/dagq/host.toml`):

```toml
[update]
release = "ask"   # "ask" (the default): open approve_release; "auto": no ask (breaking migrations still ask); "off": never check
```

A value of the wrong shape falls back to the default with a warning in `doctor`'s `release_update`; no restart is needed, the supervisor reads the file again every minute. `status`' `release_update` shows `mode`, `latest`, `current`, `checked_at` and `state` (`update_available`, `up_to_date`, `check_failed` with `error`, `unchecked`, `not_release`, `off`). A failed check (offline) is only an event and is tried again later.

**After the answer.** A live supervisor on a release build, with `release` not `off`, applies the answer and closes the ask:

- `install` starts a background job: `cargo install --locked dagq@<version>` under `<queue dir>/update/release`, then the same check, compatible migrations, rename (the old binary stays as `.previous`), handoff and 60-second watch as `install`. The runs in flight go on. Then, unless the supervisor was started with `--plugin-dir`, the job updates the installed plugin to the same release (`claude plugin marketplace update dagq`, then `claude plugin update claude-dagq@dagq`, with the supervisor's `--claude`). Success is `update_installed` with `release` and `plugin`, which reaches the inbox as `report the update`; when the plugin was updated, its `message` says to reopen the inbox and planner sessions, which keep the plugin they started with (headless jobs and new sessions already load the new one). Tell the person; reopening is theirs (`up-down.md`, "Open the inbox again"). The job's logs are `<queue dir>/logs/release-<time>-<version>.json`, `.log` and `.build.log` (cargo).
- `install` on a plugin-only `approve_release` (its question starts `The claude-dagq plugin installed in Claude Code is ...`; the binary is already the newest release and only the plugin is older) runs just the two plugin commands and never touches the binary. Success is `update_installed` with `plugin_only: true`.
- `skip` does not ask about that version again; the next release asks.
- A plugin-only answer about a version older than a newer release is not carried out: an `update_dropped` (`reason: newer_release`) is recorded, and the newer release's job updates the plugin too. Nothing to do.

With no supervisor that applies it (none live, a `-dev` build, or `release = "off"`), the answer comes back as `read the answer of ask <id> and close it`. On `install`, and on the person's word, run `"$DAGQ" install --release <version>` (and the two plugin commands), or for a plugin-only ask only the two plugin commands; then `ask close <id>`. On `skip`, `ask close <id>`.

**A breaking migration** in the release: nothing is installed, even with `release = "auto"`. The build is kept as `<queue dir>/update/staged/dagq` and an `approve_update` ask names the command (below). The supervisor this drain starts again keeps the flags of the one it stopped and reads `host.toml` as before, so release updates go on: do not type `up --auto-update` after it (a release supervisor has no auto-update, and outside dagq's source repository `up --auto-update` is an error).

## The update asks

Both have no task and no run, and are asked by `supervisor`. A newer ask of the same kind closes the older one (`superseded`), except that the `update_failed` of a person's `install` (`subject: install`) and a job's do not close each other.

A job of the automatic update that puts a build in place (`update_installed`) also closes the open `update_failed` asks whose failed build that build contains: the runtime answers them `installed` (`ask_answered` with `runtime_closed: true` and `installed_commit`), and the inbox has nothing to do with them (no `ask close`, nothing to tell the person). It closes none when the failed commit is unknown (a release job's failure, a person's `install`'s, a step with no commit), when the installed build does not contain the failed commit, or when the swap was a release job's or a person's `install`; and it leaves an ask already answered, whose `retry` or `skip` is applied as below.

- **`update_failed`** (`retry` / `skip`): the question says at which stage the update failed (`build`, `e2e`, `check`, `install`, `handoff`, `watch`, `plugin`, or `interrupted` when the job died; for `e2e` it names the failed tests, or the timeout or why it could not start, and the `.e2e.log`), the error, what became of the binary (put back, or `kept` when only some supervisors failed and the others run the new one) and of each supervisor, and the job's log. Show it as written. Answer with the person's option: `retry` builds the resolved landing branch's head again at the next check (after the cause is fixed), `skip` waits for the next runtime landing. A live `--auto-update` supervisor applies the answer and closes the ask. With none, the answer comes back as `read the answer of ask <id> and close it`: nothing applies it; update by hand with `install` if the person wants, then `ask close <id>`. If no supervisor serves the queue after a failed update (`restart supervisor`), `up` starts one with the binary now in place.
- **`update_failed` of a person's `install`** (its question starts with A person's `dagq install`; its `update_failed` event has `source: "install"`, `stage` `install` when every supervisor failed the handoff, `handoff` when only some did, `watch` when one died or hung after it registered): it is not the automatic update's, so `status`' `auto_update` and the next build ignore it, and no supervisor applies its answer, even with `--auto-update`; the answer always comes back as `read the answer of ask <id> and close it`. Show the question as written: it says what became of the binary (put back, not put back because `.previous` was another build, or `kept`) and of each supervisor (`running` on the build it had, `restarted`, or `stopped` with why: one started by hand is not started again). Then, on the person's word, do what they chose from the question: run the same `install` again after the cause is fixed (`retry`), `install --rollback` to put the binary it replaced back for every supervisor, or `down --force` and `up` to start the supervisors with the binary in place; or leave it (`skip`). Then `ask close <id>`.
- **`update_failed` of a release job** (its question names the release): a live supervisor on a release build applies the answer, as for `approve_release`. With none, it comes back to be carried out by hand.
  - `stage: build`: `cargo install` was not found, failed or left no binary; nothing was replaced. Read the cargo log the question names (`.build.log`). Usual causes: a Rust older than the crate's `rust-version` (`rustup update`), no C compiler (`xcode-select --install`), or no network. After the person fixes it, `retry` installs the same version again at the next pass; `skip` skips that version. By hand: `"$DAGQ" install --release <version>`, or `"$DAGQ" install --from <binary>` for a binary installed some other way.
  - `stage: plugin`: only the plugin update failed. After a binary job, the binary was replaced and keeps running the new release (the `update_installed` before it says so); after a plugin-only job (`plugin_only: true`, including one that died partway with `interrupted: true`), the binary was not touched. The question has the two commands and their output when they ran. Fix what it shows (often the `claude` executable or the network), then `retry`: the supervisor runs the two plugin commands again as a plugin-only job, and never touches the binary. `skip` leaves the plugin as it is. By hand: `claude plugin marketplace update dagq` and `claude plugin update claude-dagq@dagq`, then `ask close <id>`. Either way, the inbox and planner sessions load the new plugin only when reopened.
  - `stage: interrupted`: a binary job died partway; the question says after which step. `retry` starts it again.
- **`approve_update`** (`install` / `skip`): the resolved landing branch (or, for a release supervisor, the release) built as a binary with a breaking migration, so nothing was installed; the build is kept under `<queue dir>/update/staged/dagq` and the question names the migrations and the exact command. The runtime never applies it. After writing the person's answer it comes back as `read the answer of ask <id> and close it`: on `install`, and on the person's word, run the command from the question as written (`"$DAGQ" --db <db> install --from <queue dir>/update/staged/dagq --to <binary> --allow-breaking ...`), which drains as described under install (keeping `--auto-update` when the supervisor had it; a release supervisor's question has no `--auto-update`, and nothing needs it), then `ask close <id>`. On `skip`, `ask close <id>`; the next runtime landing builds again (for a release, that version is not asked about again; the next release asks).
