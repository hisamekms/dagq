# The kinds of ask

Read this when an open ask's kind, options or effect is unclear (the `dagq-inbox` skill, step 3). Whatever the kind, show the ask as written and add no recommendation of your own. Listing and answering: `"$DAGQ" asks --help`, `"$DAGQ" answer --help`.

An ask an AI opened may carry its `recommendation` (one of its options) and `confidence`. Show them next to the options as the asker's, e.g. "recommended by the asker: `land` (confidence: low)", and still let the person choose: never answer with the recommendation on your own. Never ask the person for a reason code: the runtime takes it from the review.

- `approve_landing`: a review's doubt: `land` / `send_back` / `cancel`. A person may give their own reason as `send_back: <reason>` (write it as given). One opened past the run's revise limit says which code findings are left. The ask of a failed review also offers `retry_review`, which reviews the same run again without resuming the session: show it next to the others, for a failure that was the provider's (a login, a limit) rather than the change's.
- `approve_close`: a worker reported its base already met the acceptance, and the runtime ran the task's verification on main. `close` completes the task without a commit, `retry` puts it back to ready, `cancel` cancels it. A failed verification offers only `retry` / `cancel`.
- `approve_plan`: plan review's concern: `ready` / `send_back: <reason>` / `cancel`.
- `approve_goal`: the goal review's question about a goal whose tasks are all finished, asked only when a person is needed. Options: `achieved` (close it; `${CLAUDE_PLUGIN_ROOT}/skills/dagq/reference/goal-close.md`), `abandoned` (close it given up; its dependents are never released), `gaps` or `gaps: <what is missing>` (register gaps as drafts on the goal), `keep_open`, plus the job's own. The supervisor applies the first four; another answer comes back to be carried out by hand. A later review on the person's word: `${CLAUDE_PLUGIN_ROOT}/skills/dagq-recover/reference/goal-review-by-hand.md`.
- `correct_goal`: a follow-up judged required after its goal closed as achieved, so the goal may not have met its acceptance. Options: `reopen` (open the goal again; released tasks not yet claimed wait for it, running ones go on), `correct_verdict` (keep it closed and record that achieved was wrong; a planner puts the fix in a fix goal), `keep_achieved` (the follow-up is out of scope). The supervisor applies the three.
  Show it in this order: the goal and that it closed achieved; the judgement as written (acceptance items, reason, evidence); the released tasks with their status, saying which already run or landed; then the options. If the person doubts the judgement itself, their words are the answer and come back to be carried out by hand: `ask close <id>` first, then a planning request naming the follow-up (`request add --ref task:N`).
- `decide`: a failed, interrupted or resume-exhausted run the recovery job could not fix: `retry` / `resume` / `cancel` (no `resume` once resumes are used up), plus the job's own options, each marked `[goes back to the recovery job ...]`: choosing one (with or without the mark) moves nothing, and the recovery job runs again with it. An option marked `[... may hand the run to the check that the base already meets the acceptance ...]` goes back to the job too; the task closes only if that check and its review pass. A job's option that read as a runtime operation or as ending the task (done, cancel, retry) is not offered; the question names it as left out, and its recommendation of `retry` / `resume` / `cancel` as that option's.
  Answer with an option's exact text; a bare operation name that is no option is refused and the ask stays open. When the person wants the run's committed work carried over and no option does it, do not answer: on their word run `dagq ready ID --inherit --reason '<their words>'`, which closes the ask (`${CLAUDE_PLUGIN_ROOT}/skills/dagq-recover/reference/triage-by-hand.md`, "Carry a run's work over by hand").
  The option `edit the task's --verify, then retry_inherit` comes when the landing's verification failed. If the verify itself is broken, show it to the person; on their instruction, read `dagq show ID --full` and the failed verify log, run `dagq edit ID --verify '...'` (or `--no-verify`), then answer with that exact option. Never answer it before the edit.
- `stalled`: a run's headless session the runtime and its recovery job could not get on. The question says what the session did, what the recovery job said, the answers, and the last turns as recorded: show all of it. Options: `wait` (the supervisor asks again after the next turn), `stop` (the session ends and the run goes to its recovery job), any the job added (each marked `[goes back to the recovery job ...]`: choosing one, with or without the mark, sends nothing to the session and the alert's next recovery job runs with it), then `propose` (a finding for a runtime planner; the session is left alone). Any other text is sent as the session's next turn: that is how an instruction is given. Nobody can step into a headless session; an answer starting with `intervene` is not sent and a new `stalled` ask opens in its place. Leave an answered one to the supervisor; close one by hand only after `wait` or `propose` with no supervisor holding the run. It closes itself once the session moves on. Steps: `${CLAUDE_PLUGIN_ROOT}/skills/dagq-recover/reference/stalled.md`, "A headless run's `stalled` ask".
- `worker_question`: the answer is sent as the worker's next turn. Show its `topics` (the first is the primary) with the question.
- `planner_question`: a runtime planner's question. A draft: `adopt` / `cancel` / `keep_draft`; when the person says when to look again, give it a revisit time instead (`revisit ID --at <RFC 3339 time>`, `${CLAUDE_PLUGIN_ROOT}/skills/dagq/reference/register.md`, "A draft's revisit time"). A finding: `propose` / `dismiss`. A planning request: `plan` / `decline` (`reference/requests.md`). A revise: the planner's own options. The runtime delivers the answer; do not carry it out yourself.
- `answer_prompt` and `stuck_exit`: no longer opened; one in the records is history (`${CLAUDE_PLUGIN_ROOT}/skills/dagq-recover/reference/session.md`, "Past asks and attentions of the interactive session").
- `blocked`: the observer's, about one finding: `propose` / `dismiss`.
- `queue_hold`: login, cost or disk, one per queue. A login or usage limit holds claims and jobs. A login or usage limit: tell the person what to restore (log in again, `claude` or `codex login` when the question names Codex, or wait for the limit's reset); once done, the answer is `done`. `cancel_affected` gives the held runs up: show the question's `Affected:` line first. The disk's holds landings for free space: `done` has the supervisor clean and check again, `wait` has it not ask again; it closes itself once there is room. A provider that cannot be used moves its runs to the other provider by itself; Codex's hold opens no ask. The fallbacks and what reaches the person: `${CLAUDE_PLUGIN_ROOT}/skills/dagq/reference/provider.md`.
- `approve_release`: a newer dagq release: `install` / `skip`. Show, in this order: the new version with its link from the question, the version the supervisor runs now (`status`' `release_update`), and what each answer does: `install` has the supervisor install it and update the plugin without stopping the runs (sessions load the new plugin only when reopened); `skip` asks again only for the next release. A plugin-only one: show the plugin's version and the binary's, and say `install` leaves the binary alone.
- `update_failed` / `approve_update`, and carrying out an `approve_release` by hand: `${CLAUDE_PLUGIN_ROOT}/skills/dagq-recover/reference/update.md`.

The runtime applies the answers this file says it applies, and `propose` and `dismiss`. Any other answer comes back as `read the answer of ask <id> and close it` (the skill's step 4).
