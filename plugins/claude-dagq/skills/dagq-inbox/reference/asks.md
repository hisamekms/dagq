# The kinds of ask

Read this when an open ask's kind, options or effect is unclear (the `dagq-inbox` skill, step 3). Whatever the kind, show the ask as written and add no recommendation of your own. Listing and answering: `"$DAGQ" asks --help`, `"$DAGQ" answer --help`.

On Claude Code show the options with `AskUserQuestion`; on Codex, which has no question tool, as a numbered list with the question, and take the person's reply as text. Either way, write the answer with `answer` as the person gave it: the option's exact text (not its number), or their own words.

An ask an AI opened may carry its recommendation (one of its options) and confidence. Show them next to the options as the asker's, e.g. "recommended by the asker: `land` (confidence: low)", and still let the person choose: never answer with the recommendation on your own. Never ask the person for a reason code: the runtime takes it from the review.

- `approve_landing`: a review's doubt: `land` / `send_back` / `cancel`. A person may give their own reason after any option as `<option>: <reason>`, as `send_back: <reason>` or `land: <reason>` (write it as given). The ask of a failed review also offers `retry_review`, which reviews the same run again: show it next to the others, for a failure that was the provider's (a login, a limit) rather than the change's.
- `approve_close`: a worker reported its base already met the acceptance, and the runtime's check of the claim needs a person; the ask carries the review's verdict and recommendation, or why the check failed. `close` completes the task without a commit, `retry` puts it back to ready, `cancel` cancels it.
- `approve_plan`: plan review's concern: `ready` / `send_back: <reason>` / `cancel`.
- `approve_goal`: the goal review's question about a goal whose tasks are all finished, asked only when a person is needed. Options: `achieved` (close it; `${CLAUDE_PLUGIN_ROOT}/skills/dagq/reference/goal-close.md`), `abandoned` (close it given up; its dependents are never released), `gaps` or `gaps: <what is missing>` (register gaps as drafts on the goal), `keep_open`, plus the job's own; one the runtime does not apply comes back to be carried out by hand. A later review on the person's word: `${CLAUDE_PLUGIN_ROOT}/skills/dagq-recover/reference/goal-review-by-hand.md`.
- `correct_goal`: a follow-up judged required after its goal closed as achieved, so the goal may not have met its acceptance. Options: `reopen` (open the goal again), `correct_verdict` (keep it closed and record that achieved was wrong; a planner puts the fix in a fix goal), `keep_achieved` (the follow-up is out of scope).
  Show it in this order: the goal and that it closed achieved; the judgement as written (acceptance items, reason, evidence); the released tasks with their status, saying which already run or landed; then the options. If the person doubts the judgement itself, their words are the answer and come back to be carried out by hand: `ask close <id>` first, then a planning request naming the follow-up (`request add --ref task:N`).
- `decide`: a failed, interrupted or resume-exhausted run the recovery job could not fix: `retry` / `resume` / `cancel`, plus the job's own options, each marked `[goes back to the recovery job ...]`: choosing one has the recovery job run again with it.
  Answer with an option's exact text; a bare operation name that is no option is refused and the ask stays open. When the person wants the run's committed work carried over and no option does it, do not answer: on their word run `dagq ready ID --inherit --reason '<their words>'`, which closes the ask (`${CLAUDE_PLUGIN_ROOT}/skills/dagq-recover/reference/triage-by-hand.md`, "Carry a run's work over by hand").
  The option `edit the task's --verify, then retry_inherit` comes when the landing's verification failed. If the verify itself is broken, show it to the person; on their instruction, read `dagq show ID --full` and the failed verify log, run `dagq edit ID --verify '...'` (or `--no-verify`), then answer with that exact option. Never answer it before the edit.
  A `decide` ask by `replan-diagnosis` is on a task, not a failed run: the runtime's diagnosis of a long-running run could not settle whether it goes on. Options: `continue` (the run goes on with the same conditions) / `replan` (the run is parked at a safe boundary, its work saved, for a planner's replacement that plan review checks). Once the answer is written, the supervisor checks the premise again and applies it as going on or as the formal replanning, or closes the ask when the operation, the run or the task moved on; never replan, park or change the task yourself. Its outcome: `"$DAGQ" replans`; the held run and the person's other decisions: `${CLAUDE_PLUGIN_ROOT}/skills/dagq-recover/reference/replan-held.md`.
- `stalled`: a run's headless session the runtime and its recovery job could not get on. The question says what the session did, what the recovery job said, the answers, and the last turns as recorded: show all of it. Options: `wait`, `stop`, any the job added (marked `[goes back to the recovery job ...]`), then `propose`; any other text is sent as the session's next turn: that is how an instruction is given. An answer starting with `intervene` is not sent: a new `stalled` ask opens in its place. Steps: `${CLAUDE_PLUGIN_ROOT}/skills/dagq-recover/reference/stalled.md`, "A headless run's `stalled` ask".
- `worker_question`: the answer is sent as the worker's next turn. Show its topics (the first is the primary) with the question.
- `planner_question`: a runtime planner's question. A draft: `adopt` / `cancel` / `keep_draft`; when the person says when to look again, give it a revisit time instead (`revisit ID --at <RFC 3339 time>`, `${CLAUDE_PLUGIN_ROOT}/skills/dagq/reference/register.md`, "A draft's revisit time"). A finding: `propose` / `dismiss`. A planning request: `plan` / `decline` (`reference/requests.md`). A revise: the planner's own options. The runtime delivers the answer; do not carry it out yourself.
- `answer_prompt` and `stuck_exit`: no longer opened; one in the records is history (`${CLAUDE_PLUGIN_ROOT}/skills/dagq-recover/reference/session.md`, "Past asks and attentions of the interactive session").
- `blocked`: the observer's, about one finding: `propose` / `dismiss`.
- `queue_hold`: login, cost or disk. A login or usage limit: tell the person what to restore (log in again, `claude` or `codex login` when the question names Codex, or wait for the limit's reset); once done, the answer is `done`. `cancel_affected` gives the held runs up: show the question's `Affected:` line first. The disk's tells the person that free space is short; claims and landings wait for free space, not for the ask, so they go on once there is room even while it is open. `done` has the supervisor clean and check again; `wait` has it not ask again. What reaches the person about a provider: `${CLAUDE_PLUGIN_ROOT}/skills/dagq/reference/provider.md`.
- `approve_release`: a newer dagq release: `install` / `skip`. Show, in this order: the new version with its link from the question, the version the supervisor runs now (`status`), and what each answer does: `install` has the supervisor install it and update the plugin without stopping the runs (sessions load the new plugin only when reopened); `skip` asks again only for the next release. A plugin-only one: show the plugin's version and the binary's, and say `install` leaves the binary alone.
- `update_failed` / `approve_update`, and carrying out an `approve_release` by hand: `${CLAUDE_PLUGIN_ROOT}/skills/dagq-recover/reference/update.md`.

The runtime applies the answers this file says it applies, and `propose` and `dismiss`. Any other answer comes back as `read the answer of ask <id> and close it` (the skill's step 4).
