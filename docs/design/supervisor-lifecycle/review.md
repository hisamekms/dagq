# Review (supervisor)

`[roles.review] provider = "codex"` を設定した repository では、同じ `review.md` と prompt を worktree の `codex exec --json --sandbox read-only` に渡す。最後の agent message の JSON verdict を既存の `review_finished` と差し戻し・着地の経路へ渡す。行き先は `Supervisor::review_route` が review を始めるたびに決める。`[roles.review]` に `provider` を書いた review は goal review と同じく ADR-t1063-1 決定 4・5 に従い（`domain::actor_model::job_route`）、その provider が使えない（supervisor に agent が無い＝`executable_missing`、または控えられている）ときはもう一方の provider で起動し、`review_started` の `launch` に `switched_from` と `switch_reason` を残す。Codex の review は Claude の `queue_hold` の ask が開いていても待たずに起動する（ask は Claude の控え）。起動の後に Codex が使えないと分かった review（起動できない、認証・利用上限で止まった）は、Codex を `ProviderHold` で控え（`provider_held`。ask は開かず、壁で queue を止めるのは Claude の job だけ。`job_wall`）、`review_retried`（`attempt`・`error`・`provider`・`switch_reason`）を記録して同じ pass でもう一方の provider で起動し直す。両方が使えなければ `Phase::ReviewHeld` で session を開いたまま待ち、毎 pass 行き先を見直す。行き先が同じ provider のまま（控えを書けなかった）なら起動し直さずに手動 review に渡す（`move_review`）。worktree が無いことは run の側の失敗で、provider を控えない。一般の失敗（verdict が読めない・非 0 の終了・時間の上限）は切り替えず、今までどおり。`--no-claude` では Claude に戻さず、切り替え先の無い review（Codex が無い・控えられた・止まった）は待たずに `review_failed` で手動 review（`approve_landing`）に渡す。止まった Codex の review は（読めない verdict もやり直さずに）`code: job_failed` とその error と出力を、始める前から行き先の無い review は `code: provider_disabled` と理由（`provider_disabled: Claude is disabled by --no-claude`、Codex の理由があれば ` and codex cannot be used (<理由>)` を足す。`landing::REVIEW_PROVIDER_DISABLED`）を残し、ask は no review agent ran と書く。`provider` を書かない review は Claude で動き、Claude の控えの ask の間は待ち、`--no-claude` では手動 review に渡す。job の時間の上限は review を動かす provider の `review_timeout` で決める（[ADR-t1207-1](../../adr/2026-09-30-t1207-1-codex-run-review.md) 決定 3・4）。

[ADR-0040](../../adr/0040-verify-once-review-run-env-graph-stats-and-task-priority-in-claim-order.md)の決定2と[ADR-0027](../../adr/0027-keep-worker-session-through-review-revise-verdict-and-merge-tree-precheck.md)の決定1–4。validationを通った（`awaiting_integration`になった）runを、supervisorがleaseとslotを持ったまま、sessionを開いたままheadlessでreviewする。runのstatusは`awaiting_integration`のままで新しいstatusは足さず、進行は`review_started` / `review_finished`などのイベントで読む。

1. **開始**: `review_started`（`attempt`: そのrunの何回目のreviewか、`workspace_id`、`session_live`）を記録し、[`review`](review-command.md#review)と同じ関数で`<run-dir>/review.md`を書く。
2. **headless実行**: `AgentProvider::review_command(run, prompt, access)`（application層のport。`access`は権限の意図`REVIEW_ACCESS`＝`read_files`。[Agent provider lifecycle](../provider-lifecycle.md#headless-jobのinterface)）のコマンドを起動する。Claude Codeでは`read_files`を次の`--allowedTools` / `--disallowedTools`に訳し、`claude -p --debug-file <run-dir>/claude-review.log --add-dir <run-dir> --settings <run-dir>/claude-review-settings.json --allowedTools Read,Grep,Glob --disallowedTools Bash,Edit,Write,NotebookEdit -- <prompt>`をworktreeで（worktreeは生きているsessionのものなので、reviewは読むだけ）。settingsは`Stop` hookを持たない（生きているsessionのidle markerを書かないため）。cmux workspaceは作らない。promptは`<run-dir>/review-prompt-<attempt>.txt`に残し（`runtime::review_prompt`: `review.md`のpath、taskのacceptance、verdictのJSON schema `{"verdict": "pass" | "revise" | "concern", "reasons": [{"text": string, "codes": [string]}], "summary": string}`、reviseとconcernの境界、[差し戻しの分類コード](#差し戻しの分類コード)の一覧と定義と主の選び方）、`[run.env]`をenvに足す。envには`DAGQ_ROLE=review-job`・`DAGQ_ACTOR_ID=review-job:<run id>:<attempt>`と`DAGQ_QUEUE`も渡す（[Roles](roles.md#actors)）（observerと同じく、CLIはこのroleに読むコマンドだけを許す）。stdoutは`<run-dir>/review-<attempt>.out`、stderrは`review-<attempt>.err`。observerの`AgentProvider::headless_command`とは別のportにしている: reviewはrunに属し、そのrun directoryの設定（idle markerを書かない`Stop` hookなしのsettings、debug file、`--add-dir`）と、生きているworkerがworktreeを持つので禁止するtoolを要るが、observerのjobにはrunが無い。timeoutは`AgentProvider::review_timeout`（既定600秒）で、過ぎればkillする。ループはプロセスを`try_wait`で見るだけで止まらない。
3. **verdict**: 終了コード0でstdoutから`ReviewVerdict`が読めれば（全体か、最初の`{`から最後の`}`まで。未知のフィールドは拒否）`review_finished`（`verdict`、`reasons`、`reason_codes`、`primary_code`、`summary`、`duration_secs`、`attempt`）を記録する（`reason_codes`と`primary_code`は[差し戻しの分類コード](#差し戻しの分類コード)）。非0とtimeoutはreviewの失敗（5の「reviewの失敗」）。終了コード0でもverdictのJSONが読めない（stdoutにJSONが無い、閉じていない引用符、必須フィールドの欠落など）ときは、そのreviewが読めないverdictをやり直したものでなければ、`review_retried`（`attempt`: 読めなかったreview、`error`）を記録して同じ入力（同じ`review.md`とprompt）でreviewを1回だけやり直す（task 328。次の`review_started`の`attempt`は1つ進む）。やり直しでも読めなければreviewの失敗。やり直しはsupervisorが持つ状態（`ReviewWatch::retried`）で数え、引き継いだreviewは最初からやり直す。
4. **reviseの往復**: `revise`で、そのreviewの回の`revise_requested`（7の区切りの後のもの。`revise_unsent`で取り消したものを引く）が2件（`MAX_REVISE_ATTEMPTS`）未満（domainの`decide_revise`）、sessionが生きていれば、`reasons`と手順（直してcommit、repositoryの指示がworkerに求める検証（指示が無ければ`verification_commands`。[Prompt](prompt.md)の`local_checks`）を実行、worktreeをcleanに保つ、`STOP_BACKGROUND`、receiptを新しいheadで一時ファイルとrenameで書き直す、mergeもpushもしない、短く報告して止まり`/exit`は打たない）の定型文（`revise_request`）を`<run-dir>/revise-<attempt>.txt`に残し、`revise_requested`（`attempt`、`reasons`、`sent_at`）を記録してから`WorkspaceBackend::send_text`で生きているsessionに送る（task 241。送った後・記録の前にsupervisorが落ちると、引き継いだsupervisorが同じ依頼をもう一度送っていた。記録を先にしたので、記録と送信の間で落ちたときは送られていない依頼を引き継ぎが引き継ぐ。引き継ぎは依頼を取り込みの確認（`StartCheck`）にかけ、sessionに兆候が無ければ1回だけ送り直す（7。task 546）。打たれていた依頼は二重には送らない）。送信に失敗したら`revise_unsent`（`attempt`、`error`）で取り消す（`revise_requested`の件数から引く）。送った後、receiptが送信時刻より新しくなり、idle markerがそのreceipt以上に新しくなり（`running`のbackgroundの処理が無いこと。idle markerはreceiptより先に読み、読んだ後に書き直されたreceiptは次のpollで判定する。idle markerより新しい入力のmarker（`prompt-submit.json`。idle markerの後に読む。出どころを問わず、backgroundの処理の完了の通知（`Agent`）も含む）があれば、sessionはその入力で始めたturnを作業中とみなし、そのidle markerでは段を終えない（`IdleMarker::turn_open_after`、task 672）。そのturnを終えたidle markerで段を終える。Escで中断されて印が書かれないturnは、印が入力より古いので画面から推定したidleで終える（[画面からのidleの推定](receipt-and-session-exit.md#workerのsession)）。markerが無いか最後の入力（依頼・回答・書き直されたreceipt）より古ければ、画面から推定したidleをmarkerと同じに扱う。[画面からのidleの推定](receipt-and-session-exit.md#workerのsession)、ADR-t803-1、task 804）、receiptの`commit`がcleanなworktreeのHEADに一致したら（receiptが`failed`ならそのまま）`revise_finished`（`attempt`、`head`: worktreeのHEAD）を記録し、`restart_validation`でrunを`validating`に戻して[Validation](validation.md#validation)からやり直す（書き直したreceiptの照合はvalidationが行う）。receiptがHEADと一致しない（古いcommitのまま書いた、receiptの後にcommitした、commitしていない変更がある、parseできない）ときはvalidationに渡さず（渡すと`failed`になり作業を失う）、`revise_receipt_rejected`（`attempt`、`reason`）を記録して、HEADでreceiptを書き直すよう定型文（`revise_mismatch_request`）を生きているsessionに送り、送信時刻から待ち直す（`resume_timeout`は最初の依頼から数える）。receiptを書き直さないままidleになった（backgroundの処理が`running`のmarkerはidleではない）、sessionが終わった、`resume_timeout`（既定1時間）を過ぎた、送信に失敗した場合は、concernと同じく人に聞く。回の中の3回目のreviewがpassでなければ（`revise`でも）concernとして扱う。
5. **`/exit`とclose**: pass（下の衝突の事前判定で衝突しなかったもの）・concern・reviewの失敗では、sessionが生きていれば`exit_requested`を記録して`/exit`を1回送り、wrapperの`session_exited`を待つ（`exit_timeout`を過ぎれば`exit_request_timed_out`を1回記録し、`stuck_exit`のaskを1回だけ開いて（`ask_in`。引き継いだrunは`has_stuck_exit_ask`で二重に開かない）待ち続け、sessionが終わったら`close_stuck_exit_asks`で閉じる。[Receipt and session exit](receipt-and-session-exit.md#receipt-and-session-exit)の3と同じ）。終わったら画面を`terminal-final.txt`（resumeしたsessionは`terminal-resume-<attempt>.txt`）に保存し、workspaceを閉じる（workerのworkspaceは`workspace_closed`、resumeのworkspaceは`workspace_closed`に`resume_attempt`を付けて記録する）。
   - **passの衝突の事前判定**（ADR-0027の決定4）: `/exit`を送る前に、runの`result_commit`（passしたhead）と今の`refs/heads/<branch>`を`GitRepository::merge_conflicts`（`git merge-tree --write-tree --name-only --no-messages -z <main> <head>`をrepository rootで。merge baseはGitが`git merge-base`と同じく求める。Git 2.39には`--merge-base`が無いので渡さず、payloadの`merge_base`は`git merge-base`で別に求める）で比べる。worktree・index・refは動かさず、object storeにtreeを書くだけ。衝突しなければ（終了コード0）従来どおり`/exit` → close → 着地。衝突すれば（終了コード1。treeのOIDの後にNUL区切りで並ぶpathが衝突したpathで、quoteされない）`conflict_precheck`（`main`、`head`、`merge_base`、`conflicts`、`attempt`、`requested`、送ったなら`sent_at`、送れなかったなら`error`、上限でaskにするなら`asked`（askの理由）、衝突だけの試行を使い切って着地へ進めるなら`exhausted: 数えるresumeが3回に達していなければ、送信済みの`conflict_precheck`（`requested: true`。`unsent: true`で取り消したものを除く）と衝突だけのresumeの和（`conflict_attempts`）が`dagq.toml`の`[resume] conflict_only_limit`（既定5。以下の「5回」「at most 5」はこの値）未満で、sessionが生きていれば、resumeと同じ`resume_request`（`ResumeKind::Precheck`。冒頭は「reviewはpassしたがintegrateがmainと衝突するので着地していない」、`Reason`はmerge-treeが見つけた衝突、rebase先のmainのcommit、runの`base_commit`からmainまでに着地したtaskの一覧（`landed_since`）、手順は`Landing`と同じ（integrateの検証の失敗を再現してよいという一文だけは載せない）: `git rebase <main>`と解消、`local_checks`の検証の再実行とcommit、worktreeをcleanに保つ、`STOP_BACKGROUND`、receiptを新しいheadで一時ファイルとrenameで書き直す、不要なら`failed`、mergeもpushもせず短く報告して止まる）を`<run-dir>/conflict-<attempt>.txt`に残し、`requested: true`と`sent_at`の`conflict_precheck`を記録してから`send_text`で送る（reviseと同じく送信の前に記録する。task 241）。送信に失敗したら、`requested: false`・`unsent: true`・`error`の`conflict_precheck`（`conflicts`は載せない。stats の衝突を二重に数えないため）で取り消し、送信済みの件数から引く。その後は4のreviseと同じ待ち（`ReviseWatch`、`Fix::Conflict`）で、書き直したreceiptがcleanなHEADを指してidleになれば`conflict_resolved`（`attempt`、`head`）を記録して`restart_validation`から[Validation](validation.md#validation) → review → 事前判定をやり直す。receiptがHEADと一致しなければ`conflict_receipt_rejected`（`attempt`、`reason`）と`revise_mismatch_request`（「conflict request N」）、sessionが書き直さずにidleになった・終わった・`resume_timeout`を過ぎた・送信に失敗したら、passのverdictのまま理由を付けて`approve_landing`のaskにする。数えるresumeが3回に達していれば送らず（`requested: false`）、`/exit` → closeの後にpassのverdictと「N conflict in all), and <理由>」でaskにする（`tests/it/runtime_precheck.rs`）。sessionが終わっている（生きたsessionが無い）、送信に失敗した、merge-treeが失敗したときは送らずに従来どおり着地へ進み、着地のrebaseの衝突は`needs_session`のresumeに回る。着地slotの待ちの間にmainがさらに進んで衝突したときも同じ。事前判定はresumeの回数（`begin_resume`の上限）には数えない。
   - **pass**: 事前判定で衝突しなければ、`landing_queued`（`via: exit`。`integration_approved`のあるrunがvalidationの後にsessionを閉じたときも同じ）を記録し、leaseを持ったまま、runがe2eを要れば下の[着地の前のe2e](#着地の前のe2e)を通してから着地スロットが空くのを待ち、`begin_integration`から`land_integrating`（`integrate`と同じrebase、検証コマンド、squash、完了、後始末、push、follow_upsの登録）を別threadで走らせる。`integration_approved`は記録せず、pushは常に行う。着地が`needs_session`になれば[`needs_session`](needs-session.md#needs_session)のresumeに回る。
   - **concern**（とreviseの打ち切り）: `runtime::ask`（CLIの`ask`と同じ。新しいaskならinboxのworkspaceへ`cmux notify`する）で`approve_landing`のask（`--option land --option send_back --option cancel`、`asked_by: supervisor`、questionにverdict、打ち切りの理由、`summary`、`reasons`、`review.md`のpath）を作り、leaseを外す。askを作る前に、下の「reviewの失敗」と同じく、そのrunのcloseされていない`approve_landing`のask（前のreviewのもの）を閉じる（task 425）。残すと同じrun・kindの開いたaskに重複として畳まれて新しいreviewの理由が人に届かず、回答済みで未適用の古い回答が新しいreviewに適用されうるため。
   - **reviewの失敗**（task 328）: `review_failed`を記録するのと同じstepで、concernと同じ経路（`runtime::ask`）で`approve_landing`のask（同じoptions、`asked_by: supervisor`、questionに失敗したreviewの`attempt`と`error`、`review.md`のpath、そのattemptのjobが走ったときは`review-<attempt>.out` / `.err`のpath）を開く。jobが起動できなかった失敗（promptの書き込み・materialの取得・spawnの失敗）ではそのattemptの出力は書かれていないので名指しせず、読めないverdictのretryが起動できなかったときは、走った前のattemptの`review-<attempt-1>.out` / `.err`を`Review output of the earlier review N`として載せる。どのattemptの出力があるかは`AfterExit::ReviewFailed`の`output`が持ち、fileの有無からは推測しない（task 426）。その前に、そのrunのcloseされていない`approve_landing`のask（`send_back`や手の`integrate`でrunが動く前の、前のreviewのask）を`close_approve_landing_asks`で閉じる（concernと共通の`ask_approve_landing`が行う。未回答なら`answer`に`a later review of the run asks again; closed by the runtime`を書き`runtime_closed: true`の`ask_answered`、回答済みなら`ask_closed`を記録し、閉じたaskごとにinfoのlogを出す。attentionではない）。runが`integrated`になったときも、着地の後始末がそのrunの`approve_landing`のaskを閉じる（[integrate](integrate.md)の8。task 425）。askを開いてから`review_failed`（`attempt`、`error`、`duration_secs`、`status`、開いたaskの`ask_id`）を記録してleaseを外す。askと`review_failed`はworkerのsessionの`/exit`の後だが、reviewのsessionの区間はjobが終わった（起動できなかった）時点で`job_finished`で閉じ、`/exit`の待ちを含めない（[provider-lifecycle](../provider-lifecycle.md#claude-sessionの区間)の「失敗したreview」。task 541）。runは`awaiting_integration`のままで、`ask_id`を持つ`review_failed`はattentionではなく、askの`ask_opened`がattentionになる。回答は6のとおりsupervisorが適用する（`send_back`の`reason`は`the headless review failed: <error>`）。askを開けなかったときは`ask_id`なしの`review_failed`を記録し、attentionは`review by hand`で、人がinboxから`dagq-recover`の`reference/review-by-hand.md`に従ってreviewし、`integrate`を手で呼ぶ。askが適用されずに閉じられた（自由記述の回答など）runも`review by hand`になる。
6. **askの回答**: supervisorはループの各回で、adoptの後、resumeの前に、回答済みでcloseされていない`approve_landing`のaskのうち、runが`awaiting_integration`でleaseが無いものを見る（`apply_landing_answers`）。slotの空き・`integrating`のrunの有無・`[run.env]`のプログラムの不足・landing branchの未解決・空き容量の不足に関わらず、次の回でその場で適用してaskをcloseする（task 949。以前は`land`を着地スロットと空きslotがそろうまで適用せず、`send_back` / `cancel`もslotが埋まっている間は適用しなかったので、答えたaskが閉じずに残った）。`land`なら`integration_approved`（`ask_id`付き、`push: true`）と`landing_queued`（`via: approve`、`ask_id`）を記録してaskをcloseし、runは`awaiting_integration`・leaseなしのまま着地の列に並ぶ（同じaskの承認が記録済みなら記録し直さない。`status`は`queued to land (runtime)`、`kind: landing_queued`）。着地の開始は別の段（`start_approved_landings`）で、答えの適用の後、resume・triage・新しいclaimより先に、列のrun（`awaiting_integration`でleaseが無く、`RunHistory::queued_to_land`がある: ## 着地の前のe2e

[ADR-t1233-2](../../adr/2026-10-02-t1233-2-e2e-runs-on-the-host-after-review-passes.md)（task 1239）。e2eはworkerが流さず、reviewがpassしたrun（`approve_landing`に`land`と答えたrunと、resumeから着地へ進むrunも）のうちe2eを要るものに、着地を依頼する前にsupervisorがhostで流す（`application::supervise::e2e`）。要否はvalidatingが決めて`validation_finished`の`e2e_requirement`に記録したもの（[Validation](validation.md#runtimeが流すe2e)）。

- **いつ**: runが着地スロットを待つ`Phase::AwaitingSlot`の各回で、`[run.env]`のプログラムの不足・landing branchの未解決・空き容量の不足が無ければ、着地スロットの空きを見る前に`domain::run_e2e::due`を見る。最後の`validation_finished`がe2eを要ると言い、そのrunの`result_commit`（reviewしたcommit）に`outcome: passed`か`not_configured`の`run_e2e_finished`がまだ無ければ流す。`approve_landing`の`land`で列に入ったleaseの無いrun（`start_approved_landings`）は、e2eが要れば`lease_for_e2e`（`lease_acquired`の`reason: e2e`）でleaseを取ってslotに入れ、同じ道を通す。着地のrebaseの後には流し直さない（`integrate`では流さない。ADR-t963-1決定4）。人が手で打つ`integrate`はこの工程を通らない。
- **流し方**: 自動更新の関門（[Auto-update](auto-update.md)）と同じ`infrastructure::e2e_gate::run`を、runのworktreeで`CARGO_TARGET_DIR`を与えずに（workerのbuildのtargetを使う）流す。コマンドは、main checkoutがdagqのsource（[Source repository](source-repository.md)。supervisorの起動時に判定する）なら`cargo test --locked --test e2e -- --ignored`で、supervisorのcmux（`DAGQ_E2E_CMUX`、始める前のping、後の掃除）、main checkoutの`dagq.toml`の`[run.env]`、podmanの確認（ADR-t1162-1。届かなければ`broker::`を飛ばす）、上限`E2E_TIMEOUT`（1800秒）、`TMPDIR`は`<queue dir>/e2e/`の下。sourceでないrepositoryにはruntimeの知るe2eが無いので流さず、`run_e2e_finished`（`outcome: not_configured`）を記録して着地へ進む（testは`SuperviseOptions::run_e2e`の`command`でstubのコマンドを渡す。cmuxとpodmanは確かめず、lockは`lock`を渡したときだけ取る）。出力はrun dirの`e2e-<attempt>.log`、名前で流し直した分は`e2e-<attempt>.rerun.log`。
- **同時に1本**（決定4）: 1つのsupervisorのrunは1本ずつ流し、他のrunのe2eが走っている間に順番が来たrunはslotとleaseを持ったまま`Phase::AwaitingE2e`で待ち（次の回に`Phase::AwaitingSlot`に戻って決め直す）、待ちに入るときに`run_e2e_waiting`を1回記録する。processをまたいでは、e2eの始めにhostのlock（`<data dir>/e2e.lock`。`application::install::e2e_lock_path`でqueueのdirの親、つまりhostの全queueで共通。`flock`）を取り、終わるまで持つ。自動更新の関門と`install`の関門も同じlockを取るので、先に取ったものが流し、後のもの（人の`install`を含む）は空くまで待つ。e2eのfixtureが作る使い捨てのqueueはdata dirが別なので、流しているe2eの中のdagqは同じlockを取らない。lockを待った秒は`run_e2e_finished`の`lock_wait_secs`。

## 差し戻しの分類コード<a id="差し戻しの分類コード未実装"></a>

[ADR-t947-1](../../adr/2026-09-28-t947-1-review-verdicts-carry-reason-codes.md)の決定（task 948で実装）。一覧と定義は`domain::review_reason::REVIEW_CODES`が持ち、reviewのpromptがそのまま載せる（`application::prompt`の`reason_codes_section`）。一覧はtask 945の分析（[review-sendback-reasons](../../plans/review-sendback-reasons.md#ラベルの定義案)）を元に、workerの問い（[ask](ask.md#worker_questionの分類コード)）とfollow_up（[Receipt and session exit](receipt-and-session-exit.md#follow_upsの分類コード)）の集合と同じ種類の問題の名前を揃えた。

- **verdictの形**: `reasons`の各項目は`{"text": string, "codes": [code, ...]}`（`codes`は1つ以上、先頭が主）。文字列だけの項目（コードより前の形）も読み、`codes`の無い項目として扱う。コードは集計のためのlabelなので、その形でverdictを読めなくはしない（ADR-t947-1決定3）: `codes`は文字列1つか配列（文字列でない要素は捨てる）で、それ以外の形は`codes`の無い項目、項目の他の欄は無視する。`text`の無い項目とverdictの未知の欄は今までどおり読めないverdictにする。`ReviewVerdict`は`reasons`に文だけを、`reason_codes`に項目ごとのコード（無ければ空）を持つので、`revise_requested`・askの問い・`send_back`の理由など文を使う所は変わらない。verdictの主のコードは最初の項目の主のコードで、promptはverdictを決めた項目を先頭に置かせる（止めない注意の項目は先頭にしない）。
- **記録**: `review_finished`の`reason_codes`（項目ごとのコードの配列）と`primary_code`（passは`null`。revise・concernで項目もコードも無ければ`unlabeled`）。`codes`の欠けた項目は`["unlabeled"]`、一覧に無い値はその値のまま記録し（拒否も`other`への読み替えもしない）、空白だけのコードは捨てる。コードはverdictの判定と適用に使わない。コードより前の`review_finished`は書き換えず、読む側（[Stats](stats.md#差し戻しの分類コードごとの集計)）が各理由を`unlabeled`として数える。
- **主の選び方**: 1つの項目が2つ以上に当たるときは、直すのに誰の判断が要るかの重い方を主にする。重い順: `adr_conflict` > `acceptance_conflict` > `acceptance_infeasible` > `adr_design_mismatch` > `acceptance_ambiguous` > `acceptance_unmet` > `out_of_scope_change` > `repo_rule_violation` > `code_defect` > `test_gap` > `docs_drift` > `local_slip` > `other`。

| コード | 定義 | 分析の例（無印はtask 945） |
|---|---|---|
| `adr_conflict` | taskの受け入れ条件かdescription、またはそれを満たす唯一のやり方が、acceptedのADR・design・人の決定（goalのconstraints、AGENTS.mdのユーザー決定）と食い違い、両方は満たせない。workerが一方を選んで逸脱している | task 818: 条件の「待つ」がADR-0047決定42と食い違う |

| `adr_design_mismatch` | taskの条件はADRと整合し、整合するやり方もあるのに、実装がacceptedのADR・designの決定と食い違う（新しいADRもamendsも無い） | task 445: ADR-0062と違うeventを書く |
| `acceptance_ambiguous` | 条件の文言が2通り以上に読め、実装がその一方を選んだ | task 221: 「string literalと比べない」の範囲 |
| `acceptance_unmet` | 条件やdescriptionが明示した範囲の一部を満たしていない（気づかずの漏れと、follow_upに回した部分の両方） | task 324: 上限の無い待ちが残る |
| `out_of_scope_change` | 求められていない挙動を変えた（本番の挙動、他のtaskの範囲） | task 567: testのseamのはずが本番のpollを変えた |
| `repo_rule_violation` | repositoryの手順の規則（AGENTS.mdなど）に反する | task 672: stressの失敗を流し直しで済ませた |
| `code_defect` | 実装の誤りか回帰 | task 327: 再起動でholdが消える |

- **人の答えからの補い**（ADR-t947-1決定4）: 6の`approve_landing`の答えを適用するとき（`apply_landing_answer`の最初、runの状態を変える前）、supervisorはrunの最後のreview（`review_finished` / `review_failed`の最後のもの）がreviseかconcernの`review_finished`なら（concernと、使い切った・sessionが終わった・切り替えられなかったreviseがaskになったもの）、それを指す`review_outcome`（`attempt`、`ask_id`、`outcome`、そのverdictの`reason_codes`と`primary_code`。コードより前のverdictは各理由を`unlabeled`）を記録する。`outcome`は`land` → `deviation_accepted`（reviewの誤りの候補を含む）、`send_back` → `deviation_rejected`（verdictのコードを引き継ぐ）、`cancel` → `canceled`（`domain::review_reason::answer_outcome`）。同じaskの`review_outcome`があれば記録しない（途中で止まった適用の続きで二重に書かない）。最後のreviewが`review_failed`（reviewの失敗のask）か、passの後の衝突の事前判定が開いたaskには記録しない。workerに返したreviseには人の答えが無いので記録しない（askになったreviseは答えがあるので記録し、`stats`ではそのreviseのコードの`outcomes`と`concern_wait_secs`に入る）。人にコードを選ばせない（`tests/it/runtime_review_reasons.rs`）。

## test からの retry の差し替え

`SuperviseOptions::retry_unreadable_review` は既定で `true`。読めない verdict を
1 回だけ retry する production の方針は変わらず、CLI・`dagq.toml`・環境変数から
この値を変える経路はない。test は `false` を渡すと、最初の unreadable verdict から
通常の失敗処理（review session の close、worker の exit、`approve_landing` の ask）へ
進める。起動失敗・timeout・読める verdict の扱いは変わらない。

`tests/it/runtime_support` の通常の `supervise` / `supervise_with` と `run_agent` は
この retry を省く。retry と verdict の無い review 後の ask を確認する test は
`supervise_retrying` / `supervise_retrying_with` / `awaiting_run_retrying` を明示する。
`supervise_reviewed` / `supervise_reviewed_with` と直接の runtime 呼び出しは caller の
設定を保つので、既存の `TestReviewer` による retry の検証は既定の 1 回のままである。
