# Handoff

[ADR-0045](../../adr/0045-build-identifier-explicit-migrate-schema-compat-handoff-and-auto-update.md)の決定10・11。supervisorは、sessionの終わりを待たずに、自分のpidのまま別のbinaryをexecして続ける。use caseは`src/application/supervise/handoff.rs`、execは`src/main.rs`の`run`。

- **要求**: `supervisors`の`handoff_accepted`（schema v31。`supervise`が登録の直後に1を書く）が1の登録にだけ、`up`か`install`が`request_handoff(token, binary)`で`handoff_binary`と`handoff_requested_at`を書く。受けられない登録（引き継ぎを知らない前のbinary）には書かず（`false`）、`up`はdrainに、`install`は`not_handed_off`に回す。要求をDBに置くのは、signalはlaunchd modeとin-cmux modeで届け方が違い、区切りまで待たせる必要もあるため。
- **区切り**: ループの各passの先頭で、停止要求（SIGINT/SIGTERM）が無ければ`handoff_request(token)`を読む。要求があれば新しいclaim・adopt・resume・triage・observer・plan review・goal reviewの起動を止め、DBとrunのファイルから組み立て直せないslot（`Validating`・`AwaitingSlot`・`E2e`・`Landing`、つまり検証と着地が進行中のもの）だけを進める（`tick(true)`）。待つあいだも各passで、走っているplan review / goal reviewのjobが終わっていれば回収してverdictを適用する（`plan_review_pass(options, false)`・`goal_review_pass(false)`。task 1425。verdictでreadyになったtaskは待ちのあいだclaimせず、次のプロセスがclaimする）。全slotが組み立て直せる状態になったら、`prepare_handoff`はobserverを止めた後、plan review / goal reviewのjobを1回pollし、終わっていれば（`poll`が`Some`）回収してverdictを適用する（終わったjobのverdictを捨てて次のプロセスで同じattemptをやり直さない。task 1425）。そのうえでobserverの子プロセスと、まだ走っているheadlessのreview / triage / plan review / goal reviewのjobを（その子孫ごと）止め（`headless_jobs`の行は`stopped`で閉じ、execの前に書く。[Headless job processes](headless-job-processes.md)。plan review / goal reviewの行は同じtokenのまま未完了で残り、引き継いだプロセスが最初のpassに入る前に、自分のtokenの未完了行だけを`interrupted`（error: `stopped for the supervisor handoff`）で閉じる。候補が無くても閉じ、transcriptを`read_before`で書き込みtransactionの前に読んでから既存のclose経路で`session_closed`（`reason: job_finished`、model / effortも既存の経路）を記録する。他のtokenの行は閉じない。候補のままなら以後のpassで再びreviewし、interruptedはattemptに数えない。triageはleaseを返し、次のプロセスがtriageし直す。reviewはleaseを保ち、次のプロセスがreviewし直す）、DBが持たない状態を、書いたsupervisorのtokenを添えて`runs/<id>/handoff.json`に書き（同じtokenの次のプロセスだけが読み、それ以外が残したfileは読まずに消す。resume中のsessionのworkspace・試行番号・送った依頼と時刻・`/exit`を要求したか（`exit_requested`）と打ち終えたか（`exit_typed`。task 1164。同じsupervisorのexecなので前のプロセスの値をそのまま引き継ぎ、欄の無い古いfileはfalseとして読む）、検証で`failed` / `needs_session`になって`/exit`を待つrunのsessionと`/exit`の有無）、`{"outcome":"handoff","binary","token","handed_over",…}`でループを抜ける。登録は消さない（heartbeatだけが止まり、execは数秒で終わるのでlease TTLの30秒を越えない）。停止要求は引き継ぎに勝ち、通常のdrainになる。
- **要求の受け取りと取り消し**: drain中のsupervisorは各passで`handoff_request(token)`を読み直し、取り消されていれば（None）保持した要求を捨ててdrainを解き、同じpassで通常のclaimに戻る。別のbinaryの要求に置き換わっていれば（`request_handoff`は`handoff_binary`を上書きするので、`install`と自動更新が重なると起きうる）、claimを挟まずに新しいbinaryを保持してdrainを続け、そのbinaryでexecする（task 1286。logは「置き換わった」と「取り消された」を分けて出す）。execの直前には`take_handoff(token, binary)`の条件付きUPDATEで要求の列を原子的に消し、`handoff_accepted`を0にする（取り戻しの`resume_registration`が1に戻すまで次の要求を受けない。task 824）。`hand_off`はこの「要求が無く`handoff_accepted`が0の同じtokenの行」をexecの途中と見て待ち、プロセスが死ねば失敗、新しいbuild識別子で戻れば成功、前のbuild識別子で戻ればexecの失敗とする。tokenとbinaryが一致して受け取れたときだけ`prepare_handoff`を行って`handoff`を返す。受け取れなければexecせず、`handoff_request`を読み直して、別のbinaryの要求があればそれを保持してdrainを続け（次のpassでそのbinaryの受け取りを試みる）、無ければdrainを解いて通常のclaimに戻る（task 1286）。取り消しでdrainを解くとき（各passの読み直しとexec直前の受け取りのどちらでも）は、終わったrunの掃除も通常に戻す（`resume_cleanup`。task 1427）: 頼みを再び受け、共有の停止の印（`cleanup.stop`）を下ろし、終わったrun全部の掃除をすぐ頼み直して、drainのあいだ捨てた頼みと、停止の印で今のworktreeの後に止まったjobの残りを拾う。空き容量の掃除はdrainで受けられなかった頼みを掃除の間隔（`CLEANUP_INTERVAL`）に数えないので、戻った後の容量不足はすぐ掃除のjobを走らせ、それでも足りないときだけdiskのaskになる。置き換え（task 1286）と停止要求でのdrainでは掃除を戻さない。受け取り後の`cancel_handoff`はfalseを返すので、呼び出し側は`HANDOFF_GRACE`のあいだ新しいbinaryで戻ったかを見直す。
- **停止要求の記録と引き継ぎの待ち**（task 1277）: supervisorは停止要求（SIGINT/SIGTERM。`down`・`up`や`install --allow-breaking`のdrain・launchdのbootoutのどれから来ても）に最初に気づいたpassで、queueのevent `supervisor_draining`（`EventKind::is_queue`。`supervisor`（token）・`pid`・`build`（build識別子）・`reason: stop_requested`・`handoff_binary`（保留中の引き継ぎのbinary、無ければnull）・`runs`（進行中のslotのrun ID））をプロセスごとに1回だけ記録する（書けなければlogに残して次のpassで書き直す）。停止要求は引き継ぎに勝つので、drainを続けてexecしない。`hand_off`の待ち（`wait_for_handoff`とtask 715の`look_again`）は各`poll`で最新の`supervisor_draining`を読み、待っているsupervisorがまだ引き継いでいない（`look_at_handoff`が成功を返さない）のにそのtokenの`supervisor_draining`があれば（要求の前の記録も同じく、その停止はexecせずに終わる。drainを終えて登録が消えた後も同じ）。1回の見直しは停止の記録・登録・停止の記録の順に読む（`Stops::around`）: まだ要求を持つsupervisorは登録より前に読んだ停止だけで停止中とし（新しいbuildで戻った直後に止められたsupervisorを停止中と取り違えない）、登録が消えた・heartbeatが古くなったsupervisorは登録の後に読んだ停止でも停止中とする（supervisorは登録を消す前に停止を記録するので、2つの読み取りのあいだに停止して登録を消したsupervisorも停止中と分かる）、上限を待たずにそのsupervisorを失敗にし、要求を`cancel_handoff`で取り消す。errorは`supervisor <token> (pid <pid>) is stopping (a stop request wins over the handoff) and was not handed off to <path>; …`で、`Handed`の`stopping`がtrueになり、`Handed::report`（`up`の`replaced[]`、`install`の`supervisors[]`、`update_failed`の`supervisors[]`）の要素に`stopping: true`が付く。全員の失敗で前のbinaryに戻し、一部なら新しいbinaryを残す規則（ADR-t632-1）とaskの形は変えない。上限切れのerrorの`it still finishes its validation or landing in progress`は、停止中でないsupervisorにだけ出る。
- **exec**: `main`は`supervise`の結果が`handoff`なら、queueの接続がすべて閉じた後で、自分の引数から`--handoff-token`（と`--mode`）を除いて`--handoff-token <token>`を足し（要求されたbinaryが`supervise --codex`を知らなければ、`supervise --codex probe --help`が失敗するので`--codex`とその値も除く。`install --rollback`で`--codex`より前のbinaryへ戻るとき。`HANDOFF_OPTIONAL`、ADR-t813-2）、要求されたbinaryを`CommandExt::exec`で同じpidのまま起動する（SQLiteのfdはclose-on-execで開かれる）。execが失敗したら（fileが無い、実行できない）logに残し、同じbinaryのまま同じ引数で`supervise`をやり直すので、登録は前のbuild識別子で取り戻され、頼んだ側は「別のbuild識別子で戻った」として失敗を知る。in-cmux modeのsupervisorは同じcmux workspaceの同じプロセスのままで、launchd modeのsupervisorは同じpidなので`KeepAlive`は何もしない。
- **取り戻し**: execされた`supervise --handoff-token <token>`は、`resume_registration(token, pid, build識別子)`で登録の`binary_version`とheartbeatを更新する（要求の列はexec前の受け取りで既に消えている。execに失敗したときも同じ取り戻しを行う）（tokenとpidが一致しなければerror）。`mode` / `workspace_id` / `started_at`とleaseは変えない。続けて`runs_leased_by(token)`の各runに`supervisor_handed_off`（`supervisor` / `pid` / `previous_version` / `version` / `status` / `state`）を記録し、slotを組み立て直す: `handoff.json`があればそこから（resumeは`ResumeWatch`、`/exit`待ちは`ExitWatch`。`/exit`は送り直さず、exit timeoutは今から数え直さずに、記録した`exit_requested`の時刻（resumeはその試行のもの。その後に規則でダイアログに応答した`auto_repaired`（`repair: dialog_answered`）か、`stuck_exit`の復旧jobがダイアログに応答した・プロセスを止めた`auto_repaired`（`answer_known_dialog` / `stop_processes`）があればその時刻）から数える（task 894。`handoff.json`は時刻を持たず、resumeでは要求の有無と`exit_typed`を持つ。記録が見つからなければ今から数える）。時間切れの後の`/exit`の再試行は、adoptと同じくrun_eventsの`exit_retried`から回数と最後の時刻を読んで続ける（resumeの`ResumeWatch`もtask 936から同じ）。[Receipt and session exit](receipt-and-session-exit.md#exitの再試行)）、`claimed` / `starting` / `running` / `validating`はadopt（[supervise](supervise.md)の5）と同じ`resume`、`awaiting_integration`は`adopt_review`（reviewの途中ならreviewし直し、`/exit`は送り直さない）、`handoff.json`の無い（書けなかった・消えた）`needs_session`のrunは、adoptと同じ条件（`resume_adoptable`: 最後のresumeのイベントが`resume_started`でその試行のworkspaceが記録済み、wrapperが終了を記録しておらずプロセスが生きている）を満たせばleaseを返さず`adopt_resume`でrun_eventsと`resume-<attempt>.txt`から`ResumeWatch`を組み立て直し（[Needs session](needs-session.md)。task 640）、それ以外はleaseを返す（resumeとtriageが拾う）。resumeの監視を引き継いだときは、`handoff.json`からでもイベントからでも`auto_repaired`（`repair: resume_adopted`、`conditions.handoff: true`、`detail.previous_version`）を記録する。adoptではないので`run_adopted`は書かない。execに30秒以上かかってleaseがstaleになり、その間に別のsupervisorがadoptしたrunは、[ADR-0039](../../adr/0039-adopt-stale-lease-of-live-wrapper-and-renew-own-stale-lease.md)のとおりそのsupervisorのものになる（取り戻したプロセスの`runs_leased_by`には出ない）。
- **resumeの依頼を送る前**: resumeを始めて（`resume_started`・`session_opened`）から`resume_request_sent`までの待ち（wrapperとagentの登録、入力欄が`resume_prompt_delay`のあいだ準備できていること）は、登録の待ちはqueueのprocessの行を、入力欄の待ちは画面をpassごとに1回読むだけで、passを塞がない（`ResumeWatch::poll`と`send_when_ready`。task 1161）。passを塞ぐのは依頼の送信（`submit`）だけで、`submit_check_interval`ごとの確認と`SUBMIT_RETRIES`回のEnterに、cmuxの各コマンドの時間切れが上限を付ける。resumeのslotは組み立て直せるので、この間に頼まれた引き継ぎは次のpassの先頭で受け取られ、`handoff.json`は`message_sent_at`なしで書かれ、次のプロセスは同じsessionの入力欄が準備でき次第、依頼を1回だけ送る（runをresumeし直さない。登録・`input_not_ready`・resume timeoutの時計は引き継いだときから数え直す）。
- **待ち**: 人の答えを待つrun（[人の答えを待つrun](waiting.md)）のslotは組み立て直せるので、引き継ぎはそれを待たない。次のプロセスはslotを組み立て直した後、runのイベントから待ちと戻り待ちを戻す（`run_waiting_started`を記録し直さず、上限を超えていても待ちのまま。[ADR-0062](../../adr/0062-runs-waiting-for-a-person-leave-the-slot.md)の決定11）。
- 走っているrunのwrapperはclaim時の`runner`（前のbinaryのコピー）で動き続ける。互換の範囲のschemaならそのまま動く。
- **run の review job と復旧 job**: `tick(true)`は組み立て直せるslotを進めないので、run の review job（`Review`）と復旧job（`Recovery`）は、引き継ぎを待つあいだに終わってもverdictを回収されず、`prepare_handoff`で止められて次のプロセスでやり直す（reviewはleaseを保ってreviewし直し、復旧jobはleaseを返して取り直す）。plan review / goal reviewと違い、verdictの適用がslotを着地や`/exit`へ進めて引き継ぎの待ちを延ばしうるため、task 1425では変えていない。
- **test**: `tests/it/runtime_handoff.rs`がin-processで、sessionの作業中の引き継ぎ（同じtokenのleaseのまま次のプロセスがreceipt・1回の`/exit`・検証まで進める）、検証で落ちて`/exit`を待つrunの引き継ぎ（`handoff.json`で`/exit`を送り直さない）、resume中の引き継ぎ（`handoff.json`から（依頼を送る前の引き継ぎで次のプロセスが依頼を送ることも）、および`handoff.json`が無くsessionが生きていればイベントから監視を続け、sessionが終わっていればleaseを返して次の試行でresumeする）、組み立て直せないrunのleaseの返却と消えた登録の拒否を、`a_handoff_does_not_wait_for_a_supervisor_that_drains_for_a_stop`が、着地を待つあいだに引き継ぎを頼まれて停止要求を受けたsupervisorが`supervisor_draining`を1回だけ記録し、`hand_off`が上限を待たずに`stopping`の失敗にして要求を取り消し、drainが着地まで続くことを、`a_handoff_replaced_while_draining_execs_the_new_binary_without_a_claim`と`a_handoff_replaced_at_the_take_execs_the_new_binary_without_a_claim`（`take_handoff`の時点の置き換えはSQLiteのtriggerで差し込む）が、drain中に別のbinaryへ置き換わった要求でreadyのtaskをclaimせずに新しいbinaryでexecすることを、`canceling_a_handoff_during_a_landing_resumes_claims_without_exec`が取り消しでexecせずclaimに戻ることを、`runtime_cleanup::a_withdrawn_handoff_resumes_the_cleanup`が、通常の掃除のjobを止めている間に取り消した要求と`take_handoff`の時点で取り消した要求（SQLiteのtriggerで差し込む。jobは停止の印で今のworktreeの後に止まっている）のどちらでも、取り消しの後に終わったrunの掃除（`build_outputs_removed`・`worktree_removed`）が最後の候補まで記録され、その後の容量不足でdiskのaskの前に空き容量の掃除が走ること（足りればaskを開かず着地し、足りなければaskになる）、置き換えでは掃除が戻らずexecすることを、`runtime_handoff::review_verdicts`（plan reviewのfixtureとstubのjob）が、引き継ぎを待つあいだ（host metricsの標本で待たせる）に終わったplan review / goal reviewのverdictが待ちのあいだに適用され次のプロセスでやり直されないこと、execの直前に終わっていたjobのverdictが`prepare_handoff`で適用されること、走っているjobは止めて次のプロセスでやり直すことを、`tests/it/lifecycle_handoff_stop.rs`が、まだ要求を持つ停止中のsupervisorと、停止の記録と登録の読み取りのあいだに停止して登録を消したsupervisor（clockの読み取りで差し込む）がどちらも`stopping`で失敗することを、`lifecycle_install::the_update_job_marks_a_supervisor_that_stops_as_stopping`が`update_failed`の`supervisors[]`に一部の失敗と全員の失敗の両方で`stopping: true`が載ることを、`tests/it/cli_version.rs`が実プロセスの`supervise`（stubのcmuxとClaude）に`install`と`install --rollback`で2回execさせて同じpidとtokenで続くことを、`tests/e2e.rs`の`install_hands_the_supervisor_over_while_a_session_works_and_the_run_lands`が実cmuxのworkerの作業中に`install`で引き継ぎ、そのrunが着地し、`--rollback`でもう一度引き継ぐことを確かめる。
