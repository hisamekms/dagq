# Auto-update

[ADR-0045](../../adr/0045-build-identifier-explicit-migrate-schema-compat-handoff-and-auto-update.md)の決定13・17。`up --auto-update`のsupervisorは、runtimeを変えるcommitがmainに着地するたびに、queueのdirの下でそのcommitをビルドし、同じcheckoutで全部のe2eを流して通ったときだけ（[ADR-t963-1](../../adr/2026-09-29-t963-1-e2e-required-by-diff-and-run-in-full-before-auto-update.md)決定1）、[`install`](install.md#install)と同じ手順で固定バイナリを置き換えて自分を[引き継ぎ](handoff.md#handoff)で入れ替える。走っているsessionは止まらない。supervisor側は`src/application/supervise/update.rs`、ビルドから見張りまでのjobは`src/application/update.rs`（`run`）、CLIは隠しコマンド`dagq auto-update`、配線は`src/compose.rs`の`OneShot::auto_update`。

- **有効にする**: `up --auto-update`は、起動するsupervisorを`supervise --auto-update`で起動し（登録の直後に`supervisors.auto_update`を1にする。launchdの再起動でも同じ引数なので残る）、reuseや引き継ぎで残すliveな登録には`set_auto_update`で1を書く。`--auto-update`の無い`up`は同じ登録の`auto_update`を0にする。結果の`supervisor.auto_update`に出る。execの引き継ぎは登録の行を変えないので、設定は残る。この repository は`dagq.toml`を置かないので、設定ファイルではなく`up`のフラグにした（ADR-0045のAlternatives）。
- **きっかけ**（`auto_update_pass`）: supervisorはループの各passで、前に見てから`--update-interval`（既定30秒）経っていて、自分の登録の`auto_update`が1なら、mainを見る。停止要求の後、claimを止めた後、引き継ぎの要求を受けた後は見ない。
  1. まず`update_failed`のaskの答え（下記）を適用する。
  2. 自分が起動したjobが生きているか、jobが書いた最新の段（askの答えの`update_answered` / `update_retry`は飛ばす）が`update_started` / `update_built` / `update_restored`でそのjobのpidが生きていれば、何もしない（同時に1つ。execの後の新しいプロセスもDBの行で判定する）。execの前に起動したjobはexec後のプロセスの子のままで他に回収する者がいないので、そのpidを`waitpid(WNOHANG)`で回収してから生死を見る（`ProcessControl::reap`）。その行のjobが死んでいれば（kill、再起動）、どこまで進んだか分からないので自分ではやり直さず、`update_failed`（`stage: interrupted`）を書いて`update_failed`のaskを開く。
  3. mainのhead（`refs/heads/<branch>`）と、比べる元（`base`）を決める。`base`は最新の`update_started`のcommit、無ければ自分のbuild識別子が名乗るcommit（`X.Y.Z-dev+<commit>[.dirty]`の`<commit>`）、それも無ければ（リリースのビルド、`+unknown`）このプロセスが最初に見たmain。headが`base`と同じなら何もしない。
  4. `git diff --name-only <base> <head>`のどれかが`src/`・`migrations/`・`crates/`・`Cargo.toml`・`Cargo.lock`・`build.rs`・`rust-toolchain.toml`（`RUNTIME_PATHS`。`build.rs`はbuild識別子を埋め込む。`crates/`はbrokerのcrateで、`rust-toolchain.toml`はbrokerのimageのRustの版。ADR-t827-1決定4）なら、headのjobを起動する。変えていなければそのheadを覚えて見直さず、`automatic update: main's <head> builds nothing: it changes no runtime path`をheadごとに1回logに出す（testは固定のsleepの代わりにこの行を待つ。task 1048）。`base`をGitが知らない（別のcloneのビルド）ときは、headを1回ビルドして、それが次の`base`になる。`update_retry`（`retry`の答え）が最新の`update_started`より新しければ、差分を見ずにheadをビルドする。
  - supervisorの着地でも、人が手で打った`integrate`でも、mainが進めば同じように拾う。ビルド中に次の着地があっても積まず、jobが終わった後の最初の見直しで、そのときのheadを1回ビルドする。
- **job**（`dagq --db <db> auto-update --commit <head> --token <supervisor> --to <supervisorのbinary> --repo <checkout> --log <build log> --claude … --codex … [--cmux …] [--plugin-dir …] [--build-command …] [--e2e-command …] [--e2e-timeout …] [--poll-ms …]`。`--claude`と`--codex`はsupervisorの`Layout`の値で、jobがsupervisorを起動し直す`up`にも渡す）: supervisorが自分のbinary（`current_exe`）で起動する。setsidで新しいsessionとprocess groupに入れる（supervisorのexecにも、in-cmuxのworkspaceが閉じられることにも巻き込まれないため）。stdoutは`<queue dir>/logs/update-<unix時刻>-<commit 12桁>.json`（結果）、stderrは同じ名前の`.log`、ビルドの出力は`.build.log`、jobのtracingは`auto-update-*.jsonl`（どれも最後の書き込みから14日で消える。[Logs](logs.md#logs)）。hiddenの`--poll-ms`（既定500）は3の引き継ぎの待ちと4の見張りがqueueを見る間隔で、supervisorはhiddenの`supervise --update-poll-ms`を渡されたときだけそれを付ける（testが短くする。task 1048）。起動したら、supervisorが`update_started`（`pid`・`base`・`supervisor`・`version`・logのpath）を書く。
  1. **ビルド**: `<queue dir>/update/checkout`をheadに合わせる（無ければ`git worktree add --detach --force`、あれば`checkout --detach --force`と`clean -fdx`）。`CARGO_TARGET_DIR=<queue dir>/update/target`で`cargo build --release --locked -p dagq -p dagq-broker-client`を走らせる（workerのbrokerのclientも同じbuildで`release/dagq`の隣に作る。[ADR-t827-1](../../adr/2026-09-28-t827-1-broker-crates-binaries-and-version-alignment.md)決定5。`--update-build-command`で渡したshellのコマンドに置き換えられる。testが使う）。brokerのimageはここではbuildしない（brokerを起動するときにtagが無ければbuildする。決定6、[Broker](../broker.md#配布と版)）。人のmainのcheckoutと`target/`は使わない。成功すれば`update_built`。
     - **e2eの関門**（ADR-t963-1決定1、`e2e_gate`）: 続けて同じcheckoutで、`CARGO_TARGET_DIR=<queue dir>/update/target`のまま全部のe2e（`cargo test --locked --test e2e -- --ignored`。`--e2e-command`で渡したshellのコマンドに置き換えられる。testが使う）を流す。`Binaries::e2e`の実装は`src/infrastructure/e2e_gate.rs`。envはmain checkoutの`dagq.toml`の`[run.env]`（[Run environment](run-environment.md)。`${DAGQ_QUEUE_DIR}`はqueueのdir、`${DAGQ_RUN_DIR}`は`<queue dir>/update/e2e`）に、`DAGQ_E2E_CMUX=<--cmux>`と、1回ごとの`TMPDIR=<queue dir>/update/e2e/<unix時刻>-<pid>`を足す。流す前に`cmux ping`を打ち、通らなければ（cmuxが無い・動いていない）e2eを始めずに失敗にする。出力は`logs/update-<unix時刻>-<commit 12桁>.e2e.log`（build logの`.build.log`を`.e2e.log`にした名前。他のlogと同じく14日で消える）。上限は`--e2e-timeout`（既定1800秒。supervisorには隠しflagの`--update-e2e-timeout`と`--update-e2e-command`があり、jobにそのまま渡す）で、超えたらprocess groupにSIGTERM、10秒後にSIGKILLを送って落ちた扱いにする。落ちたtestはlogの`test <name> ... FAILED`の行から読む。
     - **後始末**: 通っても落ちても、そのe2eの`TMPDIR`を使い捨ての場所として片付ける: command lineの引数にその`TMPDIR`の中のpathを持つprocess（e2eが起動したsupervisorやstubのagent。時間切れで止めたときに残る）をSIGTERM（3秒でSIGKILL）で止め、fixtureが作った使い捨てのqueueのhash（`<TMPDIR>/<fixture>/data/dagq/<hash>`）をexternal IDに持つcmuxのworkspace groupだけを`cmux workspace-group delete <id> --close-workspaces`で消し（`[dagq-e2e]`の名前ではworkerの手元のe2eのgroupと区別できないので、名前では選ばない）、`TMPDIR`を消す。groupを消せなかったときは`TMPDIR`を残し、次の関門が始まる前に`<queue dir>/update/e2e`の下の残りを同じ手順で片付ける（名前の`<pid>`のprocessが生きているdir、つまり並んで走る`install`の関門のものは片付けない）。e2eが終わった後もそのprocess groupに残ったもの（stubの`sleep`など）はSIGKILLで止める。何をしたかは`cleanup`（`processes`・`groups`・`removed`・`errors`）に残す。
     - 通れば`update_e2e_passed`（`pid`・`secs`・`log`・`cleanup`）を書いて2へ進む。落ちれば（1件でも失敗、上限切れ、始められない）何も置き換えず、非互換のmigrationのビルドも`staged`に置かず`approve_update`を開かない。`update_failed`（`stage: e2e`、`error`に落ちたtestの名前か上限切れか始められなかった理由とlogのpath、`e2e_log`・`failed_tests`・`timed_out`・`secs`・`cleanup`）を書き、`update_failed`のask（`retry` / `skip`）を開く。新しいaskのkindは作らない。askの問いに落ちたtestとe2eのlogのpathが載る。同じcommitでは繰り返さない（`base`が進むので、次にruntimeを変える着地のheadで試す。`retry`の答えは同じheadをもう一度ビルドしてe2eを流す）。[Release update](release-update.md)のjobはリリースのバイナリなので関門を持たない。
  2. **非互換のmigration**: 新しいbinaryの`migrate --check`に非互換のmigrationがあれば、`install`と同じ確認（`--version`と使い捨てのqueueでの起動）をして`<queue dir>/update/staged/dagq`にcopyし（ビルドの隣にclientがあれば、その`--version`が同じことを確かめて`staged/dagq-broker-client`にもcopyする。無ければ前に置いた`staged`のclientを消す。人が打つ`install --from <queue dir>/update/staged/dagq`が隣のclientを一緒に置く）、`approve_update`のask（下記）を開いて`update_awaiting_approval`（`version`・`migrations`・`binary`・`command`）で終わる。何も置き換えない。
  3. **入れ替え**: それ以外は`install::install`（`Source::Binary`、drainはしない）を呼ぶ: 確認、互換のmigration、renameでの差し替え（`.previous`を残す）、このqueueのliveなsupervisorへの引き継ぎの要求と、同じpidとtokenで戻るまでの待ち（tokenの登録が消えても、同じpidが引き継ぎを頼んだ後に新しいbuild識別子で登録し直していれば、その新しいtokenで戻ったとする（`lifecycle::successor`。候補は引き継ぎを頼んだ時刻以降に`started_at`を持つ登録に限り、複数なら`started_at`の最も新しいもの。pidが再利用されて同じpidとbuild識別子の古い行が残っていても、それを後継とみなさない。task 633）。`--handoff-timeout`、既定1800秒。execしたプロセスが死ねばheartbeatが止まった時点で失敗。上限の直後に新しいbinaryで登録し直したsupervisorは取り消しが要求を見つけないので、`lifecycle::HANDOFF_GRACE`の猶予のあいだ見直し、新しいbuild識別子で戻れば引き継いだとして4で見張る。task 715、[`up` / `down`](up-down.md)の引き継ぎ）。引き継ぎは最初の失敗で止まらず全員の結果を待ち、全員が失敗すれば`install`がfileを戻して`install::HandoffFailed`のerror（supervisorごとの結果と戻したかどうか）を返すので、jobは引き継がせたsupervisorのそれぞれを5で戻す（stageは`install`、`kept: false`。task 716）。一部だけが失敗すれば`install`はfileを残して`install::KeptBinary`のerrorを返すので（[ADR-t632-1](../../adr/2026-09-27-t632-1-handoff-restores-only-when-every-supervisor-failed.md)）、jobはその結果から、引き継いだsupervisorを4で見張り、引き継がなかったsupervisorをその理由で失敗にして4の一部の失敗と同じく扱う（stageは`handoff`）。
  4. **見張り**（決定13、task 497）: 引き継ぎの後、`install`が引き継がせたsupervisor（結果の`supervisors`のtokenとpid。空ならjobを起動したsupervisor）のすべてについて、同じtokenの登録が新しいbuild識別子のまま、取り戻したときより後のheartbeatを`--watch-timeout`（既定60秒）の内に書くのを待つ。`heartbeat_at`はunix秒で、supervisorは`HEARTBEAT_INTERVAL`（2秒）ごとに書くので、取り戻してから最大で約2秒と次の秒まで待つ。testはhiddenの`supervise --heartbeat-interval-ms`でheartbeatの間隔を短くし（見張りは次の秒で進む）、in-processのtestは次のheartbeatを1秒先の時計で書いて、秒をまたぐsleepを置かない（productionの間隔と判定は変えない。task 1048）。tokenの登録が消えても、同じpidが`install`を呼ぶ前の時刻以降に新しいbuild識別子で登録し直していれば（照合は3と同じ`lifecycle::successor`）、その登録を追い（heartbeatの比べる元はその登録で取り直す）、進めば成功とする。PIDが死んだ、登録が消えて同じpidの登録も無い、build識別子が違う、heartbeatが進まない、のどれかでそのsupervisorを失敗にし、他のsupervisorは最後まで見張る。fileは全員で1つなので、全員が失敗したときだけ、`.previous`が置き換えた前のbuild識別子と同じなら`restore`で戻す（違えば戻さず、その旨をaskに書く）。clientも一緒に戻す: `dagq-broker-client.previous`が同じ前のbuild識別子ならそれを戻し、そうでなければ新しいclientを消す（別のbuildのclientを前のdagqの隣に残さない。結果は`restored`の`client`）。一部だけが失敗したときは、新しいbinaryで動いているsupervisorがあるので戻さず（`kept: true`）、失敗したsupervisorだけを5で戻し（止まったものは置いたままの新しいbinaryで起動し直し、execに失敗して前のbinaryのまま動くものはそのまま）、`update_failed`のaskで人に判断を渡す（[ADR-t632-1](../../adr/2026-09-27-t632-1-handoff-restores-only-when-every-supervisor-failed.md)。askは前のbinaryのまま動くsupervisorを`down --force`と`up`で揃えるか、`install --rollback`で全員を戻すかを案内する）。戻したら、supervisorを戻した（5）後に`update_restored`（`version`・`restored_version`）を書く（書けなくても続ける）。`update_restored`は`update_started` / `update_built` / `update_e2e_passed`と同じくjobの途中の段（`JOB_STEPS`）で、jobが死んで最新の段のまま残れば2のinterruptedになる。
  5. **supervisorを戻す**（`bring_back`）: 3の引き継ぎより前の失敗（差し替えの失敗など、supervisorごとの結果が無いもの）の後はjobを起動したsupervisorだけを、3の全員の引き継ぎの失敗（`HandoffFailed`）と4の失敗の後は失敗したsupervisorのそれぞれを（入れ替え前の登録は結果のtoken、無ければpidで引く。全員の引き継ぎの失敗で、jobを起動したsupervisorが引き継がせた中に居なければ（`install`が見たときliveでなかった）、それも戻して`supervisor`に載せる）、見張りが追った今の登録（同じpidが登録し直した新しいtokenの登録なら、modeとworkspaceは入れ替え前の登録のもの）で戻す。その登録が前のbuild識別子のままheartbeatしていれば（execが失敗して前のbinaryが続けた）何もしない。PIDが生きていてheartbeatしていなければSIGTERM（10秒で止まらなければSIGKILL）で止め、止めたか死んでいた登録を起動し直す: launchd modeは`KeepAlive`が戻したbinaryで起動し直すので任せ、in-cmux modeは記録したworkspaceを閉じてから戻したbinaryの`up --in-cmux [--auto-update] --parallel <登録のparallel> --cmux … --claude … [--plugin-dir …]`を打つ（`--auto-update`はその登録が`auto_update`を持つときだけ付ける。リリースのjobが戻すsupervisorは持たない。`compose::restarter`）。手で起動した（modeの無い）supervisorは起動し直さない。jobはcmuxの端末の子孫なので、supervisorが生きている間に起動したjobの`up --in-cmux`はcmuxに受け入れられる。supervisorが死んだ後は親がlaunchdに付け替わるので、socket passwordの無いcmuxは`up`を拒みうる。そのときは`update_failed`のaskと`supervisor_stopped`で人に知らせ、人が`up --in-cmux`を打つ。
  6. 成功すれば`update_installed`（`version`・`previous_version`・`migrated`・`supervisors`）。失敗は`update_failed`（`stage`は`build` / `e2e` / `check` / `install` / `handoff` / `watch`、`error`、`restored`、`install`の失敗では、引き継ぎより前の失敗なら`supervisor`、全員の引き継ぎの失敗なら`restored`・`kept: false`とsupervisorごとの`supervisors`（`token`・`pid`・`error`・戻した結果の`supervisor`）、`handoff`（引き継ぎの一部の失敗）と`watch`の失敗では`kept`とsupervisorごとの`supervisors`（`token`・`pid`・今の登録の`now`・`error`・戻した結果の`supervisor`）、`ask_id`）で、`update_failed`のaskを開く。
- **経過の記録**（[ADR-0073](../../adr/0073-kind-additions-are-compatible.md)の決定17・19〜22、task 496）: 上の各段は、task・goal・runのどれにも属さないqueueの`run_events`（`update_started` / `update_built` / `update_e2e_passed` / `update_installed` / `update_failed` / `update_restored` / `update_awaiting_approval` / `update_answered` / `update_retry`、[Release update](release-update.md)の`update_dropped`。`domain::UPDATE_EVENT_KINDS`で、`EventKind::is_queue`が真）で、payloadの`commit`が対象のmainのcommit（askの答えの2つには無い）。`application::update::record`が`record_queue_event`で書き、supervisorと`status`は`update_events`（新しい順）で読む。kindのCHECKを外した0039の後なので、kindを足してもmigrationは要らない。task 310が作った表`binary_updates`（schema v33）は残すが、書きも読みもしない。
  - `events --kind update_installed`などで経過を読める（compactの形は`commit`・`version`・`stage`を持つ）。`update_installed`はinbox宛てのattention（`next: report the update`。人に入れ替えを知らせるだけ）で、`watch`が起きる。`update_failed`と`update_awaiting_approval`は下のaskの`ask_opened`がattentionになるので、それ自体はattentionにしない。
  - `timeline RUN`はrunの最初のeventから最後のevent（進行中なら今）までの`update_*`を、runのeventの間にidの順で並べる（引き継ぎがsupervisorの間を説明する）。gapはrun自身のeventだけから求める。

- **inboxに知らせる**: 失敗と非互換のビルドは、task・runの無い専用のkindのask（`update_failed` / `approve_update`。`AskKind::UpdateFailed` / `ApproveUpdate`で、`check_ask_kind`がtaskとrunを持たないことを検査する）で知らせる（askは`ask_opened`を書くので`watch --role inbox`が起きる）。同じkindの開いたaskは古いビルドのものなので、新しいaskを開く前に`superseded`と答えて閉じる（`open_update_ask`）。`reason_category`は`scope`、`asked_by`は`supervisor`で、`subject`は持たない。task 310の、`blocked`のaskの`subject`で区別する形は使わない（その形で開いたaskが残っていれば、他の`blocked`のaskと同じく人が読んで閉じる）。

## dagqのソースのrepositoryだけ

リリースのバイナリ（`X.Y.Z`）で動く外部のprojectの更新は、source buildではなくcrates.ioのリリースの検知とaskで行う（[Release update](release-update.md)、ADR-t618-1）。jobの確認から見張りまでは同じ`put_in_place`（`src/application/update.rs`）を通る。

`up --auto-update`のsource buildは、queueのrepositoryがdagqのソースのときだけ動く（[ADR-t614-1](../../adr/2026-09-27-t614-1-dagq-source-only-features-by-one-check.md)）。ソースでないrepositoryでは`up --auto-update`がerrorで止まり、自動更新の設定を持つsupervisorもbuildに進まない。判定と対象の一覧は[Source repository](source-repository.md)にある。`up`はpreflightで`--auto-update`とソースでないrepositoryの組み合わせを`--auto-update builds dagq from the repository's sources, and <checkout> is not dagq's source (...); leave --auto-update off and update dagq with `cargo install dagq`, or with `dagq install --from <binary or checkout>`; the supervisor was not started`で止める（`lifecycle::auto_update_refused`）。登録の`auto_update`が真のsupervisorは、見る回ごとに判定し、ソースでなければ`update_failed`のaskの答えの適用もjobの起動もせずに戻り、ソースでなくなった最初の回だけ警告をlogに出す。続けてそのときのmainのheadを読み、`automatic update: main's <head> builds nothing: the repository is not dagq's source`をheadごとに1回出す（task 1048）。
