# Draft planners (supervisor)

[ADR-0044](../../adr/0044-findings-proposals-from-findings-and-quiet-observer.md)の決定13・16（task 282）と[ADR-t807-1](../../adr/2026-09-28-t807-1-bundle-drafts-of-one-piece-of-work-for-one-runtime-planner.md)（task 807）。runtimeやjobが作ったdraftを、同じきっかけで作られ同時に待っているものの束にし、束ごとにsupervisorがruntimeのplannerを1つ立て、plannerがdraftごとに採用・不採用・askのどれかを選ぶ（2026-09-27の人の決定で、goal 29のconstraintの「follow_upのdraft 1件ごとにplannerを1つ」を置き換えた）。人の決定（2026-09-25）で、対象はfollow_upのdraftに限らず、runtimeやjobが作ったdraft全般（follow_up、goalの判断jobのgap）にした。goal 22のfollow-up triage job（[ADR-0037](../../adr/0037-follow-up-triage-job-decides-follow-up-drafts.md)、task 205）はこれに置き換え、jobのverdictと適用、`follow_up`のaskのanswerの適用、`task_leases`を消した（`follow_up_depth`と、人の判断を経ずにsubmitしない上限は残す）。再検討の時刻（[ADR-t1540-1](../../adr/2026-10-05-t1540-1-a-kept-draft-returns-to-runtime-planners-at-its-revisit-time.md)、task 1540）は下の[再検討の時刻](#再検討の時刻)。use caseは`src/application/supervise/draft_planner.rs`、storeは`src/infrastructure/draft_planners.rs`（port `DraftPlannerStore`）、規則と型は`src/domain/follow_up.rs`、promptは`application::prompt::draft_planner_prompt`。run slotは使わず、[Plan review (supervisor)](plan-review.md#plan-review-supervisor)の`tend_planners`の中で、reviseの配送の後に進める（drain中は立てない）。

1. **出どころ**（schema v28、`migrations/0028_draft_planners.sql`）: runtimeやjobがdraftを作るときに`draft_origins`の行（`task_id`、`origin` = `follow_up` / `goal_gap`、`material`（JSON object）、`created_at`）を`record_draft_origin`で書く。`integrate`の`register_follow_ups`はfollow_upのdraftに`{"source_task_id", "source_run_id", "source_goal_id", "source_goal_state", "source_goal_provenance", "index", "category", "membership_proposal"}`を書く（`category`はworkerが付けた種類、無ければ`unlabeled`。ADR-t947-3、[follow_upsの分類コード](receipt-and-session-exit.md#follow_upsの分類コード)。`membership_proposal`はworkerの所属の提案を書いたまま、無ければnull。[follow_upsの所属の提案](receipt-and-session-exit.md#follow_upsの所属の提案)）。task 1508より前に登録したdraftの材料には`membership_proposal`が無く、promptは`(none)`として扱う。task 954より前に登録したdraftの材料には`category`が無く、promptと集計は`unlabeled`として扱う。`goal_gap`は、[goal review](goal-review.md)のjobの`gaps`のverdict（と人の`approve_goal`の`gaps`のanswer）からruntimeが登録するdraftに、`{"goal_id", "goal_review_id", "criterion", "summary"}`を書く（task 375）。人が`add`で作ったdraftとobserverのdraft goalのtaskには行が無く、plannerは立たない（再検討の時刻が来たときだけ、出どころ`revisit`として立つ。[再検討の時刻](#再検討の時刻)）。migrationは導入前の`follow_up_registered`（`task_id`のあるもの）から行を埋めるので、導入前のfollow_upのdraftも対象になる。出どころ`reopened`（task 418）は、plan reviewがreadyから戻して自分のproposalに入れたtask（ADR-0044の決定14、`task_reopened`）が、そのproposalのwithdraw（`dagq proposal withdraw`）で`draft`に戻ったときにwithdrawが表`draft_reopens`（`migrations/0041_draft_reopens.sql`）に書く（材料は`reason`（verdictのreopenのreason）、`proposal_id`、`reviewed_proposal_id`）。人が作ったtaskで`draft_origins`の行が無くても、これで誰かが拾う。行が効くのはtaskがまだそのproposalのものであるあいだだけで、後で別のproposalに入ったtaskのwithdrawには古い行が効かない。同じproposalの他のmember（plannerがsubmitしたdraft）には書かず、今までどおり`draft`に戻るだけ。readyに直接戻す経路は作らない（reopenはplan reviewが食い違いを見つけた結果なので、gateを通さずにreadyに戻すと食い違ったままclaimされうる）。withdrawとreopenの繰り返しは下の4の上限（`draft_planner_exhausted`）で止まる。
2. **対象**（`planner_drafts`、ID昇順）: statusが`draft`でproposalに入っておらず（withdrawで`canceled`になったproposalは持たない）、`draft_origins`か（有効な）`draft_reopens`の行があるか再検討の時刻が来ていて、閉じていないruntimeのplanner（`planners.draft_task_id`か、taskのwithdrawされたproposalのplanner）が無く、closeされていない`planner_question`のaskが無く、answerが`keep_draft`のask（旧`follow_up`を含む）が無いか再検討の時刻が来ていて、まだ来ない再検討の時刻を持たず、`open`の計画の依頼の参照（`task:N`）に無く、`draft_planner_exhausted`が無いか人・inboxが付けた再検討の時刻が来ているdraft（時刻の条件は[再検討の時刻](#再検討の時刻)）。ただし閉じていないplannerの束と同じ束の鍵を持つdraftは、そのplannerが終わるまで待つ（同じきっかけのdraftが作業中に増えたとき。integrateは1つのreceiptの未登録follow_upsを1つの`BEGIN IMMEDIATE` transactionで登録するので、passはそのreceiptのdraftを全件見るか1件も見ない。束のplannerが`planner_unresponsive`で開いたまま人を待つあいだも、同じ鍵のdraftは待つ）。
   - **束**（ADR-t807-1）: 対象を束の鍵（`BundleKey::of`）で分ける。follow_upは材料の`source_run_id`（同じintegrateが登録したもの）、goal_gapは`goal_review_id`（同じgoal reviewが作ったもの）、reopenedは`reviewed_proposal_id`（同じwithdrawが戻したもの、reopenしたplan reviewのproposal）。人の言う「作成タイミングが同じ」をこう読んだ（plannerの解釈。根拠は2026-09-27の人の依頼の言葉）。作成時刻の近さでは束ねず、材料に鍵の無いdraft（`source_run_id`がnullなど）は1件で1つの束（鍵の種類`task_id`）。束の順は束の最も古いdraftのID順。
3. **立てる**（`open_draft_planners`）: runtimeが立てたplannerで生きているものが上限`runtime_planners`（`supervise --runtime-planners`の明示 > main checkoutの`dagq.toml`の`[supervisor] runtime_planners` > 既定1。各passで読み直す。[Run environment](run-environment.md)の`[supervisor]`、task 941。revise・finding・計画の依頼（[inboxからの計画の依頼](plan-planners.md#inboxからの計画の依頼)。依頼のplannerはdraftより先に立てる）のplannerと共有、run slotとは別、人が開いたplannerは数えない）未満のあいだ、束ごとに`open_draft_planner`で立てる（束1つで1と数える）。storeは`BEGIN IMMEDIATE`で束の全てのdraftの対象の条件を再検査し、条件を外れたdraftは束から落として残りで、`planners`の行（`origin: runtime`、`draft_task_id`は束の最も古いdraft）、`draft_bundles`と`draft_bundle_members`の行、draftごとの`draft_planner_opened`（`planner_id`、`attempt`、`origin`、`ask_id`、`goal_id`、`members`、`bundle_key`と出どころの欄。[Persistence](../persistence.md#draft-plannersdraft_plannersrs)）を書くので、2つのsupervisorが同じdraftに立てない。plannerはworkspaceを持たず、非対話のwrapperがbackgroundで起動する（[runtimeのplannerの経路](plan-planners.md#runtimeのplannerの経路)）。初期prompt（`prompt.txt`、最初のturnのprompt）は`draft_planner_prompt`（verify・paths・evidenceを決める順の`prompt::repository_rules`を含む。[Prompt](prompt.md#repositoryの規則を読む順)）: draftごとのtitle・description・context（束が2件以上なら`## Draft <id> (planner <attempt> for it)`の見出しごと）、出どころ（1回だけ。follow_upなら元のtaskのtitle・description・acceptance・verification・paths・evidenceと、元のrunの`integration_receipt`のreceiptの`summary`と`follow_ups`、束のdraftがreceiptの何番目か。goal_gapならdraftごとのmaterialのJSON、reopenedならdraftごとのreopenしたplan reviewのproposal、withdrawしたproposalとreopenのreason）、goal（束のdraftのgoalごとに1回。title・description・acceptance・constraints・doc、閉じているか）と同じgoalの束の外のtask、束が2件以上なら束の中の重複（`dagq cancel ID --duplicate-of <残す方>`）・依存（`dagq dependency add`）・採用するものを1つのproposalで出すこと（`dagq submit ID ID ...`）を先に考える手順、draftごとの3択の手順（採用: `dagq edit`でacceptance・verify・paths・evidence・contextの冒頭の出自を補い（reopenedは、taskの意図を保ってreasonの指す所を直し、contextにreopenの一行を足す）、依存を足し、`dagq lint`してから`dagq submit`。不採用: `dagq cancel`と`dagq note --task`で理由。他のtaskの重複か、completedのtaskで実装済みなら`dagq cancel ID --duplicate-of X`で重複先を記録する（[ADR-0063](../../adr/0063-full-text-search-related-with-mentions-and-search-strength-and-duplicate-of.md)の決定5。ADR-0041で廃止したfollow-upのtriageに代わり、draftを重複で閉じるのはこのplanner）。自分で決めきれない（[推奨が出せればplannerが決める](#推奨が出せればplannerが決める未実装)の3つの条件）: `dagq ask --task ID --kind planner_question --because scope --recommend ... --confidence ... --option adopt --option cancel --option keep_draft`して止まり、answerに従う。決めた理由は採用ならcontext、不採用と`keep_draft`ならnoteに書く）、`dagq search`で重複と実装済みを探すこと、記録を読むCLI（`prompt::RECORD_READING`、ADR-0044の決定22、task 420: `dagq events --full --task ID`と絞り込み（`--run` / `--goal` / `--kind` / `--since` / `--until`。`--kind`が無ければattentionだけなので、全種類は`--all`を足す）と`dagq timeline RUN`）、AGENTS.mdの規則を読むこと、自動でsubmitできない上限。promptは全体`DRAFT_PLANNER_PROMPT_LIMIT`と節ごとの上限の中に収める（task 1571。値と理由は[Prompt](prompt.md#goal-reviewrunのreview復旧jobruntimeのplannerの上限)）: draftの節は束の古い順に選び（descriptionは必須で、超えたら切って`over_limit`に書く）、入らないdraftは`## Drafts left out`に件数と`dagq show ID --full`を書く。出どころの節（元のtask・receiptの`summary`と`follow_ups`を含む）は丸ごとと欄ごとに切り、receiptは`dagq events --full --run <run> --kind integration_receipt`で読むと書く。goalの節は欄とtaskの行（新しい順）を切り、入らないgoalは`## Goals left out`に`dagq goal show ID --full`を書く。promptのbyte数は`planner_prompt_written`（`prompt: draft`。[Session prompts](session-prompts.md)）に記録する。
4. **3回まで**: plannerがdraftを決めずに終わった（sessionが終わった、idleで終了の依頼を受けて終わった）draftは次のpassで再び対象になり、残りのdraft（とその間に増えた同じきっかけのdraft）で束を作り直して次のplannerが立つ。回数はdraftごとに数える（そのdraftを含む束のplannerの数、`draft_bundle_members.attempt`）。再検討の時刻で立つplannerも1回と数える。`draft_planner_opened`が`MAX_DRAFT_PLANNERS`（3）件あるdraftは（人のanswerを運ぶときと、人・inboxが付けた再検討の時刻が来たとき以外は）束から外して`draft_planner_exhausted`（`planners`、`ask_id`、`reason`）を記録し、束の残りで立てる。attentionは`request a plan for the draft`（`AttentionNext::DecideDraft`。`status`でもdraftのまま残っているあいだ出る。`watch`も同じ文面）で、人の言葉を受けたinboxがそのdraftを参照にした計画の依頼（`dagq request add --ref task:N`、[ADR-t1394-1](../../adr/2026-10-03-t1394-1-abolish-person-planners-and-route-planning-through-inbox-requests.md)の決定8）を記録し、依頼のruntimeのplanner（[inboxからの計画の依頼](plan-planners.md#inboxからの計画の依頼)）が決めるか、人が`DAGQ_ROLE`の無い自分のterminalで決める。
5. **planner_question**（ADR-0044の決定13）: askのkindに`planner_question`を足した（CLIの`ask --kind`で作れる）。束の中でも`--task ID`でdraftごとに開く。`answer`は`planner_answer_route`で行き先を決め、`Person`以外なら`ask_answered`に`runtime_delivers: true`を書いてattentionにしない（`status`は`delivering the answer of ask N (runtime)`）。行き先は、(a) そのtaskで働く閉じていないruntimeのplanner（draftを持つ束のplannerか、taskのproposalのplanner）: supervisorがplannerの`idle`（wrapperがturnの終わりに書くidle markerがaskより新しく、`turns/`に待っている依頼が無い）を待ち、送る前に`claim_planner_answer`で配送をclaimしてから（`BEGIN IMMEDIATE`で、askが未closeで行き先が今もそのplannerであり、同じaskの`planner_answer_claimed`が`PLANNER_ANSWER_CLAIM_SECS`（120秒）以内に無いことを確かめ、`planner_answer_claimed`（`ask_id`、`planner_id`、`workspace_id`（plannerのbackgroundのhandle）、`claimed_at`）をtaskに書く。claimできなければ送らない）、`answer to ask <id>: <answer>`をplannerの次のturnの依頼（`turns/request-NNNNNN.json`、`turn_requested`の`what`が`answer of ask <id>`）として書き、`ask_delivered`でaskを閉じる。plannerには何も打ち込まない。これで引き継ぎの間に同じqueueを扱う2つのsupervisorが重なっても、answerは1回しか送られない。送れなかったときは今までどおり`ask_delivery_failed`（taskに記録）でinboxに任せる（claimは残るので送り直さない）。claimの後、送る前にsupervisorが落ちたaskは、claimが120秒より古くなった後の周回で別のsupervisorがclaimし直して送る（依頼を書くのは数秒で終わるので、生きているsupervisorのclaimを奪わない）。(b) plannerが居ないdraft: 上限の中で新しいplannerを立て（そのdraftを先頭に、同じ束の鍵で対象のdraftを束に加える。同じ鍵の束のplannerが開いていれば、それが終わるまで待つ）、初期promptに元の質問とanswerを載せ（先頭のdraftの`draft_planner_opened`の`ask_id`）、askを閉じる。依頼のplannerが作り由来もproposalも無いdraftは依頼のplannerに届け、居なければ依頼の状態に依らず答えを載せたplannerを依頼に立てる（ADR-t2015-1）。(c) `keep_draft`のanswerでplannerが居ない、またはdraftが先に進んだ（submit、cancel）: supervisorが`planner_answer_closed`（`ask_id`、`reason`）でaskを閉じる。`keep_draft`で残したdraftにはruntimeのplannerを立て直さず、人の言葉を受けたinboxがそのdraftを参照（`--ref task:N`）にした計画の依頼を記録するまでdraftのまま待つ（`PLANNER_QUESTION_OPTIONS`のdoc comment、draftのplannerのpromptの3の`keep_draft`の説明）。ただし再検討の時刻を付けたdraftは、その時刻にruntimeのplannerの対象に戻る（依頼の経路と並ぶ。[再検討の時刻](#再検討の時刻)）。(d) それ以外（依頼のplanner以外が作った出どころの無いtask、使い切ったdraft）: inboxが届ける（`send the answer of ask N to the worker and close it`）。closeされていない`planner_question`（束のどれかのdraftについて）があるplannerと、送ったanswer（`ask_delivered`）をまだturnで読み終えていないplannerには終了の依頼を送らない（送らずに閉じたaskは引き止めない。`question_wait`）。読み終えたかはturnの記録で決め、そのanswerの依頼を取ったturn（`turn_started`の依頼の番号）が終わり、Claudeのログイン切れ・利用上限・起動の失敗で終わっていなければ読み終えたとする（`headless_answer_taken`、`src/domain/turn.rs`の`request_read`。壁で失敗したturnは[下](#予定-人のplannerの廃止と非対話の経路)）。idle markerの時刻やaskの`closed_at`（送った後に`ask_delivered`が書く）とは比べない: answerを読んで仕事を終え、askのcloseより前にidleになったplannerを答えの処理中とみなして終わらせず、`--runtime-planners`の枠をふさいだため。plannerが自分で作ったaskはplannerがaskの後に止まってから、他の人が作ったaskはplannerがidleなら送る。
6. **採用の記録と上限**（`submit`の中、[persistence](../persistence.md)）: submitが出どころのあるdraftを初めて出すとき`follow_up_adopted`（goal_gapとreopenedは`draft_adopted`。`task_id`、`origin`、`source_task_id`、`source_run_id`、`by: "planner" | "person"`、`ask_id`、`depth`、`planner_id`（draftを持つ生きている束のplanner）、`bundle_key`と出どころの欄）を書く。上限はdraftごとで、束の中の1件が人の`adopt`を要しても、他のdraftは出せる。runtimeのplanner（`DAGQ_PLANNER_ORIGIN=runtime`）は、登録時の元goalが無い・閉じていた・不明か、現在のgoalが閉じているか無い、または`follow_up_depth`が`FOLLOW_UP_ASK_DEPTH`（3、[ADR-t808-1](../../adr/2026-09-28-t808-1-runtime-planners-submit-follow-ups-up-to-depth-two.md)）以上のfollow_upのdraft（深さ2までは登録時の元goalと現在のgoalがともに開いていれば人を経ずにsubmitできる）を、そのdraftへの`planner_question`（旧`follow_up`）に人が`adopt`と答えていなければsubmitできない（errorで`planner_question`を促す）。人のsubmit（origin `person`: 廃止前に人が`dagq plan`で開いたplannerか、人が`DAGQ_ROLE`の無い自分のterminalで打った`submit`）、人の`adopt`を経たsubmit、`ready --bypass-review`は深さを0に戻す。
7. **終わり**: runtimeのplannerは束のdraftをsubmitしたか、cancelしたか、`keep_draft`で（answerか、まだ来ない再検討の時刻で）残したら（決めずに残したものがあっても）、idleになったところで終了の依頼（`turns/exit`。`planner_exits`に記録）を受け、wrapperがsessionを終える。sessionの終わったplanner（exitした、見失った、backgroundのwrapperが居ない）の行は閉じられ、まだ動いているwrapperは止められる（`runtime_exited` / `runtime_lost` / `runtime_session_gone`）。終了の依頼から`WorkspaceBackend::exit_timeout`を過ぎても終わらなければ、wrapperとその子孫を止めて行を`runtime_exit_timed_out`で閉じる（[Plan review (supervisor)](plan-review.md#plan-review-supervisor)の`end_runtime_planners`）。runtimeのplannerにcmuxのworkspaceは無いので、閉じるworkspaceも無い。idleは、wrapperがturnの終わりに書くidle markerが最後の入力より新しく、`turns/`に待っている依頼が無いことで判じ、画面は読まない（画面からの推定（ADR-t803-1）はどのplannerにも無い）。`planner_question`のanswerを送られたplannerも、それをturnで読み終えれば（5）終了の依頼を受ける。持ち主の居ないreviseが上限で`--planner-timeout`を過ぎて待つときは、人の答えを待っていないidleのplannerが終了の依頼を受けて枠を空ける（`planner_released`。[Plan review (supervisor)](plan-review.md)の9）。runtimeのplannerの時間は`--planner-timeout`でなくturnの`[stall]`の上限で見る: wrapperがturnを`[stall]`の上限で止めたときに、plannerごとに1回`planner_unresponsive`（`subject: "planner"`、`draft_task_id`、`route`・`turn`・`outcome`）がinboxに届き、止めたturnでsessionが終わるので、plannerは`runtime_exited`で閉じられ、決めずに終わったplannerに数える（`tell_of_stopped_planner_turns`）。最後のturnがClaudeのログイン切れ・利用上限・起動の失敗で終わったplannerは、Claudeを待って終了の依頼を受けず、決めずに終わったplannerにも数えない（`provider_wall`）。どちらも[runtimeのplannerの経路](plan-planners.md#runtimeのplannerの経路)の「状態」と「使えないとき」。submitしたproposalはplan reviewを通り、reviseは持ち主（閉じていれば新しいruntimeのplanner）に返る。

## 所属の判断

`judge-follow-up`は採用・priorityとは別に元goalのacceptanceとの関係を記録する。required/out_of_scopeの所属変更は判断と同じtransactionで行い、set-goalによる食い違う変更は拒む。登録時の出どころ・状態と深さは移動しても変わらないので、開いたgoalへの移動で人のadoptを迂回できない。元goalのあるfollow_upのdraftは、今の判断が無い・`undecided`・要再確認ならsubmit（runtimeのplannerも人も）が拒み、人の`ready --bypass-review`もdraft / submittedのものを拒むので、plannerは採用するdraftの判断を先に記録する（人のadoptの上限とは別の検査で、判断を記録してもadoptにはならない）。`lint`は同じ欠けを`follow_up_membership_unjudged`で出し、plan reviewは判断の行を材料に検査する（[Plan review](plan-review.md)）。CLI、必須の欄、訂正とacceptanceの版、旧材料の移行は[所属の判断](../follow-up-membership.md)。

- **prompt**（task 1508、ADR-t1504-1決定1〜3・5・6）: follow_upのdraftの節は`follow_up_proposal_line`で、材料の登録時の元goal（`goal <id> (<source_goal_state>, <source_goal_provenance>)`、`none`、材料に無ければ`unknown`。今のgoalではなくこのgoalのacceptanceに照らすこと）とworkerの`membership_proposal`（無ければ`(none)`）を載せる。「What to do」は3択の前に`follow_up_membership_step`の1段落を置く: 元goalがnoneでないfollow_upのdraftは、採否・priorityと別に、workerの提案を起点に意味を自分で判断する（そのdraftを実施しなくても元goalのacceptanceを満たせるか。満たせなければrequiredで元goal、満たせればout_of_scopeで別goal。別goalは`dagq search`で既存の適切なgoalを先に探し、無いときだけ作り、無関係な大きなgoalに詰めない。）。adopt・drop・askの前に`dagq judge-follow-up ID --classification ... --acceptance-item ... --reason ... --evidence ...`（out_of_scopeは`--destination-goal`、元goalが不明なら`--source-goal`）で判断を記録する。前の判断は`dagq show ID`の`membership_judgements`で読み、まだ成り立てば記録し直さず、required・out_of_scopeの間の変更は`--corrects <id>`で行い、undecidedへは戻さない。dropするdraftは、記録に新しいgoalが要るなら記録を省いてよい（cancelしたfollow-upはgoalの閉鎖を止めない）。決まらなければundecidedを理由つきで記録し、所属の問いを含めて3のaskにし、answerの後にrequiredかout_of_scopeを記録してから従う。別goalへの移動は採用でも優先でもない。follow_upを外すためにacceptanceを弱めず、人に聞く（`--because scope`）。goal_gapとreopenedのdraftにはこの段落も提案の行も出ない（ADR-t1504-2決定10）。testは`application::prompt`の`the_follow_up_draft_planner_records_membership_before_it_decides`。

- **登録と記録**: `draft_origins.origin = recurring`とし、`material`に`key`、`previous_task_id`、`previous_registered_at`（初回はいずれもnull）、登録時の設定のsnapshotを持たせる。今の登録時刻は`draft_origins.created_at`に残す。queueの同じkeyの登録履歴から前回を引き、未完了のdraft/taskが無いことと期限を`BEGIN IMMEDIATE`で再検査して、draftと出どころを同じtransactionで書く。取り戻しも新規の登録も同じ経路を使う。
- **planner**: recurringは各登録を1件の束（task IDの鍵）として扱い、別keyや別周期を時刻の近さで束ねない。初期promptにkey・前回の登録・設定のsnapshotとgoalの材料を載せる。同時数`runtime_planners`、同じdraftへの二重起動の防止、3回の上限と使い切った後の経路は既存のものを使う。上限や`keep_draft`で残ったdraftも非終端なので、次の周期を登録して迂回しない。
- **採否**: 必要性を確認し、採用はedit・lint・submit、不採用はcancelとnote。採用の根拠はcontextに残し、通常のplan reviewを通る。Rustでは公式stableの版と確認日・今の固定版を記録し、更新が無ければcancelのnoteに根拠を残す。goalが未指定なら採用するplannerが適切な開いたgoalを探すか作り、閉じたgoalへの追加や再開は既存のgoalの規則に従う。
- **深さと柵**: recurringのdraftは`follow_up_depth = 0`で、採用の記録は`draft_adopted`とする。recurring自体にはfollow_upの元goal・深さによるadoptの柵を当てない。派生するfollow_upには通常どおり深さ+1と登録時の元goalの記録・所属の判断・自動採用の柵を適用する。
- **人への問い**: 上の「推奨が出せればplannerが決める」とADR-0047決定41を適用する。判断できる採否は自分で決め、材料で決めきれないscope/discard、低い確信度、既存の柵が求める判断だけを理由の分類・推奨・確信度つきの`planner_question`にする。不要な定期の提案をcancelすることだけで人に聞かない。
