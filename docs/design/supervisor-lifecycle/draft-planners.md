# Draft planners (supervisor)

[ADR-0044](../../adr/0044-findings-proposals-from-findings-and-quiet-observer.md)の決定13・16（task 282）と[ADR-t807-1](../../adr/2026-09-28-t807-1-bundle-drafts-of-one-piece-of-work-for-one-runtime-planner.md)（task 807）。runtimeやjobが作ったdraftを、同じきっかけで作られ同時に待っているものの束にし、束ごとにsupervisorがruntimeのplannerを1つ立て、plannerがdraftごとに採用・不採用・askのどれかを選ぶ（2026-09-27の人の決定で、goal 29のconstraintの「follow_upのdraft 1件ごとにplannerを1つ」を置き換えた）。人の決定（2026-09-25）で、対象はfollow_upのdraftに限らず、runtimeやjobが作ったdraft全般（follow_up、goalの判断jobのgap）にした。goal 22のfollow-up triage job（[ADR-0037](../../adr/0037-follow-up-triage-job-decides-follow-up-drafts.md)、task 205）はこれに置き換え、jobのverdictと適用、`follow_up`のaskのanswerの適用、`task_leases`を消した（`follow_up_depth`と、人の判断を経ずにsubmitしない上限は残す）。use caseは`src/application/supervise/draft_planner.rs`、storeは`src/infrastructure/draft_planners.rs`（port `DraftPlannerStore`）、規則と型は`src/domain/follow_up.rs`、promptは`application::prompt::draft_planner_prompt`。run slotは使わず、[Plan review (supervisor)](plan-review.md#plan-review-supervisor)の`tend_planners`の中で、reviseの配送の後に進める（drain中は立てない）。

1. **出どころ**（schema v28、`migrations/0028_draft_planners.sql`）: runtimeやjobがdraftを作るときに`draft_origins`の行（`task_id`、`origin` = `follow_up` / `goal_gap`、`material`（JSON object）、`created_at`）を`record_draft_origin`で書く。`integrate`の`register_follow_ups`はfollow_upのdraftに`{"source_task_id", "source_run_id", "index", "category"}`を書く（`category`はworkerが付けた種類、無ければ`unlabeled`。ADR-t947-3、[follow_upsの分類コード](receipt-and-session-exit.md#follow_upsの分類コード)）。task 954より前に登録したdraftの材料には`category`が無く、promptと集計は`unlabeled`として扱う。`goal_gap`は、[goal review](goal-review.md)のjobの`gaps`のverdict（と人の`approve_goal`の`gaps`のanswer）からruntimeが登録するdraftに、`{"goal_id", "goal_review_id", "criterion", "summary"}`を書く（task 375）。人が`add`で作ったdraftとobserverのdraft goalのtaskには行が無く、plannerは立たない。migrationは導入前の`follow_up_registered`（`task_id`のあるもの）から行を埋めるので、導入前のfollow_upのdraftも対象になる。出どころ`reopened`（task 418）は、plan reviewがreadyから戻して自分のproposalに入れたtask（ADR-0044の決定14、`task_reopened`）が、そのproposalのwithdraw（`dagq proposal withdraw`）で`draft`に戻ったときにwithdrawが表`draft_reopens`（`migrations/0041_draft_reopens.sql`）に書く（材料は`reason`（verdictのreopenのreason）、`proposal_id`、`reviewed_proposal_id`）。人が作ったtaskで`draft_origins`の行が無くても、これで誰かが拾う。行が効くのはtaskがまだそのproposalのものであるあいだだけで、後で別のproposalに入ったtaskのwithdrawには古い行が効かない。同じproposalの他のmember（plannerがsubmitしたdraft）には書かず、今までどおり`draft`に戻るだけ。readyに直接戻す経路は作らない（reopenはplan reviewが食い違いを見つけた結果なので、gateを通さずにreadyに戻すと食い違ったままclaimされうる）。withdrawとreopenの繰り返しは下の4の上限（`draft_planner_exhausted`）で止まる。
2. **対象**（`planner_drafts`、ID昇順）: statusが`draft`でproposalに入っておらず（withdrawで`canceled`になったproposalは持たない）、`draft_origins`か（有効な）`draft_reopens`の行があり、閉じていないruntimeのplanner（`planners.draft_task_id`か、taskのwithdrawされたproposalのplanner）が無く、closeされていない`planner_question`のaskが無く、answerが`keep_draft`のask（旧`follow_up`を含む）が無く、`draft_planner_exhausted`の無いdraft。ただし閉じていないplannerの束と同じ束の鍵を持つdraftは、そのplannerが終わるまで待つ（同じきっかけのdraftが作業中に増えたとき。integrateは1つのreceiptの未登録follow_upsを1つの`BEGIN IMMEDIATE` transactionで登録するので、passはそのreceiptのdraftを全件見るか1件も見ない。束のplannerが`planner_unresponsive`で開いたまま人を待つあいだも、同じ鍵のdraftは待つ）。
   - **束**（ADR-t807-1）: 対象を束の鍵（`BundleKey::of`）で分ける。follow_upは材料の`source_run_id`（同じintegrateが登録したもの）、goal_gapは`goal_review_id`（同じgoal reviewが作ったもの）、reopenedは`reviewed_proposal_id`（同じwithdrawが戻したもの、reopenしたplan reviewのproposal）。人の言う「作成タイミングが同じ」をこう読んだ（plannerの解釈。根拠は2026-09-27の人の依頼の言葉）。作成時刻の近さでは束ねず、材料に鍵の無いdraft（`source_run_id`がnullなど）は1件で1つの束（鍵の種類`task_id`）。束の順は束の最も古いdraftのID順。
3. **立てる**（`open_draft_planners`）: runtimeが立てたplannerで生きているものが上限`runtime_planners`（`supervise --runtime-planners`の明示 > main checkoutの`dagq.toml`の`[supervisor] runtime_planners` > 既定1。各passで読み直す。[Run environment](run-environment.md)の`[supervisor]`、task 941。reviseとfindingのplannerと共有、run slotとは別、人が開いたplannerは数えない）未満のあいだ、束ごとに`open_draft_planner`で立てる（束1つで1と数える）。storeは`BEGIN IMMEDIATE`で束の全てのdraftの対象の条件を再検査し、条件を外れたdraftは束から落として残りで、`planners`の行（`origin: runtime`、`draft_task_id`は束の最も古いdraft）、`draft_bundles`と`draft_bundle_members`の行、draftごとの`draft_planner_opened`（`planner_id`、`attempt`、`origin`、`ask_id`、`goal_id`、`members`、`bundle_key`と出どころの欄。[Persistence](../persistence.md#draft-plannersdraft_plannersrs)）を書くので、2つのsupervisorが同じdraftに立てない。workspaceは`[<repo>]planner#<id> - draft task <束の最も古いdraftのID>`で、初期prompt（`prompt.txt`）は`draft_planner_prompt`（verify・paths・evidenceを決める順の`prompt::repository_rules`を含む。[Prompt](prompt.md#repositoryの規則を読む順)）: draftごとのtitle・description・context（束が2件以上なら`## Draft <id> (planner <attempt> for it)`の見出しごと）、出どころ（1回だけ。follow_upなら元のtaskのtitle・description・acceptance・verification・paths・evidenceと、元のrunの`integration_receipt`のreceiptの`summary`と`follow_ups`、束のdraftがreceiptの何番目か。goal_gapならdraftごとのmaterialのJSON、reopenedならdraftごとのreopenしたplan reviewのproposal、withdrawしたproposalとreopenのreason）、goal（束のdraftのgoalごとに1回。title・description・acceptance・constraints・doc、閉じているか）と同じgoalの束の外のtask、束が2件以上なら束の中の重複（`dagq cancel ID --duplicate-of <残す方>`）・依存（`dagq dependency add`）・採用するものを1つのproposalで出すこと（`dagq submit ID ID ...`）を先に考える手順、draftごとの3択の手順（採用: `dagq edit`でacceptance・verify・paths・evidence・contextの冒頭の出自を補い（reopenedは、taskの意図を保ってreasonの指す所を直し、contextにreopenの一行を足す）、依存を足し、`dagq lint`してから`dagq submit`。不採用: `dagq cancel`と`dagq note --task`で理由。他のtaskの重複か、completedのtaskで実装済みなら`dagq cancel ID --duplicate-of X`で重複先を記録する（[ADR-0063](../../adr/0063-full-text-search-related-with-mentions-and-search-strength-and-duplicate-of.md)の決定5。ADR-0041で廃止したfollow-upのtriageに代わり、draftを重複で閉じるのはこのplanner）。自分で決めきれない（[推奨が出せればplannerが決める](#推奨が出せればplannerが決める未実装)の3つの条件）: `dagq ask --task ID --kind planner_question --because scope --recommend ... --confidence ... --option adopt --option cancel --option keep_draft`して止まり、answerに従う。決めた理由は採用ならcontext、不採用と`keep_draft`ならnoteに書く）、`dagq search`で重複と実装済みを探すこと、記録を読むCLI（`prompt::RECORD_READING`、ADR-0044の決定22、task 420: `dagq events --full --task ID`と絞り込み（`--run` / `--goal` / `--kind` / `--since` / `--until`。`--kind`が無ければattentionだけなので、全種類は`--all`を足す）と`dagq timeline RUN`）、AGENTS.mdの規則を読むこと、自動でsubmitできない上限。
4. **3回まで**: plannerがdraftを決めずに終わった（sessionが終わった、idleで`/exit`された）draftは次のpassで再び対象になり、残りのdraft（とその間に増えた同じきっかけのdraft）で束を作り直して次のplannerが立つ。回数はdraftごとに数える（そのdraftを含む束のplannerの数、`draft_bundle_members.attempt`）。`draft_planner_opened`が`MAX_DRAFT_PLANNERS`（3）件あるdraftは（人のanswerを運ぶとき以外は）束から外して`draft_planner_exhausted`（`planners`、`ask_id`、`reason`）を記録し、束の残りで立てる。attentionは`decide the draft in a planner`（`status`でもdraftのまま残っているあいだ出る）で、人が開いたplannerで決める。
5. **planner_question**（ADR-0044の決定13）: askのkindに`planner_question`を足した（CLIの`ask --kind`で作れる）。束の中でも`--task ID`でdraftごとに開く。`answer`は`planner_answer_route`で行き先を決め、`Person`以外なら`ask_answered`に`runtime_delivers: true`を書いてattentionにしない（`status`は`delivering the answer of ask N (runtime)`）。行き先は、(a) そのtaskで働く閉じていないruntimeのplanner（draftを持つ束のplannerか、taskのproposalのplanner）: supervisorがplannerの`idle`（idle markerがaskより新しい）を待ち、打ち込む前に`claim_planner_answer`で配送をclaimしてから（task 406。`BEGIN IMMEDIATE`で、askが未closeで行き先が今もそのplannerであり、同じaskの`planner_answer_claimed`が`PLANNER_ANSWER_CLAIM_SECS`（120秒）以内に無いことを確かめ、`planner_answer_claimed`（`ask_id`、`planner_id`、`workspace_id`、`claimed_at`）をtaskに書く。revise の`claim_revise`と同じ形。claimできなければ送らない）、`answer to ask <id>: <answer>`を`submit_input`で打ち込み、`ask_delivered`でaskを閉じる。これで引き継ぎの間に同じqueueを扱う2つのsupervisorが重なっても、answerは1回しか打ち込まれない。打ち込みの失敗は今までどおり`ask_delivery_failed`（taskに記録）でinboxに任せる（claimは残るので打ち直さない）。claimの後、打ち込む前にsupervisorが落ちたaskは、claimが120秒より古くなった後の周回で別のsupervisorがclaimし直して打ち込む（打ち込みは数秒で終わるので、生きているsupervisorのclaimを奪わない）。(b) plannerが居ないdraft: 上限の中で新しいplannerを立て（そのdraftを先頭に、同じ束の鍵で対象のdraftを束に加える。同じ鍵の束のplannerが開いていれば、それが終わるまで待つ）、初期promptに元の質問とanswerを載せ（先頭のdraftの`draft_planner_opened`の`ask_id`）、askを閉じる。(c) `keep_draft`のanswerでplannerが居ない、またはdraftが先に進んだ（submit、cancel）: supervisorが`planner_answer_closed`（`ask_id`、`reason`）でaskを閉じる。(d) それ以外（出どころの無いtask、使い切ったdraft）: inboxが届ける（`send the answer of ask N to the worker and close it`）。closeされていない`planner_question`（束のどれかのdraftについて）があるplannerと、そのworkspaceに打ち込んだanswer（`ask_delivered`）の後にまだidleになっていないplannerには`/exit`を送らない（打ち込まずに閉じたaskは引き止めない。`question_wait`）。打ち込みの後かは、打ち込む前に取った配送のclaimの時刻（`planner_answer_claimed`の`claimed_at`）と`idle_since`で決め、`idle_since`がclaimの秒以下なら答えをまだ読んでいない。askの`closed_at`（打ち込みの後に`ask_delivered`が書く）とは比べない: answerを読んで仕事を終え、askのcloseより前にidleになったplannerを答えの処理中とみなして`/exit`せず、`--runtime-planners`の枠をふさいだため（task 884。2026-09-27のask 150とplanner 338）。(b)で初期promptに載せたanswerはplannerを立てた時刻と比べる。plannerが自分で作ったaskはplannerがaskの後に止まってから、他の人が作ったaskはplannerがidleなら打ち込む。
6. **採用の記録と上限**（`submit`の中、[persistence](../persistence.md)）: submitが出どころのあるdraftを初めて出すとき`follow_up_adopted`（goal_gapとreopenedは`draft_adopted`。`task_id`、`origin`、`source_task_id`、`source_run_id`、`by: "planner" | "person"`、`ask_id`、`depth`、`planner_id`（draftを持つ生きている束のplanner）、`bundle_key`と出どころの欄）を書く。上限はdraftごとで、束の中の1件が人の`adopt`を要しても、他のdraftは出せる。runtimeのplanner（`DAGQ_PLANNER_ORIGIN=runtime`）は、goalが閉じているか無い、または`follow_up_depth`が`FOLLOW_UP_ASK_DEPTH`（3、[ADR-t808-1](../../adr/2026-09-28-t808-1-runtime-planners-submit-follow-ups-up-to-depth-two.md)）以上のfollow_upのdraft（深さ2まではgoalが開いていれば人を経ずにsubmitできる）を、そのdraftへの`planner_question`（旧`follow_up`）に人が`adopt`と答えていなければsubmitできない（errorで`planner_question`を促す）。人が開いたplannerのsubmit、人の`adopt`を経たsubmit、`ready --bypass-review`は深さを0に戻す。
7. **終わり**: runtimeのplannerは束のdraftをsubmitしたか、cancelしたか、`keep_draft`で残したら（決めずに残したものがあっても）、idleになったところで`/exit`され、終わったworkspaceは閉じられる（[Plan review (supervisor)](plan-review.md#plan-review-supervisor)の`end_runtime_planners`）。idleはStop hookのidle markerで判断し、markerが書けなかった（ディスク満杯などでhookが失敗した）ときや最後の入力より古いときは画面からの推定で判断するので（ADR-t803-1、[画面からのidleの推定](receipt-and-session-exit.md#画面からのidleの推定)）、markerが無くても仕事を終えたplannerは`/exit`される。画面にbackgroundの処理の表示（`1 shell`など）があるうちは、markerの`running`と同じく`working`として`/exit`を送らず、表示が消えてから推定でidleになったところで送る（task 823）。`planner_question`のanswerを打ち込まれたplannerも、それを読んでidleになれば（5）`/exit`される。持ち主の居ないreviseが上限で`--planner-timeout`を過ぎて待つときは、人の答えを待っていないidleのplannerが`/exit`されて枠を空ける（`planner_released`。[Plan review (supervisor)](plan-review.md)の9）。画面も読めないまま`--planner-timeout`（既定3600秒）のあいだ入力・marker・推定のidleのどれも見えなければ、plannerごとに1回`planner_unresponsive`（`subject: "planner"`、`draft_task_id`）がinboxに届き、attention `check the planner`が束の最も古いdraftのtaskに出る。束のplannerも1つで1回で、plannerは閉じない（[Planner sessions](plan-planners.md)の「runtimeのplannerの時間切れ」、task 805）。submitしたproposalはplan reviewを通り、reviseは持ち主（閉じていれば新しいruntimeのplanner）に返る。
8. **記録と読み方**（ADR-t807-1）: plannerの行が閉じるとき（`close_planner`）、束のdraftごとの結末（`submitted`（proposal）、`canceled`、`duplicate`（重複先）、`keep_draft`、`undecided`）を`draft_bundle_members`に書き、draftに`draft_planner_settled`を記録する。出どころのあるdraftの`draft_planner_opened`・`draft_planner_settled`・`follow_up_adopted` / `draft_adopted`・`draft`からのcancelの`task_status_changed`は、束の鍵（`bundle_key`）と出どころの欄（`source_task_id`・`source_run_id`・`index`・`category`・`goal_review_id`・`reviewed_proposal_id`のうち材料にあるもの）を載せ、`events --task ID`と、payloadの`source_run_id`も見る`events --run RUN`で、元のrunから各draftの結末まで引ける。`dagq show ID`（`--full`でなくても）はtaskの`origin`（種類、material、元のtaskとrun、receiptの`follow_ups`の何番目か、束の鍵、そのdraftを持った束ごとのplannerと他のdraftと結末。人が`add`したtaskとobserverのdraft goalのtaskはnull。導入前のdraftも`draft_origins`の行があれば出す）と、元のtaskなら`follow_up_drafts`（そのrunのreceiptが出したdraftのIDと今の状態）を出す。`dagq planners`はruntimeのplannerの`bundle`（鍵とdraftと結末）を出す。`dagq stats`の`draft_flow`は窓の中の`bundles`（`draft_planner_opened`の`planner_id`の数）と`bundle_sizes`（draftの数ごとの束の数）を出す。
9. **test**: `tests/it/plan_review.rs`がcmuxのdoubleで、follow_upとgoal_gapのdraftに上限の中で古い順にplannerが立ち、人のdraftには立たないこと、promptの中身、決めたplannerの`/exit`、決めずに終わったplannerの後に次のplannerが立ち3回で`draft_planner_exhausted`とattentionになること、`planner_question`のanswerが生きているplannerに打ち込まれ（`planner_answer_claimed`が1件）、別のsupervisorがclaimしたanswerは2回目のclaimが拒まれて打ち込まれず、古くなったclaimは引き継がれて1回だけ打ち込まれ、plannerの居ないdraftでは新しいplannerがanswerを持って立ち、`keep_draft`は閉じられること、を確かめる。`tests/it/planner_slots.rs`は、answerを打ち込んだ後でaskのcloseより前にidleになったplannerが`/exit`されて行が閉じ、打ち込みより前のidleのplannerは残ることを確かめる（task 884）。`tests/it/draft_bundles.rs`は束（ADR-t807-1）を確かめる: 1つのrunのfollow_ups 3件にplannerが1つだけ立ちpromptに3件と元のtaskが1回載ること、別のrunのfollow_upとgoal_gapが別の束になること、作業中に増えた同じrunのfollow_upが待つこと、一部だけ決めて終わった束の結末（`duplicate`・`submitted`・`undecided`）と残りと増えた分で次の束が立ちdraftごとに3回目の後に`draft_planner_exhausted`になること、深さ3のdraftは束の中でも人の`adopt`無しにsubmitできないこと、`show`の`origin`・`follow_up_drafts`、`planners`の`bundle`、`events --run`、`stats`の`bundles` / `bundle_sizes`、束の2件目のdraftへの`planner_question`のanswerが束のplannerに打ち込まれること。`src/domain/follow_up.rs`のunit testが鍵の分け方を、`src/domain/stats/drafts.rs`のunit testが束の数え方を確かめる。`tests/it/runtime_ask.rs`は`register_follow_ups`の出どころ、runtimeのplannerのsubmitの上限と人の`adopt`の後のsubmit、`status`の表示を、`tests/it/queue_migration.rs`は導入前のfollow_upのdraftがmigrationで対象になることを確かめる。reopenedは、`src/infrastructure/draft_planners.rs`のunit testがwithdrawでreopenのmemberにだけ出どころが付き他のmemberには付かないこと、`tests/it/plan_review.rs`の`a_withdrawn_reopen_gets_a_planner_of_the_runtimes_with_the_reason`がplan reviewのreopen・withdrawの後にplannerが立ち、promptにreasonと3択が載り、readyにならないことを確かめる。

## follow_upの種類と判断の集計<a id="follow_upの種類と判断の集計未実装"></a>

[ADR-t947-3](../../adr/2026-09-28-t947-3-follow-ups-carry-category-codes.md)の決定（task 954で実装）。新しいeventは足さず、既存のeventから引く。

- **plannerへの材料**: 2の対象のdraftをplannerに渡すとき、出どころの`material`の`category`（[Receipt and session exit](receipt-and-session-exit.md#follow_upsの分類コード)）を、promptのdraftごとの節に`Category (the worker's; keep it as it is, ...): <コード>: <定義>`の行で載せる（一覧に無い値と`unlabeled`はその旨を添える。`follow_up_category_line`）。plannerは種類を書き換えない（判断に合わせて種類が寄らないように。ADR-t947-3の代替案）。
- **判断との突き合わせ**: 8の束のdraftごとの結末（`submitted`・`canceled`・`duplicate`・`keep_draft`・`undecided`）と、plannerがそのdraftについて開いた`planner_question`とその答えを、draftの`category`で並べる。不採用（`canceled`）の理由は[cancelの理由の分類コード](../domain-model.md#cancelの理由の分類コード未実装)（ADR-t947-4）で読む。
- **集計**: [Stats](stats.md#follow_upの種類ごとの集計)の`follow_up_categories`。draftの種類は`follow_up_registered`の`category`から引き、結末は`draft_planner_settled`の`outcome`（窓の中の最後のもの）、`draft_planner_exhausted`、draftの`planner_question`の`ask_opened`と`ask_answered`の`option`、draftからの`task_status_changed`（`duplicate_of`の有無で重複を分ける）から数える。
