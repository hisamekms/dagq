# Triage (supervisor)

終わった run の復旧 job は failed / interrupted / resume_exhausted を扱い、生きている worker の stalled と非対話の idle_process は [生きているsessionの復旧job](background-recovery-job.md) が扱う。対話専用の long_background / stuck_exit / prompt_waiting は廃止した。

1. **自動recover**: fill passごとに、`active_runs`のうち`integrating`以外でlease行の無いrunについて`doctor`と同じ判定（`run_health`）を行い、`blockers`が空（登録されたwrapper / agentのprocessが無いか、`exited_at`が記録済みか、PIDが死んでいる）なら`recover_run`で`interrupted`にする。`run_recovered`のpayloadは`recover`と同じで、`by: "supervisor"`が付く。taskは`ready`にしない（再実行は復旧jobに委ねる。ADR-0003・ADR-0007の「孤児runは自動再実行しない」は維持し、ADR-0012の「wrapperが死んだrunの`recover`は手動」を`recover`の実行だけ自動に改める）。staleなleaseを持つrunは、leaseのpidが死んでいて、adoptの対象（wrapperが生きているか終了を記録した`running` / `validating`、`resume_skipped`の後のrun、`awaiting_integration`）でなければ対象にする（task 236。supervisorとwrapperが両方死んだrun）。`run_recovered`の`lease_deleted`はtrueになる。leaseのpidが生きている（heartbeatが止まったまま生きているsupervisor）runは対象外。
2. **alert**: `in_progress`のtaskの最新runで`failed` / `interrupted`のもののうち、最後の`resume_started`より後に`triage_finished`も`triage_failed`も無いもの、または最後のラウンドが`wait`でその`recheck_at`を過ぎたもの（`domain::triage_state`が`Pending` / `Waiting`）。alertは、最後の`triage_started` / `resume_started`より後に記録された`recovery_requested`があればその`alert`（resumeを使い切ったrunの`resume_exhausted`。[`needs_session`](needs-session.md#needs_session)の6）、無ければrunのstatusで`failed` / `interrupted`。resumeの後にもう一度`failed`になったrunはもう一度ラウンドを持つ。新鮮なleaseのあるrun（verdictの後の終了を待っているsessionなど）は待つ。このsupervisorがまだslotで進めているrun（ラウンドの途中でleaseが他のtokenに移ってstaleになったものも）も取らない: そのslotは次のtickでleaseを失ったとして外れてjobを止め（[supervise](supervise.md#supervise)の7）、その後のpassでだけ他のrunと同じく次のラウンドを始める（同じrunを2つのslotで進めない。task 1361）。active runが上限未満のときだけ始め、jobの間はrun slotを1つ使う。
3. **開始**: 2の候補（`triage_candidates`、`runs_to_triage`の順）は、`needs_session`の再開・readyのclaimと1つの列で、taskの効く優先度の降順（同じ優先度では再開 → 復旧job → claim）に空きslotを受け、順が来たものを`triage_run`が始める（[supervise](supervise.md#supervise)の5の「slotを渡す順」、[ADR-t1850-1](../../adr/2026-10-06-t1850-1-resumes-recovery-jobs-and-claims-share-one-line-by-effective-priority.md)）。同じrunでそのalertの`recovery_requested`が`MAX_RECOVERY_ATTEMPTS`（3）件に達していなければ、`begin_triage`が`BEGIN IMMEDIATE`の中で上の条件（runがtaskの最新runであることを含む）を再検査し（staleなleaseは置き換える。slotにあるrunは2で飛ばしてあるので、置き換えるのはslotの外のrunのleaseだけ）、runにleaseを取って`lease_acquired`（`reason: triage`）、`recovery_requested`（`alert`、`attempt`（alertごとの通し番号）、`status`、`evidence`（runをそのstatusにしたeventのID）、`last_error`。`resume_exhausted`はruntimeが記録済みなので書かない）と`triage_started`（`attempt`はラウンドの通し番号、`status`、`session_id`（Claudeのjobだけ。Codexはthreadを自分で名付けるのでnull）、`launch`（jobのprovider・model・effort。[Codexで動かす](#codexで動かす)））を記録する。同じrunを2つのsupervisorが取ろうとしても1つしか通らない。runのdirectory（無ければ`runs/<run-id>/`）に`recovery-<alert>-<attempt>.prompt.txt`を書いて、run eventの`recovery_prompt_written`（`alert`、`attempt`、`prompt_bytes`。生きているsessionの復旧jobと同じ`start_job`が書く。task 1571）を記録し、`triage_started`の`launch`（`ActorLaunch::recorded`）のproviderの`AgentProvider::headless_command`（Claudeでは`headless_command`の`claude -p`でpromptはstdin（task 1560）、`triage_started`の`session_id`付き。Codexでは`codex exec --json`の読み取りだけのsandbox）をそのdirectoryで、`DAGQ_ROLE=recovery-job`・`DAGQ_ACTOR_ID=recovery-job:<run id>:<alert>:<attempt>`（CLIはreviewと同じく読み取りだけを許す。[Roles](roles.md#actors)）と、queue serviceのsocketとjobのtokenのfile付き（`DAGQ_QUEUE`は渡さない。[Queue service](../queue-service.md#クライアントモード)）で起動し、stdout / stderrを`recovery-<alert>-<attempt>.out` / `.err`に書く（promptと一緒に、promptの固定バイナリの節の全体を`recovery-<alert>-<attempt>.binary.json`に書く。task 1633）。timeoutはreviewと同じ`AgentProvider::review_timeout`（既定600秒）。3件に達していれば、jobを起動せずに`begin_triage`（`recovery_requested`なし）の後すぐ5のescalateにする（4の後の6。使い切りとjobの番号の判断は`triage::recovery_round`）。例外は、最後のラウンドの後の人の回答が`edit the task's --verify, then retry_inherit`（`VERIFY_FIX_OPTION`）で、runの最初のeventより後にtaskの`verification_commands`を変えた`task_edited`があるとき（`domain::recovery::verify_fix_round`）で、3件に達していてもjobをもう1回起動する（ADR-t883-1。直したverifyをjobが読んで`retry_inherit`を選べるように）。その`recovery_requested`は通し番号4以降になる。editの無い回答は他のoptionと同じで、3件に達していればすぐescalateになり、同じ選択肢のaskがまた開く（人が直して答えるまで進まない）。
4. **prompt**（`prompt::recovery_prompt`に`prompt::ended_run_material`を足したもの。決定39の入力）: alertとその事実（`recovery_requested`のpayload）、taskのtitle・description・acceptance、runの`last_error`、receipt（末尾3000 byte）、run directoryの最新の`integrate`試行の`integrate-<attempt>-verify-N.log`（N順）とvalidatingが以前書いた`verify-N.log`（あわせて8つまで、各末尾3000 byte。それより前の試行のlogはpathだけ並べる。試行番号の無い旧名`integrate-verify-N.log`は最初の番号付きの試行より前の試行として読む）、`terminal-final.txt`の末尾、そのrunのevent（`events`と同じ圧縮形の直近40件）、同じtaskの他のrun（status、`last_error`、ラウンドの`action`）、worktreeに残るプロセス（cwdがworktreeの下のもの）、worktreeの`git status`とHEADとreceiptの`commit`、そのrunの過去の`recovery_finished` / `auto_repaired`、許された操作（`retry` / `retry_inherit` / `resume` / `wait`）とverdictのschema、許されない操作の一覧、規則（taskの`failed` / `interrupted`のrunが`TRIAGE_RETRY_FAILURES`（2）以上ならretryは適用されない、resumeを使い切っていればresumeを選ばない）。alertの事実の直後に、supervisorの固定バイナリの節（task 1633）: 今のbuild識別子とそのcommit、taskの依存先ごとの着地commit（最新の`run_integrated`）と今のbuildがそれを含むか（`held`）、runのclaimより後の`update_installed`（pluginだけのものを除く）と`supervisor_handed_off`（時刻・`previous_version`・`version`）、と`retry` / `retry_inherit`の選び方: 固定バイナリが依存先の着地を含まないことで関門（verifyの「build識別子のcommitがtask Xの着地を含む」など）に落ちたrunは、今のbuildがそれを含めば入れ替えで直っているので、人に聞かずに`retry`（自分のcommitのあるrunは`retry_inherit`）を`confidence: high`で選んでよく（`TRIAGE_RETRY_FAILURES`の規則でruntimeがretryを適用しないときはescalateでretryを推奨する）、まだ含まなければ同じように落ちるので`wait`かescalateにする。欄の綴り・節と上限・全体を超えたときの位置と、省いたものを読む`recovery-<alert>-<attempt>.binary.json`は[復旧job](background-recovery-job.md)のpromptと[Prompt](prompt.md#goal-reviewrunのreview復旧jobruntimeのplannerの上限)。promptは全体`RECOVERY_PROMPT_LIMIT`（96,000 byte、言語の指示を含む）と節ごとの上限の中に収め、終わったrunの資料（`ended_run_material`）は`RECOVERY_ENDED_BYTES`（24,000 byte）で先頭を残して切る。切ったものには省いたbyte数と、jobが読めるrun directoryのファイル（receipt、検証のlog、`terminal-final.txt`、`turns/`、claim時のtaskの`prompt.txt`）か、ファイルに無いものは読めないことを書く（task 1571。値・理由・切り方は[Prompt](prompt.md#goal-reviewrunのreview復旧jobruntimeのplannerの上限)、生きているsessionの復旧jobと共通の節は[復旧job](background-recovery-job.md)のprompt）。
5. **verdictの適用**（`act_on_recovery`）: stdoutから`RecoveryVerdict`を読む（全体か、最外の`{...}`、未知のfieldは拒否）。`confidence: high`の`repair`で、`actions`がちょうど1つ、かつその前提が今成り立つときだけ適用する（`plan_ended`）。前提:
   - `retry`: taskの`failed` / `interrupted`のrunが2未満で、runのbranchに自分のcommitが無い（`result_commit`、無ければworktreeのHEAD、worktreeを作る前に止まったrunなら無し、がmainの祖先。worktreeが消えていて`result_commit`も無ければ判断できないので崩れとする）。commitのあるrunを最初からやり直すのは成果の破棄なので適用しない。適用するとtaskを`in_progress`から`ready`に戻す（`task_status_changed`）。
   - `retry_inherit`: runのbranchに自分のcommitがあり、そのtaskで引き継ぐretry（`triage_finished`の`action: retry_inherit`）がまだ無い（taskごとに1回。人の手での引き継ぎは数えない。`finish_triage`が同じトランザクションで再検査する）。`refs/dagq/runs/<run-id>`にcommit（`result_commit`、無ければworktreeのHEAD）を残してtaskを`ready`に戻し、`triage_finished`に`inherit`（`branch`、`head`）を書く。次のrunはtask 358の引き継ぎ（`run_inherited`とpromptの「Carried over from run」の節）で始まる。
   - `resume`: resumeを使い切っていない（`ResumeCount::exhausted`でない。通算で数える）、worktreeとreceiptのpathがある。runを`needs_session`にし、`last_error`にjobの`instruction`（空なら`diagnosis`）を書く。[`needs_session`](needs-session.md#needs_session)の自動resumeが拾い、resolution requestは「triageが差し戻した」文面（`ResumeKind::Triage`）で`Reason:`に`instruction`を載せる。
   - `wait`: 何もしない。`recheck_at`（`recheck_after_secs`、上限3600秒）を過ぎたら、runが同じところに居ればもう一度jobを起動する（alertの3回に数える）。
   - `send_instruction`、`stop_processes`、廃止した `answer_known_dialog`、`close_and_proceed` はどの worker にも当てはまらず、ほかの生存 session 専用の操作も終わった run には当てはまらないので、前提の崩れとして扱う。
   適用したら`finish_triage`が遷移と`triage_finished`（`attempt`（ラウンド）、`alert`、`recovery_attempt`、`verdict`、`confidence`、`reason`（`diagnosis`）、`duration_secs`、Codexのjobなら`session_id`（thread）・`model`・`model_unknown`、`action`、遷移後の`status`、`resume`なら`instruction`と`code: triage_resume`、`retry_inherit`なら`inherit`、`wait`なら`recheck_at`）、`auto_repaired`（`layer: recovery`、`repair`は操作の名前、`alert`、`attempt`、`conditions`。`wait`には書かない）、`recovery_finished`（`alert`、`attempt`、`verdict`、`confidence`、`diagnosis`、`applied`、`escalated: false`、`recheck_at`、`duration_secs`、Codexのjobなら`triage_finished`と同じthreadとmodel）を1トランザクションで記録する。適用する前にleaseをまだ持っているかを確かめ、失っていれば（止まっていた間に別のsupervisorが引き継いだ）何も書かずにそのrunを手放す。
6. **escalate**: `escalate`、`confidence: low`の`repair`、前提の崩れた`repair`（操作が1つでない、許されない操作を含む）、alertの3回の使い切りは、`kind: decide`のaskをrunに作る（`asked_by: supervisor`、optionsとquestionは副作用のない`triage::ended_options`と`ended_question`が組み立てる。optionsは`retry` / `resume` / `cancel`（resumeを使い切ったrunは`retry` / `cancel`）にjobの`options`を足し、runの`integrate`の検証が落ちたことがあるrun（`integration_deferred`の`code: verification_failed`。`domain::recovery::verification_failed`）では最後に`edit the task's --verify, then retry_inherit`をruntimeが足したもの（使い切りのaskにも足す）、`reason_category`はjobの`discard` / `scope`、それ以外は`recovery_failed`）。questionはalert、escalateの理由（jobが直せなかった、自信が無い、runtimeが適用しなかった理由、使い切り）、`Why a person: <reason_category>`、jobの`diagnosis`、推奨の操作（jobの`actions`）、jobの`question`、`recovery-<alert>-<attempt>.prompt.txt`のpath、`last_error`、各optionの意味（jobの足したoptionは復旧jobにもう一度渡ること。verifyのoptionを足したaskでは、userかinboxが先に`dagq edit ID --verify ...`（か`--no-verify`）で直してから答えれば、使い切った後でも復旧jobがもう1回、直したコマンドで走ること）を持つ。askを作った後で`finish_triage`が失敗したら、このpassが開いたaskは取り下げて（`withdrawn: …`と`answered_by: runtime`で答えて）閉じ、8の失敗にする。人にはinboxのwatchが`ask_opened`として知らせる。runはそのまま。`triage_finished`（`action: ask`、`ask_id`、`reason`はescalateの理由とdiagnosis）と`recovery_finished`（`escalated: true`、`why`、`reason_category`、`ask_id`）を記録する。
7. **sessionの停止**: `triage_finished`の後、runが開いたsession（[Run workspaces](run-workspaces.md#run-workspaces)）のうち止めた記録の無いもので、backgroundのwrapperがまだ動いているもの（`run_session_open`。handleのprocessで見て、cmuxには聞かない）を止め（handleの`stop_background`、route `triage`。どう終わったかは`wrapper_stopped`に記録する。[非対話のworker](headless-worker.md)の「停止の記録」、[ADR-t1404-1](../../adr/2026-10-03-t1404-1-headless-wrappers-run-as-detached-background-processes.md)決定3）、`workspace_closed`（`workspace_id`はhandle、`by: "triage"`、resumeのものなら`resume_attempt`。workerのsessionなら`workspace_closed_at`も）を記録する。[ADR-t1433-3](../../adr/2026-10-03-t1433-3-headless-wrappers-run-only-in-the-background.md)より前にworkspaceで開いたsessionのIDは開いていないとみなし、cmuxに聞かず閉じもしない（人が自分のterminalで閉じる）。止める失敗は`cleanup_failed`（`workspace_id`、`message`、`by`）に記録して続ける（`last_error`は変えない）。1つでも閉じたら、そのrunの閉じていない`stuck_exit`のaskを閉じる。最後にleaseを解放する。`triage_finished`の後のこれらの失敗（DBのerrorなど）はsupervisor logに書くだけで、`triage_failed`にはしない（verdictは適用済み）。
8. **jobの失敗**: 起動できない、非0終了、timeout、stdoutにverdictが無い、適用中のerrorは`triage_failed`（`code: job_failed`、`attempt`（ラウンド）、`alert`、`recovery_attempt`、`error`、`duration_secs`、`status`。Codexのjobならthreadとmodel、使えなかったproviderの`provider_unusable`）と`recovery_finished`（`outcome: job_failed`、`reason_category: recovery_failed`、同じthreadとmodel）を記録してleaseを解放し、runはそのままにする。`triage_failed`はattention（`triage by hand`。ADR-0047は`recover by hand`と読む）で、人の指示でinboxのsessionか人の`DAGQ_ROLE`の無いterminalから`ready` / cancelなどを打つ（plannerは`ready`を拒まれる）。supervisorは同じrunをもう一度ラウンドにかけない（resumeされれば別。providerが使えずに失敗したjobの`provider_unusable`の付いた`triage_failed`は例外で、attentionにせず次のラウンドをもう一方のproviderで始める。[Codexで動かす](#codexで動かす)）。
9. **askの回答**: fill passごとに、`asked_by: supervisor`の`decide`のaskで回答済み・未closeのもの（`triage_answers`）のうち、回答がaskのoptionsにある`retry` / `resume` / `cancel`のどれかで、runが`failed` / `interrupted`でleaseが無いものを`decide_triage`で1トランザクションで適用する（runがtaskの最新runで、askが回答済みかつ未closeであることを中で再検査するので、2つのsupervisorが同じ回答を二重に適用しない。staleなleaseの行は同じトランザクションで消すので、止まっていたラウンドのsupervisorが起きてもleaseを更新して書けない。[ADR-0039](../../adr/0039-adopt-stale-lease-of-live-wrapper-and-renew-own-stale-lease.md)の決定7）: `retry`はtaskを`ready`（人の判断なので、commitのあるrunでもよい）、`resume`はrunを`needs_session`（`last_error`は直近の`triage_finished`の`reason`に「ask Nで人がresumeを選んだ」を添えたもの。`ResumeKind::Triage`でresumeされる）、`cancel`はtaskを`canceled`にし、askを閉じ、`triage_decided`（`ask_id`、`answer`、`reason`、`status`）を記録する。taskが既に`in_progress`でないか、より新しいrunがあれば（人が`ready`を打ったなど）適用するものが無いのでaskを閉じるだけにする。回答がjobの足したoptionかruntimeの足した`edit the task's --verify, then retry_inherit`（askのoptionsにあり`retry` / `resume` / `cancel`でないもの）なら、何も動かさずにaskを閉じ、`triage_decided`（`action: recover`）を記録する。`triage_state`はこれを`Pending`と読むので、次のfill passで同じalertのラウンドがもう一度始まり（alertの3回に数える）、その`recovery_requested`の`person_answer`（`ask_id`、`answer`）とpromptのalertの事実でjobが人の選んだものを読む。verifyのoptionの回答は、verifyを直す`task_edited`が先にあれば3の例外で使い切りの後でもラウンドを持ち、jobはpromptのtaskの今の`verification_commands`と`task_edited`（旧値・新値・actor）を読んで`retry_inherit`を選べる。次のrunの`integrate`はtaskの今のverifyを流す。optionsに無い自由な回答は人が読む（`read the answer of ask N and close it`）。ただしoptionsのどれとも一致せず、runtimeの操作の名前だけ（復旧jobの操作と`retry` / `resume` / `cancel`。前後の空白・大小・引用符は無視する）の回答は、`answer`が何も書かずに断り、askは開いたまま残る（`domain::recovery::bare_action_answer`）。書けば誰も適用しない自由な回答として閉じ、答え直せないため。断りのmessageはその名前を含むoptionの原文（そのまま答えればruntimeか復旧jobに渡る）と、`retry_inherit`なら下の人の手での引き継ぎ（`dagq ready ID --inherit`）を示す。`answer`はこの条件（optionsのどれか）のaskの`ask_answered`に`runtime_delivers: true`を書き、attentionにしない（`status`では`applying the answer of ask N (runtime)`）。

## 人の手での引き継ぎ

userとinbox（人の言葉で）は、`in_progress`のtaskの最新runが`failed`か`interrupted`のとき、`dagq ready ID --inherit --reason ...`でそのrunのbranchを次のrunに引き継いでtaskを`ready`に戻せる（[ADR-t1962-1](../../adr/2026-10-07-t1962-1-retry-carrying-the-branch-over-by-hand.md)）。
decideのaskの答えに無い引き継ぎを、人の判断として直接打つための操作で、decideの答えの集合（ADR-0047決定3）は変えない。
認可は計画管理の`ready`が行い、引き継ぎの確定は実行と着地が公開するportが行う（[境界をまたぐtransaction](../architecture.md#境界をまたぐtransaction)のT10）。

- 引き継ぐcommitは自動の`retry_inherit`と同じ選び方で決める。
  CLIは確定の前にこれを読み、`refs/dagq/runs/<run-id>`は確定が通った後にだけ書くので、断ったときはtask・ask・refのどれも変えない。
- 前提（taskの状態、runがまだ最新で`failed`か`interrupted`であること、生きたprocessとstaleでないleaseが無いこと、独自のcommitがあること）は確定のトランザクションの中で確かめ、崩れていれば理由つきで断る（独自のcommitが無ければ素の`ready`を案内する）。
- 復旧jobのラウンドとの競合は、`begin_triage`と同じ`BEGIN IMMEDIATE`の確定の中でrunのleaseを見て解く。
  staleでないlease（ラウンドが生きている）があれば断る。
  staleなleaseは同じトランザクションで消すので、止まっていたラウンドはleaseを更新できず、古い候補の`retry_inherit`も含めて何も適用しない。
  確定の後はtaskが`ready`なので、新しいラウンドはそのrunを取らない。
  どちらの順でも、runの引き継ぎは高々1回になる。
- 確定はtaskを`ready`にし（plan reviewを通らない）、runの復旧jobの閉じていない`decide`のaskをruntimeとして閉じ（その答えは誰も適用しない）、`triage_finished`（`action: retry_inherit`）を記録する。
  その`by`（`user`か`inbox`）が手での引き継ぎを自動のものと分け、eventのactorが誰が打ったかを持つ。
- 次のrunは自動の引き継ぎと同じく`run_inherited`とpromptの「Carried over from run」で始まり、promptは人が手で引き継いだことと理由を書く。
- 自動の`retry_inherit`のtaskごとに1回の制限は掛けず、手での引き継ぎはその回数を使わない。

## Codexで動かす

`[roles.recovery] provider = "codex"`の復旧job（task 1225。[ADR-t1063-1](../../adr/2026-09-29-t1063-1-headless-job-provider-per-role-with-intent-permissions.md)の決定1・2・4・5・6、[ADR-t1204-1](../../adr/2026-09-30-t1204-1-explicit-no-claude-operation.md)。providerの項は[Actor model](actor-model.md#provider)）。jobは状態を変えず読むだけ（`TRIAGE_ACCESS = JobAccess::ReadFiles`）で、verdictはClaudeのjobと同じ5・6の検査と適用を通る（許す操作、`confidence: high`の`repair`だけ、前提の再確認、alertごとの3回）。

- **行き先**（`Supervisor::recovery_route`、副作用の無い`domain::actor_model::job_start_route`）: ラウンドを始める前に決め、`triage_started`の`launch`に書く。providerを書かない役割は今までどおりClaudeで、queueのholdのあいだは始めず、`--no-claude`ではjobを起動せずに8の失敗（`error`は`the recovery job could not start: provider_disabled: Claude is disabled by --no-claude; handle this role manually`）にする。providerを書いた役割は、そのproviderが使えれば（supervisorにagentがあり控えられていない）そこで、使えなければもう一方のproviderで（`launch`の`switched_from`・`switch_reason`）、どちらも使えなければ待つ。Claudeのholdは`codex`のjobを止めない。`--no-claude`でCodexも使えなければ、jobを起動せずに8の失敗（`provider_disabled: Claude is disabled by --no-claude and codex cannot be used (<理由>); handle this role manually`）にし、Claudeに回さない。
- **起動**（`recovery::start_job`）: `triage_started`の`launch`のproviderのagent（`Supervisor::job_agent`）でjobを起動する。Codexでは`codex exec --json --skip-git-repo-check -C <run dir>`の読み取りだけのsandboxで、jobの`dagq`がqueue serviceに届くときはjobのpermission profile（`:read-only`を継ぎ、queue serviceのsocketだけに届く）にする（[Provider lifecycle](../provider-lifecycle.md)）。書けるroot・sandboxを外すflag・session idは渡さない。jobはworkerのworktree・run directory・cmuxのworkspaceに書けず、`stop_processes`などの操作はjobではなくruntimeがpidで行う。`headless_jobs`の`provider`は`launch`のprovider。
- **読み取り**: verdictはCodexの最終の`agent_message`のtext（`AgentProvider::job_reply`）から今の`RecoveryVerdict`として読む。threadとmodelは`AgentProvider::job_session`（`thread.started`のthreadと、rolloutの`turn_context`のmodel。読めなければ`model_unknown`）で、`triage_finished` / `triage_failed`と`recovery_finished`に書き、ラウンドの区間の`session_closed`もそれを取る。
- **失敗**: 非0終了・timeout・読めないverdictは、Claudeのjobと同じ8の失敗（`triage_failed`のattention）にし、Claudeに回さない。providerが使えずに失敗したjob（ログイン・使用量の上限・agentが起動しない。`JobFailure::switch_reason`）は、役割がproviderを書いていれば（ADR-t1063-1の決定4）そのproviderを控え（`provider_held`。Claudeの壁はqueueのhold askにも加わる）、`triage_failed`に`provider_unusable`を書く。この`triage_failed`は人のものではない: `domain::triage_state`はこれを`Pending`と読み（`event_attention`もattentionにしない）、次のpassで同じrunの次のラウンドが行き先のproviderで始まる（控えの間はもう一方。`launch`の`switched_from`・`switch_reason`）。そのラウンドは新しい`recovery_requested`を持つのでalertの3回に数える。`--no-claude`で残るproviderが無ければ、次のラウンドは上の行き先のとおりjobを起動せずに理由付きの8の失敗（attention）になる。queueのhold askに加わるのはClaudeのjobの壁だけ（[Queue hold](queue-hold.md)）。時間の上限ではjobとCodexが走らせた子孫（別のprocess groupのものも）をpidで止める（`HeadlessJob::stop`、task 1085・1115）。
- **test**: `tests/it/recovery_codex.rs`（読み取りだけの起動とverdictの適用・記録・`stats` / `kpi`のproviderごとの集計、終わったrunの取らない操作（`stop_processes`）がaskになること、失敗とtimeoutが`triage_failed`になりtimeoutで子孫が止まること、ログインで失敗したCodexのjobが控えられて次のラウンドがClaudeで始まり着地すること、`--no-claude`でCodexで起動しClaudeに回さず、ログインで失敗した後のラウンドが理由付きで人に渡ること。`confidence: low`は生きているrunのtest）と、`supervise::recovery`のunit test（行き先と終わりの記録）。検査そのもの（`plan_ended`・`check_live`・`Escalation`）はClaudeのjobと共有で、そのtestがproviderに依らず確かめる。
