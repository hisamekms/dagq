# Observer

[ADR-0044](../../adr/0044-findings-proposals-from-findings-and-quiet-observer.md)の決定4・18・23（task 292）。observerはnoteとdraft goalを書かず、findingを記録・更新し、見立てが人を要るfindingにだけ`blocked`のaskを上げる（`--because`は`scope` / `discard` / `recovery_failed`から選び、見立てを`--recommend`と`--confidence`で載せる。下の「人が要る見立てだけをblockedにする」）。前回から自分以外のeventが無ければagentを起動しないこと、MCPを読まないこと、`observe --history`はtask 294が実装した。同じADRの決定19〜22のうち、既定の間隔を3時間にすること、proposalを求める印からplannerを立てることはgoal 31の他のtaskが持つ。`events --full` / `timeline`はtask 293が足し、promptに示すのはtask 420。dagqが回っているかを観察して継続的改善の材料を残すjobで、個々の詰まりは解消しない。cmux workspaceを持たず、`AgentProvider::headless_command`に`assign_session_id`と`without_mcp`を足して起動する（Claudeでは`claude -p --allowedTools 'Bash(dagq:*)' --session-id <id> --strict-mcp-config`でpromptはstdin（task 1560）。`--mcp-config`を渡さない`--strict-mcp-config`で、user・project・plugin・claude.aiのどのMCP serverも読み込まない）。providerは`[roles.observer]`の`provider`で選び、既定はClaude、`codex`ならCodexの`codex exec --json`で動く（下の「Codexで動かす」、task 1223）。実装は`src/application/observer/`（ユースケース。`compose::observe`がqueueと`ObserverSources`・`ObserverHost`を組み立てて注入する）と`src/infrastructure/observer.rs`（cursorと観察のdir、`[roles.observer]`、headlessのagentのprocess）。

Codexのobserverは、jobのdagqをクライアントモードにしてqueue service経由でfindingとfindingに紐づく`blocked`のaskを書き、Claudeのobserverも同じ経路にする（[ADR-t1222-1](../../adr/2026-10-02-t1222-1-codex-observer-writes-through-the-queue-service.md)）。serviceの側のユースケース（`finding_record`・`finding_resolve`、findingに紐づく`blocked`の`ask`、読み取りの`proposal_list`・`proposal_show`など）はtask 1235が足した（[Queue service](../queue-service.md#ユースケース)）。serviceはobserverのprincipal（tokenのrole `observer`とjobのactor id）をactorにしてCLIと同じ`Dialogue`で書くので、`finding_recorded` / `finding_updated` / `finding_status_changed`の`by`と`ask_opened`の`asked_by`は`observer`、eventのactorはjobのactor idになり、拒否の`authorization_denied`もactorのroleが`observer`で残る。そのため下の0の「observer自身のeventを数えない」判定（`SqliteQueue::events_besides`）はCLIで書いたときと同じに成り立つ（ADR-t1222-1決定4）。jobのdagqのクライアントモードはtask 1236が入れ、providerによらず（Claudeのobserverも）agentの`dagq`はserviceに送り、queueのDBを開かない。tokenはjobの起動ごとに`HostActorExecutor`が発行してfileに書き、そのpathを`DAGQ_SERVICE_CREDENTIAL_FILE`で渡し、jobのprocessが終われば失効させる（4）。Codexのsandboxに足すのはserviceのsocketへの到達だけ（下の「Codexで動かす」）。書き込みがserviceのerror（serviceが居ない・`unreachable`など）で通らなかったことを、runtimeはobservationの失敗に数えない（ADR-t1222-1のConsequencesが委ねた判断。task 1223）: `outcome`は今までどおりagentの終わり方だけで決まり、agentはerrorのJSONを見て非0で終われば`failed`になって次のobservationが同じwindowを読み直し、0で終われば読み直さない。supervisorはserviceが居ない間observerを起動しない（ADR-t1233-4決定2）ので、書けないのは走っている間にserviceが落ちたときだけで、その件数とidは`observe_finished`に入らない（書かれていないので）。

- **`dagq observe [--since CURSOR] [--daily] [--dry-run] [--timeout SECS] [--claude PATH] [--codex PATH] [--cmux PATH]`**: 1回のobservation。supervisorはほかに隠したflagの`--launch`（行き先のlaunchのJSON）・`--codex-home`・`--switchable`・`--unavailable`を渡す（下の「Codexで動かす」）。
  0. **変化が無ければ起動しない**: `--since`も`--dry-run`も無いとき、同じmodeの直前の（skippedでない）`observe_finished`が`succeeded`で、その入力が読んだ最後のevent（payloadの`cursor`。agentが走っている間に他が書いたeventも読んでいないので数える）より後にobserver自身のもの以外のeventが1件も無く、今の`stats`（1の`stats --since <cursor>`と同じもの）のalertに直前のobservationの`observe_finished`の`alerts`に無いものが無ければ（[ADR-t649-1](../../adr/2026-09-28-t649-1-new-time-driven-alerts-wake-the-observer.md)。task 649）、noteなどの残りの入力を集めず、dirも`observe_started`も作らず、`observe_finished`（`outcome: skipped`、`reason`、`previous_event_id`（直前のobservationの`observe_finished`）、`since`と`cursor`（どちらも読むはずだったcursor）、`cursor_saved: false`、件数0と空のid、`duration_secs: 0`、`dir: null`、今の`alerts`）だけを記録して返す。alertの比較は、eventを出さずに時間やその時点のsnapshotだけで閾値を超えるalert（`ask_unanswered`・`idle_slots`など。止まったsessionは`stall_nudged` / `recovery_requested`のeventでskipが破れる）を拾うため。alertの識別（`observer::alert_keys`）は`stats`の`alerts`と`running_alerts`の各項目の`kind`と、あれば対象の`task_id`・`run_id`・`path`・`ask_id`・`workspace_id`だけのobjectで（時間とともに伸びる`value`は含めない）、並べて重複を除いた配列にする。前回に無かった識別が1つでもあれば起動し、同じか減っただけなら起動しない。`alerts`を持たない古い（task 649より前の）`observe_finished`の後は、alertが1つでもあれば起動する。observer自身のものとして数えないのは、`observe_started` / `observe_finished`、KPIの記帳のevent（`domain::kpi::BOOKKEEPING_KINDS`: supervisorのcandidatesの標本の`candidates_sampled`（[`supervise`](supervise.md)の5）とレポートの`report_written`（[レポート](report.md)）と、見込みのsnapshotの`forecast_recorded`（[stats](stats.md#完了見込み)）と、pushの`kpi_push_sent` / `kpi_push_failed` / `kpi_push_abandoned`（[push](push.md)。失敗はattentionでinboxに届く）。目標割れの`kpi_breach_started` / `kpi_breach_resolved`は数える。ADR-0051の決定24。記帳のeventを足すtaskはこの一覧に足す。記帳のeventだけではobserverを起こさない）、payloadの`by`が`observer`の`finding_recorded` / `finding_updated` / `finding_status_changed`、`asked_by`が`observer`の`ask_opened`、payloadの`kind`が`observer`の`session_opened` / `session_closed` / `session_turns`（`SqliteQueue::events_besides`）。直前が`failed` / `error`なら（何も観察できていないので）起動する。skippedの`observe_finished`もtimerの期日の起点になる。
  1. 入力を集める: `stats --since <cursor>`（`--since`が無ければ前回のobserveが保存した`<queue dir>/observer/cursor`、それも無ければ`stats`の既定の直近50件。`--daily`は24時間前より前の最後のevent id）、`open` / `proposed`のfinding（`findings`）、直近20件のnote（`notes`）、openなask（`asks --open`）、`graph`の`candidates`と`critical`、KPIの`kpi`と改善のproposalの`improvements`（下の「KPIの目標割れと改善の上限」）。入力のJSONは`observer::observer_input`が組み立て、キーは`stats`・`kpi`・`findings`・`improvements`・`notes`・`open_asks`・`graph`。promptが切る一覧はpromptが残す順に並べる（`kpi.breaches`は`streak`の長い順・同じなら`subject`の順、`findings`は`impact`のhigh・normal・low、`occurrences`の多い順、新しい順、`open_asks`は新しい順。下の「promptの入力の上限と選ぶ順」）ので、promptが省いたものは`input.json`のその一覧のoffsetから後になる（task 1567）。
  2. promptを作る。役割は「dagqが回っているかを観察し、うまくいっていないことを`finding record`でfindingに記録し（根拠はrun_eventsのidを`--evidence`で渡し、本文に埋めない。同じ種類・対象・subjectは既存のfindingの更新になるので、持っていない根拠か読みの変化があるときだけ記録し直す）、remedyが要るfindingには`--propose`で理由を付け、もう起きていない問題は`finding resolve`し、見立てが「待てば解ける」「leave it」のものはaskにせずfindingの`--detail`に見立てを書いて記録・更新だけにし、見立てが人を要るものだけを`ask --kind blocked --finding ID --recommend ... --confidence ...`でinboxに上げる（openなaskのあるfindingには上げない。下の「人が要る見立てだけをblockedにする」）。note、goal、taskは書かず、個々の詰まりは解消しない。run / task / goalの状態は変えない」。promptは止まったsessionの閾値の読み方も持つ（ADR-0043の決定6、ADR-0044の決定21、task 408）: statsの`stall_thresholds`は`[stall]`の設定ごとの1項目で、`outcomes`の`answered_wait`が多ければ閾値が早すぎ、`preempted`が多ければ遅すぎの疑い、`resolved_by_nudge` / `resolved_by_enter` / `resolved_by_resend`は検知が効いている印、`pending`は未決で、`by_threshold_secs`で値の変更の前後を比べる。`running_alerts`の`idle_without_receipt`で`nudged: false`かつ`asked: false`のまま閾値を超えたものはsupervisorの検知の漏れの疑い。見直しが要ればkind `threshold`・subjectに設定名のfindingを記録し、繰り返すなら`--propose`を付け、閾値そのものは変えない。promptはflakyなtestの読み方も持つ（task 642）: statsの`failed_tests.flaky_candidates`（[stats](stats.md)。別々のrunの`integrate`の検証で`flaky_runs`回以上落ちたtestと、nextestの流し直しで通った（FLAKYの印の`flaky`が1以上の）test。task 768）の各testを、kind `flaky_test`・対象`--queue`・subjectにtestの名前・根拠（`--evidence`）にその`integrate_event_ids`で`finding record`し、同じ根拠を持つfindingは記録し直さない。workerのsessionだけで落ちたtestは作業中なのでfindingにしない。候補から消え、windowの`failed_tests.tests`でも`integrate`で落ちていないtestの`flaky_test`のfindingは`finding resolve`してよい。自動更新のe2eの関門のtestも同じくflakyなtestとして読む（task 1166、[ADR-t1165-1](../../adr/2026-09-30-t1165-1-e2e-gate-reruns-failed-e2e-once-and-records-quarantined-failures.md)決定4）: statsの`updates.e2e.tests`（[stats](stats.md)の`updates`）のtestごとの`failed`・`passed_on_rerun`・`quarantined`・`failed_gate`・`failures_in_a_row`・`event_ids`・`marked` / `mark_task`を読み、windowの関門で2回以上落ちた（流し直しで通ったもの・印で通したものを含む）testを、kind `flaky_test`・対象`--queue`・subjectにtestの名前・根拠にその`event_ids`で`finding record`する。安定化のtaskが要るもの（繰り返し落ちる、`failed_gate`か`failures_in_a_row`が1以上、印が付いたまま）には`--propose`を付け、runtimeのplannerが`search` / `related`で既存のtask（`mark_task`もその1つ）を確かめて重複させない。同じ根拠のfindingは記録し直さない。数えるのはstatsのwindowの中だけなので、2回の失敗は主に日次の観察の24時間で見える。promptはKPIの読み方も持つ（下の「KPIの目標割れと改善の上限」）。根拠を読むCLIとして、自由文ではなく記録を読む`events --full`と絞り込み（`--run` / `--task` / `--goal` / `--kind`（繰り返せる） / `--since` / `--until`。`--kind`が無ければattentionだけなので全種類は`--all`を足す）、`timeline RUN`、`observe --history`を示し、`events --all`だけの形は示さない（ADR-0044の決定22、task 420）。queueのコマンドは`dagq`の形で渡す（4）。`--daily`は24時間の傾向を見る別の文面にする。`--dry-run`はpromptを`{dry_run, mode, since, cursor, prompt, prompt_bytes, prompt_limit, prompt_sections}`で返し、dirを作らず何も起動・記録しない（promptが名指すobservationは`DRY-RUN`）。 promptの渡し方・節ごとと全体の上限・省いたことの明示・byte数の記録は[Prompt](prompt.md#headlessのjobのprompt)の「headlessのjobのprompt」の節が持つ（[ADR-t1566-1](../../adr/2026-10-03-t1566-1-headless-job-prompts-carry-decision-material-within-limits.md)）。入力は下の「promptの入力の上限と選ぶ順」の上限と順で載せる（task   3. promptを組む前に`<queue dir>/observer/<started_at>/`（同じ秒に既にあれば`-1`以降の接尾辞）を作り（promptはその名前を`observe --input`の読む先として名指す）、`prompt.md`と`input.json`（入力の全体）を書き、`observe_started`（`mode`: `hourly` / `daily`、`since`、`dir`、`session_id`、`launch`、promptの`prompt_bytes`・`prompt_limit`・`prompt_sections`（下の「promptの入力の上限と選ぶ順」の記録））をtaskの無いrun_eventsに記録する。`session_id`はClaudeのjobだけで、Codexのjobはnull（threadはCodexが名付け、5の終わりが記録する）。
  4. そのdirをcwdに、env `DAGQ_ROLE=observer`、queue serviceの`DAGQ_SERVICE_SOCKET`とobserverのtokenのfileの`DAGQ_SERVICE_CREDENTIAL_FILE`（`DAGQ_QUEUE`は渡さない。tokenはjobの終わりで失効する）、PATHの先頭に`dagq`のdirを置いてagentを起動し（promptは`dagq --db <db>`ではなく`dagq`を名指し、agentの`dagq`はクライアントモードでserviceに送る。[Queue service](../queue-service.md#クライアントモード)）、stdoutを`output.out`、stderrを`output.err`に分けて書く（`Streams::Files`）。`--timeout`（既定1800秒）を過ぎたらkillする。killの前にagentの子孫（`ProcessControl::descendants`。agentのBashとそれが起動したもの）を読み、agentの後にそれらもSIGKILLするので、agentの子プロセスは残らない（task 245）。Codexのjobも同じ`run_agent`で止め、Codexがコマンドごとに別のprocess groupで走らせたものも、killの前に列挙した子孫としてpidで止まる（task 1085と同じ形）。
  5. 終了後、`observe_started`より後にobserverが書いた`finding_recorded`と`finding_updated`（payloadの`by: observer`）のfindingと、observerが閉じたfinding（`finding_status_changed`のうち`by: observer`かつ`to`が`resolved`か`dismissed`のもの。再記録による開き直しの`to: open`と、人やplannerの`resolve` / `dismiss`は数えない。task 448）とobserverのaskを集め、`observe_finished`（`mode`、`outcome`: `succeeded` / `failed`（非0終了） / `error`（起動できない・timeout）、`consecutive_failures`（このobservationまで続く`error` / `failed`の回数。modeを問わずqueueの最後の`observe_finished`の値に1を足し（その値が無い前のバイナリの失敗は1と数える）、`succeeded`と、0の「変化が無ければ起動しない」の`skipped`では0。providerが無く起動しなかった`error`も数える。task 1574）、`exit_code`、`error`、`since`、`cursor`（`stats`の`next_cursor`）、`cursor_saved`、`findings_recorded`、`findings_updated`、`findings_closed`、`asks`、`findings_without_ask`（それぞれ件数）、`recorded_finding_ids`、`updated_finding_ids`、`closed_finding_ids`、`ask_ids`、`without_ask_finding_ids`、`duration_secs`、`dir`、見たalertの識別の`alerts`（0の比較に使う）。Codexのjobはほかにproviderの`job_session`の`session_id`（thread）・`model`・`model_unknown`（`JobSession::record`）、役割がproviderを書いたCodexのjobがCodexを使えずに止まったときは`provider_unusable`（下の「Codexで動かす」））を記録して返す。`succeeded`のhourlyのときだけ`cursor`を`<queue dir>/observer/cursor`に保存する（一時ファイルからrename）。失敗したobservationのwindowは次のobservationが読み直す。dailyはcursorを動かさない。保存する`cursor`は`stats`の`next_cursor`（runのpageの続き）のままなので、終わったrunを飛ばさない。`stats`の期間集計（`asks`・`jobs`・`waiting`など）はpageに依らず窓の終わりまで数える（[stats](stats.md)の期間集計の窓、task 1379）ので、1時間に50件を超えるrunが終わったときだけ、次のobservationの期間集計が前のobservationと重なる。observationごとの期間集計を足し合わせず、1回の値をその窓の値として読む。`consecutive_failures`がちょうど2の`observe_finished`（2回続けた失敗）はinbox宛てのattention（`check the failed observer`）になり、`--role inbox`のwatchを起こす。1回目と3回目以降、成功に戻ったものはattentionにしないので、1つの連続に1回だけ届く（毎時のobserverが止まり続けてもinboxを毎時起こさない。ADR-t1418-1）。askにせず、claimと着地を止めず、`status`にも残らない（[`events` / `watch`](events-watch.md)のattentionの列挙）。
- **`dagq observe --history [--limit N]`**: 過去のobservationを新しい順に`{observations: [...]}`で返す（既定20件。`observe_finished`ごとに1件で、読むだけなのでqueueを読み取り専用で開き、observerのenvからも打てる）。各件は`event_id`（`observe_finished`）、`mode`、`outcome`、`skipped`、`started_at`（同じ`dir`の`observe_started`の時刻。skippedは`finished_at`と同じ）、`finished_at`、`duration_secs`、入力の範囲の`input: {since, through}`（`since`より後から`through`（`stats`の`next_cursor`）までに終わったrunを読んだ。期間集計はpageに依らず窓の終わりまで）、`cursor_saved`、`consecutive_failures`（task 1574より前のものは`null`）、書いた・閉じたfindingの`findings: {recorded, updated, closed, recorded_ids, updated_ids, closed_ids}`、askの`asks: {count, ids}`、askにせずfindingだけにした`without_ask: {count, ids}`、`exit_code`、`error`、`dir`、同じ`dir`の`observe_started`のpromptの`prompt_bytes`・`prompt_limit`・`prompt_sections`（skippedとtask 1567より前のものは`null`）を持つ。idを記録する前のバイナリの`observe_finished`はidが`null`で件数だけになり、閉じた数を記録する前のバイナリのものは`closed` / `closed_ids`が`null`、task 1319より前のものは`without_ask`の両方が`null`になる。
  `dir`の出力は新しい観測では`output.out` / `output.err`。過去の`output.log`は移行も削除もしない。historyはeventの`dir`を返し本文を読まないため、過去の観測も同じように表示され、そのdirの`output.log`を人が読める。終了した観測の出力をruntimeが読み直して分類することはない。失敗時の分類は、Claudeのjobは`AgentSignals::job_failure`に両streamを改行でつないで渡し（壁ならqueueのhold askに入る）、Codexのjobは役割がproviderを書いたときだけ`AgentProvider::job_failure(stdout, stderr)`で読む（下の「Codexで動かす」の`provider_unusable`）。成功時は分類しない。
- **`dagq observe --input OBSERVATION [--section PATH] [--offset N] [--limit N]`**（task 1567）: observation（`observe --history`の`dir`の名前。数字と`-`だけで、他は拒む）の`input.json`、promptが省いたものを含む入力の全体を読む。読むだけで、queue serviceの読み取りのユースケース`observe_input`（[Queue service](../queue-service.md#ユースケース)、`queue.read`）なので、observerのenv（クライアントモード）からも打てる。`--section`が無ければ2段までのpath（`stats`・`stats.runs`など）ごとの`bytes`と`items`の一覧、一覧の節は`--offset`（既定0）から`--limit`（既定`INPUT_PAGE`の10）件を`INPUT_READ_BYTES`（24,000 byte。少なくとも1件）の中で`{total, offset, items, next_offset}`、24,000 byteを超えるobjectはkeyごとの`bytes`の一覧（`--section <path>.<key>`で読む）、それ以外は`value`で返す。observerのClaudeは`Bash(dagq:*)`だけでファイルを読めないので、promptはファイルのpathではなくこのコマンドを読む方法として書く（Codexのobserverはread-onlyのsandboxでファイルを読めるが、promptはproviderに依らず同じ）。

- **選び方**: 節を上の順（必須の資料、省いてよい節）に、項目を節の順に、節の上限と全体の残りに入る間だけ取る。一覧は入らない最初の項目で止め（省いたものはoffsetから後の続き）、keyの節は入らないkeyを飛ばして次を試す。見積もりは件数の桁と節の注記を含まないので、組んだ後で全体が上限を超えれば、後ろの節の最後の項目から落とす。LLMには選ばせない。
- **項目の縮め方**: 一覧の1件はcompactなJSONの1行。文字列は300文字（`TEXT_CHARS`）で切って残りの文字数を書き、項目の中の一覧（根拠のid・印・期間の値）は最後の10件（`NESTED_ITEMS`。queueの一覧は古い順なので新しいもの）にして`<key>_omitted`に残りの件数を書く。keyの節の値は縮めず、入れるか省くか（`kpi`の`trend`・`forecast`は上の要約）。

- **記録**: `observe_started`の`prompt_bytes`（言語の指示を含むpromptのbyte数）、`prompt_limit`、`prompt_sections`（`instructions`から節の順に、各節の`name`・`bytes`（見出しと注記を含む）・`total`・`kept`・`omitted`。`bytes`の合計は言語の指示の無いpromptのbyte数）。`observe --history`と`--dry-run`も同じ名前で返す。起動に失敗したobservation（引数の大きさなど）も`observe_started`に残る。

## KPIの目標割れと改善の上限

[ADR-0051](../../adr/0051-kpi-time-series-report-and-push.md)の決定24〜26（task 433）。observerはKPIの目標割れの継続を種類`kpi`のfindingにし、そこから作る改善のproposalは同時の数に上限がある。

- **入力の`kpi`**（`OneShot::observer_kpi`、純粋関数は`domain::kpi::observe::observer_input`）: [`kpi`](kpi.md)を直近7日（`--period day --last 7`）と直近4週（`--period week --last 4`）で`dagq kpi`と同じ設定（main checkoutの`dagq.toml`の`[kpi]`にhost.tomlを重ねたもの）で計算し、次を載せる。数字は`kpi`の出力をそのまま引き、observerは作らない。読めなければ`{"error": ...}`にして他の入力で観察を続ける。
  - `config`: `min_samples`・`breach_periods`・`breach_weeks`。
  - `targets`: 日と週の各目標の`period`（`day` / `week`）・`kpi`・`stratum`・`stat`・`min`・`max`・`state`（`ok` / `missed` / `breach` / `not_judged`）・`streak`・`breach_since`と、期間ごとの`values`（`period`・`value`・`n`・`met`・`reason`）。
  - `breaches`: `state`が`breach`の目標ごとに、findingの`finding_kind`（`kpi`。`forecast.*`のKPIは`forecast`、下の「完了見込みの誤差」）と`subject`（`<KPI>/<層>`。例: `phase.work/change=fix`。`forecast.*`のKPIは接頭辞`forecast.`を除く）、根拠の`evidence_event_id`（同じ期間・KPI・層の閉じていない`kpi_breach_started`のevent ID（`SqliteQueue::kpi_breach_events_open`）。supervisorがまだ記録していなければnull）、最後に判定した期間の`value`と`latest_period`、`streak`・`breach_since`、目標割れが始まった期間からの印の`marks`（`period`・`label`・`kind`・`at`）。
  - `trend`: `day` / `week`の期間ごとに`label`・`partial`・`runs`・その期間の印の`marks`と、前の期間より悪化した（判定済みで`verdict: worsened`）KPIの`worsened`（`kpi`・`stratum`・`previous`・`delta`・`ratio`。層は`all`と`change=*`だけ）。
  - `forecast`: `day` / `week`の期間のうち答え合わせの標本か除いた行がある期間ごとに、`label`・`partial`・`details`（`kpi`の`details.forecast`: `samples`・`excluded`・`with_marks`・`marks_between`）と`kpis`（`forecast.*`の各KPIの、標本のある層だけ）。
- **入力の`improvements`**（`OneShot::improvements_of`）: 動いている改善の数`running`、上限`limit`、`reached`、上限に達しているときにplannerを待つfindingの`waiting`（`finding_id`と`reason: improvement_limit`）。`dagq findings`も同じものを`improvements`として返す。
- **promptの読み方**: `breaches`の各項を、その`finding_kind`・対象`queue`・その`subject`・根拠`evidence_event_id`で`finding record --kind <finding_kind> --queue --subject '<subject>' --evidence <id>`にし、summaryとdetailに値・目標・続いた期間・印をそのまま写す。根拠が無い（まだ記録されていない）目標割れは次のobservationに回す。日と週の同じKPIと層、続いている目標割れは`subject`が同じなので1件のfindingにまとまり（ADR-0044の決定18）、新しいeventがあるときだけ記録し直す（決定21）。`missed`と`not_judged`はfindingにしない。`kpi`か`forecast`のfindingの目標が`ok`に戻ったら、戻った期間を理由に`finding resolve`する。影響と続いた期間から改善が要ると読めば`--propose`を付け、目標割れを`blocked`のaskにはしない。`trend`は印と並べて読み、入力に無い数字を計算しない。
- **改善の上限**（[Finding planners](finding-planners.md)の3と11）: runtimeのplannerがfindingに紐づけて出したproposalのうち終わっていないもの（人が開いたplannerのproposalは数えない）と、`open`のfindingのために立ったruntimeのplannerの数が、`dagq.toml`の`[kpi]`の`max_improvement_proposals`（既定2。host.tomlでは変えない）に達しているあいだ、supervisorは印の付いたfindingに新しいplannerを立てない。findingは`open`のまま待ち、1つ終われば印の古い順に立つ。
- **優先度**: 改善のproposalのtaskは`normal`以下。plan reviewがpassのときに、findingに紐づいたproposalの`high`以上のtaskを`lower_priority`で`normal`に下げる（[Finding planners](finding-planners.md)の6）。
- **test**: `domain::kpi::observe`のunit test（目標割れのsubject・根拠・印、根拠の無い目標割れ）、`observer`のunit test（入力のキーとpromptの読み方。flakyなtestの読み方（e2eの関門のtestごとの回数を含む）は`prompt_explains_how_to_record_the_flaky_tests`）、`tests/it/runtime_observer.rs`の`observe_reads_the_kpis_and_the_improvements_and_keeps_one_kpi_finding_per_subject`（`dagq.toml`の目標と上限が入力に載り、同じsubjectの`kpi`のfindingが1件にまとまる）と`observe_reads_the_forecast_errors_and_a_forecast_breach_becomes_a_forecast_finding`（下の「完了見込みの誤差」）。

## 完了見込みの誤差

[ADR-0070](../../adr/0070-forecast-snapshots-and-scoring.md)の決定5（task 477）。答え合わせのKPI（`forecast.*`、[kpi](kpi.md#完了見込みの答え合わせ)）と日次レポートの欄はtask 476が実装した。

- **入力**: 入力の`kpi.forecast`（上）に、日と週の期間ごとの答え合わせの指標（p50の誤差の秒と絶対値と比、p90の的中率、遅れ側・早い側の割合を`all`・`target=*`・`change=*`・`band=*`・`method=*`・`marks=0` / `marks=1+`の層で）と件数が載る。`marks=0`は見積もり方法そのものの誤差、`marks=1+`は計画の変更を含む。
- **偏りの判定**: 「偏りが続く」は`forecast.*`の目標（`dagq.toml`の`[kpi.targets]`。planner が書く。初めの案はp50の誤差の比の中央値が±25%以内、p90の的中率が75%以上）の目標割れ（`breach`）だけで、別の経路は作らない。observerは`kpi.forecast`の数字から自分で偏りを判定しない。
- **finding**: `forecast.*`のKPIの目標割れは`kpi.breaches`に`finding_kind: forecast`、`subject`は接頭辞`forecast.`を除いた`<指標>/<層>`（例: `p50_error_ratio/change=feature`、`p90_hit_rate/all`）で載り（`domain::kpi::observe::finding_kind`と`subject`）、observerは種類`forecast`・対象`queue`のfindingを記録か更新する。根拠・日と週のまとめ・解消・`--propose`はKPIの目標割れと同じで、改善のproposalの上限と優先度（ADR-0051の決定25・26）も同じく効く。`blocked`のaskにはせず、人には上げない。
- 見込みのsnapshotのeventは記帳のeventとしてobserverを起こさない。`dagq forecast`は読み取りのコマンドで、promptの読むコマンドに並ぶ。
- **test**: `domain::kpi::observe`のunit test `a_forecast_breach_is_a_forecast_finding_and_its_scoring_is_listed`と、`tests/it/runtime_observer.rs`の`observe_reads_the_forecast_errors_and_a_forecast_breach_becomes_a_forecast_finding`（p90を過ぎて完了したtaskの答え合わせが入力に載り、p90の的中率の目標割れが種類`forecast`のfindingになり、`kpi`のfindingにはならない）。

## 人が要る見立てだけをblockedにする<a id="人が要る見立てだけをblockedにする未実装"></a>

[ADR-t451-1](../../adr/2026-10-02-t451-1-ai-decides-recommendable-asks-and-escalates-only-the-undecidable.md)の決定2（ADR-0047決定4・23をamends。task 1319）。observerは見立てが人を要るfindingにだけ`blocked`のaskを上げ、ほかの見立てはfindingに残す。

- **prompt**（`observer::observer_prompt`）: 問題ごとに見立て（次に何が起きるべきか、それを人がする必要があるか）を出させる。見立てが「待てば解ける」「leave it」のものは`blocked`のaskにせず、findingの`--detail`に見立てを書いて記録・更新だけにする（人は`dagq findings`で見る）。`blocked`のaskにするのは、見立てが人の判断（`--because scope`: 受け入れ条件・範囲・ADR・goalの決定、`--because discard`: 成果を捨てるか）か、runtimeと復旧jobが行えない人の手の操作（`--because recovery_failed`）を要るときだけで、`authentication`・`cost`はqueueの控えのaskが持つのでblockedにしない。askには人が選べる次の手をoptionに、見立てを推奨のoption（`--recommend`。optionのどれかか、runtimeが足す`propose` / `dismiss`）と確信度（`--confidence high|low`）で載せる（[ask](ask.md#aiの推奨と確信度未実装)）。終わりの1行には、askにせずfindingだけにした件数も書かせる。
- **CLI**: `ask --kind blocked`は`--recommend`が無ければ（空白だけも）理由つきで拒む（`NewAsk::check_asker`を`Dialogue::ask`が呼ぶので、CLIとqueue serviceの`ask`の両方。[ask](ask.md#aiの推奨と確信度未実装)）。推奨がleave it / waitに当たるかはCLIでは判定しない（promptの規則）。
- **集計**: `observe_finished`の`findings_without_ask`は、そのobservationが記録か更新し（`finding_recorded` / `finding_updated`の`by: observer`）閉じなかったfindingのうち、そのobservationが開いた`blocked`のaskも、終わった時点でopenな`blocked`のaskも無いものの件数で、idは`without_ask_finding_ids`（`SqliteQueue::written_by`の`without_ask`）。skippedの`observe_finished`は0と空。[Stats](stats.md#aiの推奨と確信度の集計)の`recommendations.observer`がwindowの合計を`blocked`のaskの件数と並べ、`recommendations.decided_without_ask`の`blocked`（AIが決めてaskにしなかった判断）に足す。
- findingごとにopenな`blocked`のaskは1件のまま（決定23）。askの無いfindingは普通の状態で、人は`dagq findings`で見る。
- **test**: `observer`のunit test `prompt_keeps_a_wait_or_leave_it_reading_to_the_finding`（promptの文）、`application::commands::dialogue`のunit test `a_blocked_ask_without_a_recommendation_is_refused_before_the_store`、`domain::stats::recommendations`のunit test `the_observers_findings_without_an_ask_stand_next_to_the_blocked_asks`、`tests/it/cli_dialogue.rs`の`the_observer_still_records_findings_and_raises_blocked_asks`（CLIの拒否と理由）、`tests/it/queue_service_findings.rs`の`the_observer_writes_findings_through_the_service_as_the_command_line_does`（serviceの拒否）、`tests/it/runtime_observer.rs`の`observe_records_findings_and_a_blocked_ask_and_advances_the_cursor`（agentの`--recommend`の無いblockedの拒否と`findings_without_ask`）。
