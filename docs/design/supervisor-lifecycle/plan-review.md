# Plan review (supervisor)

execの[引き継ぎ](handoff.md)を待つあいだに終わったjobと、`prepare_handoff`の時点で終わっていたjobは、捨てずに回収してverdictを適用する（task 1425。新しいjobは始めず、verdictでreadyになったtaskも待ちのあいだはclaimしない）。走っていて止めたjobは、引き継いだsupervisorが最初のpassに入る前に自分のtokenの未完了行を`interrupted`（error: `stopped for the supervisor handoff`）で閉じる。候補が無くても閉じ、transcriptをtransactionの前に`read_before`で読んで既存のclose経路で区間の`session_closed`（`reason: job_finished`、model / effortを含む）を記録する。他のtokenの行は触らない。候補が残れば以後のpassでreviewをやり直し、interruptedはattemptに数えない（task 1087）。

[ADR-0044](../../adr/0044-findings-proposals-from-findings-and-quiet-observer.md)の決定10〜15・17（task 281）。submitされたproposalを、supervisorが起動するheadlessのplan review jobが検査し、そのverdictと人のanswerをruntimeが適用する。use caseは`src/application/supervise/plan_review.rs`、storeは`src/infrastructure/plan_reviews.rs`（port `PlanReviewStore`）、verdictの型と順序は`src/domain/plan_review.rs`。run slotは使わず、observerと同じくloopの各passで進める（`--once`のloopは走っているplan reviewを待ち、passでverdictかanswerを適用したらもう1 pass回ってreadyになったtaskをclaimしてから終わる。`--once`で立てたplannerは終わらせない）。drain中（`stop`、provisioningの失敗）は新しいplan reviewを始めず、reviseの配送もしない（走っているjobとanswerの適用は続ける）。

1. **記録**（schema v27、`migrations/0027_plan_review.sql`）: jobは`plan_reviews`の1行（`proposal_id`、`attempt`、`supervisor_token`、`dir`、`started_at`、`finished_at`、`outcome` = `pass` / `revise` / `concern` / `failed` / `interrupted`、`verdict`のJSON、`error`）。未完了の行は部分unique indexで1つまでなので、queue全体で同時に1つ。`proposals`に`review_hold`（`failed` / `concern`: plan reviewが自分では取り直さない）、`revise_reasons`（plannerに渡す指摘のJSON配列）と`revised_at`（差し戻した時刻）、`revise_sent_at` / `revise_planner_id`（配送を取った時刻と渡した相手。nullならまだ渡していない）、`unresponsive_at`を足した。`submit`（出し直しを含む）はこれらをすべて消す。askのkindに`approve_plan`を足した。eventはrun_eventsがtaskかgoalを要るので、proposalの最初のtask（ID最小）に`proposal_id`付きで記録する。
2. **順序**（`next_to_review`）: 対象は`submitted`で`review_hold`が無く、`submitted`のtaskを持つproposal。`interrupt`の優先度のsubmittedのtaskを持つものが先、次にsubmitの古い順、次にID順。gateは飛ばさない。
3. **開始**（`begin_plan_review`、`BEGIN IMMEDIATE`）: 未完了の行があり、そのsupervisorの登録が生きていれば（heartbeatが30秒以内）始めない。そうでない行は`interrupted`で閉じる（supervisorが死んだjobの引き継ぎ）。対象であることを再検査し、行を作って`<queue dir>/plan-reviews/<行のID>/`を`dir`にし、`plan_review_started`（`proposal_id`、`plan_review_id`、`attempt`、`dir`、`session_id`、jobを起動するrepositoryのcheckoutの`cwd`、proposalの特徴の`features`（`{origin, follow_up_depth, related_score, related, revise_count}`。task 579、書き込みのロックの前に読み、読めなければnull。規則は[kpi](kpi.md#計画の品質)）、jobを起動するmodel / effortと出どころの`launch`（`[roles.plan_review]`から。無ければ`source: default`で何も渡さない。[Actor model](actor-model.md)、task 580。区間の`session_opened`にも写る））を記録する。promptを`prompt.txt`に書き、`AgentProvider::headless_command`（権限の意図`PLAN_REVIEW_ACCESS`＝`read_files_and_queue_cli`。Claudeでは`claude -p --allowedTools Read Grep Glob 'Bash(dagq:*)'`でpromptはargvでなくstdin（task 1560。[Agent provider lifecycle](../provider-lifecycle.md#headless-jobのinterface)の「promptの渡し方」）、`launch`がmodel / effortを持てば`--model` / `--effort`も）をrepositoryのcheckoutで、`DAGQ_ROLE=plan-review-job`・`DAGQ_ACTOR_ID=plan-review-job:<proposal id>:<attempt>`と、queue serviceのsocketとjobのtokenのfile付き（`DAGQ_QUEUE`は渡さず、jobの`dagq`はクライアントモードでserviceに送る。[Queue service](../queue-service.md#クライアントモード)）で起動し、stdout / stderrを`review.out` / `review.err`に書く。timeoutは`AgentProvider::review_timeout`。

`plan_review_prompt`は`PlanReviewPrompt`（promptの文と`PromptBytes`）を返し、promptの節を必須の節と省いてよい節に分けて上限の中に収める。上限の値と理由は[Prompt](prompt.md#plan-reviewの上限)が持つ。
   - **必須の節**（指示と検査とverdictの形、proposalのtaskの全field、proposalのtaskの予想するファイル、goal、`lint`、最後の言語の指示）は省かない。合わせて`PLAN_REVIEW_REQUIRED_LIMIT`を超えるとき（proposalのtaskが多い、1つのtaskやgoalの本文が巨大など）だけ、黙って切らずに、1,000 byte（`STUB_BYTES`）より大きいものを大きい順に（同じ大きさなら節の順・節の中の順）1行の代わり（`{"id", "title", "left_out_bytes", "read_with"}`、予想するファイルの代わりは`title`なし。`read_with`はtaskなら`dagq show ID --full`、goalなら`dagq goal show ID --full`、予想するファイルなら`dagq show ID --full`の宣言pathと、無ければ`dagq related ID`。`lint`は節ごと`dagq lint --proposal ID`の案内）に替えて収める。代わりの行だけでも収まらなければ、task・予想するファイル・goalの節をそれぞれ1行の案内（`dagq proposal show ID`で一覧、`dagq show ID --full`・`dagq goal show ID --full`で中身）に替え、重さの予測の対象のIDの並びも`dagq proposal show ID`への案内にする。替えたことと理由（必須の節のbyte数と上限）はtaskの節の頭に書き、`PromptBytes.over_limit`に残す。読む経路はplan reviewのjobの今の権限（`read_files_and_queue_cli`で、roleの`plan-review-job`は`queue.read`だけ）で打てる読むだけの`dagq`のコマンドに限り（ADR-t1566-1決定3）、jobのdirのファイルには退避しない（Claudeの`Read`がrepositoryの外のjobのdirを読めるかに頼らない）。
   - **省いてよい節**（CLIで読み直せるもの）は、残す順に衝突の多いファイル、重複と実装済みの候補（proposalのtaskの順）、他のproposal（proposal単位）、人が答えたask（新しい順）、全文、要約。どれも自分の上限と、全体の上限`PLAN_REVIEW_PROMPT_LIMIT`から必須の節と前の節が使った残りの小さい方に収まる行だけを順に載せ、収まらない行は飛ばして次の行を試す（1つの巨大な行が残りを塞がない）。省いてよい6節それぞれの注記の分（`OMISSION_NOTE_BYTES`×6）を全体の上限から先に空けておくので、promptは全体の上限を超えない。
   - **全文の選ぶ順**: 全文の候補（重複の候補に載ったものと、proposalのtaskと同じhotspotを触ると予想されるもの。task 591の判定のまま）を、proposalのtaskが依存するもの → proposalと共有するhotspotの数の多い順 → proposalのtaskの予想するファイルと重なる数の多い順（`claim_defer::touches`をどちら向きにも当てる） → 重複の候補の中の位置（`related`と`search`の順位の良い方）の良い順 → IDの新しい順に並べ、上限まで載せる。節もこの順に並ぶ。
   - **要約の選ぶ順**: 全文の候補を上の順に先に、残りをIDの新しい順に選び、載せる行はIDの新しい順（今までの形）に並べる。`full_text_below`は全文の節に実際に載ったものだけに付く。
   - **省いたことの書き方**（ADR-t1566-1決定5）: promptの冒頭で、上限で切った一覧はその件数と読むコマンドを書くと伝え、各節の末尾に省いた件数と読む方法を書く。全文は`(N more ready or in-progress tasks that meet this rule are left out by its limit of 20 tasks and 100000 bytes, the most related to the proposal first: <ID>...; read one in full with `dagq show ID --full`)`。要約は`QUEUED_TASKS`で読まなかった分の今までの注記に加えて、上限で省いた件数と`dagq list --status ready,in_progress --limit 200`・`dagq show ID --full`。人が答えたaskは`dagq asks --all`（20件を読んだときは、古いものも同じコマンドで読めると書く）、hotspotは`dagq stats`、重複の候補は`dagq related ID`と`dagq search`、他のproposalは`dagq proposal show ID`と`dagq show ID --full`。注記のIDの並びは40件（`NOTE_IDS`）までで、残りは件数。読む方法の`dagq`のコマンドは`prompt::PLAN_REVIEW_READS`に並べ、plan reviewのjobのroleがコマンドラインでもqueue serviceのクライアントとしても打てる読み取りであることをtestが確かめる。
   - **byte数の記録**（ADR-t1566-1決定6）: jobを終える`plan_review_finished`と`plan_review_failed`（promptを書いた後にproviderのprocessを起動できなかったときを含む）に`prompt_bytes`（`total`、`limit`、節ごとの`sections`（`instructions`・`tasks`・`expected_files`・`goals`・`lint`・`other_proposals`・`summaries`・`full_text`・`precedents`・`hotspots`・`candidates`・`language`。合計が`total`で、`instructions`は固定の文と重さの予測の対象のIDの並び）、節ごとの省いた・替えた件数の`omitted`（要約は`QUEUED_TASKS`で読まなかった分を含む）、必須の節を替えた理由の`over_limit`（替えなければnull））を記録する。promptを組み立てる前に失敗した`plan_review_failed`は`prompt_bytes: null`: jobのdirを作れない・材料を読めないときと、行き先が人になるとき（`--no-claude`で、役割がproviderを名指さないか、名指したproviderともう一方のproviderのどちらも使えない。`start_plan_review`の`PlanReviewRoute::Manual`で、promptを作らずに`PlanReviewFailure::default()`で失敗にする）。`prompt_bytes`が付くのはpromptを書いた後の失敗（providerのprocessを起動できない、非0終了、timeout、verdictが無い・適用できない）。
5. **verdict**（`PlanReviewVerdict`、全体か最外の`{...}`、未知のフィールドは拒否）: `{"verdict": "pass" | "revise" | "concern", "reasons": [{"text", "codes": [...]}]（[差し戻しの分類コード](#差し戻しの分類コード)。文字列だけの項目も読む）, "summary", "actions": [...], "reopen": [{"task_id", "reason"}], "precedents": [ask id], "predictions": [{"task_id", "size": "S" | "M" | "L", "nature": "mechanical" | "implementation" | "design_judgment" | "investigation", "uncertainty": 0〜1, "expected_output_tokens": 正の整数, "rework_probability": 0〜1, "reason"}], "recommendation": "ready" | "send_back" | "cancel", "confidence": "high" | "low", "reason_category": "scope" | "discard" | null}`（最後の3つは`concern`の推奨で、[AIが決めるconcern](#aiが決めるconcern未実装)）。`predictions`は未知のフィールドの拒否の対象外で、どんな形でもverdictの解釈を失敗させない（生のJSONのまま受け、6で検査する。`domain::prediction::parse_predictions`）。`actions`は`add_dependency`（`task_id`、`depends_on`）/ `lower_priority`（`task_id`、`priority`）/ `cancel_duplicate`（`task_id`、`duplicate_of`）だけで、`pass`のときだけ適用する。findingに紐づいたproposal（改善のproposal）では、passの適用がverdictの`actions`の後に、submittedのtaskで`normal`より上のものに`lower_priority`（`normal`）を当てる（ADR-0051の決定26、[Finding planners](finding-planners.md)の6）。
6. **適用**（`finish_plan_review`、1トランザクション）: 行がまだ自分の未完了の行でなければ何もしない。proposalがもう`submitted`でないか保留されていれば、行を`interrupted`で閉じて何もしない。jobの開始（その`plan_review_started`のevent）より後にproposalのいずれかのtaskに`task_edited`があれば（[ADR-0041](../../adr/0041-on-demand-planners-proposals-submitted-and-plan-review-job.md)の決定9。eventのIDで前後を比べる）、verdictはpass / revise / concernのどれも古い内容へのものなので適用しない。行を`interrupted`で閉じて（`verdict`は残し、`error`に`task N of the proposal was edited during its review`）、`plan_review_discarded`（`proposal_id`、`plan_review_id`、`attempt`、`verdict`、`edited`、`error`）を記録する。proposalは`submitted`で保留もないままなので、次のpassで編集後の内容をplan reviewにかけ直す（`interrupted`の行は`attempt`に数えない）。検査中でないsubmittedのtaskの編集と、他のproposalのtaskの編集は、verdictの適用を妨げない（次のplan reviewが新しい内容を読む）。runtimeは`revise`で`revise_count`が2（`MAX_PLAN_REVISES`、runのreviewと同じ）以上なら`concern`にする（`overridden`）。`precedents`のaskは`precedent: ask N (kind) asked: … — a person answered: …`の行にして、reviseの指摘の後ろとconcernのaskのquestionに足す。

   - `concern`: `recommendation`と`confidence`を持ち、`high`で`reason_category`が`null`の`ready` / `send_back`は、上の`pass` / `revise`として適用する（下の[AIが決めるconcern](#aiが決めるconcern未実装)）。それ以外は`review_hold = concern`にし、`approve_plan`のask（proposalの最初のtask、runなし、`asked_by: plan_review`、options `ready` / `send_back` / `cancel`、questionにsummary・上書きの理由・reasons・先例・`prompt.txt`のpath）を同じトランザクションで作り、適用の後にinboxへ`cmux notify`する。
