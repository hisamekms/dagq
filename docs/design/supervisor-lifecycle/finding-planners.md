# Finding planners (supervisor)

[ADR-0047](../../adr/0047-irregularities-in-three-layers-recovery-job-ask-reasons-and-goal-review.md)の決定18〜20（ADR-0044の決定を引き継いだもの。task 295）。proposalを求める印の付いたfindingごとに、supervisorがruntimeのplannerを1つ立て、plannerがproposalを作ってplan reviewに出すか、findingを`dismissed`にするか、人に聞く。人の承認は一律には求めず、人に聞くのはplannerが`planner_question`にしたときとplan reviewが`concern`にしたときだけ。use caseは`src/application/supervise/finding_planner.rs`、storeは`src/infrastructure/finding_planners.rs`（port `DraftPlannerStore`に足したメソッド）、規則は`src/domain/finding.rs`（`FindingAnswer`、`mark_for_proposal`、`check_link`、`settle`、`MAX_FINDING_PLANNERS`）、promptは`application::prompt::finding_planner_prompt`。run slotは使わず、[Plan review (supervisor)](plan-review.md#plan-review-supervisor)の`tend_planners`の中で、reviseの配送、`planner_question`のanswerの配送、[Draft planners](draft-planners.md#draft-planners-supervisor)の後に進める（drain中は立てない）。

1. **印**: findingの`propose_reason` / `propose_requested_at`。(a) observerが`finding record --propose '<why>'`で付ける（[Observer](observer.md)）。(b) 人がaskに`propose`（または`propose: <why>`）と答えると、`answer`の同じトランザクションでruntimeが付ける（下の5）。印は`open`のfindingにだけ付き、`proposed`のfindingには付かない。
2. **対象**（`planner_findings`、印の古い順、次にID）: statusが`open`で印があり、閉じていないruntimeのplanner（`planners.finding_id`）が無く、closeされていない`planner_question`（`asks.finding_id`）が無く、今の印（`marked_at` = `propose_requested_at`）の`finding_planner_exhausted`が無いfinding。
3. **立てる**（`open_finding_planners`）: runtimeが立てたplannerで生きているものが`--runtime-planners`（reviseとdraftのplannerと共有、run slotとは別、人が開いたplannerは数えない）未満のあいだ、`open_finding_planner`で立てる。storeは`BEGIN IMMEDIATE`で対象の条件を再検査してから`planners`の行（`origin: runtime`、`finding_id`）と`finding_planner_opened`（`finding_id`、`planner_id`、`attempt`、`ask_id`、`propose_reason`）を書くので、2つのsupervisorや同じsupervisorの2つのpassが同じfindingに立てない。eventはfindingの対象（runならrunとtask、task、goal、queueなら何にも付かないqueueのevent）に付く。workspaceは`[<repo>]planner#<id> - finding <finding-id>`。
4. **初期prompt**（`finding_planner_prompt`）: findingの種類・対象・subject・影響・回数・最初と最後に見た時刻・記録者・印の理由・見立て、根拠のevent（`findings ID --full`と同じもの）、根拠を読むCLI（`findings ID --full`、`events --all --full`と絞り込み、`timeline RUN`）、findingに紐づくask（observerの`blocked`、人の`propose`のanswer、前のplannerの`planner_question`）とそのanswer、対象のgoal（findingのgoal、またはtask / runのtaskのgoal。無ければ`dagq goal list`を示す）とそのtask、手順。手順は、`dagq search` / `related`で既存のtaskと実装済みを確かめてから、(1) 既存のopenなgoalにtaskを足して`dagq submit ID... --finding <id>`、(2) 範囲に入るgoalが無ければdraftのgoalとtaskを書いて`dagq submit --goal GOAL --finding <id>`（新しいgoalでも人の承認は要らない）、(3) 手当てしない（既存のtaskで足りる、もう起きていない、割に合わない）なら`dagq finding dismiss <id> --reason`、(4) 人が決めるもの（計画の意図や範囲、受け入れ条件、goalのconstraintsやADRとの矛盾、先例との食い違い、大きく取り消しにくい変更）だけ`dagq ask --finding <id> --kind planner_question --because scope --option propose --option dismiss`で聞いて止まる、のどれか1つ。`--context`の冒頭は`finding <id>（<kind>）から`。人のanswerを運ぶplannerには元の質問とanswerを載せる。
5. **askの「提案にする」**（`answer`の中、`finding_planners::apply_answer`）: findingに紐づいた`blocked`のaskには、askを作るときにruntimeがoptionsの末尾に`propose`と`dismiss`を足す（`finding::with_finding_options`）。`stalled`のaskには`propose`を足す（`with_propose_option`。復旧jobが足すoptionの後）。askが載せたoptionへの答えだけを適用する: `propose[: <why>]`はfindingに印を付け（`resolved` / `dismissed`のfindingは`open`に戻す。既に`proposed`か印のある`open`なら変えない。理由を書かなければ`a person answered propose to ask N`）、`finding_status_changed`（戻したとき）と`finding_updated`（`changed: ["propose_reason"]`、`ask_id`）を記録する。findingの無い`stalled`のaskでは、先にaskのkindを種類に、askのrun（無ければtask、queue）を対象に、questionの最初の行を要約、全体を見立て、askの`ask_opened`を根拠にしたfindingを記録し（同じ種類・対象・subjectの閉じていないfindingがあればその更新）、askの`finding_id`に書く。`dismiss[: <why>]`はaskのfindingを`dismissed`にする。適用したanswerの`ask_answered`は`finding_id`・`finding_applied`（`propose` / `dismiss`）・`runtime_delivers: true`を持ち、attentionにならない。`blocked`のaskはその場で閉じ（`ask_closed`も記録する）、`stalled`のaskはrunのstallの見張りが閉じる（`propose`は`wait`と同じく、sessionをそのままにしてidleの数え直しを始める）。それ以外の答えと`planner_question`の答えは従来どおり。
6. **submitでの紐づけ**（`submit_linking`、`submit`と同じトランザクション）: `dagq submit ... --finding ID`（繰り返し可）で名指したfindingと、submitするworkspace（`CMUX_WORKSPACE_ID`）のruntimeのplannerが立てられたfindingを、proposalに紐づける。`open`のfindingは`proposed`になり`proposal_id`を持つ（`finding_status_changed`、`to: proposed`、`proposal_id`、`by: planner | person`）。同じproposalで既に`proposed`（resubmit）は変えない。名指したfindingが紐づけられない（他のproposalで`proposed`、`resolved` / `dismissed`）ならsubmit全体が失敗する。plannerの自分のfindingは`open`のときだけ紐づける。紐づいたproposalはplan review（ADR-0047の決定10〜15）を通る。follow_upの自動採用の上限（決定16）はfindingのproposalには掛からない（draftの出どころが無いので`check_adoptions`の対象外）。
7. **終わったproposal**（`settle_findings`、各passで立てる前）: `proposed`のfindingの紐づいたproposalが`canceled`になったか、そのtaskがすべて`completed` / `canceled`になったら、1つ以上`completed`なら`resolved`（`its proposal ended: N of M tasks completed`）、1つも無ければ`open`に戻す（`every task of its proposal was canceled` / `its proposal was canceled`）。`open`に戻すときは`proposal_id`と印を消すので、もう一度proposalにするには新しい印が要る。`finding_status_changed`は`proposal_id`と`by: runtime`を持つ。
8. **3回まで**: plannerがfindingを決めずに終わった（sessionが終わった、idleで`/exit`された）findingは次のpassで再び対象になる。今の印の後に立てたplannerが`MAX_FINDING_PLANNERS`（3）件あるfindingは（人のanswerを運ぶとき以外は）立てずに`finding_planner_exhausted`（`finding_id`、`planners`、`marked_at`、`reason`）を記録する。attentionは`decide the finding in a planner`（kind `finding_planner_exhausted`、findingの対象のtask / run、`last_error`に`finding N: <summary>`。印のある`open`のあいだ`status`に出る）で、人が開いたplannerで`submit --finding`するか`finding dismiss`する。
9. **planner_question**: `planner_question`は`--finding ID`を持てる（taskもrunも無くてよい。`NewAsk::validate`と`check_ask_kind`）。answerの行き先（`planner_answer_route`）はfindingで決める: runtimeのplannerが一度も立っていないfindingなら人（人が開いたplannerの質問）。閉じていないそのfindingのruntimeのplannerがあれば、plannerが自分で作ったaskはplannerがaskの後にidleになってから、他の人が作ったaskはplannerがidleなら、draftと同じく`claim_planner_answer`で配送を取ってから（`planner_answer_claimed`はfindingの対象に付く）`answer to ask <id>: <answer>`を打ち込み`ask_delivered`で閉じる。無ければ、findingがまだ対象（`open`、印あり、使い切っていない）なら上限の中で新しいplannerがanswerを持って立ち、そうでなければsupervisorが`planner_answer_closed`で閉じる。打ち込みの失敗は`ask_delivery_failed`（findingの対象に記録）でinboxに任せる。askとanswerの配送のevent（`ask_opened`・`ask_answered`・`ask_delivered`・`ask_delivery_failed`・`planner_answer_closed`）は、queueが対象のfindingではqueueのeventになる（`QUEUE_EVENT_KINDS`）。
10. **終わり**: runtimeのplannerは、closeされていない自分のfindingの`planner_question`があるあいだと、打ち込んだanswerの後にまだidleになっていないあいだは`/exit`されない。それ以外でidleになれば`/exit`され、終わったworkspaceは閉じられる（`end_runtime_planners`）。
11. **test**: `tests/it/finding_planner.rs`がcmuxのdoubleとstubのplan reviewで、印のあるfindingにだけplannerが1つ立ち（次のpass、上限を上げたpass、直接の`open_finding_planner`でも2つ目は立たない）、promptの中身、plannerのworkspaceからのsubmitでfindingが`proposed`になりproposalに紐づくこと、他のproposalで`proposed`のfindingを名指したsubmitの失敗、plan reviewのpassでtaskが`ready`になりplannerに`/exit`が送られること、taskのcancelでfindingが印なしの`open`に戻ること、`blocked`のaskのoptionsと`propose` / `dismiss`のanswerの適用（askが閉じ、attentionにならない）、`stalled`のaskの`propose`でfindingが作られること、findingへの`planner_question`のanswerがplannerに打ち込まれること、決めずに終わったplannerの後に次が立ち3回で`finding_planner_exhausted`とattentionになること、人の`submit --finding`でそれが消えることを確かめる。規則は`src/domain/finding.rs`のunit test。
