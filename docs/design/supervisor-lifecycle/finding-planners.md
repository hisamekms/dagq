# Finding planners (supervisor)

[ADR-0047](../../adr/0047-irregularities-in-three-layers-recovery-job-ask-reasons-and-goal-review.md)の決定18〜20（ADR-0044の決定を引き継いだもの。task 295）。proposalを求める印の付いたfindingごとに、supervisorがruntimeのplannerを1つ立て、plannerがproposalを作ってplan reviewに出すか、findingを`dismissed`にするか、人に聞く。人の承認は一律には求めず、人に聞くのはplannerが`planner_question`にしたときとplan reviewが`concern`にしたときだけ。use caseは`src/application/supervise/finding_planner.rs`、storeは`src/infrastructure/finding_planners.rs`（port `DraftPlannerStore`に足したメソッド）、規則は`src/domain/finding.rs`（`FindingAnswer`、`mark_for_proposal`、`check_link`、`settle`、`MAX_FINDING_PLANNERS`）、promptは`application::prompt::finding_planner_prompt`。run slotは使わず、[Plan review (supervisor)](plan-review.md#plan-review-supervisor)の`tend_planners`の中で、reviseの配送、`planner_question`のanswerの配送、計画の依頼のplanner、[Draft planners](draft-planners.md#draft-planners-supervisor)の後に進める（drain中は立てない）。

1. **印**: findingの`propose_reason` / `propose_requested_at`。(a) observerが`finding record --propose '<why>'`で付ける（[Observer](observer.md)）。(b) 人がaskに`propose`（または`propose: <why>`）と答えると、`answer`の同じトランザクションでruntimeが付ける（下の5）。印は`open`のfindingにだけ付き、`proposed`のfindingには付かない。
2. **対象**（`planner_findings`、印の古い順、次にID）: statusが`open`で印があり、閉じていないruntimeのplanner（`planners.finding_id`）が無く、closeされていない`planner_question`（`asks.finding_id`）が無く、今の印（`marked_at` = `propose_requested_at`）の`finding_planner_exhausted`が無いfinding。
3. **立てる**（`open_finding_planners`）: runtimeが立てたplannerで生きているものが上限`runtime_planners`（`--runtime-planners`か`dagq.toml`の`[supervisor] runtime_planners`、既定1。[Run environment](run-environment.md)の`[supervisor]`。revise・draft・計画の依頼（[inboxからの計画の依頼](plan-planners.md#inboxからの計画の依頼)）のplannerと共有、run slotとは別、人が開いたplannerは数えない）未満のあいだ、`open_finding_planner`で立てる。storeは`BEGIN IMMEDIATE`で対象の条件を再検査してから`planners`の行（`origin: runtime`、`finding_id`）と`finding_planner_opened`（`finding_id`、`planner_id`、`attempt`、`ask_id`、`propose_reason`）を書くので、2つのsupervisorや同じsupervisorの2つのpassが同じfindingに立てない。同じトランザクションで改善の数を数え、上限に達していれば何も書かずに`FindingPlannerStart::AtLimit`を返し、そのpassでは後のfindingにも立てない（下の11）。eventはfindingの対象（runならrunとtask、task、goal、queueなら何にも付かないqueueのevent）に付く。plannerはworkspaceを持たず、非対話のwrapperがbackgroundで起動する（[runtimeのplannerの経路](plan-planners.md#runtimeのplannerの経路)）。
4. **初期prompt**（`finding_planner_prompt`）: findingの種類・対象・subject・影響・回数・最初と最後に見た時刻・記録者・印の理由・見立て、根拠のevent（`findings ID --full`と同じもの）、根拠を読むCLI（`findings ID --full`と、記録を読むCLI（`prompt::RECORD_READING`、ADR-0044の決定22、task 420: `dagq events --full --task ID`と絞り込み（`--run` / `--goal` / `--kind` / `--since` / `--until`。`--kind`が無ければattentionだけなので、全種類は`--all`を足す）と`dagq timeline RUN`））、findingに紐づくask（observerの`blocked`、人の`propose`のanswer、前のplannerの`planner_question`）とそのanswer、対象のgoal（findingのgoal、またはtask / runのtaskのgoal。無ければ`dagq goal list`を示す）とそのtask、手順。手順は、`dagq search` / `related`で既存のtaskと実装済みを確かめてから、(1) 既存のopenなgoalにtaskを足して`dagq submit ID... --finding <id>`、(2) 範囲に入るgoalが無ければdraftのgoalとtaskを書いて`dagq submit --goal GOAL --finding <id>`（新しいgoalでも人の承認は要らない）、(3) 手当てしない（既存のtaskで足りる、もう起きていない、割に合わない）なら`dagq finding dismiss <id> --reason`で理由を書く、(4) 自分で決めきれないもの（[推奨が出せればplannerが決める](#推奨が出せればplannerが決める未実装)の条件: 決定41の`scope`・`discard`に当たり材料で決めきれないものと確信度`low`のもの）だけ`dagq ask --finding <id> --kind planner_question --because scope --recommend ... --confidence ... --option propose --option dismiss`で聞いて止まる、のどれか1つ。`--context`の冒頭は`from finding <id> (<kind>)`。verify・paths・evidenceは`prompt::repository_rules`の順（AGENTS.md → CLAUDE.md → README・CIの設定・buildの設定 → `planner_question`）で決めさせる（[Prompt](prompt.md#repositoryの規則を読む順)）。人のanswerを運ぶplannerには元の質問とanswerを載せる。promptは全体`FINDING_PLANNER_PROMPT_LIMIT`と節ごとの上限の中に収める（task 1571。値と理由は[Prompt](prompt.md#goal-reviewrunのreview復旧jobruntimeのplannerの上限)）: 見立て（必須。超えたら切って`over_limit`に書く）とsummary・subject・印の理由は切り、根拠のeventは新しい順に1件ずつのJSONの行で選び、省いたeventの件数・IDと`dagq findings ID --full`（1件なら`dagq events --full --all --after <ID - 1> --limit 1`）を書く。askは新しい順、goalは欄とtaskの行を切る。promptのbyte数は`planner_prompt_written`（`prompt: finding`。[Session prompts](session-prompts.md)）に記録する。
5. **askの「提案にする」**（`answer`の中、`finding_planners::apply_answer`）: findingに紐づいた`blocked`のaskには、askを作るときにruntimeがoptionsの末尾に`propose`と`dismiss`を足す（`finding::with_finding_options`）。`stalled`のaskには`propose`を足す（`with_propose_option`。復旧jobが足すoptionの後）。askが載せたoptionへの答えだけを適用する: `propose[: <why>]`はfindingに印を付け（`resolved` / `dismissed`のfindingは`open`に戻す。既に`proposed`か印のある`open`なら変えない。理由を書かなければ`a person answered propose to ask N`）、`finding_status_changed`（戻したとき）と`finding_updated`（`changed: ["propose_reason"]`、`ask_id`）を記録する。findingの無い`stalled`のaskでは、先にaskのkindを種類に、askのrun（無ければtask、queue）を対象に、questionの最初の行を要約、全体を見立て、askの`ask_opened`を根拠にしたfindingを記録し（同じ種類・対象・subjectの閉じていないfindingがあればその更新）、askの`finding_id`に書く。`dismiss[: <why>]`はaskのfindingを`dismissed`にする。適用したanswerの`ask_answered`は`finding_id`・`finding_applied`（`propose` / `dismiss`）・`runtime_delivers: true`を持ち、attentionにならない。`blocked`のaskはその場で閉じ（`ask_closed`も記録する）、`stalled`のaskはrunのstallの見張りが閉じる（`propose`は`wait`と同じく、sessionをそのままにしてidleの数え直しを始める）。それ以外の答えと`planner_question`の答えは従来どおり。
6. **submitでの紐づけ**（`submit_linking`、`submit`と同じトランザクション）: `dagq submit ... --finding ID`（繰り返し可）で名指したfindingと、submitしたruntimeのplannerが立てられたfindingを、proposalに紐づける。submitしたplannerは、そのturnの環境の`DAGQ_PLANNER_ID`で引いたplannerの行のbackgroundのhandle（行の`workspace_id`）で決まり、それがproposalの持ち主になる（`CMUX_WORKSPACE_ID`は、cmuxのworkspaceで動く人のplannerのときだけ使う）。`open`のfindingは`proposed`になり`proposal_id`を持つ（`finding_status_changed`、`to: proposed`、`proposal_id`、`by: planner | person`）。同じproposalで既に`proposed`（resubmit）は変えない。名指したfindingが紐づけられない（他のproposalで`proposed`、`resolved` / `dismissed`）ならsubmit全体が失敗する。plannerの自分のfindingは`open`のときだけ紐づける。紐づいたproposalはplan review（ADR-0047の決定10〜15）を通る。
   改善のproposalのtaskは個別の優先度を持たずgoalから継ぐ（ADR-t1971-1決定4）。
   plannerの初期promptは`--priority`を付けず、受け入れ条件に要るときだけ`normal`以下の既存のgoalに入れ、ほかは新しいgoal（改善は`normal`以下）かgoalの無いtaskにするよう書き、上限はtaskの値でなくgoalと所属で守る（plan reviewが見て外れれば`revise`）。
   findingのplannerが作ったtaskは記録の由来が`ai`なので、passの適用がsubmittedのtaskのAIが置いた個別の優先度を外す（[Plan review](plan-review.md)の6の`pass`）。
   人が作ったtask（`submit --finding`で出したものを含む）と人の出どころの優先度（taskが継ぐgoalのものを含む）には、passも`lower_priority`も触らない。
   人のconcernへの`ready`の答えと`ready --bypass-review`では外さない。
   follow_upの自動採用の上限（決定16）はfindingのproposalには掛からない（draftの出どころが無いので`check_adoptions`の対象外）。
7. **終わったproposal**（`settle_findings`、各passで立てる前）: `proposed`のfindingの紐づいたproposalが`canceled`になったか、そのtaskがすべて`completed` / `canceled`になったら、1つ以上`completed`なら`resolved`（`its proposal ended: N of M tasks completed`）、1つも無ければ`open`に戻す（`every task of its proposal was canceled` / `its proposal was canceled`）。`open`に戻すときは`proposal_id`と印を消すので、もう一度proposalにするには新しい印が要る。`finding_status_changed`は`proposal_id`と`by: runtime`を持つ。
8. **3回まで**: plannerがfindingを決めずに終わった（sessionが終わった、idleで終了の依頼を受けて終わった）findingは次のpassで再び対象になる。今の印の後に立てたplannerのうち、人の答えだけを待って終わったもの（行の`answer_wait_at`。10）を除いた数が`MAX_FINDING_PLANNERS`（3）に達したfindingは（人のanswerを運ぶとき以外は）立てずに`finding_planner_exhausted`（`finding_id`、`planners`、`marked_at`、`reason`）を記録する。attentionは`request a plan for the finding`（`AttentionNext::DecideFinding`。kind `finding_planner_exhausted`、findingの対象のtask / run、`last_error`に`finding N: <summary>`。印のある`open`のあいだ`status`に出る。`watch`も同じ文面）で、人の言葉を受けたinboxがそのfindingを参照にした計画の依頼（`dagq request add --ref finding:N`、[ADR-t1394-1](../../adr/2026-10-03-t1394-1-abolish-person-planners-and-route-planning-through-inbox-requests.md)の決定8）を記録し、依頼のruntimeのplanner（[inboxからの計画の依頼](plan-planners.md#inboxからの計画の依頼)）が決めるか、人が`DAGQ_ROLE`の無い自分のterminalで`submit --finding`するか`finding dismiss`する。
9. **planner_question**: `planner_question`は`--finding ID`を持てる（taskもrunも無くてよい。`NewAsk::validate`と`check_ask_kind`）。answerの行き先（`planner_answer_route`）はfindingで決める: runtimeのplannerが一度も立っていないfindingなら人（runtimeのplanner以外の質問。廃止前に人が開いたplannerのものなど）。閉じていないそのfindingのruntimeのplannerがあれば、plannerが自分で作ったaskはplannerがaskの後にidleになってから、他の人が作ったaskはplannerがidleなら、draftと同じく`claim_planner_answer`で配送を取ってから（`planner_answer_claimed`はfindingの対象に付く）`answer to ask <id>: <answer>`をplannerの次のturnの依頼（`turn_requested`の`what`が`answer of ask <id>`）として書き、`ask_delivered`で閉じる（plannerには何も打ち込まない）。無ければ、findingがまだ対象（`open`、印あり、使い切っていない）なら上限の中で新しいplannerがanswerを持って立ち、そうでなければsupervisorが`planner_answer_closed`で閉じる。送れなかったときは`ask_delivery_failed`（findingの対象に記録）を残し、plannerは人の答え待ちと同じく終わり、answerは新しいplannerが運ぶ（[Draft planners](draft-planners.md)の5）。askとanswerの配送のevent（`ask_opened`・`ask_answered`・`ask_delivered`・`ask_delivery_failed`・`planner_answer_closed`）は、queueが対象のfindingではqueueのeventになる（`EventKind::is_queue`）。
   人の答えだけを待って終了の依頼を受けたplanner（10）は行き先にならず、その行が閉じるまでanswerは待つ。
   前のplannerが人の答えだけを待って終わったなら、answerを運ぶplannerの初期promptにそのnoteと作った・編集したdraftも載り、そのplannerは決めずに終わったときだけ8の回数に数える。
10. **終わり**: runtimeのplannerは、自分のfindingの`planner_question`のanswerを届ける前と、送ったanswerをまだturnで読み終えていないあいだ（`headless_answer_taken`。[Draft planners](draft-planners.md)の5と同じ）は終了の依頼を受けない。それ以外でidleになれば終了の依頼（`turns/exit`）を受けてwrapperがsessionを終え、行は閉じられ、まだ動いているbackgroundのwrapperは止められる（`end_runtime_planners`。`exit_timeout`を過ぎても終わらなければwrapperを止めて`runtime_exit_timed_out`）。runtimeのplannerにcmuxのworkspaceは無く、画面も読まない。idleはwrapperがturnの終わりに書くidle markerで判じ（画面からの推定（ADR-t803-1）はどのplannerにも無い）、時間は`--planner-timeout`でなくturnの`[stall]`の上限で見る: wrapperがturnを`[stall]`の上限で止めたときに、plannerごとに1回`planner_unresponsive`（`subject: "planner"`、`finding_id`、`route`・`turn`・`outcome`）がinboxに届き、止めたturnでsessionが終わるので、plannerは`runtime_exited`で閉じられ、決めずに終わったplannerに数える（`tell_of_stopped_planner_turns`）。最後のturnがClaudeのログイン切れ・利用上限・起動の失敗で終わったplannerは、Claudeを待って終了の依頼を受けず、決めずに終わったplannerにも数えない（`provider_wall`）。どちらも[runtimeのplannerの経路](plan-planners.md#runtimeのplannerの経路)の「状態」と「使えないとき」。
    未回答の`planner_question`のほかに待つものが無いidleのplannerは、人の答えだけを待つとして終了の依頼を受け、行は`runtime_answer_wait`で閉じ、askは開いたまま残る（[ADR-t1704-1](../../adr/2026-10-05-t1704-1-human-answer-wait-releases-runtime-planner-slots.md)決定1。[runtimeのplannerの経路](plan-planners.md#runtimeのplannerの経路)の「人の答えだけを待つplannerの終わり」）。
    findingは2のとおりそのaskが閉じるまで対象にならず、answerで9の新しいplannerが続ける。
11. **改善の上限**（ADR-0051の決定25、task 433）: 動いている改善（`ImprovementLimit`、`SqliteQueue::improvements`）は、`findings.proposal_id`が指す別々のproposalで持ち主がruntimeのplanner（`owner_origin: runtime`）のもののうち`finding::improvement_running`（`settle`がまだ決めない: `canceled`でなく、終わっていないtaskがある）のものと、閉じていないruntimeのplannerのうちfindingが`open`のもの（submitすればfindingが`proposed`になり、そのproposalの方を数える）の合計。ADR-0051の決定25は数え方をproposalで書くが、runtimeのplannerも数えるのは、同時に立ったplannerがそれぞれsubmitして上限を超えないため（決定25の「plannerがすでに立った後に上限を超えることはない」）。上限は`dagq.toml`の`[kpi]`の`max_improvement_proposals`（既定2、host.tomlでは変えない。supervisorは`Ports::max_improvement_proposals`で毎回読み直し、読めなければ既定値でwarnを出す）。合計が上限以上のあいだ、`open_finding_planner`は（人のanswerを運ぶとき以外は）plannerを立てず、findingは`open`のまま待つ。eventは書かない。人のanswerを運ぶplannerは、質問したplannerが数えられていたことと人の判断であることから上限を超えて立つ。人が`submit --finding`したproposal（持ち主が`person`: 廃止前に人が`dagq plan`で開いたplannerか、人が`DAGQ_ROLE`の無い自分のterminalで打った`submit`。runtimeのproposalを人が出し直すと持ち主が替わり、数えなくなる）とfollow_upのdraftの採否は数えず止めない。`dagq findings`は`improvements`（`running`・`limit`・`reached`・`waiting`: 上限に達しているときの対象のfindingの`finding_id`と`reason: improvement_limit`）を返し、observerの入力にも同じものが載る。
12. **test**: `tests/it/finding_planner.rs`がplan reviewのbackend（`PlanWorkspace`。runtimeのplannerのwrapperはbackgroundに停めてtestが演じ、cmuxのdouble・画面・打ち込みは使わない。[Draft planners](draft-planners.md)の9）とstubのplan reviewで、印のあるfindingにだけplannerが1つ立ち（次のpass、上限を上げたpass、直接の`open_finding_planner`でも2つ目は立たない）、promptの中身、plannerのhandleを持ち主にしたsubmitでfindingが`proposed`になりproposalに紐づくこと、他のproposalで`proposed`のfindingを名指したsubmitの失敗、plan reviewのpassでtaskが`ready`になりplannerに終了の依頼が送られること、taskのcancelでfindingが印なしの`open`に戻ること（`a_marked_finding_gets_one_planner_whose_proposal_plan_review_readies`）、`blocked`のaskのoptionsと`propose` / `dismiss`のanswerの適用（askが閉じ、attentionにならない）、`stalled`のaskの`propose`でfindingが作られること（`a_propose_answer_marks_the_finding_and_a_planner_takes_it`）、findingへの`planner_question`のanswerがplannerの次のturnの依頼になること、決めずに終わったplannerの後に次が立ち3回で`finding_planner_exhausted`とattentionになること、人の`submit --finding`でそれが消えること（`a_planner_question_about_a_finding_reaches_its_planner_as_a_turn_and_undecided_planners_end_in_the_inbox`）を確かめる。`improvement_planners_wait_at_the_limit_and_their_tasks_are_normal_at_most`は、`dagq.toml`の上限1で2つ目のfindingにplannerが立たず（直接の`open_finding_planner`は`AtLimit`）、`improvements_of`が待つfindingを出し、plannerがsubmitした`high`のtaskの個別の優先度がplan reviewのpassで外れてgoalから継ぎ（taskの`origin: ai`、`priorities_inherited`）、proposalが終わるまで待ち、終われば立ち、人が`submit --finding`したproposalは数えないことを確かめる。規則は`src/domain/finding.rs`のunit test。

## 推奨が出せればplannerが決める（ADR-t451-1）<a id="推奨が出せればplannerが決める未実装"></a>

[ADR-t451-1](../../adr/2026-10-02-t451-1-ai-decides-recommendable-asks-and-escalates-only-the-undecidable.md)の決定5（task 1320）。findingのplannerも、[Draft planners](draft-planners.md#推奨が出せればplannerが決める未実装)と同じく、dagq-planner skillの「Basic policy」に従う（`finding_planner_prompt`の「What to do」、`prompt::DECIDE_YOURSELF`）。推奨が出せる判断（既存のgoalへのtask、新しいgoal、`finding dismiss`）は自分で決め、理由をproposalのtaskの`--context`（`from finding N (kind)`に続けて、その手当てを選んだ理由）かfindingの`--reason`に書く。`planner_question`は、ADR-0047決定41の`scope`・`discard`に当たりqueue・repository・ADR・人の先例で決めきれないものと確信度が`low`のものだけにし（repositoryの規則でverify・paths・evidenceが決まらないこと自体は理由にしない。`prompt::RUNTIME_PLANNER_ASK`）、推奨（`--recommend <propose|dismiss>`）と確信度（`--confidence <high|low>`）を載せる。findingから作るproposalはfollow_upの上限の対象にならない（ADR-0047決定20）。unit testは`application::prompt`の`the_finding_planner_decides_what_it_can_recommend`。

## 人のplannerの廃止と非対話の経路（ADR-t1394-1の`dagq plan`の拒否とADR-t1394-2の経路は実装済み）<a id="予定-人のplannerの廃止と非対話の経路"></a>
