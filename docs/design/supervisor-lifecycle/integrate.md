# `integrate`

`dagq integrate ID`（taskの`awaiting_integration`または`needs_session`のrun）と`dagq integrate --next`（`awaiting_integration`のrunを検証完了の古い順に1件）は、検証済みのrunをruntimeが`main`へ着地させる操作で、repository内で実行する（[ADR-0008](../../adr/0008-merge-queue-squash-landing.md)）。reviewがpassしたrunはsupervisorが同じ`Integrator`に依頼して着地させるので、人が呼ぶのは`review_failed`のrunと、review以前のsupervisorが残した`awaiting_integration`のrunだけ（[Review](review.md#review-supervisor)）。`--db PATH`と`--repo REPO`は明示override。repositoryは`GitRepository::inspect`で開き、common directoryが`queue_repository.git_common_dir`と一致することを要求する。

ユースケースの本体はapplication層の`src/application/integrate.rs`にある（[ADR-0013](../../adr/0013-layered-architecture-and-type-function-style.md)の方針1と8）。着地とpushはこのmoduleの`Integrator`だけが行い、supervisorと人の`integrate`は`IntegrationRequest`を渡す（[ADR-t728-2](../../adr/2026-09-27-t728-2-landing-only-by-the-trusted-integrator.md)。依頼者の検査・lease・承認かreviewのpassの確認と、eventの依頼者とIntegratorの記録は[Authorization](../authorization.md#着地とpushintegrator)）。`begin`（束縛の確認、runの選択、supervisorのleaseの確認、人が打つ`integrate`の空き容量の確認（`Integration::disk`。[空き容量](disk-space.md#人が打つintegrate)、task 638）、`integration_approved`、tokenの生成、`begin_integration`）と`land_integrating`（下の2〜10）に分かれ、どちらも`Integration`（`&mut dyn Queue`＝`TaskStore`とrunのport（`RunTransitions`・`RunLog`など）と`AskStore`、`&dyn Repository`、検証コマンドを走らせる`&dyn Verifier`、`Option<&dyn MainRemote>`、worktreeの有無・receiptと検証logの読み取りの`&dyn RunFiles`、common directoryの文字列、`Clock`、`IdGenerator`、leaseの`pid`の生死を見る`ProcessControl`）だけを受け取り、`SqliteQueue`・`GitRepository`・rusqliteを参照しない。portは`src/application/ports.rs`にあり、`SqliteQueue`（`runtime_store/`の固有メソッドへの委譲）、`GitRepository`、`infrastructure::run_env::ShellVerifier`（main checkoutの`dagq.toml`の`[run.env]`と`/bin/sh`）、`SystemProcesses`が実装する。`begin`と`land_integrating`はmoduleの外から呼べず、`Integrator::approve`（`begin`）と`Integrator::land`（検査の後に`land_integrating`）が入口になる。`runtime::integrate`はqueueとrepositoryを開き、portの実装を組み立てて、このプロセスのactor（userかinbox）を依頼者に`Integrator::approve`を呼び、leaseのheartbeat threadを立ててから`Integrator::land`を呼ぶ入口だけで、supervisorの着地threadも自分のtokenでslotを取ったrunの`IntegrationRequest`（依頼者は`supervisor:<pid>`）を`Integrator::land`に渡す。validationの`check_receipt`（[Validation](validation.md#validation)）も同じファイルにあり、`Repository`越しにGitを、`RunFiles`越しにreceiptを読む。run directoryの検証logの一覧（`log_names`・`next_integrate_attempt`・`integrate_logs`）も`RunFiles::read_dir`越しで、applicationはファイルI/Oを直接しない（`runtime::integrate_logs`などの旧名は`LocalRunFiles`を渡す薄い入口）。

1. **スロット**: runを`integrating`にし、このプロセスのtokenで`run_leases`の行を作る（`begin_integration`、`integration_started`）。同時に`integrating`のrunは1件（`one_integrating_run_per_queue`）で、別のrunが着地中ならerror。leaseは`supervise`と同じthreadで2秒ごとにheartbeatし、`status`/`doctor`に`integrating`のrunとして並ぶ。`--next`の順序は`validation_finished`イベントのid順で、`needs_session`のrunは取らない。 スロットを取ったら、まず**着地済みか**を確かめる（task 1118）: runの`base_commit`..main headのfirst-parentの履歴に、trailer `Dagq-Run: <run id>`を持つcommitがあれば（`Repository::landed_run_commit`）、前の着地がmainを進めた後、完了を記録する前に止まった（supervisorの死など）ので、rebase・検証・commitをせずにそのcommitを着地commit（`main_before`はその第1親、`source_commit`はworktreeのHEAD、`message`はreceiptから作り直したもの）として`auto_repaired`（`repair: landing_found_on_main`、`conditions`: `commit`・`main`、`detail.main_before`）を記録し、7〜10（完了・後始末・push・follow_upsの登録）へ進む。同じrunを二重に着地させない。
2. **worktreeの前処理**: worktreeが存在し、run branch `dagq/<run-id>`をcheckoutしていること。worktreeのpathはqueueの今の`runs/`から解決したもので、queueディレクトリを移した後でも見つかる。repository側の管理情報が旧pathを指したままだと後始末の`worktree remove`が失敗するので、主working treeで`git worktree repair <worktree>`を実行する（移していなければno-op。[ADR-0017](../../adr/0017-resolve-run-paths-from-the-queue-directory.md)）。途中のrebase（`rebase-merge` / `rebase-apply`）が残っていれば`git rebase --abort`する（`integration_rebase_aborted`）。
3. **receiptの検査**: `<run-dir>/receipt.json`がparseでき、`result`が`succeeded`で（`failed`ならrunを`failed`にして終わる。下記）、`Receipt::check`を通り、`commit`がworktreeの現在のHEADに一致する。ただし、このrunの前の着地のrebaseと振り直し（`integration_rebased`と`migration_renumbered`の`head_before` → `head_after`を古い順にたどる）がreceiptの`commit`から今のHEADへ至るなら、前の着地がrebaseの後に止まって残したheadなので一致とみなす（`RunHistory::landing_rewrote`、task 1118。以前は`commit_mismatch`で`needs_session`になり、死んだ着地のやり直しにresumeを使った）。衝突なしのrunではHEAD = `result_commit`なので検証済みのreceiptがそのまま通る。`needs_session`から戻るrunでは、セッションが新しいheadでreceiptを書き直したことの検出になる。worktreeはcleanであること。`Receipt::check`の後、taskの`required_evidence`が欠けていれば（validationの8と同じ判定。resumeしたsessionがevidenceを書かずにreceiptを書き直した場合）着地せず`needs_session`にし、`last_error`を`evidence missing: …`、`integration_deferred`のpayloadに`checks`（欠けたcheckの配列）を書く。`Receipt::check`と要求evidenceを通った時点で、読んだreceiptを`integration_receipt`イベント（`main`、receiptの`commit`、`receipt`にJSON全体。`follow_ups`を含む）に記録する。HEAD不一致・衝突・再検証の失敗で着地しなかった場合も記録は残り、`integrate`を繰り返せばその回数だけ並ぶ。`validation_finished`は検証時のreceiptしか持たないので、セッションが書き直したreceiptの`commit`、evidence、`summary`、`follow_ups`をDBが持つのはこのイベントだけ。
4. **rebase**: `git rebase --no-autostash --no-verify <main head>`（main headは着地開始時に読んだ`refs/heads/<branch>`）。すでにmainの上にあればno-op。衝突したら`git diff --name-only --diff-filter=U`とGitの出力を取り、`rebase --abort`でworktreeを検証済みheadに戻して`needs_session`にする。成功したら`integration_rebased`（`head_before`、`head_after`）を記録する。
5. **再検証と検証コマンド**: rebase後のHEADがmain headと異なり（同じなら「commitが残らない」として`needs_session`。変更が不要ならセッションが`failed` receiptを書く）、main headの子孫であること。`git status --porcelain --untracked-files=all`が空であること。runが足したmigration（main head..rebase後のHEADで追加された`migrations/NNNN_<name>.sql`）の番号を、rebase後のHEADの`migrations/`でrunが足していない別のファイル（mainから来たもの）が使っていれば、振り直す（runが既存のmigrationを改名・置き換えただけなら重ならない）（[ADR-0067](../../adr/0067-migrations-are-listed-by-build-and-renumbered-on-landing.md)の決定3。`application::integrate::renumber_migration`）。runが足したmigrationが1つで、その番号の4桁をrunが変えた他のファイル（main head..HEADの変更パスからmigration自身を除いたもの。`git grep -F`）のどれも含まなければ、worktreeで`git mv`して、runが足していないmigrationの最大の番号+1へ移し、run branchにcommitして（`fix: renumber migration NNNN to MMMM`）`migration_renumbered`（`main`、`from`、`to`、`old_number`、`new_number`、`head_before`、`head_after`）を記録し、以降はそのcommitをrebase後のHEADとして扱う。Gitがそのcommitを拒んだとき（`commit.gpgsign`の署名の失敗、user identityが無い、`--no-verify`でも走る`prepare-commit-msg`のhookの失敗など。時間切れで終わらなかったcommitも同じ）は、`git reset --hard HEAD`で`git mv`を戻し（振り直しの前にworktreeはcleanなので、戻すのはrenameだけで、HEADはrebase後のHEADのまま）、`migration_renumbered`は記録せず、下の振り直せないときと同じ`migration_number_taken`の`needs_session`にする（`Repository::rename_and_commit`が`Ok(Err(<gitの出力>))`を返す）。payloadには`commit_error`（gitの出力の空でない行を`; `でつないで500文字まで）を足し、`last_error`にも同じものを書くので、sessionはresumeで自分で振り直せる。戻す操作自体が失敗したときはintegrateのエラーのままで、そのメッセージにcommitの失敗と戻せなかったことを書く。runが足したmigrationが2つ以上か、番号を含むファイルがあれば、何も書き換えず検証コマンドも実行せずに`needs_session`にし、`integration_deferred`の`code`を`migration_number_taken`、payloadに`migrations`・`taken`・`next_number`（次の空き番号）と、番号を含むファイルがあれば`referring`を書く（`last_error`は理由と次の空き番号と直し方）。taskの`paths`が空でなければ、squashしてmainに載せる範囲（main head..rebase後のHEAD）の変更パスがすべてどれかのglobに合うこと（validationの7と同じ判定。validationの後にsessionが足したcommitやrebaseで変わった差分もここで止まる。[ADR-0029](../../adr/0029-task-declares-paths-and-verification-follows-the-kind-of-change.md)の決定4）。外れれば検証コマンドを実行せずmainも動かさず、`last_error`を`changed paths outside the task's --paths: <paths> after the rebase onto main <main>; …`にして`needs_session`にし、`integration_deferred`のpayloadに`scope_violation`（外れたパス）と`allowed`（taskのglob）を書く。taskの`verification_commands`を順に`/bin/sh -c`でworktree内で、[Run environment](run-environment.md#run-environment)の`[run.env]`をenvに足して実行し、出力を`<run-dir>/integrate-<attempt>-verify-N.log`、終了コードと末尾を`verification_command`イベント（`phase: integration`、`attempt`、`log_path`）に残す。payloadにはコマンドの所要時間`duration_secs`（秒、小数3桁）と、実行中のload average（開始時・5秒ごと・終了時に読んだものの`load_avg_mean` / `load_avg_max`。読めなければnull）も書く（task 197。load average は`Integration::load_average`で読み、supervisorの着地も人の`integrate`も同じ）。`attempt`はrun directoryにある`integrate-*-verify-*.log`の最大の試行番号+1（無ければ1、旧名`integrate-verify-N.log`は0とみなす）で、同じrunの2回目の`integrate`が1回目のlogを上書きしない。非0で終わったコマンドは、終了コード・signal・logから失敗を分類し（task 467。`domain::verify_failure::classify`）、`verification_command`のpayloadに`signal`（signalで終わったときの番号、無ければnull）と`failure`（`{class, evidence}`。成功したコマンドはnull）を書く。`class`は上から順に最初に当たったもの: `disk_full`（`No space left on device`・`os error 28`・`ENOSPC`）、`killed`（signalで終わった、shellの終了コードが129〜192（128+signal）、cargoの`process didn't exit successfully`の行の`(signal: 9, SIGKILL` / `(signal: 15, SIGTERM`、nextestの`SIGKILL [` / `SIGTERM [`）、`flaky`（落ちたtestが全て、nextestが流し直して通ったtestである。下の「不安定なtestの着地のやり直し」。task 768）、`timeout`（`tests/common`の`within`の、`test `で始まる`… timed out: … did not happen within …`の行、nextestの`TIMEOUT [`と`TRY n TMT [`、終了コード124）、`build_error`（`error[E…]`で、続く`-->`の位置も書く。無ければ`error: could not compile` / `error: linking with`）、`lint`（コマンドがclippyで`could not compile`のもの。lint自身の`error: `の行）、`test_failure`（下の「nextestの失敗のstatusの集合」の失敗のうちkillと時間切れ以外（`FAIL [`・`FAIL + LEAK [`・`TRY n FL+LK [`・`ABORT SIG 64 [`・`TRY n SEGV [`など）、`test … ... FAILED`、`test result: FAILED`、`error: test failed` / `error: test run failed`）、`format`（rustfmtの`Diff in `）、`coverage_below`（コマンドに`--fail-under-`があり`TOTAL `の行がある。cargo-llvm-covは下回ったことを書かずに1で終わるため）、`unknown`（logの最後の空でない行。空なら終了コード）。`disk_full`と`killed`を先に見るのは、ディスク満杯やkillが後に残すbuildやtestのエラーに引きずられないため。`flaky`を`timeout`より先に見るのは、`within`で時間切れになり流し直しで通ったtestも不安定なtestとして扱うため。retriesの下のnextestのkill（`TRY n KILL [` / `TRY n TERM [`）も同じ理由で`flaky`の後、`timeout`の前に`killed`と見る（task 1272。1回目にkillされ流し直しで通ったtestは`flaky`）。コマンド全体の上限（`VERIFICATION_TIMEOUT`、30分。`ShellVerifier::verification_timeout`、testは`OneShot::verification_timeout`で縮める）を過ぎたコマンドは、止めてから着地処理のエラーにせず、`timeout`（`evidence`は`the command ran past its <秒> s limit and was killed`、`exit_code`は128、`signal`は9）の失敗として同じく記録する（task 639。verifierは`domain::verify_failure::CommandTimedOut`のerrorを返し、integrateがそれを見分ける）。検証コマンドは自分のprocess group（`process_group(0)`）で起動し、上限を過ぎるとgroup全体（`/bin/sh`と、それが起動した`cargo`・nextest・testなどの子孫）と、子孫が移った別のprocess group（cargo-nextestはtestを1件ずつ自分のgroupで流す。止める前と猶予のあいだに子孫を`ps`で辿って`getpgid`で見つける）にSIGTERMを送る。どのgroupにもprocessが残らなくなればそこで、残っていれば猶予（15秒。nextestがSIGTERMでtestに与える猶予の10秒より長い）の後にSIGKILLを送り、processが残っていないこと（`kill(-pgid, 0)`が`ESRCH`）を確かめてから（SIGKILLの後は10秒まで送り直して待つ）時間切れとして返す（task 1098。`infrastructure::adapters::run_shell_to_log`）。shellだけをkillすると子孫が生き残ってlogに書き続け、下の「hostの失敗のやり直し」が同じworktreeで始めた次の実行と競合したため（task 965の着地）。親が先に終わってから自分でprocess groupを分けた子孫は辿れず止まらない。`evidence`は当たった行（ANSIの色を除き300文字まで）。logはUTF-8として不正なbyteを置き換えて読む（killやディスク満杯で途中で切れたlogでも印を拾うため）。分類による扱いは下の「hostの失敗のやり直し」（task 639）。`class`が`test_failure`・`timeout`・`flaky`なら、logから落ちたtestの名前を読み（task 515。`domain::verify_failure::failed_tests`。cargo testの`test <name> ... FAILED`・`---- <name> stdout ----`・`failures:`の下の一覧・testのthreadの`thread '<name>' panicked`（名前に`::`のあるもの）、nextestの下の「nextestの失敗のstatusの集合」の(A)(B)の行の最後の語（statusが`FAIL + LEAK`・`ABORT SIG 64`・`TRY 2 SIG 64`のように複数語でも最後の語）、`tests/common`の`within`の`test <name> timed out: …`。重ねず出た順に20件まで）、`verification_command`のpayloadに`failed_tests`（名前の配列。名前の無い失敗は空の配列）と`failed_tests_omitted`（20件を超えた数）を書く。それ以外の失敗と成功したコマンドはどちらもnull。あわせて`flaky_tests`に、落ちたtestのうちnextestが流し直して通ったもの（FLAKYの印。`domain::verify_failure::flaky_tests`。`FLKY-FL n/m [`・`FLAKY n/m [`・`TRY n PASS [`の行の最後の語）を書く（task 768。`flaky`でない失敗でも、同じコマンドの中の不安定なtestには付く。無ければ空の配列）。コードの分類（`flaky`・`build_error`・`lint`・`test_failure`・`format`・`coverage_below`・`unknown`）で非0なら`needs_session`で（`flaky`は下の着地のやり直しを先に1回使う）、`integration_deferred`のpayloadにも同じ`signal`・`failure`・`failed_tests`・`failed_tests_omitted`・`flaky_tests`を書き、`last_error`に`(<class>: <evidence>)`を足す。supervisorが自動resumeする。hostの分類（`disk_full`・`killed`・`timeout`。`FailureClass::is_environmental`）の失敗は、次の「hostの失敗のやり直し」に従う。validatingは検証コマンドを実行しないので、これがそのcommitに対する唯一の実行で（[ADR-0040](../../adr/0040-verify-once-review-run-env-graph-stats-and-task-priority-in-claim-order.md)の決定1）、rebaseがno-opでも、headがrunの`result_commit`のままでも必ず実行する。task 48が入れたskip（no-op rebaseで再実行しない）は廃止し、`integration_verification_skipped`イベントはもう記録しない（kindは過去のeventを読むために残す）。
6. **着地**: `git commit-tree <HEAD>^{tree} -p <main head>`で1 commitを作る。messageはtaskのtitle、receiptの`summary`（空なら省略）、trailer `Dagq-Task: <task id>` / `Dagq-Run: <run id>`。`refs/dagq/runs/<run-id>`をrebase後のHEADに向けてから、mainをcheckoutしているworktree（`git worktree list --porcelain`）があればそこで`git merge --ff-only <commit>`、なければ`git update-ref refs/heads/<branch> <commit> <main head>`でmainを進める。
7. **完了**: 1トランザクションでrunを`integrated`、`result_commit`を着地commit、`last_error`をnull、Taskを`completed`にし、lease行を消して`run_integrated`（`result_commit`、`source_commit`、`main_before`、`history_ref`、`message`、`verification_skipped`、`git_common_dir`）、`lease_released`、`task_status_changed`を記録する（`finish_integration`）。
8. **後始末**: そのrunのcloseされていない`approve_landing`のask（開いたままのものも、回答済みで適用されていないものも）を`close_approve_landing_asks`で閉じる（task 425。supervisorの着地でも手の`integrate`でも同じ`land_integrating`が行う。未回答なら`answer`に`the run was integrated; closed by the runtime`を書き`runtime_closed: true`の`ask_answered`、回答済みなら`ask_closed`を記録し、閉じたaskごとにinfoのlogを出す。mainはもう進んでいるので、閉じられなくてもwarnのlogだけで着地は変わらない）。同じ後始末が、そのrunか、runを名指さないそのtaskの`blocked`のask（observerが開いたもの）も`close_blocked_asks`で同じ`answer`と記録で閉じる（task 329。着地した後に残ると`ask_unanswered`のalertを出し続けるため）。`ask_answered` / `ask_closed`はaskの`ask_opened`と同じrun・taskに記録する（task だけのaskはrunを持たない）。askに紐づくfindingは変えない。続いて`git worktree remove --force <worktree>`と`git branch -D dagq/<run-id>`（`worktree_removed`）。失敗は`cleanup_failed`イベントと`last_error`に残し、statusは変えない。
9. **push**（ADR-0019の決定3、ADR-t615-1）: 着地したbranchを`dagq.toml`の`[repository] remote`（既定`origin`）へ`git push <remote> refs/heads/<branch>:refs/heads/<branch>`で送る。`push = false`ならremoteを見ずにpushしない。Gitはapplication層のport `MainRemote`（`push_config`、`has_remote`、`push_main`。`push_main`はIntegratorだけが作れる`PushGrant`を取る）を通して呼び、adapterは`GitRepository`（run worktreeは消えている場合があるのでcommon directoryを`--git-dir`にし、`GIT_TERMINAL_PROMPT=0`、timeout 300秒）。成功は`push_finished`（`remote`、`branch`、`commit`、`already_delivered`。通常のpush成功は`false`）、`--no-push`・`push = false`・`remote`を書かずに`origin`が無いときは`push_skipped`（`remote`、`branch`、`commit`、`reason`は順に`--no-push`・`push = false in dagq.toml`・`the repository has no remote origin`。`--no-push`でもremoteの有無は見ずに、`remote`には着地の後にapplication層のport `Repository`の`repository_config`で読んだ`[repository] remote`（既定`origin`。読めなければ`origin`で、着地は成功のまま）を記録する）、Gitのpushが失敗しても、`MainRemote::contains_landed_commit`でremoteのbranch先端を照会し、着地したcommitがその祖先（先端自身を含む）なら、すでに届いているとして`push_finished`（`already_delivered: true`）を記録する。照会が失敗するか、remoteが着地commitを含まないとき、および明示した`remote`が無い・`[repository]`が読めないときは`push_failed`（`code`、`remote`、`branch`、`commit`、`error`）を着地したrunに記録する。どの場合もrunは`integrated`、taskは`completed`のままで、`integrate`は成功（exit 0）で終わる。`push_failed`はattention（`push main`）になり、人がinboxから原因を直して`git push <remote> <branch>`を打つ。
10. **follow_upsの登録**（ADR-0019の決定4）: 着地したreceipt（ステップ3で読んだもの）の`follow_ups`の未登録項目を、1つの`BEGIN IMMEDIATE`トランザクションでまとめてdraft taskとして登録する（`application::integrate::register_follow_ups`。`runtime::register_follow_ups`として再公開）。titleとdescriptionはfollow_upのもの、acceptance・`verification_commands`・dependenciesは空、goalは元のtaskと同じ（無ければgoalなし）、`context`は`follow_up proposed by the receipt of run <run-id> of task <id> (<title>)`（task 625より前の着地は日本語の「task <id>（<title>）の run <run-id> の receipt が提案した follow_up」）。登録ごとに着地したrunへ`follow_up_registered`（`task_id`、`title`、配列内の位置`index`、種類の`category`）を記録する。`category`は項目の`category`をworkerが書いたまま（前後の空白は落とし、一覧に無い値もそのまま）、空でない文字列でなければ`unlabeled`にする（`domain::follow_up_category`、[ADR-t947-3](../../adr/2026-09-28-t947-3-follow-ups-carry-category-codes.md)、一覧は[follow_upsの分類コード](receipt-and-session-exit.md#follow_upsの分類コード)）。goalが閉じていればgoalなしで登録し、payloadに`goal_closed: true`を書く。同じrunの`follow_up_registered`が既に持つ`index`は登録しないので、同じrunについて2回呼んでも二重に登録しない（`needs_session`で着地しなかった`integrate`は登録しないので、再着地で登録されるのは1回だけ）。`title`が空でない文字列でないか`description`が文字列でない項目は登録せず、`follow_up_registered`に`task_id: null`、`skipped`（理由）、`follow_up`（項目そのもの）と`category`を書く。各draftのtask作成・`follow_up_depth`・`draft_origins`と、登録した項目・skippedの項目の`follow_up_registered`を同じトランザクションで書く。途中で書き込みに失敗したらその呼び出しの未登録項目は全件rollbackされ、次の`integrate`のやり直しでまとめて登録できる。supervisorのpassには、同じreceiptの新しいdraftが全件見えるか1件も見えないかのどちらかになる。登録の失敗はstderrに出すだけで、着地とexit codeは変えない。draftの`follow_up_depth`は元のtaskの値+1にし、出どころ（`draft_origins`の`follow_up`と材料`{"source_task_id", "source_run_id", "index", "category"}`。`category`は`follow_up_registered`と同じ値）を記録する。draftなのでsupervisorのclaimは拾わず、補ってsubmitするか、cancelするか、人に聞くかは、supervisorが同じrunのfollow_upの束ごとに立てるplannerが決める（plannerのpromptはdraftの`category`を見せる）（[Draft planners (supervisor)](draft-planners.md#draft-planners-supervisor)）。`follow_up_registered`はattentionにしない。

**hostの失敗のやり直し**（task 639、[ADR-t639-1](../../adr/2026-09-27-t639-1-retry-verification-failures-of-the-host-once.md)、goal 37）: 検証コマンドの失敗の`class`が`disk_full`・`killed`・`timeout`なら、コードではなくhostの原因として、workerのsessionをresumeせず、同じ試行（同じ`attempt`）の中でそのコマンドを1回だけやり直す。

- やり直しがコードの分類で落ちたら、そのやり直しの結果で上と同じ`verification_failed`の`needs_session`にする（`last_error`はやり直しのlogを指す）
- やり直しもhostの分類で落ちたら（と`disk_full`で容量が足りないとき）、runをresumeせずに`awaiting_integration`に戻す（`hold_integration`。`integration_held`イベント（code `verification_environment`、`index`、`main`、`head`、`command`、`exit_code`、`signal`、やり直しの`failure`と`log_path`、`retried`、最初の失敗の`first_failure`と`first_log_path`（やり直さなかったときはnull）、`disk`（容量不足のときだけ）、`status: awaiting_integration`、`reason`）と`lease_released`を記録してleaseとslotを返す）。`last_error`は`verification command "<command>" failed on the host after the rebase onto <main> (<class>: <evidence>); see <logs>. <hostを直す手がかり>, then land it with dagq integrate <task>; no session is resumed`。`needs_session`にしないのでresumeの回数（`resume_started`）は使わない
- holdしたrunはleaseの無い`awaiting_integration`なので、inboxのattention（`next`は`review and integrate`、`kind`は`integration_held`、`last_error_code`は`verification_environment`）に1件出る（[`status`](status.md)の`run_attention`）。人がhostを直して（空き容量を空ける、負荷を下げる）`dagq integrate <task>`を打てば、新しい試行で検証からやり直す。supervisorはleaseの無い`awaiting_integration`のrunを自分では着地させない（ただし着地の後のlanding recheckは他の着地待ちのrunと同じくholdしたrunも確かめ、衝突か`[recheck] command`の失敗なら`needs_session`にする。[Landing recheck](landing-recheck.md)）
- 分類の集合（`disk_full`・`killed`・`timeout`）は人の判断なしに広げない（ADR-t639-1）

**nextestの失敗のstatusの集合**（task 1272）: nextest（0.9.146、nextest-runner 0.124.0の`status_str`・`short_status_str`）がtestの行の先頭に書くstatusのうち、失敗と読むものを明示の一覧で持つ。行は`<status> [ <時間>] … <binary id> <test name>`で、statusは12文字に右寄せされる（`TRY 2 LKFAIL`のように12文字ちょうどなら行頭に空白が無い）。testの名前は最後の語、binaryはその前の語。

**不安定なtestの着地のやり直し**（task 768、[ADR-t768-1](../../adr/2026-09-27-t768-1-rerun-failed-tests-once-and-land-again-on-flaky-only.md)）: `.config/nextest.toml`の`[profile.default]`は`retries = 1`と`flaky-result = "fail"`を持ち、nextestは落ちたtestを1回だけ流し直す。流し直して通ったtestは`TRY 2 PASS`と、終わりの一覧に`FLKY-FL 2/2`と出るが、runは失敗（exit 100）のままで、関門は通らない。nextestの設定に置くので`integrate`の`cargo llvm-cov nextest`だけでなく、CI・人の手元・workerのstress（`cargo nextest run --stress-count`）にも同じく効く（`[run.env]`や`integrate`の引数に置かないのは、不安定なtestをどこでも同じ印で見えるようにするため。`NEXTEST_RETRIES`・`NEXTEST_FLAKY_RESULT`で上書きできる）。`cargo test`（nextestでないもの）の検証には効かず、`flaky`にもならない。

`[profile.default]`は`fail-fast = false`も持ち（task 777）、nextestは最初の失敗で新しいtestの開始を止めず（`Cancelling due to test failure`にならず）、全部のtestを流しきる。`flaky-result = "fail"`の下ではFLAKYのtestも失敗と数えるので、既定のfail-fastではFLAKYが1件出た時点で残りのtestが始まらず、同じ回の本当の失敗（流し直しても落ちるtest）がlogに出ないまま、落ちたtestが全てFLAKYとして`flaky`に分類されうる。流しきるので、`flaky`の判定（落ちたtestが全て`flaky_tests`にある）はその回の全部のtestの結果に対して行われ、本当の失敗を見落として着地のやり直しに回すことはない（やり直しで初めて見つかってresumeが1往復遅れることもない）。本当の失敗が複数あれば、resumeされたsessionは1回の検証のlogで全部を見られる。費用は失敗する検証だけにかかり、fail-fastなら止まっていた時点からtest段の終わりまでの分で、1回の失敗した検証あたり最大でtest段1回分（`NEXTEST_TEST_THREADS = "8"`で中央値約160秒。[nextestの測定](../../plans/nextest-measurement.md)）。流し直すのは落ちたtestだけなので、加わるのはその分だけ。通る検証と、buildが落ちてtestを流さない検証の時間は変わらない。`NEXTEST_FAIL_FAST`か`--fail-fast` / `--no-fail-fast`で上書きできる。

- 検証コマンドの失敗の`class`が`flaky`（落ちたtestの名前が全て`flaky_tests`にあり、20件を超えて切れていない）で、この着地の試行でまだflakyのやり直しをしていなければ、`needs_session`にせず`integration_retried`（code `verification_flaky`、`index`、`main`、`head`、`attempt`（落ちた検証のlog番号）、`flaky_result: "pass"`、`command`、`exit_code`、`failure`、`failed_tests`、`flaky_tests`、`log_path`、`reason`）を記録し、同じ着地の中で検証をもう1回やり直す。receiptの照合とrebaseはやり直さない（rebaseがrun branchをreceiptの`commit`の先へ動かしているので、照合し直すと`commit_mismatch`になる）。runは`integrating`のまま、同じslotとleaseで、rebase後の同じhead（`head`）に対して続けるので、supervisorの着地でも人の`integrate`でも同じに動き、resumeの回数（`resume_started`）もsessionも使わない。main headは着地の開始時のまま（slotを持つ間はmainは動かない）
- やり直しの検証は新しいlog番号（`attempt`が1つ進み、logは`integrate-<attempt+1>-verify-N.log`）で、検証コマンドを最初から全部流す（`land`の検証のloop）
- やり直しは着地の試行（1回の`integrate`のrebase後のhead）ごとに1回まで（task 1039、[ADR-t1039-1](../../adr/2026-09-30-t1039-1-retry-flaky-verification-per-landing-and-record-passing-flakes.md)）。やり直しの検証コマンド全てに`NEXTEST_FLAKY_RESULT=pass`をenvで渡す（`[run.env]`の同名の値より優先。nextestを使わないコマンドには効かない）。1回目は従来の`.config/nextest.toml`の`flaky-result = "fail"`で、設定ファイルは変えない。検証コマンド（integrateと着地のrecheck、`run_shell_to_log`）は、プロセスが受け継いだ`NEXTEST_FLAKY_RESULT`を外し、runtimeが渡したもの（やり直しの`pass`か`[run.env]`の値）だけを渡す。flakyのやり直しの検証の中で動くtestのintegrateが、1回目からやり直しの扱いにならないため（task 1161）。やり直しはFLAKYだけなら成功し、coverageを含む全コマンドが通れば着地する。resume・復旧後の新しい着地でもまた1回やり直せる。過去の`integration_retried`は制限に使わない。logの`attempt`はやり直しにも新しい番号を使う
- 成功した`verification_command`にもFLAKYの名前を`failed_tests`と`flaky_tests`に残す（同じ20件の上限と`failed_tests_omitted`）。`exit_code: 0`・`failure: null`とFLAKYの名前、その後の`run_integrated`で、FLAKYを記録して着地したことが読める。1回目とやり直しで別のtestがFLAKYでも両方をstatsに数える
- やり直しが`test_failure`・`build_error`などで落ちたら、従来どおり`verification_failed`の`needs_session`にする。hostの分類は上のhostの失敗のやり直しに従う。1回目からflaky以外のコードの失敗なら直ちに`needs_session`にする
- `integration_retried`はattentionにしない（人の判断は要らない）。inboxとobserverは`dagq events --kind integration_retried`と、[`stats`](stats.md)の`verification_failures`の`flaky`の行（`retried`・`retry_passed`・`retry_failed`）、`failed_tests`の`flaky`の数と`flaky_candidates`で読む

結果は`IntegrationOutcome`: `{"outcome":"integrated","task":…,"run":…,"verification_skipped":…,"push":{"outcome":"pushed"|"skipped"|"failed","remote":…,"branch":…,"error":…,"reason":…},"follow_ups":[{"task_id":…,"title":…}]}`（`verification_skipped`はステップ5が検証コマンドを常に実行するので常に`false`で、出力の形を保つために残す。`run_integrated`イベントのpayloadにも同じ項目が入る。`push`はステップ9の結果で、`error`は`failed`のときだけ文字列（ほかは`null`）、`reason`は`skipped`のときだけ入る。`follow_ups`はステップ10でこの呼び出しが登録したtaskの`[{"task_id","title"}]`で、無ければ空配列）、`{"outcome":"needs_session","run":…,"main":…,"reason":…}`、`{"outcome":"failed","run":…,"reason":…}`、`{"outcome":"held","run":…,"main":…,"reason":…}`（上の「hostの失敗のやり直し」のhold）、`--next`で対象がなければ`{"outcome":"no_run_awaiting"}`。

supervisorが着地させたrunが`integrated`で終わるたびに、着地待ちのrunをその後のmainに対して`git merge-tree`と`[recheck] command`で確かめ、着地しなくなったrunは次の`integrate`を待たずに`needs_session`にする（[Landing recheck](landing-recheck.md)、[ADR-0068](../../adr/0068-recheck-waiting-runs-after-each-landing.md)）。人が打った`integrate`の着地の後には走らない。

上の手順5のmigrationの番号の振り直しは、queueのrepositoryがdagqのソースのときだけ動く（[ADR-t614-1](../../adr/2026-09-27-t614-1-dagq-source-only-features-by-one-check.md)）。ソースでないrepositoryでは番号を見ず、`migrations/`の変更を他のファイルと同じに扱う。判定と対象の一覧は[Source repository](source-repository.md)にある。`renumber_migration`（`src/application/integrate.rs`）は`Repository::is_dagq_source`が偽なら何もせずに戻り、`migration_renumbered`も`migration_number_taken`も記録しない。

手順4・6の`refs/heads/<branch>`と手順9の`origin`は、`dagq.toml`の`[repository]`で指定でき、指定が無ければ推定するbranchとremoteに変わる（[ADR-t615-1](../../adr/2026-09-27-t615-1-landing-branch-and-push-remote-per-repository.md)）。`push = false`は`push_skipped`、明示したremoteが無いのは`push_failed`になる。解決の規則とeventのpayloadは[Landing branch](landing-branch.md)にある。branch・remote・pushの解決はどれも実装済みで、`refs/heads/<branch>`は着地の開始時に1度だけ解決した着地先を指し（手順4〜9で同じbranchを使い、着地するcommitが`[repository] branch`を書き換えても、そのpushは開始時のbranchへ行く。task 667）、手順9のremoteは`[repository] remote`（既定`origin`）を指す。
