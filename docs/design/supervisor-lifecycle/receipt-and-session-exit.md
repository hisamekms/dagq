# Receipt and session exit

receiptの受領とセッション終了は別の事象である。agentはreceiptを`<run-dir>/receipt.json`へ一時ファイルからrenameして公開し、応答完了後もセッションを維持する。セッション終了はwrapperが記録する終了コード（`session_exited`）だけで確認し、画面文言は使わない。

receipt受領後の流れは次の順で自動化している。[ADR-0027](../../adr/0027-keep-worker-session-through-review-revise-verdict-and-merge-tree-precheck.md)の決定1で、idleになったsessionにはすぐ`/exit`を送らず、sessionを開いたまま[Validation](validation.md#validation)と[Review](review.md#review-supervisor)に進み、`/exit`はverdictが出た後に送る。

1. **idle判定**: Claude adapterがrunごとの`<run-dir>/claude-settings.json`に`Stop` hookを書き、`--settings`で渡す。hookはClaudeが応答を終えるたびにstdinのイベントJSON（`session_id`、`hook_event_name`など）を`<run-dir>/idle.json`へ一時ファイル + renameで書き、置き換える前に同じ内容を時刻付きで`<run-dir>/idle.log`へ追記する（`long_background`の経過の起点。`running`の処理を載せないmarkerではlogをその1行に置き換え、今の連なりの分だけを持つ。task 422。[stats](stats.md#stats)）。supervisorはreceiptを観測した後、`idle.json`のmtimeが`receipt.json`のmtime以上で、markerの`background_tasks`に`status`が`running`の要素が無ければ「receipt提出後に応答が完了した」と判定する。receiptより古いmarker（質問で止まった以前のturnなど）は無視する。**idleの定義**（task 147。`IdleMarker`。markerの内容の読み取り、つまり`background_tasks`と記録するhookのフィールドはClaude Code固有の形式なので`AgentSignals::idle_hook`（`infrastructure::claude`）が行い、mtimeとreceiptの比較はapplicationが行う）: Stop hookのmarkerがあり、その`background_tasks`に`running`の処理が無いこと。Claude Code（2.1.281で確認）はbackgroundの処理（`run_in_background`のshellなど）を残してturnを終えてもStop hookを発火し、入力JSONの`background_tasks`に`{id, type, status: "running", description, command}`を載せる。その間に`/exit`を送ると「Background work is running」の確認画面が出て、処理が終わっても誰かが答えるまで消えない。処理が終わるとClaude Codeは自分でturnを再開し、Stop hookが`background_tasks: []`で再び発火するので、supervisorはそのmarkerを待つ。`background_tasks`の無いmarker（古いClaude Code）は従来どおりidleとみなす。markerのmtimeと内容は1つのopenしたfileから読む（hookはrenameで置き換えるので同じ書き込みのものになる）。画面は読まない（ADR-0016のTUI非結合）。この定義は、最初のsessionのidle、resumeの(i)(ii)、reviseの書き直し、verdictの後の`/exit`で使う（[workerの質問への回答の送信](worker-question-answer.md#workerの質問への回答の送信)は従来どおりmarkerのmtimeだけを見る。promptへの打ち込みは確認画面を出さず、`/exit`だけが出すため）。終わらないbackgroundの処理でrunが無期限に止まらないよう、最初のsessionはreceiptを観測してから`resume_timeout`（既定1時間）過ぎれば（supervisorの引き継ぎ（adoptとexecの引き継ぎ）の後も、引き継いだ時刻ではなく記録した`receipt_observed`の時刻から数える。task 879）、`running`の処理が残っていてもreceipt以上に新しいmarkerで先へ進む。その前に、`background_alert_secs`を過ぎた処理は`long_background`の復旧jobにかかり、jobが止めれば`running`の無いmarkerで先へ進む（task true`。その後の`/exit`は、その同じmarkerのままなら下の2のとおり待ち直さずに送り、確認画面で止まれば3の`stuck_exit`のaskになる。task 242。receiptから`stuck_exit`のaskまでは`resume_timeout`とexit timeoutと復旧jobの分に収まり、以前のように`resume_timeout`の2倍はかからない）。判定の根拠（両ファイルのmtime、hookのフィールド、`background_running`）は`session_idle_observed`に記録する。権限確認や質問で止まっているturnでは`Stop`が発火しないため、その間は先へ進まない。idleと判定したら`finish_supervision_live`でrunを`running`から`validating`にし（`supervision_finished`の`{"status":"validating","exit_code":null,"session_live":true}`）、同じleaseのまま検証に進む。sessionは開いたまま。
2. **終了要求**（verdictの後。[Review](review.md#review-supervisor)の5）: idle ### `/exit`の再試行<a id="exitの再試行"></a>

ADR-0047の決定25、task 555（`ExitRetry`、`application::supervise::exit_retry`）。`exit_request_timed_out`の後（`cause: exit_timeout`）と、cmuxの時間切れで`/exit`が届かず着地もできなかった`exit_unsent`の後（`cause: backend_timeout`）、supervisorはleaseを持ったまま`/exit`を間隔を空けて再試行する。対象は最初のsessionの`SessionWatch`とverdictの後の`ExitWatch`で、resumeのsession（`ResumeWatch`）はexit timeoutで手放す今の扱いのまま。headlessのsessionは画面が無く終了の依頼が書かれたままなので再試行しない。

- **回数と間隔**: main checkoutの`dagq.toml`の`[exit]`（[Run environment](run-environment.md)）の`retries`（既定3）と`retry_intervals_secs`（既定`[30, 60, 120]`）。1回目は時間切れのすぐ後に行い、n回目の後は`retry_intervals_secs`のn番目（足りなければ最後の値）だけ待ってから次の再試行（か使い切りの判定）に進む。既定では時間切れから30秒・60秒・120秒を待ち、210秒後に使い切る。`retries = 0`は再試行も下の閉じて進める経路も行わず、時間切れの後すぐ`stuck_exit`の復旧jobに進む（テストの既定）。
- **画面の規則**: 再試行ごとに画面を読む（`WorkspaceBackend::capture`）。読めなければ何も送らない（`unreadable`）。ダイアログの兆候（`AgentSignals::detect_prompt`か`known_dialog`）があれば`dialog`で、[既知のダイアログ](prompt-waiting.md#既知のダイアログ)ならその規則で応答し（`answer_known_dialog`。段ごとに1回、`auto_repaired`の`dialog_answered`）、それ以外のダイアログには`/exit`もEnterも送らない。入力欄に`/exit`が残っていれば（`input_pending`）Enterだけを送り直す。ダイアログが無く入力欄が準備できていれば（`input_ready`。入力欄が描かれていること。最初の`/exit`と同じく、入力欄の中身までは見ない）`/exit`を送り直す（`submit`を通るので、入力欄に残ればEnterの送り直しと`submit_retried`が続く）。どれでもない画面（作業中など、`not_ready`）には何も送らない。
- **記録**: 再試行ごとに、画面を読んで送るものを決めてから、送る前に`exit_retried`（`attempt`、`retries`、`cause`、`screen`（`input_ready` / `input_pending` / `dialog` / `not_ready` / `unreadable`）、`send`（`exit` / `enter` / `keys`（既知のダイアログの規則。条件がそろわず送らなかったときは`known_dialog_unanswered`が残る） / `nothing`）、`next_secs`、`workspace_id`、画面の`excerpt`）を記録する。`exit_requested`と同じく、sessionが送信の戻りより先に終わりうるのと、引き継いだsupervisorに同じ再試行を重ねさせないため。送信の失敗（cmuxの時間切れ、Enterの失敗）はlogに書き、次の再試行に任せる。再試行の間にsessionが終われば、wrapperの`session_exited`を見た時点で`auto_repaired`（`layer: runtime`、`repair: exit_retry`、`conditions`に`attempts`・`cause`・最後の`screen`）を記録し（失敗はlogだけ。`dialog_answered`と同じ）、`stats`の`auto_repairs`に数えられる。使い切った後にsessionが終わっても`exit_retry`は記録しない。
- **閉じて進める**: 使い切っても終わらず、verdictの後の行き先が着地（`AfterExit::Land`）で、`landable_without_exit`（reviewしたcommitがHEADでreceiptがcleanなworktreeに対して成り立つ（`check_receipt`）こと、worktreeでrebaseの途中でないこと、runの`worker_question`のaskが開いていないこと）がそろえば、workspaceを閉じて（一覧に無いworkspaceは閉じ済み）`workspace_closed`を記録して着地へ進み、`auto_repaired`（`repair: exit_forced_close`、`conditions`に`cause`・`attempts`（再試行の回数）・`exit_reached`（`exit_timeout`なら`true`）・`then: land`・`review: pass`・`receipt_holds`）を記録する。rebaseと`worker_question`の条件は`exit_unsent`の`close_and_land`と復旧jobの`close_and_proceed`にも同じく効く。そろわないか閉じられなければ、そのほかの段（最初のsession、`approve_landing`のaskや人への引き渡しに進むrun）と同じく`stuck_exit`の復旧jobとaskに進む。reviewの前の`SessionWatch`はこの経路を使わない。
- **1段に1回**: 再試行の回数は段（最新の`exit_requested`）ごとに数え、復旧jobのrepair（`answer_known_dialog`・`stop_processes`）がexit timeoutを数え直しても再試行はやり直さない（ADR-0047の決定38）。
- **引き継ぎ**: adopt（`resume`・`adopt_review`・`adopt_failed_review_ask`）とexecの引き継ぎ（`handoff.json`の`exit`）は、最新の`exit_requested`の後の`exit_request_timed_out`と`exit_retried`（`RunHistory::latest_exit_timeout` / `latest_exit_retries`）から回数・`cause`・最後の再試行の時刻を読み（`ExitRetry::adopt`）、記録済みの再試行を重ねずに次の再試行から続ける。`exit_requested`はあるが時間切れがまだ記録されていないrunは、引き継いだsupervisorが自分の時間切れを記録してから再試行し、使い切れば`stuck_exit`の経路に進む（以前はこのとき`stuck_exit`のaskを開いたものとして扱い、時間切れの後も復旧jobもaskも起きなかった。task 555で`exit_asked`を最新の`exit_requested`の後の`stuck_exit`の`ask_opened`の有無だけで決めるようにした）。最新の時間切れの後に`stuck_exit`の`recovery_requested`か`ask_opened`があれば、前のsupervisorが使い切って復旧jobに進んだものとして再試行も`exit_retry`の記録もしない。`close_and_land`の`exit_unsent`を引き継いで条件がそろわなかったrunのうち、workspaceがもう一覧に無いものは、再試行にも`stuck_exit`の経路にも進まず、sessionが終わったものとして行き先へ進む（上の2、task 757）。

人の手動`/exit`はいつでも有効で、markerがない（hookが無効化されているなど）場合は従来どおり手動終了を待つ。sessionがreceiptの後に自分で終わった場合は、wrapperの`session_exited`から`supervision_finished`（`exit_code`付き）→`validating`へ進み、reviewでは`/exit`を送らずにworkspaceを閉じる。ただし生きているsessionが無いので、`revise`は人に聞く（`approve_landing`）。

## 画面からのidleの推定

[ADR-t803-1](../../adr/2026-09-27-t803-1-infer-idle-from-the-screen-when-the-idle-marker-is-missing-or-stale.md)。idleの印（`idle.json`）は主な信号のまま残し、印が無いか最後の入力より古いときだけ、画面（`cmux capture`）からidleを推定する。判定はproviderにもsessionの種類にも依らない`application::screen_idle`の1つにまとめ、plannerの`planner_view`（[Plan planners](plan-planners.md)）と、workerの最初のsession・resume・reviseのsession（下の[workerのsession](#workerのsession)、task 804）が使う。

- **印が判断できないとき**: 印が無い（`missing`）か、印のmtimeがsessionの最後の入力より古い（`stale`）。最後の入力は`screen_idle::last_input`が、agentの入力の印`prompt-submit.json`のmtime、supervisorが打った文の印`supervisor-input.json`（`SUPERVISOR_INPUT_FILE`。supervisorが文をsessionに打つ直前に`record_supervisor_input`が書く。plannerではreviseの配送とplanner_questionのanswerの配送。`/exit`は書かない）のmtime、sessionを開いた時刻（plannerは行の`created_at`）の遅い方として読む。印が最後の入力より新しい間は、今までどおり印で判断する（印の`background_tasks`に`running`があれば`working`）。
- **1回のcaptureの見え方**（`screen_idle::look` / `look_of`）: 入力欄が入力を受けられ（`AgentSignals::input_ready`）、作業中の表示が無く（`AgentSignals::working`）、ダイアログも無い（`AgentSignals::detect_prompt`）なら`Idle`で、`AgentSignals::transcript`の指紋と、画面にbackgroundの処理が動いている表示があるか（`AgentSignals::screen_background`。task 823）を持つ。`screen_background`の既定は`None`（画面から読めないprovider。backgroundの処理が無いものとして扱う）で、Claude adapter（`claude::background_on_screen`）は入力欄の下の行（status line）を`·`で区切った項目のうち、0より大きい数とbackgroundの処理の種類（`shell(s)`・`background task(s)`・`monitor(s)`・`agent(s)`、`BACKGROUND_COUNTS`）の組（例 `⏵⏵ auto mode on · 3 shells · ← for agents · ↓ to manage`。2026-09-28のClaude Codeで確認）があれば`Some(true)`、無ければ`Some(false)`を返す。数の無いhint（`← for agents`）と入力欄より上のtranscript（`3 shells still running`）は読まない。入力欄があり、`detect_prompt`の読むダイアログが無く作業中の表示があれば`Working`（task 845。captureの間隔を延ばすためだけに`Busy`と分ける）、それ以外（ダイアログ、入力欄が無い）は`Busy`、captureの失敗は`Unreadable`。
- **区間**（`screen_idle::observe`、`Observation`）: `Idle`のcaptureは、最後の入力より後に始まり同じtranscriptで同じbackgroundの表示の区間を延ばし（backgroundの処理が終わって表示が消えれば新しい区間になり、そこから`screen_idle_secs`を数え直す）（前のcaptureより後の秒のときだけ`captures`を1つ足す）、そうでなければ新しい区間を始める。`Working`と`Busy`は区間を終わらせ、`Unreadable`は区間をそのままにする。supervisorは区間をメモリ（`Spans`）に持ち、idleの印の隣の`screen-idle.json`（`SCREEN_IDLE_FILE`。`first_seen`・`last_seen`・`captures`・`transcript`・`background`・`recorded`。`background`の無い古い写しは`null`として読む）には写しを書けるときに書く。ディスク満杯で写しが書けなくても区間は失われない（写しは読むだけのコマンドと、引き継いだ次のプロセスがメモリに無い区間を読むためのもの）。
- **推定**（`ScreenProbe::infer`、`Observation::idle`）: 今のcaptureが読め、区間の`captures`が2以上で、`last_seen - first_seen`が`[stall].screen_idle_secs`（既定120秒、`DEFAULT_SCREEN_IDLE_SECS`。[Stall thresholds](stall-thresholds.md)）以上ならidleと推定し、idleの始まり（`idle_since`）を区間の`first_seen`に、推定の`background_running`を区間の`background`にする。今のcaptureが読めなければ推定しない（`working`）。supervisorは区間を持って写しを書き（`ScreenIdle::Record(&Spans)`）、読むだけのコマンド（`dagq planners`）は書かずに次のcaptureとして判断する（`ScreenIdle::Peek`。閾値はmain checkoutの`dagq.toml`の`[stall]`、読めなければ既定値）。
- **記録**: supervisorは区間ごとに1回、queueのevent `idle_inferred`（`source: "screen"`、`marker`（`missing` / `stale`）、`since`、`observed_secs`、`captures`、`background_running`（画面から読んだbackgroundの表示の有無。読めないproviderは`null`）、plannerでは`planner_id`・`origin`・`workspace_id`）を記録し、区間の`recorded`を立てる（`Spans::mark_recorded`）。eventを書けなかったとき（queueのエラー）はlogに残して他のplannerの扱い（reviseやanswerの配送、`/exit`）を止めず、次のpassで記録し直す。agentのdebug log（plannerは`<planner dir>/claude.log`、`PLANNER_DEBUG_LOG`）の末尾64KiBにidleのhookの失敗の行があれば（`screen_idle::hook_failure`、`AgentSignals::idle_hook_failure`。Claude Codeでは`Hook Stop`と`error`を含む最後の行）、その先頭300文字を`hook_error`に入れる。`dagq events --kind idle_inferred`で読める。
- **backgroundの処理**（task 823）: 画面にbackgroundの処理の表示がある推定は、印の`background_tasks`に`running`があるときと同じに扱う（区間を切って`working`にする形は取らなかった。印の`background_running`の待ちと`stuck_exit`までの流れ（task 147・242）にそのまま乗せるため）。plannerは`working`のままで（`PlannerProbe::screen_idle`の`IdleProbe::background_running`）、runtimeのplannerも`/exit`を受けない。表示が消えれば新しい区間が`screen_idle_secs`続いたところでidleになり、`/exit`を受ける。backgroundの表示のある区間も`idle_inferred`（`background_running: true`）に記録し（`dagq planners`の`idle_inferred`も`working`のまま出す）、表示が消えた後の区間は別に`background_running: false`で記録する。表示を読めないprovider（`screen_background`が`None`）では今までどおりbackgroundの処理が無いものとして推定し、backgroundを残したruntimeのplannerは「Background work is running」の確認で止まって`end_runtime_planners`がexit timeoutの後にworkspaceを閉じる。
- **限界**: 印が最後の入力より古いだけ（turnを始めないslash commandの後など）のplannerは、以前はすぐ`idle`だったが、今は`screen_idle_secs`の間`working`に見える。
- **workerのsession**<a id="workerのsession"></a>（task 804、`Supervisor::session_idle`）: 印を読む次の判定は、印が無いか最後の入力より古ければ画面の推定を印と同じidleとして扱う。推定のidleは区間の`first_seen`に書かれた印のように扱い、画面にbackgroundの処理の表示があれば印の`background_running`が立ったものとして扱う（`IdleMarker::inferred`。`background_tasks`は載らない）。推定できなければ読んだ印（古くても）をそのまま使うので、印の新しいsessionの振る舞いは変わらない。
  - 最初のsessionのreceiptの後のidle（上の1、`SessionWatch::poll`）: 最後の入力にreceiptのmtime（とsupervisorがreviseなどで打った時刻、古いreceiptの書き直しの依頼の時刻）を足すので、receiptより後に始まった区間だけがidleになる。`session_idle_observed`のevidenceは印の代わりに`source: "screen"`・`marker`・`observed_secs`・`captures`を持ち、`marker_modified`は区間の`first_seen`、`background_running`は画面から読んだbackgroundの表示の有無（読めないproviderは`null`）。backgroundの表示があれば、印の`background_running`と同じく`resume_timeout`まで待ってから先へ進む。
  - receiptの無いidle（[receiptの無いidleの検知](idle-without-receipt.md#receiptの無いidleの検知)、`StallWatch`）: 最後の入力にsupervisorが最後に打った文の時刻を足す。
  - resumeとrevise・衝突の依頼の段（[Needs session](needs-session.md)、[Review](review.md#review-supervisor)）: 最後の入力に依頼と回答の時刻（`input_at`）、書き直されたreceiptのmtime（resumeでは古いreceiptの書き直しの依頼の時刻も）を足す。印が書けなくても入力待ちになれば、`resume_timeout`を待たずに段を終える。
  - verdictの後の`/exit`（上の2、`ExitWatch`）: 印が最後の入力より古く画面がidleなら、画面にbackgroundの処理の表示が無ければ`/exit`を送り、あれば印のbackgroundの処理と同じく待つ（`background_waits`）。
  - **backgroundの処理**（task 823）: Claude Codeは処理を残してturnを終えると作業中の表示は出さないが、入力欄の下のstatus lineに処理の数（`3 shells`など）を出すので、推定のidleはその表示の有無をbackgroundの処理として持つ。表示があれば印の`background_running`と同じ流れ（receiptの後は`resume_timeout`まで待って進み、verdictの後の`/exit`も待ち、同じ印のまま確認で止まれば`stuck_exit`）になり、表示が無ければbackgroundの処理が無いidleとして扱う。表示を読めないproviderは今までどおりbackgroundの処理が無いものとする（backgroundが走っている扱いにすると、印の書けないsessionはreceiptの後も`resume_timeout`まで待ち、goal 56が防ぐ放置に近づくため。そのとき`/exit`が確認で止まれば、worktreeがcleanでreceiptの`commit`がHEADのときだけ[既知のダイアログ](prompt-waiting.md#既知のダイアログ)として応答するか、`stuck_exit`の復旧jobにかかる）。receiptの無いidleの促しとそのpayloadの`background_running`は画面から読んだ値（読めないproviderは`null`）になり、表示があれば促しに「Background work was still running when you stopped.」、askに「background work was running (not listed)」と書く（`stall_nudge`の`running`）。
  - **capture**: 印が判断できないsessionは、pollごとではなく`screen_idle_secs`の半分（上限60秒、`idle::probe_interval`）に1回だけ画面を読み、その間は前のcaptureの推定を使う（作業中のsessionのcaptureを増やしすぎないため）。推定は閾値より最大でその間隔だけ遅れる。作業中のturnでも入力の印（`prompt-submit.json`）が印より新しければ判断できない扱いになるので、receiptの無いidleの検知は作業中のworkerの画面も読む。
  - **作業中のcaptureの間隔の延長**（task 845。`idle::ScreenProbes`）: 同じ最後の入力のまま続けて`Working`を見たsessionは、次のcaptureまでの間隔を`probe_interval`から倍々に延ばし、`probe_interval`の4倍（`PROBE_BACKOFF_LIMIT`、`idle::max_probe_interval`。既定の`screen_idle_secs` 120秒で60→120→240秒、上限240秒）で止める。task 804の着地の後に作業中のworkerの画面を60秒ごとに読むようになり、cmuxのcaptureの失敗（`stats`の`backend_failures.by_op.capture`）が増えたため。1時間作業するsessionのcaptureは60回から約17回になる。`Working`以外（`Idle`・ダイアログや入力欄の無い`Busy`・captureの失敗の`Unreadable`）を見たcaptureの後と、最後の入力の時刻が前のcaptureのときより進んだとき（新しい入力。進んだ時点で延ばした待ちを打ち切り、`probe_interval`で次を読む）は`probe_interval`に戻す。ダイアログとcaptureの失敗は延ばさない（ダイアログ待ちの検知と、読めない画面を読み直す間隔を変えないため）。ここでのダイアログは`detect_prompt`が読むもので、作業中の表示の下にそれが読まないパネル（[既知のダイアログ](prompt-waiting.md#既知のダイアログ)のSettings / Usageなど）があれば`Working`として延びうるが、ダイアログ待ちの検知は自分でcaptureするので影響は`session_idle`のcaptureの間隔だけ。延ばす待ちはidleの印ごとに1つで、読む側ごとに最後の入力（`after`）が違うと前のcaptureと同じ最後の入力に見えず、延ばさずに`probe_interval`に戻る（延長前と同じ間隔になるだけ）。印が無いsession（`Missing`）も`Stale`と同じに延ばす: 最初のsessionの最初のturnは印が無いまま長く作業するのでcaptureの多くを占め、延ばすのは画面が作業中を示す間だけなので、印が書けないsessionの推定も入力待ちになれば上限以内に始まる。入力待ちになったsessionは、延ばした間隔の上限（既定240秒）以内に`Idle`のcaptureを受け、その後は`probe_interval`ごとに読まれて`screen_idle_secs`で推定のidleになる（receiptの後のvalidating、receiptの無いidleの促し（`idle_without_receipt_secs`、既定1200秒）、resume・reviseの段の終わりの遅れは、延ばさない場合より最大で上限と`probe_interval`の差（既定180秒）だけ）。`screen_idle_secs`が小さく`probe_interval`が0なら延ばさない。印が新しいsessionと、headlessのsession（ADR-t813-1）は`session_idle`が画面を読む前に返るので変わらない。runtimeのplannerの推定（`planner_view`）はこの間隔を使わず、変わらない。印も入力の印も書けないsessionでは、人が打った入力はその間隔のあいだ前のcaptureの推定に隠れうる。読む側ごとに最後の入力が違うので（`ExitWatch`は印の隣の入力の印だけ）、区間とcaptureはidleの印ごとに1つを共有し、推定を使う側がそれぞれの最後の入力より後に始まった区間だけを受け取る。
  - **記録**: 区間ごとに1回、runのevent `idle_inferred`（`phase`（`session` / `resume` / `revise` / `exit_wait`）、`workspace_id`、`source`、`marker`、`since`、`observed_secs`、`captures`、`background_running`、あれば`hook_error`）を記録する。`hook_error`はresumeしたsessionのdebug log（`<run-dir>/claude-resume.log`、`RESUME_DEBUG_LOG`）、最初のsessionのdebug log（runの`log_path`）の順に探す。
  - `worker_question`への回答の配送（`SessionWatch::deliver_answers`、task 844）: 印が無いか最新のaskの`created_at`より古いときだけ推定を使い、最後の入力に最新のaskの`created_at`・段の`input_at`・supervisorが最後に打った文の時刻を足す（[workerの質問への回答の送信](worker-question-answer.md)）。最初のsession・resume・reviseのどの段でも同じで、`idle_inferred`の`phase`は`SessionWatch`が持つ段の名前（`session` / `resume` / `revise`）。
  - 復旧jobの`send_instruction`の前提（`SessionWatch::at_prompt`、task 844）: 印と入力の印で成り立たなければ、段の`input_at`とsupervisorが最後に打った文の時刻を最後の入力に足した推定のidleで成り立つ（その後にEscで中断されたturnの規則を見る。[receiptの無いidleの検知](idle-without-receipt.md#receiptの無いidleの検知)、task 672）。推定のidleにbackgroundの表示があっても成り立つ（指示を打っても確認画面は出ない）。
