# Receipt and session exit

receiptの受領とセッション終了は別の事象である。agentはreceiptを`<run-dir>/receipt.json`へ一時ファイルからrenameして公開し、応答完了後もセッションを維持する。セッション終了はwrapperが記録する終了コード（`session_exited`）だけで確認し、画面文言は使わない。

receipt受領後の流れは次の順で自動化している。[ADR-0027](../../adr/0027-keep-worker-session-through-review-revise-verdict-and-merge-tree-precheck.md)の決定1で、idleになったsessionにはすぐ`/exit`を送らず、sessionを開いたまま[Validation](validation.md#validation)と[Review](review.md#review-supervisor)に進み、`/exit`はverdictが出た後に送る。

1. **idle判定**: Claude adapterがrunごとの`<run-dir>/claude-settings.json`に`Stop` hookを書き、`--settings`で渡す。hookはClaudeが応答を終えるたびにstdinのイベントJSON（`session_id`、`hook_event_name`など）を`<run-dir>/idle.json`へ一時ファイル + renameで書き、置き換える前に同じ内容を時刻付きで`<run-dir>/idle.log`へ追記する（`long_background`の経過の起点。`running`の処理を載せないmarkerではlogをその1行に置き換え、今の連なりの分だけを持つ。task 422。[stats](stats.md#stats)）。supervisorはreceiptを観測した後、`idle.json`のmtimeが`receipt.json`のmtime以上で、markerの`background_tasks`に`status`が`running`の要素が無ければ「receipt提出後に応答が完了した」と判定する。receiptより古いmarker（質問で止まった以前のturnなど）は無視する。**idleの定義**（task 147。`IdleMarker`。markerの内容の読み取り、つまり`background_tasks`と記録するhookのフィールドはClaude Code固有の形式なので`AgentSignals::idle_hook`（`infrastructure::claude`）が行い、mtimeとreceiptの比較はapplicationが行う）: Stop hookのmarkerがあり、その`background_tasks`に`running`の処理が無いこと。Claude Code（2.1.281で確認）はbackgroundの処理（`run_in_background`のshellなど）を残してturnを終えてもStop hookを発火し、入力JSONの`background_tasks`に`{id, type, status: "running", description, command}`を載せる。その間に`/exit`を送ると「Background work is running」の確認画面が出て、処理が終わっても誰かが答えるまで消えない。処理が終わるとClaude Codeは自分でturnを再開し、Stop hookが`background_tasks: []`で再び発火するので、supervisorはそのmarkerを待つ。`background_tasks`の無いmarker（古いClaude Code）は従来どおりidleとみなす。markerのmtimeと内容は1つのopenしたfileから読む（hookはrenameで置き換えるので同じ書き込みのものになる）。画面は読まない（ADR-0016のTUI非結合）。この定義は、最初のsessionのidle、resumeの(i)(ii)、reviseの書き直し、verdictの後の`/exit`で使う（[workerの質問への回答の送信](worker-question-answer.md#workerの質問への回答の送信)は従来どおりmarkerのmtimeだけを見る。promptへの打ち込みは確認画面を出さず、`/exit`だけが出すため）。終わらないbackgroundの処理でrunが無期限に止まらないよう、最初のsessionはreceiptを観測してから`resume_timeout`（既定1時間）過ぎれば（supervisorの引き継ぎ（adoptとexecの引き継ぎ）の後も、引き継いだ時刻ではなく記録した`receipt_observed`の時刻から数える。task 879）、`running`の処理が残っていてもreceipt以上に新しいmarkerで先へ進む（`session_idle_observed`の`background_running: true`。その後の`/exit`は、その同じmarkerのままなら下の2のとおり待ち直さずに送り、確認画面で止まれば3の`stuck_exit`のaskになる。task 242。receiptから`stuck_exit`のaskまでは`resume_timeout`とexit timeoutと復旧jobの分に収まり、以前のように`resume_timeout`の2倍はかからない）。判定の根拠（両ファイルのmtime、hookのフィールド、`background_running`）は`session_idle_observed`に記録する。権限確認や質問で止まっているturnでは`Stop`が発火しないため、その間は先へ進まない。idleと判定したら`finish_supervision_live`でrunを`running`から`validating`にし（`supervision_finished`の`{"status":"validating","exit_code":null,"session_live":true}`）、同じleaseのまま検証に進む。sessionは開いたまま。
2. **終了要求**（verdictの後。[Review](review.md#review-supervisor)の5）: idle markerが`running`のbackgroundの処理を示している間は送らずに待ち（receiptの後にsessionが別のturnでbackgroundの処理を始めた場合。上限は`ExitWatch`を始めてから`resume_timeout`で、過ぎれば送り、確認画面で止まれば下の3の`stuck_exit`のaskになる。ただしidle markerが、最後の`session_idle_observed`が`background_running: true`で記録したmarker（`marker_modified`が同じ秒）のままなら、1で既にreceiptから`resume_timeout`待ったbackgroundの処理なので待たずに送る（task 242。reviseやresumeでsessionが別のturnを取ればmarkerが書き直されるので、そのときは待つ）、logに1回だけ書く。`WorkspaceBackend::send_exit(workspace_id)`で、cmuxでは`cmux send --workspace <uuid> -- /exit`の後に`cmux send-key --workspace <uuid> -- enter`を送る。人が打つのと同じ経路で、1回だけ送り、プロセスのkillはしない。cmuxの時間切れで`/exit`が届かなかったと画面で分かるときだけ、backoffを置いて`call_attempts`回まで送り直す（task backend_timeout`、`workspace_id`、`attempts`、`action`、`close_and_land`でないときは理由の`held`）を記録し、次の条件がそろえばworkspaceを閉じて（sessionはそれで終わる。`workspace_closed`を記録し、sessionの`answer_prompt`のaskを閉じる）sessionが終わったものとして進む（`action: close_and_land`。[Review](review.md#review-supervisor)の5の着地へ。workspaceを閉じられなければ着地せず、下の復旧jobとaskにする）: verdictの後の行き先が着地（reviewがpass、または承認された解消済みのresume）であること、`check_receipt`（validationと同じ検査）が通ること、つまりreceiptの`commit`がworktreeでcheckoutされたrun branchのHEADで、worktreeがcleanで、evidenceとscopeが満たされていること、そのHEADがreviewしたcommit（`result_commit`。無ければ進まない）であること。どれかが欠ければ（`action: recover`。task 441の前は`ask`）、`exit_request_timed_out`（`unsent: true`付き）を記録して下の3と同じ`stuck_exit`の復旧jobを直ちに起動し（`recovery_requested`の`unsent`に`held`の理由。`/exit`は届いていないのでBackground workへの応答の条件はそろわない）、escalateしたら`stuck_exit`のaskを作り（questionの`after`の頭に届かなかったことと`held`の理由が入る）、runは手放さずにsessionの終了を待つ。`exit_unsent`の`action: close_and_land`を記録してから`workspace_closed`を記録する前にsupervisorが死んだとき（最新の`exit_requested`の後に`close_and_land`の`exit_unsent`があり、その後に`workspace_closed`も`exit_request_timed_out`も無いrun。`RunHistory::latest_exit_unsent_to_land`）は、引き継いだsupervisor（`adopt_review`）が`exit_timeout`を待たずに同じ条件（`landable_without_exit`）を判定し直す（task 464）。そろえばworkspaceを閉じ（cmuxが一覧に出さないworkspaceは閉じ済みとして扱い、閉じるのに失敗しても一覧から消えていれば閉じたものとする）、`workspace_closed`を記録してsessionの`answer_prompt`のaskを閉じ、`auto_repaired`（`exit_forced_close`、`conditions`に`adopted: true`と`exit_unsent`の`attempts`）を残して着地へ進む。そろわないか閉じられなければ、`exit_request_timed_out`（`unsent: true`、`adopted: true`、理由の`held`）を記録し、上と同じ`stuck_exit`の復旧jobとaskの経路に進む（askは開いたものを二重に開かない）。`/exit`は送り直さない。`action: recover`の`exit_unsent`の後は`exit_request_timed_out`が記録済みなので、今までどおりの引き継ぎになる。`ExitWatch`以外の`/exit`（走行中のsessionやresumeのsession、runtimeのplanner）は`Unsent`を無視して従来どおり`exit_timeout`を待つ。`exit_requested`（`timeout_secs`付き）は送る前に記録する。sessionは`enter`で即座に終わり得て、wrapperの`session_exited`が`send_exit`の戻りより先にcommitされることがあるので、送った後に記録するとイベントの順序が因果と逆になる。送信の失敗はrunをabandon（leaseを外す）するので、引き継ぎの対象にならない。記録と送信の間でsupervisorが死んだ場合だけ、引き継いだsupervisorは`exit_requested`を見て`/exit`を送らず、runは`exit_request_timed_out`まで待って人の`/exit`を待つ（送った後に記録していたときは逆に`/exit`を2回送り得た。2回送らないことを優先する）。
3. **終了確認**: wrapperの`session_exited`を待ち、workspaceを閉じて次へ進む（[Review](review.md#review-supervisor)の5）。ADR-0027より前のsupervisorが`/exit`を要求済みのrunを引き継いだときは、従来どおり`session_exited`を待って`supervision_finished`へ進む。要求から`WorkspaceBackend::exit_timeout`（cmuxは120秒）以内に終了しなければ（最初のsessionの`/exit`を引き継いだsupervisorは、記録した`exit_requested`の時刻（その後に規則でダイアログに応答していればその`auto_repaired`の時刻）から数える。task 879）、`exit_request_timed_out`（`workspace_id`、`timeout_secs`）を1回だけ記録してlogに書き、そのrunを手放さずに監視を続ける（ADR-0019の決定2）。runはそのときのstatus（verdictの後なので`awaiting_integration` / `needs_session` / `failed`。前の経路で引き継いだrunは`running`）のままleaseも保持し、`last_error`と`runtime_error`は書かない。Claude Code自身のダイアログなどが`/exit`を止めた状態を想定しており（典型は、workerが残したbackgroundのshellや待ちループに対する「Background work is running」の確認画面。promptとresumeの依頼が`STOP_BACKGROUND`で予防する。[Prompt](prompt.md#prompt)）、`/exit`は再送しない（開いたダイアログの別の選択肢を押しかねないため）。ただし記録の前に画面を読み、[既知のダイアログ](prompt-waiting.md#既知のダイアログ)のうち「Background work is running」なら、worktreeがcleanでreceiptの`commit`がHEADのときだけ「Exit and stop tasks」を選んで`auto_repaired`を記録し、exit timeoutを数え直す（ADR-0047の決定29、task 355）。条件がそろわなければ`known_dialog_unanswered`を記録して下の記録に進む。記録の後、supervisorはまず[生きているsessionの復旧job](background-recovery-job.md#生きているsessionの復旧job)（alert `stuck_exit`。ADR-0047の決定39・40、task 441）を起動し、そのrepair（`answer_known_dialog`・`stop_processes`ならexit timeoutを数え直す。着地するrunの`close_and_proceed`ならworkspaceを閉じて着地へ進む。`wait`なら再確認まで待つ）が適用されればaskは作らない。jobがescalateしたか、自信が無いか、前提が崩れたか、失敗したか、3回を使い切ったときに、supervisorはinbox宛ての`kind: stuck_exit`のaskを作る（task 104。常駐sessionの退役で`send /exit`のattentionを拾う役が居なくなるため、ADR-0019の決定2の「timeoutで人に知らせる」を[ADR-0022](../../adr/0022-ask-answer-inbox-planner-and-landing-on-doubt.md)の決定5の枠組み（通知はaskだけ）で行う）。askはtaskとrunに紐づき、`asked_by`は`supervisor`、optionsは`exit`（ダイアログに応答してsessionを終わらせ`/exit`を送る）と`wait`（sessionをそのままにする）にjobの`options`を足したもの、`reason_category`はjobの値（既定`recovery_failed`）で、questionは人に宛てて、jobのdiagnosisと推奨の操作に加えて、run id・task id・timeoutの秒数・workspace id・sessionが終わった後にrunがどう進むか（`running`なら`validating`へ、verdictの後なら着地・`approve_landing`のask・review by hand・resume・人への引き渡しのどれか。`ExitWatch::after`）・2つの選択肢の意味と、`WorkspaceBackend::capture`で読んだ画面の末尾15行（空行を除く。[ダイアログ待ちの検知](prompt-waiting.md#ダイアログ待ちの検知)の`excerpt`と同じ`screen_tail`。読めなければその旨）を持つ。同じ（run、kind）のopenなaskがあれば作らず（askの重複抑止）、通知は新しいaskのときだけaskの経路で1回inboxへ送る（[人への通知](cmux-notify.md#人への通知cmux-notify)）。引き継いだrunは、`exit_request_timed_out`が記録済みで`stuck_exit`のaskが（closeされたものも含めて）1件も無いときだけ復旧jobから始め直す（記録とaskの間でsupervisorが死んだ場合と、askを作らない前のversionのbinaryが記録したtimeout）。`exit_request_timed_out`のイベント自体はattentionではなく（`event_attention`は`None`。kind名とpayloadはそのまま記録する）、`status`もこのrunをrunのattentionに出さない（`run_attention`は`exit_pending`の`running`に`None`を返し、その前の`prompt_waiting`も出さない）。人に届くのは`stuck_exit`のaskの`ask_opened`（`answer ask <id>`、role inbox）で、`send /exit`の`next`は無くなった（`AttentionNext::SendExit`を消した）。inboxは人に見せてanswerを書き戻し、その`ask_answered`（`read the answer of ask <id> and close it`）を受けて、人の指示として`dagq-recover` skillの`reference/stuck-exit.md`に従って動く: 画面を読み、「Background work is running」なら worktreeがcleanでreceiptの`commit`がHEADを指すことを確かめてから「Exit and stop tasks」を選び（確かめられなければ選ばず人に確かめる）、ほかのダイアログは人の選んだキーで応答してから`/exit`を送る。`wait`ならsessionに触らず`ask close`する。人がsessionを終わらせれば、wrapperの`session_exited`を観測した時点で、supervisorはそのrunのcloseされていない`stuck_exit`のaskを閉じてから（未回答なら`answer`に`the session exited; closed by the runtime`を書いて`ask_answered`（`ask_id`、`kind`、`runtime_closed: true`）を記録する。`runtime_closed`の`ask_answered`はattentionではない。回答済みなら`closed_at`だけ）、runを進める: `running`（前の経路）なら通常どおり`supervision_finished`→`validating`へ、verdictの後なら[Review](review.md#review-supervisor)の5のとおりworkspaceを閉じて着地・`approve_landing`のask・`review_failed`・resume待ち・`failed`のまま（workspaceは残す）のどれかへ。wrapperのheartbeatが切れた場合は、wrapperのプロセスが死んでいれば従来どおりabandon（下記）、生きていれば下の[wrapperが黙ったsession](silent-wrapper.md#wrapperが黙ったsession)になる。supervisorがleaseを持っている間は`recover`が拒否されるので、人が止めるときは`down --force`でsupervisorを止めてから`recover`する経路も変わらない。引き継いだrunは`exit_request_timed_out`が記録済みなら再記録しない。このrunはsessionが終わるまでslotを占め、drain（`down --wait`、SIGINT / SIGTERM、`up`によるversionの入れ替え、`--once`）もそのrunを待ち続けるので、drainの前に`stuck_exit`のaskを片付けてsessionを終わらせる（待てなければ`down --force`）。

人の手動`/exit`はいつでも有効で、markerがない（hookが無効化されているなど）場合は従来どおり手動終了を待つ。sessionがreceiptの後に自分で終わった場合は、wrapperの`session_exited`から`supervision_finished`（`exit_code`付き）→`validating`へ進み、reviewでは`/exit`を送らずにworkspaceを閉じる。ただし生きているsessionが無いので、`revise`は人に聞く（`approve_landing`）。

## 画面からのidleの推定

[ADR-t803-1](../../adr/2026-09-27-t803-1-infer-idle-from-the-screen-when-the-idle-marker-is-missing-or-stale.md)。idleの印（`idle.json`）は主な信号のまま残し、印が無いか最後の入力より古いときだけ、画面（`cmux capture`）からidleを推定する。判定はproviderにもsessionの種類にも依らない`application::screen_idle`の1つにまとめ、plannerの`planner_view`（[Plan planners](plan-planners.md)）と、workerの最初のsession・resume・reviseのsession（下の[workerのsession](#workerのsession)、task 804）が使う。

- **印が判断できないとき**: 印が無い（`missing`）か、印のmtimeがsessionの最後の入力より古い（`stale`）。最後の入力は`screen_idle::last_input`が、agentの入力の印`prompt-submit.json`のmtime、supervisorが打った文の印`supervisor-input.json`（`SUPERVISOR_INPUT_FILE`。supervisorが文をsessionに打つ直前に`record_supervisor_input`が書く。plannerではreviseの配送とplanner_questionのanswerの配送。`/exit`は書かない）のmtime、sessionを開いた時刻（plannerは行の`created_at`）の遅い方として読む。印が最後の入力より新しい間は、今までどおり印で判断する（印の`background_tasks`に`running`があれば`working`）。
- **1回のcaptureの見え方**（`screen_idle::look` / `look_of`）: 入力欄が入力を受けられ（`AgentSignals::input_ready`）、作業中の表示が無く（`AgentSignals::working`）、ダイアログも無い（`AgentSignals::detect_prompt`）なら`Idle`で、`AgentSignals::transcript`の指紋と、画面にbackgroundの処理が動いている表示があるか（`AgentSignals::screen_background`。task 823）を持つ。`screen_background`の既定は`None`（画面から読めないprovider。backgroundの処理が無いものとして扱う）で、Claude adapter（`claude::background_on_screen`）は入力欄の下の行（status line）を`·`で区切った項目のうち、0より大きい数とbackgroundの処理の種類（`shell(s)`・`background task(s)`・`monitor(s)`・`agent(s)`、`BACKGROUND_COUNTS`）の組（例 `⏵⏵ auto mode on · 3 shells · ← for agents · ↓ to manage`。2026-09-28のClaude Codeで確認）があれば`Some(true)`、無ければ`Some(false)`を返す。数の無いhint（`← for agents`）と入力欄より上のtranscript（`3 shells still running`）は読まない。それ以外（作業中、ダイアログ、入力欄が無い）は`Busy`、captureの失敗は`Unreadable`。
- **区間**（`screen_idle::observe`、`Observation`）: `Idle`のcaptureは、最後の入力より後に始まり同じtranscriptで同じbackgroundの表示の区間を延ばし（backgroundの処理が終わって表示が消えれば新しい区間になり、そこから`screen_idle_secs`を数え直す）（前のcaptureより後の秒のときだけ`captures`を1つ足す）、そうでなければ新しい区間を始める。`Busy`は区間を終わらせ、`Unreadable`は区間をそのままにする。supervisorは区間をメモリ（`Spans`）に持ち、idleの印の隣の`screen-idle.json`（`SCREEN_IDLE_FILE`。`first_seen`・`last_seen`・`captures`・`transcript`・`background`・`recorded`。`background`の無い古い写しは`null`として読む）には写しを書けるときに書く。ディスク満杯で写しが書けなくても区間は失われない（写しは読むだけのコマンドと、引き継いだ次のプロセスがメモリに無い区間を読むためのもの）。
- **推定**（`ScreenProbe::infer`、`Observation::idle`）: 今のcaptureが読め、区間の`captures`が2以上で、`last_seen - first_seen`が`[stall].screen_idle_secs`（既定120秒、`DEFAULT_SCREEN_IDLE_SECS`。[Stall thresholds](stall-thresholds.md)）以上ならidleと推定し、idleの始まり（`idle_since`）を区間の`first_seen`に、推定の`background_running`を区間の`background`にする。今のcaptureが読めなければ推定しない（`working`）。supervisorは区間を持って写しを書き（`ScreenIdle::Record(&Spans)`）、読むだけのコマンド（`dagq planners`）は書かずに次のcaptureとして判断する（`ScreenIdle::Peek`。閾値はmain checkoutの`dagq.toml`の`[stall]`、読めなければ既定値）。
- **記録**: supervisorは区間ごとに1回、queueのevent `idle_inferred`（`source: "screen"`、`marker`（`missing` / `stale`）、`since`、`observed_secs`、`captures`、`background_running`（画面から読んだbackgroundの表示の有無。読めないproviderは`null`）、plannerでは`planner_id`・`origin`・`workspace_id`）を記録し、区間の`recorded`を立てる（`Spans::mark_recorded`）。eventを書けなかったとき（queueのエラー）はlogに残して他のplannerの扱い（reviseやanswerの配送、`/exit`）を止めず、次のpassで記録し直す。agentのdebug log（plannerは`<planner dir>/claude.log`、`PLANNER_DEBUG_LOG`）の末尾64KiBにidleのhookの失敗の行があれば（`screen_idle::hook_failure`、`AgentSignals::idle_hook_failure`。Claude Codeでは`Hook Stop`と`error`を含む最後の行）、その先頭300文字を`hook_error`に入れる。`dagq events --kind idle_inferred`で読める。
- **backgroundの処理**（task 823）: 画面にbackgroundの処理の表示がある推定は、印の`background_tasks`に`running`があるときと同じに扱う（区間を切って`working`にする形は取らなかった。印の`background_running`の待ちと`stuck_exit`までの流れ（task 147・242）にそのまま乗せるため）。plannerは`working`のままで（`PlannerProbe::screen_idle`の`IdleProbe::background_running`）、runtimeのplannerも`/exit`を受けない。表示が消えれば新しい区間が`screen_idle_secs`続いたところでidleになり、`/exit`を受ける。backgroundの表示のある区間も`idle_inferred`（`background_running: true`）に記録し（`dagq planners`の`idle_inferred`も`working`のまま出す）、表示が消えた後の区間は別に`background_running: false`で記録する。表示を読めないprovider（`screen_background`が`None`）では今までどおりbackgroundの処理が無いものとして推定し、backgroundを残したruntimeのplannerは「Background work is running」の確認で止まって`end_runtime_planners`がexit timeoutの後にworkspaceを閉じる。
- **限界**: 印が最後の入力より古いだけ（turnを始めないslash commandの後など）のplannerは、以前はすぐ`idle`だったが、今は`screen_idle_secs`の間`working`に見える。
- **workerのsession**<a id="workerのsession"></a>（task 804、`Supervisor::session_idle`）: 印を読む次の判定は、印が無いか最後の入力より古ければ画面の推定を印と同じidleとして扱う。推定のidleは区間の`first_seen`に書かれた印のように扱い、画面にbackgroundの処理の表示があれば印の`background_running`が立ったものとして扱う（`IdleMarker::inferred`。`background_tasks`は載らない）。推定できなければ読んだ印（古くても）をそのまま使うので、印の新しいsessionの振る舞いは変わらない。
  - 最初のsessionのreceiptの後のidle（上の1、`SessionWatch::poll`）: 最後の入力にreceiptのmtime（とsupervisorがreviseなどで打った時刻、古いreceiptの書き直しの依頼の時刻）を足すので、receiptより後に始まった区間だけがidleになる。`session_idle_observed`のevidenceは印の代わりに`source: "screen"`・`marker`・`observed_secs`・`captures`を持ち、`marker_modified`は区間の`first_seen`、`background_running`は画面から読んだbackgroundの表示の有無（読めないproviderは`null`）。backgroundの表示があれば、印の`background_running`と同じく`resume_timeout`まで待ってから先へ進む。
  - receiptの無いidle（[receiptの無いidleの検知](idle-without-receipt.md#receiptの無いidleの検知)、`StallWatch`）: 最後の入力にsupervisorが最後に打った文の時刻を足す。
  - resumeとrevise・衝突の依頼の段（[Needs session](needs-session.md)、[Review](review.md#review-supervisor)）: 最後の入力に依頼と回答の時刻（`input_at`）、書き直されたreceiptのmtime（resumeでは古いreceiptの書き直しの依頼の時刻も）を足す。印が書けなくても入力待ちになれば、`resume_timeout`を待たずに段を終える。
  - verdictの後の`/exit`（上の2、`ExitWatch`）: 印が最後の入力より古く画面がidleなら、画面にbackgroundの処理の表示が無ければ`/exit`を送り、あれば印のbackgroundの処理と同じく待つ（`background_waits`）。
  - **backgroundの処理**（task 823）: Claude Codeは処理を残してturnを終えると作業中の表示は出さないが、入力欄の下のstatus lineに処理の数（`3 shells`など）を出すので、推定のidleはその表示の有無をbackgroundの処理として持つ。表示があれば印の`background_running`と同じ流れ（receiptの後は`resume_timeout`まで待って進み、verdictの後の`/exit`も待ち、同じ印のまま確認で止まれば`stuck_exit`）になり、表示が無ければbackgroundの処理が無いidleとして扱う。表示を読めないproviderは今までどおりbackgroundの処理が無いものとする（backgroundが走っている扱いにすると、印の書けないsessionはreceiptの後も`resume_timeout`まで待ち、goal 56が防ぐ放置に近づくため。そのとき`/exit`が確認で止まれば、worktreeがcleanでreceiptの`commit`がHEADのときだけ[既知のダイアログ](prompt-waiting.md#既知のダイアログ)として応答するか、`stuck_exit`の復旧jobにかかる）。receiptの無いidleの促しとそのpayloadの`background_running`は画面から読んだ値（読めないproviderは`null`）になり、表示があれば促しに「Background work was still running when you stopped.」、askに「background work was running (not listed)」と書く（`stall_nudge`の`running`）。
  - **capture**: 印が判断できないsessionは、pollごとではなく`screen_idle_secs`の半分（上限60秒、`idle::probe_interval`）に1回だけ画面を読み、その間は前のcaptureの推定を使う（作業中のsessionのcaptureを増やしすぎないため）。推定は閾値より最大でその間隔だけ遅れる。作業中のturnでも入力の印（`prompt-submit.json`）が印より新しければ判断できない扱いになるので、receiptの無いidleの検知は作業中のworkerの画面もこの間隔（既定60秒）で読む（増えるcaptureの負荷と引き換え）。印も入力の印も書けないsessionでは、人が打った入力はその間隔のあいだ前のcaptureの推定に隠れうる。読む側ごとに最後の入力が違うので（`ExitWatch`は印の隣の入力の印だけ）、区間とcaptureはidleの印ごとに1つを共有し、推定を使う側がそれぞれの最後の入力より後に始まった区間だけを受け取る。
  - **記録**: 区間ごとに1回、runのevent `idle_inferred`（`phase`（`session` / `resume` / `revise` / `exit_wait`）、`workspace_id`、`source`、`marker`、`since`、`observed_secs`、`captures`、`background_running`、あれば`hook_error`）を記録する。`hook_error`はresumeしたsessionのdebug log（`<run-dir>/claude-resume.log`、`RESUME_DEBUG_LOG`）、最初のsessionのdebug log（runの`log_path`）の順に探す。
  - 対象外: workerの`worker_question`への回答の配送（`deliver_answers`）、ダイアログ待ちの検知の片付け、`long_background`の検知は今も印だけで判定する（画面の推定のbackgroundの表示は`long_background`にかけない）。復旧jobの`send_instruction`の前提（`at_prompt`）は画面から推定したidleを使わず、印と入力の印で判定し、Escで中断されたturnだけ画面の作業中の表示とダイアログを見る（[receiptの無いidleの検知](idle-without-receipt.md#receiptの無いidleの検知)、task 672）。
