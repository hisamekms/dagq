# `plan` / `planners`

> **予定（goal 92）**: runtimeのplannerの対話の経路は廃止し（[ADR-t1433-2](../../adr/2026-10-03-t1433-2-abolish-the-interactive-route.md)）、非対話のplannerはbackgroundのwrapperだけで動く（[ADR-t1433-3](../../adr/2026-10-03-t1433-3-headless-wrappers-run-only-in-the-background.md)）。`[roles.runtime_planner]`の経路の欄と画面からのidleの推定（ADR-t803-1。置き換え済み）、plannerのworkspace、`planner screen` / `planner send`の記述は、後続のtaskが実装するまでの今の姿である（[runtimeのplannerの経路](#runtimeのplannerの経路)の予定の注記も見る）。廃止前から開いている人のplannerは、新しいバイナリが行を閉じた扱いにし、そのworkspaceにcmuxを呼ばない（ADR-t1433-2決定5）。末尾の予定の節はこれらの決定に合わせてある。

> 人が開くplannerは[ADR-t1394-1](../../adr/2026-10-03-t1394-1-abolish-person-planners-and-route-planning-through-inbox-requests.md)で廃止し、計画の入口をinboxからの依頼にする。依頼の記録・CLI・依頼ごとのruntimeのplanner・結末・`planner_question`の行き先は実装した（task 1395、[inboxからの計画の依頼](#inboxからの計画の依頼)）。`dagq plan`は案内を付けて拒む（task 1399、下の`dagq plan`）。人のplannerを前提にした行き先の読み替えは実装した（末尾の[予定: inboxからの依頼と非対話のplanner](#予定-inboxからの依頼と非対話のplanner)の2）。廃止前から開いている人のplannerは、今はADR-t1394-1決定9のとおり終わるまで動き、下の「人のplannerの終わり」で閉じる（ADR-t1433-2決定5の、行を閉じた扱いにすることは**まだ実装していない**。末尾の予定の1）。runtimeのplannerの経路（対話・非対話）は[ADR-t1394-2](../../adr/2026-10-03-t1394-2-runtime-planner-route-interactive-or-headless.md)の決定1・2を実装した（下の[runtimeのplannerの経路](#runtimeのplannerの経路)。区間・控え・ADR-t1228-1のCLIの非対話の扱いはまだ）。

[ADR-0044](../../adr/0044-findings-proposals-from-findings-and-quiet-observer.md)の決定1・6・12・13。plannerは常駐せず、proposalごとにオンデマンドのworkspaceを開く。use caseは`src/application/planner.rs`、entry pointは`compose::planners` / `compose::planner_session`（`dagq plan`は`main.rs`で拒む）。

- **記録**: planner 1つが`planners`表（schema v23、[persistence](../persistence.md)）の1行。`session_workspaces`はroleが主キーでplannerを1つしか持てないので使わない。行は`origin`（`person` / `runtime`）、runtimeが立てたときの`proposal_id`、workspaceのUUID（`workspace_id`、UNIQUE）、session wrapperの`wrapper_pid` / `agent_pid` / `heartbeat_at` / `exit_code` / `exited_at`、終わった印の`closed_at`と`error`、agentの経路の`route`（schema v60、`migrations/0060_planner_route.sql`。`headless`か、NULLの`interactive`。開くときに`set_planner_route`で書く）を持つ。plannerのディレクトリは`<queue dir>/planners/<planner-id>/`で、初期prompt（`prompt.txt`）、wrapperとして動くバイナリの写し（`runner`。runの`runner`と同じく、ビルドし直しても動いているplannerは変わらない）、Claudeのsettings（`claude-settings.json`）・debug log（`claude.log`、`PLANNER_DEBUG_LOG`）・idle marker（`idle.json`）とその履歴（`idle.log`。runと同じhookが書き、`running`の処理を載せないmarkerで切り詰める。[stats](stats.md#stats)）、入力の印（`prompt-submit.json`）、supervisorが打った文の印（`supervisor-input.json`）、画面のidleの区間（`screen-idle.json`。[画面からのidleの推定](receipt-and-session-exit.md#画面からのidleの推定)）を置く。
- **`dagq plan`**（[ADR-t1394-1](../../adr/2026-10-03-t1394-1-abolish-person-planners-and-route-planning-through-inbox-requests.md)決定1、task 1399）: 何も開かず、行も作らず、cmuxもClaudeも呼ばずに失敗し、errorに案内（`application::planner::PLAN_REFUSED`）を出す: 人が開くplannerは廃止したこと、計画はinboxに人の言葉で頼み、inboxが計画の依頼として記録する（`dagq request add --text '...'`。`DAGQ_ROLE`の無いterminalの人も打てる）と、supervisorがruntimeのplannerを立ててsubmitか理由付きの却下まで進めること（`dagq requests`で追う）、開いているplannerは終わるまで動くこと（`dagq planners`）、plannerは開かなかったこと。前の`plan`の引数（`--plugin-dir` / `--repo` / `--cmux` / `--claude`）は受け付けて無視し、同じ案内を出す。権限の検査（`planner.open`）は前のままなので、打てるactor（人・inbox・planner・supervisor）は案内を、打てないactor（observer・worker・job）は今までどおりの`authorization_denied`を受ける。人が`DAGQ_ROLE`の無いterminalで打つ`add` / `goal add` / `submit`は今までどおり通る（決定8）。
- **plannerの開き方**（`open_planner`。runtimeのplannerを`open_runtime_planner` / `open_draft_planner`が開く）: 何度でも新しいworkspaceを開くので、plannerは複数同時に開ける。行を作り、ディレクトリに残っている`idle.json`を消し（queue DBを作り直すとplannerのIDは1から振り直されるので、前のDBの同じIDのplannerが残したmarkerで新しいplannerが`idle`に見えないように。task 344）、promptと`runner`を書き、`cmux workspace create --name "[<repo>]planner#<id>" --description "dagq role=planner queue=<queue hash> planner=<id>" --env DAGQ_ROLE=planner --env DAGQ_QUEUE=<db> --env DAGQ_SESSION_KIND=<planner、runtimeが立てるものはruntime_planner> --env DAGQ_PLANNER_ORIGIN=<origin> --env DAGQ_PLANNER_ID=<id> --env DAGQ_LAUNCH=<launchのJSON> [--group <queueのgroup>] --command "<planner dir>/runner --db <db> planner-session --planner <id> --claude <resolved> [--plugin-dir PATH] [--model <model> --effort <effort>]" --focus false --cwd <repository root>`で作り、UUIDを行に書く。cmuxが作れなければ行を`error`付きで閉じてerrorで止まる。createが失敗を返してもcmuxが実際にはworkspaceを作っていることがある（createの時間切れ。planner#236、task 806）ので、失敗したときは`ActorExecutor`（`close_unrecorded`）が`WorkspaceBackend::workspaces_described`でdescription（`dagq role=planner queue=<queue hash> planner=<id>`。そのplannerだけを名指す）が一致するworkspaceを全windowの一覧から探して閉じ、閉じたか・閉じるのに失敗したかをerrorに書く（一覧が取れなければerrorはそのまま）。一覧の後に遅れて作られたworkspaceは、下のwrapperが自分で閉じる。UUIDを行に書けなかったとき（`planner_workspace_created`の失敗）も、そのworkspaceを閉じてから行をerror付きで閉じる。作った後に`cmux identify`がUUIDを返さなければ、cmuxのadapter（`create_named`。runの`create` / `create_resume`も同じ）がそのworkspaceを作成の返答のhandle（`workspace:N`）で`workspace close`し（UUIDが無いので後から見つけられず、孤児として残るため。task 344）、閉じたか・閉じるのにも失敗したかをerrorに書く。行はそのerrorで閉じる。色`Blue`とpill`dagq_role planner --icon map`を当て（失敗は`warnings`）、ピンは付けない。結果は`{"planner": {planners表の行}, "name", "dir", "warnings", "launch"}`。**model / effort**（[Actor model](actor-model.md)、ADR-0079の決定7、task 580）: runtimeのplannerはsupervisorが読む`[roles.runtime_planner]`（`PlannerLaunch::roles`）で決め（廃止前の人のplannerは`dagq plan`がmain checkoutの`[roles.planner]`で開いた）、表が無ければ`--model` / `--effort`を付けない。reviseのために開くruntimeのplanner（`open_runtime_planner`）はeffortを1段上げる。決めた`launch`（`ActorLaunch`）は結果と`DAGQ_LAUNCH`に入り、pluginのhookが記録するplannerの区間の`session_opened`の`launch`になる。下記の**行の片付け**はsupervisorだけが行い（`dagq plan`はもう行わない）、`planners`は行を閉じない。`submit`は`CMUX_WORKSPACE_ID`と`DAGQ_PLANNER_ORIGIN`からproposalの持ち主を決めるので、plannerが出したproposalはそのworkspaceのものになる。
- **runtimeが立てるplanner**: `open_runtime_planner(launch, proposal, tasks, reasons)`がproposalの存在を確かめ、`origin: runtime`・`proposal_id`付きの行で`[<repo>]planner#<id> - proposal <proposal-id>`を開く。初期promptは`runtime_planner_prompt`で、proposal、そのtask（ID・状態・title）、plan reviewの指摘（reasons）と記録を読むCLI（`prompt::RECORD_READING`、ADR-0044の決定22、task 420: `dagq events --full --task ID`と絞り込み（`--run` / `--goal` / `--kind` / `--since` / `--until`。`--kind`が無ければattentionだけなので、全種類は`--all`を足す）と`dagq timeline RUN`）と、verify・paths・evidenceを決める順（`prompt::repository_rules`。[Prompt](prompt.md#repositoryの規則を読む順)）を載せ、直して`dagq submit --proposal <id>`で出し直すこと、計画の意図を変える修正はinboxにaskして答えを待つことを指示する。`DAGQ_PLANNER_ORIGIN=runtime`で出し直すので、そのplannerがproposalの持ち主になる。supervisorはplan reviewのrevise（持ち主のplannerが生きていないとき）とreopenでこれを呼ぶ（[Plan review (supervisor)](plan-review.md#plan-review-supervisor)の9）。follow_upの経路はgoal 29の後続taskが足す。
- **session wrapper（`planner-session`、hidden）**: runの`session`と同じく、自分を`register_planner_wrapper`で登録し（1つのplannerに1回だけ。閉じたplannerは拒む）、`AgentProvider::planner_command`（Claudeでは`claude --debug-file <dir>/claude.log --add-dir <dir> --settings <dir>/claude-settings.json [--plugin-dir PATH] -- '<prompt>'`をrepository rootで。settingsはworkerと同じ`stop_hook_settings`で、`Stop` hookが`<dir>/idle.json`を書く。runtimeが立てたplanner（origin `runtime`）はworkerと同じく入力欄のサジェストを止める`promptSuggestionEnabled: false`も持ち（`runtime_session_settings`、[Agent provider lifecycle](../provider-lifecycle.md)）、人が開いたplannerは持たない。wrapperはoriginを`planners`の行から読んで`PlannerCommand`に渡す）でagentを起動し（argvに`--model` / `--effort`があれば`AgentProvider::select_model`で渡す）、`register_planner_agent`し、agentが終わるまで`wait_interval`ごとに`heartbeat_planner`し、終了コードを`planner_exited`で記録する。人が開いたplanner（origin `person`）では、記録の後にterminal（stderr）へ`dagq closes this workspace in 60 seconds (planner <id>, exit code <code>, log at <planner dir>/claude.log)`の1行を出し（`exited_notice`。書き先は`PlannerWrapper::terminal`で、`planner-session`ではstderr）、結果のJSONにも`notice`として載せる。workspaceを閉じるのは下の「人のplannerの終わり」のsupervisorで、wrapperは閉じない（ADR-t1300-1）。logは`<queue dir>/logs/planner-session-*.jsonl`。**登録を断られたwrapper**（task 806）: 閉じた行か、別のwrapperが登録済みの行で`register_planner_wrapper`が断ると、wrapperは断られたことをlog（`warn`）に書き、自分のworkspace（cmuxが渡す`CMUX_WORKSPACE_ID`）を行が記録していなければ（`workspace_id`が無いか別のもの）そのworkspaceを`cmux workspace close`で閉じてから（`application::session::wrapper_refused`）errorで終わる。createが失敗扱いになって行が閉じた後にcmuxが作ったworkspaceは、UUIDがどこにも無いので他に見つける手段が無いため。行が記録している自分のworkspace（同じplannerの2つ目のwrapperなど）は閉じない（そのplannerのものなので、終わらせる側に任せる）。行が読めなければ閉じない。閉じるcmuxはhiddenの`--cmux`（既定`cmux`、PATHで解決。launcherはargvに付けない）で、`CMUX_WORKSPACE_ID`が無ければ（cmuxの外）閉じずにlogだけ書く。
- **非対話のplannerのwrapper**: `route`が`headless`の行のwrapper（`planner-session --headless`、backgroundなら`--background`も）は、agentを1つ起動する代わりに非対話のworkerと同じ`Turns`でturnを動かす（下の[runtimeのplannerの経路](#runtimeのplannerの経路)、[非対話のworker](headless-worker.md#非対話のruntimeのplanner)）。端末は要らず（`--headless`の無いwrapperだけが端末を確かめる）、終了の依頼で0、sessionを終わらせたturnの後は1で`planner_exited`を記録する。
- **生存とidleの判定**（`planner_view`、`PlannerSession::state`）: workerと同じ材料で決める。非対話のplannerは画面を読まず、idle markerが最後の入力より新しければ`idle`、そうでなければ`working`（下の[runtimeのplannerの経路](#runtimeのplannerの経路)）。対話のplannerは次のとおり。閉じた行か、workspaceのUUIDが`cmux workspace list`に居なければ`closed`。workspaceかwrapperの登録がまだなら`opening`、行を作ってから120秒（`PLANNER_STARTUP_SECS`）たってもそのままなら`lost`（cmuxがwrapperを起動できなかった、開いたプロセスがworkspaceを記録する前に死んだ）。agentの終了が記録されていれば`exited`。wrapperのPIDが死んでいるかheartbeatが30秒（`HEARTBEAT_TIMEOUT_SECS`）より古ければ`lost`。wrapperが生きていてもagentのPID（`agent_pid`）をまだ記録していなければ、markerや画面に依らず`opening`（agentの起動前の画面をidleと推定して、agentの居ないplannerに文面を送らない。originに依らない。task 1329）。それ以外は動いているsessionで、idle markerがplannerの最後の入力（`prompt-submit.json`、`supervisor-input.json`、行の`created_at`の遅い方）より新しければ、画面（`capture`）が作業中（`AgentSignals::working`）なら`working`、markerにbackgroundの作業が残っていなければ（`AgentSignals::idle_hook`）`idle`、残っていれば`working`。markerが無いか最後の入力より古ければ、画面からの推定（[画面からのidleの推定](receipt-and-session-exit.md#画面からのidleの推定)、ADR-t803-1）でidleで、画面にbackgroundの処理の表示（Claude Codeのstatus lineの`1 shell`など、`AgentSignals::screen_background`）が無ければ`idle`、そうでなければ（captureの失敗と、markerの`running`と同じく扱うbackgroundの表示を含む。task 823）`working`。`alive`は`opening` / `working` / `idle`。`idle_since`はidleのときのmarkerの書かれた時刻か、推定した区間の最初のcaptureの時刻（Unix秒）で、送った文面より後にidleになったかの比較に使える。推定でidleのときと、推定の区間にbackgroundの表示があって`working`のときは`idle_inferred`（`source`・`marker`・`since`・`observed_secs`・`captures`・`background_running`）も持つ。supervisorの`planner_views`は区間を持ち、区間ごとに1回queueのevent `idle_inferred`を記録する。これでStop hookが印を書けなかったruntimeのplannerも、仕事を終えれば`end_runtime_planners`が`/exit`を送り、終われば行を閉じる。backgroundの処理を残してturnを終えたplannerには、表示が消えて新しい区間が`screen_idle_secs`続くまで`/exit`を送らない（「Background work is running」の確認で止めてexit timeoutで閉じることを避ける）。`planner_question`の答えを打ち込まれたplannerは、`idle_since`が配送を取った時刻（`planner_answer_claimed`）より後なら答えを読み終えたとみなし、askが閉じた時刻とは比べない（askの`closed_at`は打ち込みの後に書くので、その前にidleになったplannerを待ち続けて枠をふさいだ。task 884）。上限で持ち主の居ないreviseが期限を過ぎて待つときは、何も待たないidleのruntimeのplannerを`/exit`して枠を空ける（`planner_released`。[Plan review (supervisor)](plan-review.md)の9）。人が開いたplannerには今までどおり`/exit`を送らず、`state`だけが直る（agentが終わった後は下の「人のplannerの終わり」で閉じる）。
- **runtimeのplannerの時間切れ**（`tell_of_silent_planners`、`tend_planners`の各pass、task 805）: 画面からの推定も効かない（captureが失敗し続ける、画面が見慣れない状態）ときのbackstop。runtimeが立てたplanner（draft・finding・reviseのどれも）で、`alive`かつ`idle`でないもののうち、最後に動きが見えた時刻（`planner_last_activity`: 最後の入力（`prompt-submit.json`・`supervisor-input.json`・行の`created_at`の遅い方）と、idle markerの書かれた時刻（最後の入力より古いものも）の遅い方）から`--planner-timeout`（既定3600秒、`PLANNER_TIMEOUT`。reviseの時間切れと同じ値）を過ぎたものについて、inbox宛てのattentionを出す。推定でidleのplannerは`idle`なのでこの対象にならず、`/exit`で終わる。kindは新しく作らず`planner_unresponsive`を広げた（attentionは同じ`check the planner`で、人がすることもそのplannerのworkspaceを見ることで同じため）。reviseの`planner_unresponsive`とはpayloadの`subject: "planner"`で分かれ、queueのevent（task・goal・runに付かない）として`planner_id`・`origin`・`workspace_id`・`draft_task_id`・`finding_id`・`state`・`last_activity`・`waited_secs`・`reason`を持つ（proposalの`proposal_id`は持たない）。plannerごとに1回だけで（`planner_silent`が同じトランザクションで既存のeventを確かめる）、その後に動いても消さず、もう一度は出さない。`status`のattention（`silent_planners`）はそのplannerの行が閉じるまで出て（その後にreviseを渡されたplannerはreviseの時間切れに任せて外す）、draftのplannerならdraftのtaskに付く。attentionのeventなのでKPIの`attentions_per_landing`にも数えられる。plannerは閉じず`/exit`も送らない。reviseを渡されたplanner（`revise_planner_id`がそのplanner）はreviseの`planner_unresponsive`（出し直されないまま`revised_at` / `sent_at`から期限）が見るので対象から外し、reviseの振る舞いは変えない。自分の`planner_question`を待っているplanner（`question_wait`。[Plan review (supervisor)](plan-review.md)の10）は人を待っているので対象から外す。人が開いたplannerは対象にしない。testは`tests/it/planner_timeout.rs`（入力とmarkerが期限を延ばすこと、期限を過ぎると1回だけ出て`status`と`watch`に`check the planner`で出ること、`/exit`も閉じもしないこと、人のplannerには出ないこと、行が閉じるとattentionが消えること、findingのplannerにも`finding_id`付きで1回だけ出ること、markerが無く画面で推定のidleになったplannerは`/exit`され期限を過ぎても出ないこと）。
- **人のplannerの終わり**（`close_exited_person_planners`、`PlannerSession::person_exit_closes`、[ADR-t1300-1](../../adr/2026-10-02-t1300-1-runtime-closes-exited-person-planners-after-a-grace.md)）: 人が開いたplanner（origin `person`）で、閉じていず、workspaceとwrapperが記録され、agentの終了（`exited_at`）から60秒（`PERSON_PLANNER_CLOSE_GRACE_SECS`。人が最後の画面を読むための猶予）を過ぎたものを閉じる。状態でいえば`exited`だけで、wrapperが死んだ`lost`（原因を見るために画面を残す）と生きているplannerは閉じない。cmuxの全windowの一覧（`listed_workspace_ids`を1回）に居るworkspaceを、runtimeのplannerと同じ閉じ方（`WorkspaceBackend::close`。cmuxのadapterはピンを外してから閉じる。task 184）で閉じ、行を閉じて`planner_closed`（`code: person_exited`、`workspace_closed: true`）を記録する。一覧に居ないworkspaceの行は下の行の片付けに任せる。一覧が取れなければ何も閉じず、closeが失敗した行は閉じずに残し（次の回で再試行）、どちらもlog（`warn`）に残す。行うのはsupervisorの`tend_planners`の各passの初め（`--no-claude`でも。`tend_planners`そのものを行わない回、つまり止める途中・claimを止めた間・queueの控え（`queue_hold`）の間は行わない）。supervisorが居ないあいだは閉じない（前は`plan`の実行時にも行ったが、`dagq plan`は何もしなくなった）。

## runtimeのplannerの経路<a id="runtimeのplannerの経路"></a>

[ADR-t1394-2](../../adr/2026-10-03-t1394-2-runtime-planner-route-interactive-or-headless.md)の決定1・2（goal 87、task 1396）。

> **予定（goal 92）**: [ADR-t1433-2](../../adr/2026-10-03-t1433-2-abolish-the-interactive-route.md)決定3で対話の経路を廃止し、[ADR-t1433-3](../../adr/2026-10-03-t1433-3-headless-wrappers-run-only-in-the-background.md)決定1・2でwrapperはbackgroundだけになる。下の「選ぶ欄」の`route`は受け付けて無視し（値に関わらず`headless`）、後で`dagq.toml`から消す。`planners.route`は過去の対話のplannerを読むために残し、新しい行は`headless`になる。「非対話のplanner」の`[headless] wrapper`によるworkspaceの中かbackgroundかの選択は無くなり、backgroundだけになる。下の記述は、goal 92の後続のtaskが実装するまでの今の姿である。

- **選ぶ欄**: `[roles.runtime_planner]`の`route = "interactive" | "headless"`（既定`interactive`。[Actor model](actor-model.md#runtimeのplannerの経路)）。supervisorはplannerを開くたび（reviseの`open_runtime_planner`、draftとfindingの`open_draft_planner`）に`PlannerLaunch::roles`から読み、`headless`なら行の`route`に残す（`launch_planner`。書けなければ行をerror付きで閉じる）。動いているplannerの経路は変えない。人が開くplannerは常に対話。`dagq doctor`の`roles.runtime_planner`が`route`と`route_source`を出す。
- **非対話のplanner**: plannerのディレクトリに`turns/`（[非対話のworker](headless-worker.md#run-dirのturns)と同じ`request-NNNNNN.json`・`.taken.json`・`exit`・`limits.json`・`turn-NNNNNN.jsonl` / `.err`）を置き、wrapperが非対話のworkerと同じ`Turns`（`TurnOwner::Planner`）で動く。初期prompt（`prompt.txt`）が最初のturn。`turn_started` / `turn_finished` / `turn_session_identified`と、supervisorが書く`turn_requested`はqueueのevent（`planner_id`付き）。reviseの配送（`plan_revise_sent`）、`planner_question`のanswer（`ask_delivered`）、`end_runtime_planners`と`release_runtime_planner`の`/exit`は、`Supervisor::send_to_planner`が次のturnの依頼（`what`は`revise` / `answer of ask <id>`）と終了の依頼にし、`submit_input`・Stop hook・画面からのidleの推定を使わない。wrapperはworkspaceの中かbackgroundかを[ADR-t1404-1](../../adr/2026-10-03-t1404-1-headless-wrappers-run-as-detached-background-processes.md)の`[headless] wrapper`で選ぶ（backgroundのhandleは`workspace_id`に入り、`dagq submit`はplannerの記録からそのhandleを持ち主にする）。
- **状態**: `planner_view`は非対話のplannerで、wrapperがturnの終わりに書くidle markerが最後の入力（supervisorの入力の印を含む）より新しければ`idle`（`idle_since`はmarkerの時刻）、そうでなければ`working`、wrapperが死ねば`lost`。`question_wait`（自分の`planner_question`を待つ）の間は`/exit`しないのは対話と同じ。`planner_unresponsive`（`subject: "planner"`）は対話と同じく`--planner-timeout`で出る（turnの上限で止めたときに出すことは後続task）。
- **終わり**: 終了の依頼でwrapperが終わると、backgroundではhandleも無くなる。agentの終了が記録された行は、`end_runtime_planners`と行の片付けのどちらが閉じても`runtime_exited`。行の片付け（`close_abandoned_planners`）はbackgroundのhandleをcmuxの一覧でなく`exists`（pidと起動時刻）で判じ、生きているwrapperの行はheartbeatが遅れても閉じない。wrapperが殺されて残ったturnは、handleを閉じるときに止める（[非対話のworker](headless-worker.md#非対話のruntimeのplanner)）。
- **test**: `tests/it/planner_headless.rs`（[非対話のworker](headless-worker.md#非対話のruntimeのplanner)のtest）。

3. **立てる**（`open_request_planners`、各pass）: 対象は`open`で、閉じていないruntimeのplannerも閉じていない`planner_question`も無い依頼（ID順）。runtimeが立てたplannerで生きているものが上限`runtime_planners`（[Draft planners](draft-planners.md)の3と同じ値。revise・draft・findingのplannerと枠を共有し、人が開いたplannerは数えない）未満のあいだ、依頼ごとに`open_request_planner`で立てる。storeは`BEGIN IMMEDIATE`で対象の条件を確かめ直してから`planners`の行（`origin: runtime`、`request_id`）と`request_planner_opened`（`request_id`・`planner_id`・`attempt`・`ask_id`）を書くので、2つのsupervisorや同じsupervisorの次のpassが同じ依頼に2つ立てない。workspaceは`[<repo>]planner#<id> - request <request-id>`（`[headless] wrapper`でbackgroundに起動した非対話のplannerはworkspaceを持たず、titleも無い。経路は上の[runtimeのplannerの経路](#runtimeのplannerの経路)）。`--no-claude`の間と`tend_planners`を行わない回（止める途中・claimを止めた間・queueの控えの間）は立てず、依頼は`open`のまま待ち、`requests`に出る。
4. **依頼の言葉の受け渡し**（`planner_handoff::hand_request_to_planner`、[ADR-t1228-1](../../adr/2026-10-02-t1228-1-inbox-and-planner-reach-sessions-through-the-dagq-cli.md)の決定2）: 人の言葉は`<planner dir>/requests/request-<request-id>.md`に書き、promptはそれを決まった文（`handed_request_sentence`: `dagq: a request for you is in the file <path>: read it and work on it as it says.`）で指す。依頼の本文をキー列として打たない。開いているruntimeのplannerへの続きの依頼（task 1533。task 1229の差し替え）は同じ関数でファイルを書き、同じ文をplannerに送る（名前はそのtaskが決める。`requests/`の下の1つのpathの部品で、英数字・`-`・`_`だけ）。
5. **初期prompt**（`request_planner_prompt`）: 依頼のファイルを指す文、inboxの補足（人の言葉と分けて）、参照先の中身（askの問いと答え、taskのtitle・description・acceptanceと最後の`integration_receipt`の`summary`と`follow_ups`、runのtaskと着地したreceipt、eventのkindとpayload、findingの種類・状態・見立て。読めない参照はそう書く）、参照から引けるgoal（`goal_led_to`: goalの参照、taskとrunのtaskのgoal、findingのgoalかそのtaskのgoal、askのtaskのgoalかそのfindingのgoal、eventのgoalかそのtaskのgoal。title・description・acceptance・constraints・task。どれも引けなければ`dagq goal list`を読む手順）、前のplannerの`planner_question`とanswer、AGENTS.md（無ければCLAUDE.md）と名指す文書を先に読むこと、`prompt::repository_rules`、`dagq search` / `related` / `show` / `goal list`で既存のtaskと実装済みを確かめる手順、記録を読むCLI（`prompt::RECORD_READING`）、[ADR-t451-1](../../adr/2026-10-02-t451-1-ai-decides-recommendable-asks-and-escalates-only-the-undecidable.md)の上げる基準（`prompt::DECIDE_YOURSELF`）と3択（計画して`--context`の冒頭を`from request <id>`にしてsubmit、`dagq request decline ID --reason`、決めきれないものだけ`dagq ask --request ID --kind planner_question --because scope --recommend <plan|decline> --confidence <high|low> --option plan --option decline`）。人のanswerを運ぶplannerには元の質問とanswerを載せる。
6. **結末**: plannerが自分のworkspace（`CMUX_WORKSPACE_ID`。backgroundの非対話のplannerはplannerの記録のhandle）から`dagq submit`すると、submitが同じトランザクション（`submit_linking`の`link_requests`）でproposalを依頼に結ぶ（`plan_request_proposals`。1件の依頼から複数のproposalを出してよい）。最初のsubmitで依頼は`proposed`になり、`request_proposed`（`request_id`・`proposal_id`・`planner_id`）を記録する。その後はproposalの通常の流れ（plan review、revise、concernの`approve_plan`）で進み、依頼の状態はproposalの結末で変えない。手当てしないと決めたら、plannerは`dagq request decline ID --reason '...'`で`declined`にし、`request_declined`（`request_id`・`planner_id`・`reason`・`by`）を記録する（capability `request.decline`。打てるのはその依頼に立てられたplanner自身だけで、他のplanner・inbox・人は拒まれる。`open`でない依頼は`RequestNotOpen`で拒む。判定に使った依頼のplannerが却下のトランザクションの中で変わっていれば拒む）。決めずに終わったplanner（sessionが終わった、idleで`/exit`された）の依頼は次のpassで再び対象になり、依頼の`planners`の行が`MAX_REQUEST_PLANNERS`（3）に達していれば（人のanswerを運ぶとき以外は）立てずに`exhausted`にして`request_planner_exhausted`（`request_id`・`planners`・`reason`）を記録する。inboxの`watch`は`request_proposed`を知らせ（`report the request's proposal`）として、`request_declined`と`request_planner_exhausted`をattention（`rephrase or drop the request`。人が言い直すか取り下げる）として受け、依頼した人に結末を伝える。どれもqueueのeventで、`dagq events --kind request_proposed`のように読める。
7. **`planner_question`**: `ask --request ID`は`planner_question`だけが持て、task・run・findingを名指さない（他のkindと、それらを名指すものは`AskRequestNotPlannerQuestion`）、`asks.request_id`に依頼を、`subject`に`request:<id>`を書く（openなaskを1件に限る`asks_open`が依頼ごとに分かれるように。[Persistence](../persistence.md#asks)）。answerの行き先（`planner_answer_route`、`plan_requests::route_of`）は、その依頼の閉じていないruntimeのplannerがあれば`Planner`（[Draft planners](draft-planners.md)の5と同じく、plannerが自分で作ったaskはaskの後にidleになってから、他の人が作ったaskはidleなら、`claim_planner_answer`で配送を取ってから`answer to ask <id>: <answer>`を打ち込み（非対話のplannerには`send_to_planner`が次のturnの依頼にする）`ask_delivered`で閉じる。打ち込みの失敗はqueueのevent `ask_delivery_failed`（`request_id`付き）でinboxに任せる）、居なければ依頼がまだ`open`なら上限の中でanswerを持った新しいplannerを立てて渡し（`NewPlanner`。依頼の3回の上限を越えて運ぶ。立てる前に同じトランザクションでaskが回答済み・未closeであることも確かめ直し、閉じられたanswerでは立てない）、`open`でなければ（submit・却下・上限の後）`planner_answer_closed`で閉じる（`Close`）。`Person`にはならない。answerの`ask_answered`は`runtime_delivers: true`を持ちattentionにしない。依頼のaskの配送のevent（`planner_answer_claimed`・`planner_answer_closed`）はqueueのevent。依頼の`planner_question`が閉じていないあいだと、打ち込んだanswerの後にまだidleになっていないあいだは、そのplannerに`/exit`を送らない（`question_wait`）。
8. **終わりと時間切れ**: 依頼のplannerは、draft・findingのplannerと同じく、仕事を終えてidleになれば`end_runtime_planners`で`/exit`され（非対話のplannerでは終了の依頼）、`planner_closed`（payloadに`request_id`）を残す。画面も読めないまま`--planner-timeout`を過ぎれば、plannerごとに1回`planner_unresponsive`（`subject: "planner"`、`request_id`）がinboxに届く（上の「runtimeのplannerの時間切れ」）。`dagq planners`の行は`request_id`を持つ。
9. **test**: `tests/it/request_planner.rs`がcmuxのdoubleとstubのplan reviewで確かめる。`a_request_the_inbox_records_gets_one_planner_whose_submission_proposes_it`: inboxの`request add`（`--file`・`--note`・`--ref`）が記録と`request_recorded`を残し、次のpassで依頼にplannerが1つだけ立ち（次のpass、上限を上げたpass、直接の`open_request_planner`でも2つ目は立たない）、依頼のファイルがplannerのディレクトリに書かれpromptがそれを指して人の言葉を載せないこと、promptの中身、workspaceからのsubmitで依頼が`proposed`になりproposalが結ばれ（2つ目のproposalも結ばれ、知らせは1回）`watch`の知らせになり、idleのplannerに`/exit`が送られること。`only_the_requests_own_planner_declines_it_and_the_inbox_is_told`: 他のplanner・inbox・人の`request decline`が拒まれて`authorization_denied`が残り、依頼のplanner自身の却下で`declined`と`rephrase or drop the request`のattentionになり、2回目の却下は拒まれ、その後plannerが立たないこと。`a_planner_question_about_a_request_reaches_its_planner_or_a_new_one_and_three_exhaust_it`: 依頼の`planner_question`のanswerが生きているplannerに打ち込まれ、plannerが居ないあいだのanswerは新しいplannerがpromptに持って立ち、決めずに終わったplannerの後に3つ目まで立ち`exhausted`とattentionになり、その後のanswerは閉じられること。`requests_share_the_limit_of_the_runtimes_planners_and_come_first`: 依頼がfindingのplannerと上限を共有し先に立つこと。`questions_about_two_requests_stay_apart_and_a_closed_answer_opens_no_planner`: 2つの依頼の`planner_question`が同時に開け、未回答・closeされたanswer・別の依頼のanswerではanswerを持つplannerが立たないこと。`an_ask_or_an_event_alone_leads_the_prompt_to_its_goal`: goalのtaskのask、goalのfindingのask、goal自身のevent、goalのtaskのeventのどれか1つだけを参照にした依頼のpromptに、そのgoalのacceptance・constraints・taskが載ること。`only_the_inbox_and_a_person_record_a_request`: planner・worker・observer・5つのjobの`request add`が拒まれ`authorization_denied`に残り、inboxと人の記録はそれぞれの`requested_by`になり、空の言葉と知らない参照が拒まれること。`tests/it/planner_headless.rs`の`a_headless_request_planner_takes_the_answer_as_its_next_turn_and_declines`は非対話（background）の依頼のplannerで、`planner_question`のanswerが次のturnの依頼になり、そのturnの`request decline`で依頼が`declined`になることを確かめる。規則は`src/domain/plan_request.rs`、判定は`src/application/commands/requests.rs`と`src/domain/authorization.rs`、受け渡しは`src/application/planner_handoff.rs`のunit test。

## 予定: inboxからの依頼と非対話のplanner<a id="予定-inboxからの依頼と非対話のplanner"></a>

[ADR-t1394-1](../../adr/2026-10-03-t1394-1-abolish-person-planners-and-route-planning-through-inbox-requests.md)（goal 87）の予定のうち、**まだ実装していない**もの（依頼の記録から結末までは上の[inboxからの計画の依頼](#inboxからの計画の依頼)、非対話のplannerは上の[runtimeのplannerの経路](#runtimeのplannerの経路)）。綴りと数値は実装のtaskが決める仮のもので、実装したらこの節を今の姿に書き直し、上の節の人のplannerの記述を消す（廃止前から開いている人のplannerは下の1のとおり行を閉じた扱いにする）。runtimeのplannerはgoal 92の[ADR-t1433-2](../../adr/2026-10-03-t1433-2-abolish-the-interactive-route.md)・[ADR-t1433-3](../../adr/2026-10-03-t1433-3-headless-wrappers-run-only-in-the-background.md)で非対話とbackgroundだけになるので、この節もその形で書く。

### 流れ

1. `dagq plan`の拒否は実装した（上の`dagq plan`）。廃止の時点で開いている人のplanner（origin `person`）は、[ADR-t1433-2](../../adr/2026-10-03-t1433-2-abolish-the-interactive-route.md)決定5のとおり、新しいバイナリが行を閉じた扱いにして[ADR-t1300-1](../../adr/2026-10-02-t1300-1-runtime-closes-exited-person-planners-after-a-grace.md)決定2の`planner_closed`を残し（codeは仮）、そのworkspaceにはsendもcloseもしない（cmuxを呼ばない）。持ち主の居なくなったproposalへのreviseと`planner_question`のanswerは、持ち主のplannerが閉じているときの経路で、新しい非対話のplannerが受ける。残ったworkspaceは人が`DAGQ_ROLE`の無い自分のterminalで閉じる。人が`DAGQ_ROLE`の無いterminalで打つ`add` / `submit`は今までどおり通り、持ち主の居ないproposal（`owner_origin: person`、workspaceなし）のreviseはruntimeのplannerが受ける。
2. 人のplannerを前提にした行き先の読み替え: observerの古いdraft goal・goal closeの人の判断は、inboxがそのdraft・goalを参照にした依頼を記録するか、人が自分のterminalで決める。`draft_planner_exhausted`・`finding_planner_exhausted`・`dependency_stranded`のattention（`request a plan for the draft`・`request a plan for the finding`・`request a plan for the waiting tasks`）と`keep_draft`のdraftは、inboxがそのdraft・finding・taskを参照（`--ref task:N` / `--ref finding:N`）にした依頼を記録するか人が自分のterminalで決める案内に変えた（実装済み、[Draft planners](draft-planners.md)の4・5、[Finding planners](finding-planners.md)の8）。
3. `status`のinbox向けの欄（仮: `requests`）に、plannerを待っている`open`の依頼を出す（`--no-claude`の間に待っている依頼を人に見せるため。ADR-t1394-1のConsequences）。今は`dagq requests`で読む。
4. [ADR-t1228-1](../../adr/2026-10-02-t1228-1-inbox-and-planner-reach-sessions-through-the-dagq-cli.md)のplannerへの依頼のCLI（task 1533。task 1229の差し替え）は、開いているruntimeのplannerへの続きの依頼に使い、上の[inboxからの計画の依頼](#inboxからの計画の依頼)の4の受け渡し（`planner_handoff::hand_request_to_planner`）を使う。非対話のplannerには決まった文を次のturnの依頼として置く（上の[runtimeのplannerの経路](#runtimeのplannerの経路)の予定）。
