# `supervise`

> supervisorはcmuxを呼ばない（[ADR-t1433-1](../../adr/2026-10-03-t1433-1-cmux-is-used-only-by-the-inbox.md)）。
> supervisorはlaunchdで常駐し、in-cmux modeでは新しく起動しない（[ADR-t1433-4](../../adr/2026-10-03-t1433-4-supervisor-resides-without-cmux.md)）。
> 登録済みのin-cmuxのsupervisorは、そのworkspaceに居たまま引き継ぎと`down`だけを受ける。

ユースケースの本体はapplication層の`src/application/supervise/`にある（`mod.rs`がループとslotの`Phase`・`step`、phaseごとのwatchとその処理が`session.rs`・`exit.rs`・`jobs.rs`・`landing.rs`・`revise.rs`・`resume.rs`・`triage.rs`・`adopt.rs`、idle markerの判定が`idle.rs`、watcherの居ないinboxへの知らせが`inbox_nudge.rs`（[通知経路](notification-route.md#supervisorによるinboxへの知らせadr-t1433-5)）。review・triageのpromptとsessionに渡す依頼文は`src/application/prompt.rs`）（[ADR-0013](../../adr/0013-layered-architecture-and-type-function-style.md)の方針1と8）。`supervise(&Ports, &LoopSettings)`が下の起動時の1〜4とループを行い、外のものにはすべて`Ports`のport越しに触れる: queueは`Queue`（`TaskStore`、runの6つのport（[overview](../overview.md)）、`AskStore`など）で、ループ自身の接続とheartbeat・検証・着地の各threadの接続を`QueueOpener`が開く。Gitは`Repository`（worktreeの作成、`merge-tree`の衝突判定、着地したtaskの`Dagq-Task` trailerの読み取りを含む）と`MainRemote`、`[run.env]`と検証コマンドは`Verifier`、wrapperの起動と停止は`SessionWrappers`（`BackgroundSessions`。cmuxを呼ばない）、agentは`AgentProvider`（sessionのagentとheadlessのreview / triageのコマンドをapplicationの`CommandSpec`で返す）、idle markerの内容とheadless jobの出力の壁の読み取りは`AgentSignals`（Claude Code固有の形式なので実装は`infrastructure::claude`）、子プロセス（observer、review、triage）の起動は`Spawner`（標準入出力の行き先は`Streams`で指定）、pidの生死は`ProcessControl`、run directory・prompt・receipt・idle markerの読み書きとファイルの時刻と比べる壁時計は`RunFiles`、時刻とIDは`Generators`（進行メッセージはportを通さず`tracing`で出す。[Logs](logs.md#logs)）。path（DB、`runs/`、repositoryのrootとcommon dir、`claude`、runner）とworker / job / observerの環境変数は`Layout`として値で渡す。`runtime::supervise`は`SqliteOpener`（`infrastructure::runtime_store`）、`GitRepository`、`ShellVerifier`、`LocalSpawner`（`infrastructure::process`）、`LocalRunFiles`（`infrastructure::run_files`）、`SystemProcesses`を組み立てて呼ぶ入口だけで、公開API（`SuperviseOptions`、`supervise`、`supervise_with_reviewer`）は変わらない。askの登録は`application::ask`（通知はしない。inboxのwatchが知らせる）、doctor・`recover`と同じrunのhealth判定は`application::health`、workspaceの名前付けとshellの引用は`application::naming`にある。

観測と分析と、host運用の更新・sccache・disk・後始末などの状態は`contexts.rs`の`ObservationState`・`HostOpsState`にあり、そのcontextのsubmoduleのpassだけが変える。
host運用の登録・引き継ぎ・sweepの欄は`Supervisor`に残る（[Architecture](../architecture.md#supervisorの状態)）。

`dagq supervise [--parallel N] [--max-waiting N] [--runtime-planners N] [--once] [--log-dir DIR] [--observe-interval SECS] [--observe-daily BOOL]`はrepository内で実行する常駐ループ（通常は`up`がlaunchdで起動する。手で専用ターミナルから起動してもよい）で、依存が解けたtaskを上限N（既定4）まで同時に実行する。人の答えだけを待つrunはslotから外れ、`--max-waiting`（既定4）までslotの外で待つ（[人の答えを待つrun](waiting.md)、[ADR-0071](../../adr/0071-runs-waiting-in-revise-and-resume-leave-the-slot.md)）。「active runが上限未満」「空いたslot」は、待ちと戻り待ちのrunを除いたslot（`used_slots()`）で数える。queueはcwdから解決し（[persistence](../persistence.md)のQueue location）、repositoryのcheckoutもcwdを使う。`--db PATH`と`--repo REPO`はそれぞれの明示override（[ADR-0053](../../adr/0053-queue-in-data-dir-run-paths-from-queue-and-rebind.md)）。

起動時:

1. DBのpathを正規化し、checkoutのroot、Git common directoryを取得する。DBはworktree外か、common directory配下に置く（ユーザーDIRのqueueは常に満たす）。worktreeの作成元は`repo_path`に記録したcheckout。
2. Claude（`--version`）のpreflightを行う（`--cmux`はe2eと自動更新のjobに渡すだけ）。
3. queueをrepositoryに束縛する（`bind_repository`）。別repositoryに束縛済みなら開始しない。queue全体の排他はなく、同じqueueに別のsupervisorがいても構わない。
4. supervisorプロセスのtoken（UUID）を作り、`supervisors`表に自分を登録し（`register_supervisor`: token、PID、`parallel`・`max_waiting`・`runtime_planners`とその出どころ、`started_at`）、引き継ぎを受けられる印を付ける（`accept_handoff`）。hiddenの`--handoff-token TOKEN`で起動されたとき（引き継ぎのexecの後）は新しく登録せず、そのtokenの登録を同じPIDのまま取り戻し（`resume_registration`）、そのtokenのleaseを持つrunのslotを組み立て直す（[Handoff](handoff.md#handoff)）。runを1つも持たない常駐supervisorも、この登録で`status`/`doctor`に並ぶ。続けて別スレッドで2秒（`HEARTBEAT_INTERVAL`）ごとにそのtokenの登録と全leaseのheartbeatを1トランザクションで更新する（`heartbeat(token)`）。testはhiddenの`--heartbeat-interval-ms`で間隔を短くする（引き継ぎの後の[Auto-update](auto-update.md)の見張りが次のheartbeatを待つため）。heartbeatの書き込みが他の接続の書き込みのlockでSQLiteのbusy / locked（busy timeoutの5秒、`QUEUE_BUSY_TIMEOUT`を待っても取れない）で失敗したときは止めず、次の間隔で書き直す。heartbeatのthreadは失敗のたびにWARNの`supervisor heartbeat busy (N failures, Xs since the last write); trying again`をlogに書き、書き直せたら失敗の回数と時間をINFOのlogと`supervisor_heartbeat_retried`のqueue event（`token`、`failures`、`secs`（最初の失敗から書き直せるまで）、`error`（最後の失敗））に残す。busyのまま書き直さないのは、最後に書けた時刻からの時間に次の間隔と次の書き込みの待ち（5秒）を足すと、leaseがstaleと見なされる30秒（`HEARTBEAT_TIMEOUT_SECS`）に届くときで（既定の2秒の間隔では最後に書けてから23秒）、そこで諦めれば最後に書いたheartbeatがstaleになる前に止まるので、他のsupervisorが引き継ぐ前に自分から退く（`HeartbeatPolicy::retries`）。busy / locked でない失敗（書き込みの拒否、I/O errorなど）はこれまでどおりその場で止める。書き込みが通っても登録の行が無かったとき（PIDが死んだかstaleと見なされて`up`や`down --force`に消された）はleaseを失ったとして止める（登録を持たない`integrate`のheartbeatはこの判定をしない）。runのlease行が他のtokenに移ったことは、これまでどおり下の7の各tickの確認がrunごとに見て、そのrunだけをslotから外す。止めるときはループで検知し、全runに`runtime_error`（`lease_lost`、文に失敗の回数と時間を含む）を記録してleaseと登録を残したまま終了する（プロセス終了後にstaleになる）。`parallel`・`max_waiting`・`runtime_planners`はそれぞれflag（`--parallel` / `--max-waiting` / `--runtime-planners`）の明示 > main checkoutの`dagq.toml`の`[supervisor]` > 既定（`parallel`と`max_waiting`は4、`runtime_planners`は1）で決め（`SlotLimits::resolve`）、値と出どころ（`flag` / `dagq.toml` / `default`）は登録の行を作るのと同じトランザクションで書き、登録が見えた時点で`status`と登録を読む側が値と出どころを読める（引き継ぎでは取り戻しの直後に書き直す（`set_slot_limits`）。[Run environment](run-environment.md)の`[supervisor]`）。
   登録の後、`stall_config_loaded`に続けて変更の印`supervisor_started`（build識別子・`parallel`・`mode`（`up`が渡すhiddenの`--mode`）・`auto_update`・`handoff`）を1件記録する。
   停止要求（SIGINT/SIGTERM）に最初に気づいたpassでは、drainに入ったことをqueueのevent `supervisor_draining`（`supervisor`・`pid`・`build`・`reason: stop_requested`・`handoff_binary`・`runs`）で1回だけ記録する（[Handoff](handoff.md#handoff)の停止要求の記録と引き継ぎの待ち）。
   loopが終わって登録を消すとき（execするときを除く）は`supervisor_stopped`を記録する。
   ループの各passでは、環境の検査に続けてsccacheの監視と再起動を行う。
   監視と待ちの入口は`application::supervise::sccache`、serverをsandboxの外で持つ分担と観測の限界は[Run environment](run-environment.md#sccacheのserver)が持つ。
   続けてmain checkoutの`[run.env]`の正規化したhashがqueueの最新の`run_env_changed`と違えば`run_env_changed`を記録する（`Verifier::run_env_table`、hashの鍵はqueueのsaltの`Verifier::run_env_salt`。
   [変更の印](marks.md)、ADR-0051の決定10・11）。
   続けてmain checkoutの`[conflicts]`を読み直し、使用中と違う同じ値を2 pass続けて読んだときだけ以後の判定に使い、hotspotのcacheを捨てて`conflicts_config_changed`を記録する。
   表の削除も2回の読みで既定値を適用し、欠落・parseエラーでは使用中の値を保って変更候補を捨てる。
   起動時は即時に適用し、最初の読み直しが起動時と同じ値を読み、それがqueueの最新の`conflicts_config_changed`の`to`と違えば`source: start`で1回記録する。
   `SuperviseOptions.conflicts`の上書き時は読み直さない（[Conflict thresholds](conflict-thresholds.md#読み直し)、ADR-0080・ADR-t774-1・ADR-t775-1）。
   続けて、flagで明示されなかった`parallel` / `max_waiting` / `runtime_planners`のために`[supervisor]`を読み直し、値が変われば以後のclaimと待ちとruntimeのplannerを立てる判定に使い、登録に書いて`supervisor_config_changed`を記録する（[Run environment](run-environment.md)の`[supervisor]`）。
   続けて`[provider_fallback]`を読み直し、`workers`が変われば以後のclaimの経路とturnの壁の判定に、`jobs`が変われば以後のheadlessのjobの行き先と失敗の後の扱いに使う（logにinfoを出す。
   [Run environment](run-environment.md)の`[provider_fallback]`、[ADR-t1857-1](../../adr/2026-10-06-t1857-1-provider-fallback-can-be-turned-off-for-workers-and-jobs.md)）。
   続けて`[ci_watch]`を読み直し、CIの確かめを受け取り・始める（下の「CIの見張り」）。

ループ（1秒ごと）: 各passの先頭で、待ちの終わったrunを新しい仕事より先にslotへ戻し（drain中も）、各tickの先頭で人の答えを待つrunを待ちに移す（[人の答えを待つrun](waiting.md)）。待ちのrunのslotは下の監視の代わりにsessionへ何も送らない見張りだけを受ける。workerのsessionはclaimでもresumeでも非対話で、supervisorは依頼をrun directoryに書き、workerの画面を読まず打ち込まない（対話のworkerのrunは廃止した。task 1437。[非対話のworker](headless-worker.md)）。

   **slotを渡す順**（[ADR-t1850-1](../../adr/2026-10-06-t1850-1-resumes-recovery-jobs-and-claims-share-one-line-by-effective-priority.md)）: `needs_session`のrunの再開（[`needs_session`](needs-session.md)）、`failed` / `interrupted`のrunの復旧job（12）、readyのtaskのclaim（下）は1つの候補の列になり、候補のtaskの効く優先度の降順にslotを受ける。効く優先度の求め方は下のclaim順と同じで、`in_progress`のtaskも自分の基の優先度と自分を推移的に待っている`ready`のtaskの基の優先度の最大値になる。同じ効く優先度では再開 → 復旧job → claimの順、同じ種の中は各種の今の順（再開は古い順、復旧jobは`runs_to_triage`の順、claimは下のclaim順）。列の順は`domain::slot_order`の純粋関数が決める。`fill_slots`は再開の候補（`resume_candidates`。試行を使い切った再開の`exhaust`と、終わったsessionの`stuck_exit`のaskのcloseはここでslotに関わらず行う）と復旧jobの候補（`triage_candidates`）を集め、`graph_input`を読み直し（`exhaust`の引き継ぐretryで`ready`に戻ったtaskも同じpassでclaimの候補になる）、claimの候補を読み、列の先頭から種ごとに始める（`resume_run` / `triage_run` / claimのloop）。claimは1つの効く優先度の候補をまとめて下のclaimのloop（その優先度以上の候補だけを取る）で取り、空きが無いか、claimの間隔・着地のbranch・provisioningの失敗でそのpassのclaimを止めたら、以降のclaimを飛ばす。再開と復旧jobは通常のslotだけを使い（軽い枠はclaimだけ）、空きが無ければその候補を飛ばす。種ごとの保留（再開: 着地のbranch・`[run.env]`のprogram・`[ci_watch]`の読む手段・Claudeを使えない・生きたleaseかwrapper、復旧job: 行き先の待ち（`Supervisor::recovery_route`。`[roles.recovery]`に`provider`を書かない役割では`queue_hold`、書いた役割ではどちらのproviderも使えないとき）・着地のbranch・`wait`、claim: 下の各保留）は、その種の候補を列から外すだけで、上位の候補のためにslotを空けて待たない。走っているrunは止めず、自動のagingは無い。人とinboxは`set-priority`で`in_progress`のtaskの順も変えられる（[Authorization](../authorization.md)）。
