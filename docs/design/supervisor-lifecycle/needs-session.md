# `needs_session`

衝突（4）と再検証の失敗（5。宣言外のパスを含む）は`defer_integration`でrunを`needs_session`にし、理由を`last_error`、詳細（衝突ファイル、Gitの出力の末尾、rebase後のheadなど）を`integration_deferred`イベントに書いて、lease行を消しスロットを空ける。worktreeは衝突なら検証済みhead、再検証の失敗ならrebase済みのheadに置いたまま残す。検証コマンドの失敗のうちhostの分類（`disk_full`・`killed`・`timeout`）は`needs_session`にせず、integrateが同じ試行で1回やり直し、なお落ちればrunを`awaiting_integration`に戻して（`integration_held`）inboxに知らせる（task 639。[`integrate`](integrate.md#integrate)の5）。resumeの回数は使わない。runはTaskを占有し続け、`ready`/`cancel`はできない。

引き継いだsupervisorが、task 1437より前に`/exit`がcmuxの時間切れで届かなかった（`exit_unsent`の`close_and_land`）runを判定し直し、workspaceがもう無いのに、integrateの検査しない理由（HEADがreviewしたcommitでない・`worker_question`が開いている・rebaseの途中など）で着地できないときも`needs_session`になる（task 960。[Receipt and session exit](receipt-and-session-exit.md)）。parkのイベントは`session_gone_parked`（code `session_gone`、payloadの`status: needs_session`）で、resumeの依頼文は`ResumeKind::SessionGone`（理由の示すものを片付けてcommitし、receiptを書き直す）、試行は上限に数える。resumeが解消すればvalidatingとreviewをやり直す。

reviewがpassしたrunのうちe2eが要るものは、着地の前にruntimeがhostで流したe2eが落ちると（上限の内に終わり、名前で流し直しても落ちたtestが印で通らないとき。上限切れと流し直しの上限切れ・始められない流し直しは変更のせいとせず、runを`needs_session`にせずに流し直す）`needs_session`になる（[ADR-t1233-2](../../adr/2026-10-02-t1233-2-e2e-runs-on-the-host-after-review-passes.md)、[Review](review.md#着地の前のe2e)）。parkのイベントは`run_e2e_failed`（code `e2e_failed`、payloadの`status: needs_session`、落ちたtestと流し直しの結果とlogの場所）で、resumeの依頼文は`ResumeKind::E2e`（reasonのlogを読んで落ちたtestを直してcommitし、再現は名前で絞った1本だけ）、試行は上限に数え、modelは上げない。resumeが解消すれば、`integrate`が呼ばれていないrunはvalidatingとreviewをやり直し、着地の前に新しいcommitのe2eをもう一度流す。

着地待ちのrun（`awaiting_integration`）は、着地の後のlanding recheck（[Landing recheck](landing-recheck.md)、[ADR-0068](../../adr/0068-recheck-waiting-runs-after-each-landing.md)）でも`needs_session`になる。parkのイベントは`action: resumed`の`landing_recheck_failed`（code `rebase_conflict`か`verification_failed`、payloadの`status: needs_session`）で、resumeの依頼文は`ResumeKind::Recheck`、試行の数え方ではcode `rebase_conflict`ならreviewのverdictを問わず衝突だけのresumeになる（下の「試行の数え方」。使い切ったときの引き継ぐretryはreviewがpassしたかapproveされたrunだけ）。resumeが解決したrunに閉じていない`approve_landing`のaskがあれば、`validating`の後にreviewをやり直さず、sessionを閉じて答えを待つ。

resumeで開くworkerのsessionは、直前のsessionのmodel / effortを引き継ぐ。runを`needs_session`にした最新のeventのcodeが`verification_failed`（integrateかlanding recheckの検証の失敗）か`sent_back`（`approve_landing`の`send_back`）なら1段上げ（Opus 5.5 medium → high → xhigh、xhighが上限）、衝突（`rebase_conflict`）・kill（復旧jobの`triage_resume`）・`evidence_missing`・`scope_violation`などでは上げない。`begin_resume`が`resume_started`に`model`・`effort`・`group`と、上げたなら`escalated_from`・`escalation_reason`を書く（[Worker model](worker-model.md#段上げ決定5)、[ADR-0079](../../adr/0079-record-task-weight-predictions-and-trial-model-effort-selection.md)の決定5）。

`integrate`は呼ばれた時点で、runに`integration_approved`イベント（`status`: 呼ばれた時のrunのstatus、`pid`、`push`: `--no-push`でなければtrue）を1回だけ記録する。supervisorが承認済みのrunを着地させるときは、この`push`に従ってmainを`origin`へpushする（`integrate`と同じ`push_main`）。`integrate`を呼ぶことが着地の承認で（ADR-0016の決定5）、runtimeが自分で着地させるのは承認済みのrun、reviewがpassしたrun、`approve_landing`に`land`と答えたrun（`integration_approved`に`ask_id`を付けて記録する）だけ（[ADR-0027](../../adr/0027-keep-worker-session-through-review-revise-verdict-and-merge-tree-precheck.md)）。`integration_deferred`のpayloadには`resumes_left`（supervisorが残り何回resumeするか。3から数える試行（下の「試行の数え方」）の件数を引いた値で、0未満にならない）が付く。

**試行の数え方**（[ADR-0047](../../adr/0047-irregularities-in-three-layers-recovery-job-ask-reasons-and-goal-review.md)の決定24、task 358）: 判定はdomainの`domain::resume`がrunのイベントだけから行う。`resume_started`ごとに、それより前のイベントで (a) reviewがpass済み（`integration_approved`がある（`integrate`か`approve_landing`の`land`）か、最新の`review_finished`の`verdict`が`pass`）で、(b) runを`needs_session`にした最新のイベント（`integration_deferred` / `integration_error` / `evidence_missing` / `scope_violation` / `landing_decided` / `triage_finished` / `triage_decided`）が`code: rebase_conflict`の`integration_deferred`なら、その試行は**衝突だけの試行**で、上限の3回（`MAX_RESUME_ATTEMPTS`）に数えない（`ResumeCount::conflict_only`）。それ以外（検証の失敗、`evidence_missing`、`scope_violation`、人の`send_back`、triageのresume、reviewがpassしていない衝突）は数える（`ResumeCount::counted`）。着地前の衝突の確認（[Review](review.md#review-supervisor)の5のprecheck、ADR-0027の決定4）が生きているsessionに送った解消依頼（`conflict_precheck`の`requested: true`。後の`unsent: true`で取り消したものを除く。`ResumeCount::conflict_requests`）も、reviewがpassした後の衝突だけなので衝突だけの試行で、3回に数えない（task 511）。衝突だけの試行（衝突だけのresumeとprecheckの依頼の和、`ResumeCount::conflict_attempts`）は別に`dagq.toml`の`[resume] conflict_only_limit`（既定5。`domain::resume::ResumeConfig`、既定値は定数`CONFLICT_ONLY_RESUME_LIMIT`。書式は[Run environment](run-environment.md)）で止める（同じ衝突が解けないまま回り続けないための柵。task 512）。以下の「5回」はこの上限で、`ResumeCount::exhausted`・`decide_conflict`・`begin_resume` / `exhaust_resumes`の使い切りの判定と、askやlast_error・復旧jobのpromptの文面は、supervisorが起動時に読んだ設定の値を使う。数える試行が3回か、衝突だけのresumeが5回に達したrun、または衝突だけで`needs_session`になっている（次のresumeが衝突だけの試行になる。`ResumeCount::parked_for_conflict`）runで衝突だけの試行（precheckの依頼を含む）が5回に達したものは、試行を使い切っている（`ResumeCount::exhausted`）。precheckの依頼で5回に達したrunでも、検証の失敗・`evidence_missing`・`scope_violation`など別の理由でparkしたなら、数える試行が残っていればresumeする。triageのresumeの上限と`resumes_left`は数える試行だけを見る。precheckは、数える試行が3回に達していればaskにし、衝突だけの試行が5回に達していれば依頼を送らずに着地へ進め、着地のrebaseの衝突で`needs_session`になったrunは試行を使い切っているので下の「引き継ぐretry」に進む（引き継げなければprecheckがaskにする。`domain::decide_conflict`）。

**killだけの試行**（[ADR-t946-1](../../adr/2026-09-29-t946-1-kill-only-resumes-have-their-own-limit.md)、task 946）: 外からのsignalでsessionが終わって（`session_killed`）runが失敗し、復旧jobの`resume`（`triage_finished`）か人の`decide`の`resume`（`triage_decided`。どちらも`code: triage_resume`）で`needs_session`に戻ったrunの次の`resume_started`は、それより前のrunの`last_error`（`domain::reason`の`last_error_code`と同じ規則で読む）が`session_killed`なら、上の3回に数えない（`counted: false`、`ResumeCount::kill_only`）。`begin_resume`は同じトランザクションで（試行の通し番号・`counted`・下の`auto_repaired`のpayloadは、衝突だけの試行の`conflict_resume_uncounted`と合わせてイベントから`domain::resume::resume_start_plan`が組む。task 1412）`auto_repaired`（`repair: kill_resume_uncounted`、`conditions`に`parked: session_killed`・`counted_resumes`・`kill_only_resumes`）を記録する。killだけの試行は別に定数`KILL_ONLY_RESUME_LIMIT`（3。設定にしない）で止め、達したrunは試行を使い切っている（`ResumeCount::exhausted`。復旧jobの`resume`も`exhausted`で拒まれ、`resume_exhausted`として下の「復旧jobに渡す」に進む）。killだけの試行はkillの後の`resume`の直後の1回だけで、そのresumeのsessionが解消せずに終わって次のresumeに回るなら（間に新しいkillが無ければ）数える試行になる。また数えるかどうかは衝突だけの試行と同じくresumeの直前の`needs_session`の理由で決まるので、killの後のresumeが検証の失敗などでparkすれば次のresumeは数える試行、reviewがpass済みの衝突なら衝突だけの試行になる。`resume_exhausted`の`recovery_requested`は`kill_only_resumes`も持ち、使い切ったrunの`last_error`・復旧jobのpromptの文面はkillだけの試行の数も書く。

supervisorは`needs_session`のrunを自分でresumeする（ADR-0019の決定1。`resume_candidates`と`resume_run`）。ループの各回で、adoptの後、`needs_session`のrunを古い順に見て再開の候補を集める。候補は復旧job・claimと1つの列で、taskの効く優先度の降順（同じ優先度では再開が先、再開の中は古い順）に空きslotを受ける（[supervise](supervise.md#supervise)の5の「slotを渡す順」、[ADR-t1850-1](../../adr/2026-10-06-t1850-1-resumes-recovery-jobs-and-claims-share-one-line-by-effective-priority.md)）。人とinboxは`set-priority`で再開待ちのtaskの優先度を変えて、次の再開の順を変えられる（走っている再開は止めない）。試行を使い切ったrun（上の「試行の数え方」）、staleでないleaseを持つrun、前のsessionのwrapperのプロセスがまだ生きている（未終了でPIDが生きている。heartbeatが止まっていても）runは飛ばす。このsupervisorが見ていないsessionと同じworktreeで2つ目のsessionを始めないため。このsupervisorがまだslotで進めているrun（leaseが他のtokenに移ってstaleになり、sessionが終わっていても）も飛ばす: そのslotは次のtickでleaseを失ったとして外れ（[supervise](supervise.md#supervise)の7）、その後のpassでだけ他のrunと同じく次の試行を始める（同じrunを2つのslotで進めない。task 1361）。resumeの前に、このrunの`workspace_created` / `resume_finished`に記録されたresumeのsession（backgroundのwrapperのhandle）のうち止めた記録の無いもの（手放したsession、errorで残したもの）が`run_session_open`でまだ動いていれば止め（handleの`stop_background`、route `resume`。停止は`wrapper_stopped`にも記録する）、`workspace_closed`（`resume_attempt`、`by: supervisor`）を記録する（`close_left_resume_workspaces`）。動いているかはhandleのprocessで見て、cmuxには聞かない（[ADR-t1433-3](../../adr/2026-10-03-t1433-3-headless-wrappers-run-only-in-the-background.md)）。ADR-t1433-3より前にworkspaceで開いたresumeのsessionのIDは動いていないとみなし、閉じずに人に任せる（人が自分のterminalで閉じる）。resume中に死んだsupervisorが起動したwrapper（handleの記録が無い）は見つけないが、wrapperが生きている間は上の条件で飛ばす。

0. **解消済みの確認**（`resolved_head`、task 148）: resumeを始める前に、前の試行で解消済みかを確かめる。前の試行のsessionがreceiptを書き直した後に判定された（rebaseもreceiptも済んでいて、次の試行のsessionが何もせずにidleになる）runは、`rewritten_receipt`がresume開始より新しいreceiptを要求するので`unresolved`になり、試行を空費する（task 122）。次をすべて満たせばsessionを開かない: (a) runを`needs_session`にした最後のイベント（`integration_deferred` / `integration_error` / `evidence_missing` / `scope_violation` / `landing_decided`）が`landing_decided`（人の`send_back`。指摘への対応はsessionが要る）ではなく、それらと`resume_finished` / `resume_skipped`のうち最後が`outcome: unresolved`の`resume_finished`（parkの後にsessionの走ったresumeが終わっている。開けなかったresume（`outcome: error`）は何も変えていないので数えない）、(b) receiptがparseでき、`run_id`がこのrunで`succeeded`、taskの`required_evidence`を満たす、(c) receiptの`commit`がworktreeのHEADに一致し、worktreeがclean、(d) HEADが今の`main`ではなく、`main`を祖先に持つ（`merge-base --is-ancestor`）。`resolved_head`はqueue・receipt・gitを読むだけで、条件の判定は読んだ事実を値で受ける副作用のない`skips_resume`（`SkipFacts`）が行う（task 1412）。どれかが読めない・満たさないときは従来どおり1に進む。宣言外のパス（`--paths`）はここでは見ず、skipの後の[Validation](validation.md#validation)か着地が検査する。満たせば`skip_resume`が1トランザクションで`begin_resume`と同じ確認（`needs_session`、leaseが無いかstale、heartbeatしている未終了のprocessが無い）をしてleaseし（`lease_acquired`の`reason: resume_skipped`。sessionを始めないので前のsessionの`run_processes`の行は消さない）、`resume_skipped`（`head`、`main`、`approved`、`status`）を記録する。`resume_started`は記録しないので試行回数は増えず、試行が3回に達したrunには行わない（最初の除外条件のまま）。`integration_approved`があればrunは`needs_session`のまま着地スロットを待ち、下の5と同じく`land_integrating`で着地させる。無ければrunを`validating`にし、sessionの無いまま[Validation](validation.md#validation)→[Review](review.md#review-supervisor)に進める。skipの後にどの経路で`needs_session`に戻っても（着地の`integration_deferred`、着地スロット待ちのerror、supervisorの死）、最後が`resume_skipped`かparkのイベントなので(a)が成り立たず、次は必ずsessionを開いてresumeする（skipはresumeを挟まずに繰り返さない）。未承認でskipしたrunを持つsupervisorが`validating`か`awaiting_integration`のうちに死んだときは、wrapperが無い（`begin_resume`が消した）か生きていなくても、最後のresumeのイベントが`resume_skipped`ならadoptする（`run_adopted`の`wrapper`はwrapperが無ければnull）。そのrunのsessionは無いものとして扱う（`session_of`）。`resume_skipped`はattentionにしない。
1. **開始**: `begin_resume`が1トランザクションで、runがまだ`needs_session`で試行を使い切っておらず、leaseが無いかstale（staleなら置き換える）で、heartbeatしている未終了のprocessが無いことを確かめ、runをこのsupervisorのtokenでleaseし（`lease_acquired`の`reason: resume`）、`supervisor_token`を移し、前のsessionの`run_processes`の行を消し（履歴はイベントに残る）、`resume_started`（`attempt`: 数えない試行も含めた通し番号、`counted`: この試行を上限に数えるか、`reason`、`main`）を記録する。`reason`は最後の`integration_deferred` / `integration_error` / `evidence_missing` / `scope_violation` / `landing_decided`の`reason`（無ければ`last_error`）。そのイベントが`scope_violation`か、`scope_violation`を持つ`integration_deferred`なら、下の3の依頼を宣言パス用の文面にする。そのイベントが`evidence_missing`か、`checks`を持つ`integration_deferred`（上の要求evidenceで着地しなかった）なら、下の3の依頼をevidence用の文面にする、`main`はその時点の`refs/heads/<branch>`。runの状態は`needs_session`のままで、新しい状態は足さない。進行は`resume_started` / `resume_finished`で読む。
2. **起動**: worker と同じ非対話の wrapper を起動する。begin_resume は歴史上 interactive と記録された run も headless に変換し、worker_mode_converted（phase: resume）を同じ transaction で記録する。runtime の snapshot を置き換え、resume の wrapper（`session --resume --background`）を background で起動する（`ActorProgram::RunSession`、`WorkspaceBackend::launch_background`。output は run dir の `session-resume-<attempt>.log`。[ADR-t1433-3](../../adr/2026-10-03-t1433-3-headless-wrappers-run-only-in-the-background.md)。run は workspace を開かない）。handle を `resume_attempt` 付きの `workspace_created` で記録し、`wrapper_launched` を記録してから、wrapper の登録を45秒待つ。記録できなければ wrapper を止めてエラーにし、起動できなければ `backend_call_failed`（op `launch_background`）を run に記録して下の6の error になる。
3. **解消依頼**: wrapper が登録されたら、定型の解消依頼を次の turn の request file として書き、resume_request_sent を記録する。起動中の入力欄や固定の paste 待ちは使わない。依頼は現在の task と検証、前の失敗と修正すべき理由を含む。
4. **監視と終了**: 依頼より新しい receipt と turn の終了、wrapper の生存を確認する。worker_question の回答は次の turn として届け、stalled の待ちも slot の外で保持する。非対話の idle_process の復旧は残す。解消・失敗・未解消で終了を依頼し、wrapper の終了を確認する。時間の判断（wrapperの登録の待ち、依頼か最後の入力からの`resume_timeout`、終了の依頼からのexit timeout）は注入した`Clock`の単調時計（`monotonic`）で測り、時刻を値で受ける`resume::exit_wait`（待つか手放すか）と`resume_deadline`（終了を求めるか。古いreceiptの書き直しの依頼が答えを待つあいだは求めない）が決める。ちょうど上限で過ぎたとみなす（task 1557）。dialog、StartCheck、画面の idle 推定、/exit の打鍵・再試行・stuck_exit は廃止した。

5. **その後**: `resolved`で`integration_approved`があれば（0の解消済みの確認で`resume_skipped`になった承認済みのrunも）、`landing_queued`（`via: resume`）を記録し、leaseを持ったまま着地スロットが空くのを待ち（他のrunが`integrating`なら次の回に回す）、`begin_integration`（同じtokenのleaseはそのまま使う）から`integrate`と同じ関数（`land_integrating`: rebase、再検証、squash、完了、後始末）を別threadで走らせる。着地がまた`needs_session`になればleaseは外れ、次の回に1に戻る。`integration_approved`が無ければ、上の4のとおりsessionを開いたままrunを`validating`にしてreviewに進む（resumeしたsessionが自分で終わっていた場合も同じ経路で、wrapperはreviewの後に止める）。`failed`ならrunを`failed`にし、`last_error`を`session reported the run as failed: <summary>`にする。`unresolved`は`needs_session`のままleaseを外し、試行が残っていれば次の回に再びresumeする。
6. **打ち切りとerror**: 試行を使い切った後の`resume_finished`が未解消なら`exhausted: true`になる。次の`resume_candidates`で、そのrunにstaleでないleaseも生きているwrapperも無ければ（slotの空きに関わらず）、supervisorは次の**引き継ぐretry**か、人に渡すかを決める。

   **引き継ぐretry**（ADR-0047の決定24、task 358）: runが今も衝突だけで`needs_session`（上の(a)(b)がすべてのイベントについて成り立つ）で、同じtaskのどのrunにも`action: retry_inherit`の`triage_finished`が無ければ（taskごとに1回まで。`inherits_on_exhaustion`）、人に聞かずにretryする。runの`result_commit`（reviewがpassした検証済みのcommit。無ければ、rebaseの途中でないworktreeのHEAD）がbaseと違えば、それを`refs/dagq/runs/<run-id>`に向け（branchを消されても残るように）、`exhaust_resumes`（store）が1トランザクションで下と同じ確認と、衝突だけで止まっていることとtaskごとに1回までであることの再確認をしてrunを`failed`にし、taskを`in_progress`から`ready`に戻し（中身は変えないのでplan reviewにはかけない。triageの`retry`と同じ例外）、`auto_repaired`（`layer: runtime`、`repair: inherit_retry`、`conditions`: `review: pass`、`parked: rebase_conflict`、試行の数、`branch`、`head`）と`triage_finished`（`by: runtime`、`code: resume_exhausted`、`verdict` / `action: retry_inherit`、`inherit`: `branch`と`head`、`resumes`、`counted_resumes`、`conflict_only_resumes`、`conflict_requests`）を記録する（`auto_repaired`の`conditions`にも`conflict_requests`を載せる）。askは開かない。残したresumeのwrapperはtriageと同じく止め、worktreeとbranchはtaskが`ready`なので残る。次のrunのclaimでsupervisorは、前のrunのうち最も新しい`retry_inherit`で終わったrunがあれば（`retried_with_inheritance`。直前のrunが早くに失敗してtriageでretryされても引き継ぐ）、worker promptに引き継ぎの節（`Carried over from run <id>`: 前のrunのreviewはpassしたが衝突で試行を使い切ったこと、commit（`refs/dagq/runs/<id>`とbranch）と、そのrun自身のcommitの範囲（headと新しいrunのbaseのmerge-baseから。途中までrebaseしたresumeがmainのcommitを下に積んでいても、それを含めない）、`git cherry-pick <merge-base>..<head>`などで今のmain（新しいrunのbase）に載せ直して衝突を解き、検証を再実行して自分のheadでreceiptを書くこと、前のreceiptのpathとsummary）を足し、新しいrunに`run_inherited`（`inherit_from_run`、`head`、`branch`）を記録する。commitがbaseと同じ（載せ直すものが無い）か、refを作れなければ人に渡す。2回目の使い切りも人に渡す（ADR-0047は復旧jobに回すとするが、`resume_exhausted`の復旧jobは未実装）。

   **復旧jobに渡す**（`exhaust_resumes`。ADR-0047の決定39、task 441。以前は先に`decide`のaskを開いていた）: `exhaust_resumes`（store）が1トランザクションで、runがまだ`needs_session`で試行を使い切り、taskが`in_progress`でrunがその最新で、staleでないleaseが無いことを確かめ、runを`failed`にし（`last_error`は`resumed N times (at most 3) and still needs a session: <元のlast_error>`。衝突だけの試行があれば括弧の中に数える試行と衝突だけの試行の内訳を書き、precheckの依頼があれば`resumed N times (C of at most 3 counted) and asked R times by the conflict precheck (A of at most L attempts for conflicts only after its review passed)`にする。Lは`[resume] conflict_only_limit`）、`recovery_requested`（`alert: resume_exhausted`、`attempt`、`evidence`（最後の`resume_finished`）、`code: resume_exhausted`、`by: runtime`、`reason`、`resumes`（すべての試行）、`counted_resumes`、`conflict_only_resumes`、`kill_only_resumes`、`conflict_requests`、`previous_status: needs_session`、`status: failed`）を記録する。`triage_finished`は書かないので、[Triage](triage.md#triage-supervisor)の復旧jobがこのalertでrunを取る（resumeはもう選べない。jobの`retry_inherit`や`retry`は前提を満たせば適用され、escalateなら`decide`のask（`retry` / `cancel`とjobのoptions））。続けて残したresumeのwrapperを止める。wrapperの起動・依頼の書き込み・heartbeat切れなどresume自体のerrorは`resume_finished`（`outcome: error`、`error`、`exhausted`）とsupervisor logに書き、leaseを外す。runの`last_error`（衝突の理由）は変えず、試行は1回と数える。resumeのwrapperは、leaseを外した時点で未登録（leaseが無いのでもう登録できない）か終了済みなら止め（`stop_run_session`。起動の途中で失敗してhandleが返らなければ何もしない）、生きていれば調査のため残す（`resume_finished`の`workspace_id`にhandleを記録する）。残したwrapperは上の条件で次の試行を止めるが、このrunの`resume_finished`に記録されたhandleは、runのwrapperがもう生きていなければ次の回に止めて次の試行を始める。着地スロットを待つ間（`AwaitingSlot`）のerrorでは`resume_finished`は記録済みなので、leaseだけを外す。resume中にsupervisorが死んだ場合は下の「supervisorの入れ替わり」。

resumeのwrapperを起動するのはsupervisorだけ。`status`のattentionは、`needs_session`のrunならどの場合も`next: resuming (runtime)`（resume中、試行が残っている、生きているsessionが次の試行を止めている、resume中のsupervisorが死んだ、試行を使い切って復旧jobへ移る直前のいずれもsupervisorのもの）。`kind`はrunを`needs_session`にした最新のイベント（payloadの`status`が`needs_session`のもの）。

セッションが変更不要と判断した場合はreceiptを`result: failed`と理由（`summary`）で書き直す。`integrate ID`は`fail_integration`でrunを`failed`にし（`integration_failed`。payloadの`receipt`にそのreceiptのJSON全体を持つ。`integration_receipt`は記録しない）、mainには触れない。worktreeは残る。`failed`になったrunはsupervisorがtriageする（[Triage](triage.md#triage-supervisor)。triageのresumeは`needs_session`に戻し、ここの試行の上限を通算で共有する）。

## supervisorの入れ替わり

- 解消依頼と終了依頼は file に書く。対話の打鍵・ダイアログ応答・exit_retried の再試行は廃止した。過去の記録と handoff の欄は読める。

引き継がないもの: wrapperが終了を記録したか死んでいるrunは、今までどおり`resume_run`がstaleなleaseを置き換えて（`lease_acquired`の`previous_token`）次の試行を始める。試行の`workspace_created`が無い（wrapperを起動してhandleを記録する前にsupervisorが死んだ）runは監視する手段が無いので引き継がず、sessionが終わるまで次の試行を止める（人が wrapper の生存を確認する）。`resume_request_sent`を記録しないバイナリが始めたresumeを引き継ぐと、依頼を送ったかが分からないので、次の turn の依頼としてもう一度書く。依頼を書いてから`resume_request_sent`を記録するまでの間にsupervisorが死んだときも同じく2回目が送られる。
