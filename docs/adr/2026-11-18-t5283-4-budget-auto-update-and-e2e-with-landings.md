# ADR-t5283-4: 着地を優先しながら自動更新の待ちを有界にし、e2eを着地側の予算で流す

## Context

着地のたびに自動更新のbuildとe2eが先にturnを予約すると、長い着地の検証の合間に更新が必ず入り、列が進みにくい。
一方で着地を無条件に優先すると、列が続く間は自動更新が本番へ届かない。
e2eの要るrunがworkerのslotを使うと、着地に向かう待ちが新しい実行の空きを塞ぐ。
重い処理を並列に増やさず、workerの予算と着地を進める予算を分ける必要がある。

ADR-t5107-1決定5の着地への戻りはADR-t5265-1が改めている。
ADR-t1233-2決定4のe2eの予算の理由はADR-t2159-1決定7により実cmuxを前提にしない形になっており、その決定とhostの排他は保つ。
改めるのはworkerのslotの使用と、自動更新・着地の間の順番の方針である。

## Decision

1. **着地を優先し、自動更新は列が空いたときに入れる。ただし更新の待ちには上限を設ける。**
   待つ更新のために、次に実行できる着地を毎回止めない。
   列が空いたときは更新を始め、列が続いても更新が待ち始めてからの有限の待ち上限に達したら、進行中の重い処理の終わりで更新へturnを渡す。
   列はあっても全entryが控えで着地を始められない場合も、資源を取れる更新を進めてよい。
   更新の候補が新しくなっても待ちの起点をリセットせず、着地が続くことで更新が際限なく待つことを防ぐ。
   上限とその設定の具体の値は実装が定義し、このrepositoryの値をruntimeの既定に固定しない。
2. **重い処理の排他を保ち、turnを渡す境界を共同検証の外にする。**
   自動更新のbuildからe2eの関門までと、着地側の重い検証を重ねない。
   バッチの検証とその失敗を切り分ける二分は一つの着地の機会として終えてから更新に渡し、進行中の検証を更新のために止めない。
   上限は新しい着地の開始を抑えて更新へ機会を渡す境界であり、走っている処理を打ち切る期限ではない。
   更新の関門を終えたら着地に機会を返し、候補の更新が続くだけで関門を連続させて着地を止め続けない。
   複数のprocessと直接のintegrateにも同じ順番と排他を効かせる。
3. **e2eの要るrunは、workerでなく着地側の予算で待ち、実行する。**
   実行中の開発・reviewはworkerのslot、着地の許可後の待ち（e2eを含む）は着地の列と分ける。
   ADR-t5107-1決定1・5とADR-t5265-1の、e2eの開始をworkerの空きで判じる部分を改める。
   e2eの開始も一本の列と資源の控えの判断で選び、workerの空きは待たない。
   ただしrunのe2eと着地の検証と自動更新の関門は同じ着地側の重い処理の予算で直列に流し、hostの同時負荷を増やさない。
   e2eを終えるまで着地を許さず、ADR-t5283-3の単独の着地として進める。
4. **e2eの実行場所と失敗の境界を保つ。**
   runtimeがreviewのpassや必要な着地の承認の後にhostで流し、workerは流さない。
   runのworktreeの承認した変更に対する実行であり、バッチに合わせるためにintegrateのrebase後へ移さない。
   host全体のe2eの排他は保ち、自動更新と人のinstallのe2eとも同時に流さない。
   流し直し・関門の印・変更による失敗をworkerへ返す規則は保つ。
   返されたrunは列を出てworkerの空きを待ち、環境による待ちは着地の列の控えとして理由を残す。
5. **既存の所有とworkerの背圧を保つ。**
   着地側はqueue全体で同時に一つの重い検証を使い、列はqueueの記録から組み立てschemaを変えない。
   列とe2eをworkerのslotには数えないが、順番待ちを無制限に増やさない既存のclaimの背圧は保つ。
   予算の切り替えのために走っているrunとleaseを持つrunへ触れず、既に始まった処理を奪わない。
   statusでは実行中のworkerと、e2eを含む着地の列を分け、何の資源とturnを待つかを人とAIが読めるようにする。

## Alternatives

- 着地のたびに更新と交互にする: 更新の必要性だけで毎回着地の待ちを増やす。
- 決まった本数の着地ごとに更新する: 検証の長さとバッチの大きさで待つ時間が変わり、更新の待ちを時間で保証しにくい。
- 列が空くまで無条件に更新を待たせる: 混んだqueueでは更新が際限なく待つ。
- e2eをworkerのslotに残す: 着地のための待ちが開発の空きを使い、列を分ける目的を満たさない。
- e2eや更新を着地の検証と並列にする: hostのCPUとメモリの負荷を増やし、今回の資源の制約に反する。

## Consequences

domainは列の順序に加え更新へturnを渡す条件を判断し、superviseの着地の開始はe2eも同じ予算へ載せる。
integrateの照合の権限は変えず、共同検証の間に更新が割り込まない境界を保つ。
reviewを終えたrunはworkerを空け、statusは実行と着地の待ちを分けて説明する。
実装とともにintegrate・claim-hold・review・statusと自動更新のdesignを更新する。
更新はすぐ入らないことがあり、e2eが長いrunは着地側を使うが、workerのslotと重い処理の同時数を増やさない。
