# ADR-t5283-3: 列の先頭から上限までをまとめて検証し、失敗は直列に二分して切り分ける

## Context

着地をrunごとに検証すると、同じmainを基に積み重ねる検証の費用が待つ本数だけ掛かる。
検証は一回に長い時間を使うので、その間に溜まる列をまとめれば、hostの並列負荷を増やさずに着地の処理量を上げられる。
ただしバッチの失敗を全員の差し戻しにしては、無関係のrunが巻き戻される。

ADR-0008決定3（番号の無い箇条の「手順」）のrunごとの検証を改める。
ADR-t615-1が改めた着地先の選択は保ち、このADRのmainもその着地先を指す。
landing recheckのきっかけはADR-0068決定1を改めたADR-t1310-1決定1、検査の範囲はADR-0068決定2を改めたADR-t2032-1が今の決定である。
後者の範囲の規則は保ち、バッチに選んだrunの重複検査だけを除く。

## Decision

1. **列の先頭からn本までを順に重ねたmain＋A＋B＋…を一回検証する。**
   各runに要る着地の検証の関門を満たす共同の検証とし、通れば各runをそれぞれのsquash commitで列の順に着地させる。
   検証した積み重ねと異なる差分を着地させず、途中で着地先が変わって一致を保証できなくなれば組み直して検証する。
   各runの承認はADR-t5283-2の照合を通し、共同の検証を承認の代わりにしない。
2. **nはprojectの設定による上限で、たまるのを待たない。**
   着地の検証のturnが空いた時点で列にある進めるrunを先頭からn本まで取り、すぐに検証を始める。
   一本なら一本で始め、待つ窓を設けない。
   検証中に列に入ったrunはそのバッチに足さず、次の選択で優先度と入った時刻に従う。
   runtimeの既定はどのprojectにも通じる側、すなわち従来の一本ずつの着地と同じ振る舞いにする。
   このrepositoryの値をruntimeに持ち込まず、projectの設定の変更で別に決める（ADR-t2257-1決定1）。
3. **e2e・衝突・控えをバッチで隠さない。**
   e2eの要るrunは単独の着地として扱い、e2eを省略したり他のrunの成功で代用したりしない。
   そのrunの前までをバッチとし、先頭ならそのrunだけを選ぶ。
   重ねると衝突するrunは衝突の解消へ返して列から外し、承認の聞き直しを要する。
   衝突を自動で解消してバッチを通すことはしない。
   控えのあるrunは選ばず、後続を選べるのはADR-t5283-1決定4の条件に限る。
   開始したrunとleaseを持つrunに、バッチを大きくするために触れない。
4. **落ちれば二分し、原因のrunだけを外して残りを進める。**
   一度も通っていない集合は着地させず、列の順序を保った前半と後半へ分けて検証する。
   前半を先に切り分け、通った変更を基に後半を検証することで、先行runとの組み合わせでだけ落ちる場合も調べる。
   単独まで分けても、その先行する通った変更の上で落ちるrunを原因として列から外し、今の着地の検証の失敗と同じ経路へ返す。
   原因を外した残りは積み重ねを作り直して必要な検証を通し、列の順に着地させる。
   全体で落ちても単独のmain上では全部通るという理由だけで、未検証の組み合わせを着地させない。
5. **検証の資源はqueue全体で同時に一つのまま。**
   バッチの検証も二分の各段の検証も直列にし、二分を並列化しない。
   バッチも一つの着地の検証としてADR-t639-1の分類とやり直しを保ち、hostの失敗をrunの原因と決めつけて二分しない。
   ADR-t4950-1の失敗の分類とADR-t3344-1のhandoffでやり直しを次へ渡す境界も保つ。
6. **landing recheckは残る待ちの先回りに限る。**
   同じバッチに選んで照合・検証するrunを、途中の各squash commitの後に重ねてrecheckしない。
   バッチの着地が終わった最新のmainに対し、バッチの外に残る待ちのrunをまとめて一度確かめる。
   直接の着地・再起動の間・外からのmainの動きも拾うADR-t1310-1の保証は保つ。
   残るrunの衝突と軽い検査、結果をaskにも残すこと、mainも落ちる場合にrunを差し戻さないADR-t2141-1の境界は保つ。
   走っているrunと他者がleaseを持つrunには触れず、recheckを次の着地の必須の前段にはしない。

## Alternatives

- 検証を並列にする: hostのCPUとメモリの制約に反する。
- バッチが落ちたら全runを差し戻す: 原因でないrunにもworkerと再承認の費用を課す。
- 二分した両側を元のmainだけで調べる: 組み合わせの失敗を見失い、合わせると落ちる変更を着地させうる。
- n本がたまるまで窓を設けて待つ: 人はrequest 361で即時開始を選んだ。検証は直列で一回に長い時間が掛かり、その間に列が溜まるため混雑時ほどバッチが大きくなる。窓は空いているときの待ちを足し、interruptのように一本ずつ急ぐrunまで遅らせる。
- landing recheckを全て廃止する: 人の答えを待つrunなど、まだバッチに選ばれないrunの破綻に気づくのが遅れる。

## Consequences

domainは一つの順番から共同検証の対象を決め、superviseの着地の開始は空いたturnですぐバッチを固定する。
integrateは共同検証とrunごとの承認の照合・squashを両立し、失敗時の切り分けも同じ直列の予算で行う。
reviewの判断の単位はrunのままで、statusは列の待ちと進行中の共同検証を説明する。
実装とともにintegrate・claim-hold・review・statusのdesignを直し、recheckの地図に重複させない境界を反映する。
成功時の検証回数は減る一方、失敗時には切り分けと残りの再検証の費用を受け入れる。
