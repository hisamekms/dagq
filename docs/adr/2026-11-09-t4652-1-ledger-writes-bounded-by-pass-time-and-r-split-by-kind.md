# ADR-t4652-1: 台帳の書く量はpassの時間で決め、Rは種類ごとに分ける

## Context

台帳を作る係（[ADR-t1662-1](2026-10-04-t1662-1-runs-are-covering-phase-intervals-folded-into-a-ledger.md)決定11）は、一定の間隔ごとに1回のpassを立て、1回のpassで書く行の数を件数で固定している。
本番の流入（2026-11-08の標本で約9千event／時）が増えると、書く量は流入に追いつかず、遅れ（Rが読める最新より後ろ）が縮まなかった。
Rは1本で、1回の読みで付いたqueueの行の印が全部書かれるまで進まないので、queueの行の遅れがrun・task・session・nodeの行の保証（読み手の新しさ）と起動ごとの読み直しの量まで決めていた。

[書く量のSpike](../plans/ledger-write-budget-spike.md#判定)の判定はholdsで、根拠は次のとおり。
- 間隔を待たずに続けて回せば、行ごとに書く今の形でも1時間に書ける行数は流入の約690倍・10倍の洪水の約69倍になる。
- 間隔を残すと、1 sのpassでも洪水に約1.0〜1.6倍しか勝てない。
- 流入との差を決めているのは書く速さでなく件数と待ちだった。
- passは周回と別のthreadで走り、周回の書き込みを待たせるのは1つの書き込みの要求がqueue serviceの書き込みの列を占める時間である。
- その時間は1要求に載せる行の量で決まり、大きい組はまとめても速くならない。

queueの行から写さないkindと窓の端の補いは別のADRが決め、このADRは書く量と書き方とRの分割だけを決める。

## Decision

1. **書く量は1回のpassの経過時間で決める。** 1回のpassの上限は件数でなく、読み・畳み・書きの全部を含む経過時間で決める。
   遅れがある間はpassの間隔を待たずに次のpassを立て、追いついたら今の間隔に戻る。
   上限の値の意味は定義のそばのdoc commentが持ち、根拠はSpikeの判定へのリンクで示す。
2. **1つの書き込みの要求はbyteで切る。** 1要求に載せる行は件数でなく行のtextのbyteで切る。
   通常の組（2行以上を載せる組）は、分けて送る段の要らない大きさ以下に収め、足すと上限を超える行の手前で組を閉じる。
   大きい組はまとめても速くならないので、この上限を上げて1要求を大きくしない。
   1行だけで上限を超える行（巨大な単独行）は他の行と組にせず1行だけの組にし、今の巨大な行の経路（部分を預けてから1つのwholeとして書く経路）で送る。
   この経路は今の保存能力・読んだ行の指紋の照合・1つのtransaction・Rを同じ書き込みに載せる形を保つ。
   大きすぎることを理由に行を飛ばさず、書けていない行の後ろまでRを進めない。
   上限が抑えるのは通常の組が列を占める時間で、巨大な単独行の部分ごとの要求の大きさは今と変えない。
3. **1要求の行は1つのtransactionで書き、印と行を分けない。** 1要求の行は読みを1回にまとめ、1つのtransactionで書き、読み直しが読んだ行と違えば組の全部を戻す。
   巨大な単独行の組もwholeを1つのtransactionで書き、照合が違えば何も書かない。
   R（行の印）は印が覆う最後の組のtransactionで書き（最後の組が巨大な単独行ならそのwholeに載せる）、印と行が別れない。
   読み直しの違いで戻った組があれば、そのpassは後ろの組とRを書かず、次のpassで読み直す。
   passは今どおり周回と別のthreadで走り、周回はpassの終わりを見るだけで待たない。
4. **Rを種類ごとに分ける。** Rを少なくともqueueの行のRと、run・task・session・nodeの行のRに分ける。
   各Rは、自分の種類の行がその位置までの全入力を記録したことだけを保証する。
   queueの行の遅れ（印が書かれ切らないこと）はrun・task・session・nodeのRを押さえない。
   起動の読み直しは種類ごとに自分のRから始め、ある種類の遅れが他の種類の読み直しの量を決めない。
   今の1本のRしか無い台帳からは、両方のRを今のRから始めて移り、台帳の版を上げて全行を書き直さない。
5. **保証は種類ごとのRでも同じ。** 決定9・13（台帳は計測専用で、runtimeの判断は台帳を読まない）と、RとWの約束（印の位置までの全入力を行が記録する、入力を飛ばしてRを進めない）を種類ごとのRでも保つ。
   台帳に残る行の中身は全件のfoldと同じにする。
   stats・kpi・reportの値は、同じ入力を記録した今の形の台帳を今の読み取り関数で読んだ値と同じにする（人の決定same_inputs、ask 1606）。
   共通の読み取り関数がRを使う所（読み手の新しさ）は、種類ごとのRをその種類の行の読みに当てる。

## Alternatives

- **件数の上限を上げる・間隔を縮める**: 流入が増えれば再び追いつけず、1回のpassの長さも1要求の大きさも行の大きさで揺れる。
  Spikeでは間隔を残すと、1 sのpassでも洪水に約1.0〜1.6倍の余裕しか残らず、流入の揺れや行の大きさで遅れが縮まなくなる。
- **1回のpassの全行を1つの要求・1つのtransactionで書く**: 1要求が列を占める時間が延び、周回の書き込みを待たせる。
  大きい組ではまとめる上乗せも無かった。
- **巨大な単独行を飛ばす・後回しにしてRを進める**: Rの約束（入力を飛ばしてRを進めない）を破り、行が全件のfoldと食い違う。
- **Rを1本のまま、queueの行の印を先に書き切る**: queueの行の遅れが他の種類の保証と起動の読み直しを押さえる形が残る。
- **Rを分ける移りで台帳の版を上げる**: 全行の書き直しになり、版上げの印が大量に積まれる（goal 264の件）。
- **passを別のprocessか専用のthreadの常駐に移す**: passは既に周回と別のthreadで走り、周回を待たせるのは列の占有なので、移しても得るものが無い。

## Consequences

- 書く量は流入に比例して伸び、遅れは続けて回すpassで縮む。
  周回の1つの書き込みがpassのせいで待つのは、多くて通常の組の1要求か、巨大な単独行の1つの要求（部分を預ける要求か、wholeを組み立てて照合し1つのtransactionで書く最後の要求）が列を占める時間である。
  巨大な単独行の最後の要求の占有は行の大きさで決まり、通常の組のbyteの上限では抑えられず、今の巨大な行の経路と同じ長さのまま残る。
- queueの行の遅れがrun・task・session・nodeの読み手の新しさと起動の読み直しを決めなくなる。
- 印と行が同じtransactionに載るので、途中で止まっても印の位置までの行は揃い、戻った組は次のpassで読み直される。
- 種類が増えればRも増やせるが、種類ごとのRの読み書きと移りの扱いは実装のtaskが定義のそばのdoc commentに書く。
- 決定11の「周回が終わった後に畳み直す」と決定17の入力の到達点と確定の印の意味は変えず、このADRは1回の書く量と書き方とRの数だけを変える。
- 今の姿は[計測](../design/measurement.md)の「台帳を作る係」が持つ。
