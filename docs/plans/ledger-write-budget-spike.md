# スパイク：台帳の書く量を時間で決める

問いは「台帳の係の書く量の上限を件数（`WRITES_PER_PASS`=200、`INTERVAL_SECS`=60、`src/domain/ledger/builder.rs`）でなく 1 回の pass の時間で決め、遅れ（R が最新より後ろ）がある間は `INTERVAL_SECS` を待たずに pass を続け、queue 行をまとめて 1 transaction で書く形にしたとき、file に置いた SQLite の store で 1 秒あたり何行書け、本番の流入（約 9 千 event／時 ≒ 2.5 event／秒）とその 10 倍の洪水より十分速く、supervisor の周回を妨げない pass の時間の上限が取れるか」。
本番と同じ開き方の file の store に本番の形の行を、(A) 今の書き方（行ごと）と (B) 1 つの要求・1 transaction にまとめた書き方で、queue service の書き込みの列（write line）の上で行われる処理まで含めて書いて測り、周回との関係はコードを読んで書いた。

判定は holds（下の「判定」）。
書く速さの中央値は (A) 約 1.7 千行／秒、(B) 約 1.6〜2.4 千行／秒で、続けて回す形なら 1 時間に書ける行数はどちらでも流入の 600 倍以上、洪水の 60 倍以上になる。
pass は周回と別の thread で走る。周回の書き込みを待たせるのは、pass の 1 つの書き込みの要求が queue service の書き込みの列を占める間（要求の読み・行の読み直しと指紋の照合・transaction）で、その長さは 1 要求に載せる行の量で決まるので、上限で切れば周回を妨げない。

- (B) 1 要求・1 transaction: pass が N 行を `ledger_rows_of` で 1 回に読み、行と指紋を 1 つの text にして送る。列の上では service の dispatch の `write_sessions_over` と同じく、text を読み、行ごとに `ledger_row` で読み直して指紋を照合し、`write_session_rows_marked`（全行を読み直して書く 1 transaction）で書く。
- 表の「全体」は pass の読みから書き終わりまで、「列」はそのうち列の上の処理（text の読みから transaction の終わりまで）、「transaction」は書き込みの transaction だけ。socket の往復と、512 KiB を超える要求を分けて送る段（`stage_ledger_row`）は含めていない。
- 同じ N で A,B,A,B… と交互に流す。各組 5 周、1 周目は暖機として捨てる。ぶれ（残りの周の最大 ÷ 最小）はどの組も 2 以下（最大は N=5,000 の B の 1.82）だったので 10 周に増やしていない。

## 周回との関係（コードから）

- pass は supervisor の周回の thread で走らない。`LedgerWatch::pass`（`src/application/supervise/observation/ledger.rs`）は間隔が来ると `spawn_traced` で job の thread を立てて `pass_of_watch_timed` を走らせ、周回は次の周で `JoinHandle::is_finished` を見て終わったものだけを `reap` する。走っている間は何も待たず、次の pass を立てないだけ。待つのは周回の終わりの `LedgerWatch::finish` で、`FINISH_WAIT`（30 秒）か EndBy の早い方まで。
- 本番の pass の store は queue service を通る（`compose::supervisor` の `ledger_port` に渡す `SupervisorQueues`）。service は書き込みの要求を 1 本の列に載せる（`queue_service::handled` が `on_write_line` の要求を `ServiceWriteLine` の `run` で走らせ、書き込みの接続 `WriteConnection` は 1 要求ずつ貸す）。読みだけの要求は列に載らない。
- 列が 1 つの要求に使う時間は transaction より長い。dispatch の `write_over`（(A) の 1 行）と `write_sessions_over`（(B) の行の組）は、要求の text の読みの後、transaction（`write_tx`、`BEGIN IMMEDIATE`）を始める前に、行ごとに `ledger_row` で読み直して指紋を照合し、transaction の中でもう一度読み直してから書く。512 KiB（`LEDGER_ROW_REQUEST_BYTES`）を超える組は `stage_ledger_row` の要求に分けて送られ、最後の `write_staged_session_rows_over` が列の上で組み立て直してから同じことをする。この間ずっと、周回の claim・遷移・heartbeat の書き込みの要求は同じ列の後ろで待つ。
- 測った列の時間（組ごとの中央値の表）: (A) は 1 要求（1 行）あたり約 0.42〜0.43 ms、(B) は 1 要求に N 行を載せて N=200 で約 62 ms、N=1,000 で約 326 ms、N=5,000 で約 2.3 s（1 行あたり約 0.31〜0.47 ms、そのうち transaction は約 6 割）。
- pass は 1 本の thread で要求を 1 つずつ送るので、pass の要求と要求の間には周回の要求が列に入れる。周回の 1 つの書き込みが pass のせいで待つのは、多くて pass の 1 要求の列の時間で、それは 1 要求に載せる行の量で決まる（pass の時間の上限ではない）。
- 長い列の占有の目安は `WRITE_HOLD_WARN`（2 秒、write の lock の長い保持を log と event で名指す）と `QUEUE_BUSY_TIMEOUT`（5 秒、他の接続の書き込みが失敗する）。N=5,000 の (B) の 1 要求（約 2.3 s）は `WRITE_HOLD_WARN` を超えるが、1 要求を `LEDGER_ROW_REQUEST_BYTES`（512 KiB、本番の形の平均で約 180 行、この host の列で約 55 ms）以下にすれば、分けて送る段を通らず、どちらにも十分遠い。列の時間だけで見れば約 600 行（約 200 ms）までが目安だが、それは約 1.8 MB で `MAX_REQUEST_BYTES`（1 MiB）を超え、測っていない分けて送る段を通る。

## 判定

holds。

- 書く速さ: 列の上の処理まで含めて、(B) は 1 秒あたり約 1.6〜2.4 千行、(A) は約 1.7 千行（組ごとの中央値の表）。
- 流入との比: 続けて回す形では、(B) で 1 時間に約 570〜860 万行、本番の流入の約 635〜955 倍、10 倍の洪水の約 64〜96 倍（上限の候補の表）。(A) のままでも続けて回せば流入の約 690 倍・洪水の約 69 倍で、流入に勝つのに効くのは「続けて回す」こと。まとめることの上乗せは小さい組（200〜1,000 行）で約 1.3〜1.4 倍、5,000 行の組では無い。
- 周回を妨げない上限: pass は別の thread で走り（`LedgerWatch::pass`・`spawn_traced`）、周回を待たせるのは pass の 1 つの書き込みの要求が列を占める間（`queue_service::handled`・`write_sessions_over`）。1 要求を 512 KiB（`LEDGER_ROW_REQUEST_BYTES`、約 180 行）以下に切れば、列の時間は約 55 ms（N=200 の (B) の 1 行あたり約 0.31 ms から）で、周回の 1 つの書き込みの遅れはそれ以下、`WRITE_HOLD_WARN` の約 1/35。その大きさの要求を続けて送れば 1 秒あたり約 2.4 千行（N=200 の (B) の中央値 2,388）で、洪水（25 行／秒）の約 95 倍。

条件と限界:

- 測ったのは store の読みと書き込み、列の上の text の読み（serde）まで。socket の往復、分けて送る段、pass が畳むための読み（run の event・steps・resources、`fold_and_write`）は測っていない。socket の往復は (A) では行ごと、(B) では組ごとにかかり、(A) との差を広げる側に効く。畳むための読みはどちらも行ごとにかかる。pass の時間の上限は経過時間（読みと畳みを含む）で取るので、この不足があっても 1 回の長さは上限に収まり、書く速さが下がるだけ。
- Rust の code は最適化なしの test の build で、本番の release の build より遅い側（行の text の読み書きは Rust の code）。
- run 行は event 101 件で 42.9 KB。それより大きい run 行は 1 行の列の時間が長いので、1 要求の量は行数でなく byte で切る方が列の時間に合う。
- host のほかの run の負荷の下で測った（load average 7〜10）。同じ試作をこの log の前に `cargo-brief.sh` を通さずに流した 1 回は記録にしないが、組ごとの中央値は (B) 2,241〜2,967、(A) 1,708〜2,025 行／秒で、N=5,000 でも (B) が速かった。N=5,000 の (A) と (B) の順は負荷のぶれの中にある。

## 後続の計画への推奨

- 時間の上限: 1 pass の経過時間（読み・畳み・書きの全部）の上限を約 1 s にし、遅れ（R が最新より後ろ）がある間は `INTERVAL_SECS` を待たずに次の pass を立てる。
- 1 要求の上限: 周回の書き込みの遅れを決めるのは pass の時間でなく 1 つの書き込みの要求の列の時間なので、それを別の上限にする。行の text の byte で切り、`LEDGER_ROW_REQUEST_BYTES`（512 KiB、分けて送る段が要らない大きさ。本番の形の平均で約 180 行、この host の列で約 55 ms）程度にする。大きい組はまとめても速くならない（N=5,000 の表）ので、上限を上げて 1 要求を大きくしない。
- transaction のまとめ方: 1 要求の行を、読みを 1 回にまとめ（`ledger_rows_of`）、書きを 1 つの transaction（`write_session_rows_marked` と同じ、読み直して違えば全部を戻す形）にする。R（行の印）は印が覆う最後の組の transaction に書けば、印と行が別れない。列の上の行ごとの読み直し（`write_sessions_over` の transaction の前の `ledger_row`）は transaction の中の読み直しと重なるので、1 回の読みにまとめると列の時間が縮む。
- 周回との関係: pass は今どおり job の thread で走らせ、周回は `is_finished` を見るだけにする。別の thread に移す次の Spike は要らない。
- 書く速さは続けて回せば流入に十分勝つので、queue 行を減らすこと（[queue 行の kind と読み手](ledger-queue-rows-readers-spike.md)）は書く量のためには前提でなく、起動の読みと窓の読みのために進める。
