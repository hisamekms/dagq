# DAGQ: Agent比較実験・観測基盤の設計依頼

## 依頼

リポジトリ **`hisamekms/dagq`** の最新の `main` と関連ドキュメントを調査し、既存アーキテクチャを踏まえて、Actorごとに利用するAgentを切り替えながら比較実験できる仕組みを**設計**してください。

**この依頼の主目的は設計であり、実装はしないでください。** 既存コードから確認できた事実、仮説、設計上の提案を区別してください。既存の概念・機能を優先して再利用し、不要な新規基盤を作らないでください。

## 背景と目的

DAGQでは少なくとも以下のActorが協調して開発作業を進めます。

- `planner`
- `plan reviewer`
- `worker`
- `reviewer`

各Actorには異なる能力が求められます。Claude Code、CodexなどのAgentを、どのActorに割り当てるのが適しているか、また同種・異種Agentの組み合わせによって成果が変わるかを、通常運用と制御された比較実験を通じて調べたいです。モデル・CLI・設定・評価観点は今後変わり得ます。

### 確定している設計原則

1. **DAGQは優劣を決めない。** DAGQが責任を持つのは実験条件の設定・割当・実行、および事実・計測値・成果物の収集、永続化、提供です。
2. **Evaluation PolicyはDAGQの外側。** どの指標を重視するか、スコア・重み付け・ランキング・モデル選定などは、外部の分析者やツールが判断します。DAGQに固定の「総合評価スコア」を導入しないでください。
3. **過去のデータを後から再分析できること。** 生のEvidenceと、その測定・集計結果は区別し、測定定義やスキーマはバージョンを追跡できるようにします。計測値だけでなく可能な範囲で元データを残します。
4. **ActorごとのAgent割当比率が必要。** 例：Plannerの50%をClaude、50%をCodexにする。さらに、Worker×Reviewerなど複数Actorの**組み合わせを実験群として割り当てる**方式も必要です。
5. **割当と実行の実態を記録する。** 意図された割当と実際に起動したAgentを区別し、途中失敗・リトライ・フォールバック・キャンセル等も追跡します。
6. **本番でのWeighted Routingと、入力を固定したReplay/Benchmarkは異なる。** 比較目的と制約が異なるため区別しつつ、実行・記録の共通化を検討してください。
7. **段階的に実装可能であること。** 最初から大規模な評価プラットフォームにしないでください。既存のDAGQの通常運用への影響を最小化します。

## 調査事項（最初に実施）

リポジトリを読み、少なくとも次の内容を確認してください。

- Actor/Agentの既存の定義、Provider/Model選択、プロンプト・Effort等の設定方法
- Planner→Plan Reviewer→Worker→Reviewerの制御フロー、Supervisor、キュー、再実行、差し戻しループ
- Task/Goal/Invocation/SessionなどのID・ライフサイクルと、割当を固定するのに適切な境界
- 永続化（例：SQLiteやPostgreSQLの現状）、イベント・ログ・実行履歴、メトリクス・成果物の保存先
- ワークツリー、Git統合、並列実行やコンフリクト処理への影響
- 既存のAgent Eval、テスト・検証・分析機構の有無と再利用範囲
- CLI/API/設定ファイルの慣習、マイグレーションと後方互換性の制約

※ ここに列挙した名称・方式が実装済みであるとは決めつけないこと。実際のファイルパスとコード根拠を示してください。

## 設計してほしい機能

### A. Actor別の重み付き割当（Independent Routing）

- Actor単位で複数AgentとWeightを設定できる。
- Weightは割当確率であり、少数実行時に厳密な件数比率を保証するものではないことを明示する。
- 割当対象はProvider名だけでなく、必要に応じてModel、Effort、実行設定も表現できるよう検討する。
- 既存設定からの段階的移行と、実験を行わない通常実行の挙動を定義する。

### B. 組み合わせ単位の割当（Combination Routing）

- 複数Actorへの割当を一つのVariantとして定義し、VariantごとにWeightを指定する。
- 例：Worker=Claude／Reviewer=Codexを25%、Worker=Codex／Reviewer=Claudeを25%、同種モデルの2パターンをそれぞれ25%。
- 組み合わせの一部のActorのみ指定した場合の扱い、Independent設定との優先順位、重複実験の競合を定義する。
- Planner×Plan Reviewer、Worker×Reviewer、4役一括の比較にも拡張可能にする。

設定例（**概念例。構文・命名は現行DAGQに合わせて再設計してよい**）：

```yaml
experiments:
  - id: worker-reviewer-ab
    assignmentUnit: task
    variants:
      - id: claude-claude
        weight: 25
        actors: { worker: claude, reviewer: claude }
      - id: claude-codex
        weight: 25
        actors: { worker: claude, reviewer: codex }
      - id: codex-claude
        weight: 25
        actors: { worker: codex, reviewer: claude }
      - id: codex-codex
        weight: 25
        actors: { worker: codex, reviewer: codex }
```

### C. 割当の一貫性・再現性

- Invocation / Task / Goal のどの単位で割当を固定すべきか、各方式の意味とトレードオフを整理する。**Task単位Sticky Assignmentを初期候補**とするが、PlannerのようにTask作成前から動くActorとの整合を必ず検討する。
- レビュー差し戻し・Worker再実装・リトライ・Supervisor再起動でも、どのタイミングで割当を保持／変更するかを明確にする。
- Seed、割当キー、設定バージョン等によって、割当の理由・確率・実験群を監査できるようにする。ランダム抽選の再現と「実際のLLM出力の完全再現」は別問題として扱う。
- 同一Goal内のTask間の依存性やAgent間の情報共有により実験群が汚染される可能性を検討する。
- Weightの更新・一時停止・削除、実行中の設定変更、競合するルール、Agent利用不可時の挙動を定義する。

### D. EvidenceとMeasurementの収集

最低限、以下を欠損も含めて表現・関連付けられるよう検討する。

- Experiment / Variant / Assignment / Run / Attempt / Actor Invocationの識別子と関係
- 実験設定・割当確率・抽選キー・設定バージョン・対象Task/Goal
- 意図したAgentと実際のProvider/Model/Effort、実行CLIやプロンプト・設定のバージョン／ハッシュ
- 入力要求、計画、レビュー指摘と判定、修正ループ、生成成果物とGit diff／コミット
- 実行開始・終了時刻、キュー待機時間、処理時間、token usage、利用可能な費用情報
- テストの個別結果、受け入れ検証コマンドと結果、失敗・タイムアウト・キャンセル・フォールバック
- Git競合・マージ・統合結果等、並列処理に関する観測情報
- 実行環境・ベースコミット・ツールバージョンなど比較に影響する要因

測定値には単位、計測範囲、計測方法、バージョン、欠損理由を記録する設計を検討する。費用が推計値なら推計値と明示する。

Evidenceの大量保存、機密情報・シークレット・個人情報のマスキング、保存期間、アクセス制御、ストレージ費用も設計に含めること。必ずしも全ログを無制限に保持する必要はない。

### E. 比較できるデータの提供

- JSONLなどの機械可読な形式で、実験条件・割当履歴・実行結果・測定値・成果物参照を出力できるようにする。
- DAGQの責務は観測・算術集計までとし、外部での評価・統計分析・重み付け・可視化が可能なデータ契約を設計する。
- 通常運用の観測データと、同一入力・初期コミットで実行する制御Benchmarkを識別できるようにする。
- 将来、過去のスナップショットから別のReviewerに同じ成果物を与えるReplay Harnessを追加できる拡張点を検討する。ただしReplay自体をMVPの必須条件とはしない。

## 比較実験として特に検討してほしい論点

- Weighted Routingだけで、Task難易度・曜日・時間帯・実行ホスト等の偏りが入り得る。何を記録し、どのような割当制御で偏りを抑えるか。
- Reviewer比較では**同一の成果物**に対する独立レビューと、レビュー→修正を含むEnd-to-End比較は区別すべきである。
- Plannerの出力が下流Taskの数や難易度を変えるため、Planner比較をTask件数や単純成功率だけで判断できない。Goal単位の比較や単位の整合を検討する。
- 運用で観測できた相関と、統制実験から推定できる因果効果を混同しないこと。
- Agentの性能がモデル更新・プロンプト変更によって変わり、比較条件が時間とともにずれるリスクへの対応。
- 評価指標は今後進化するため、DAGQに現時点の品質観・ランキング規則を埋め込まないこと。

## 想定する成果物

設計提案をMarkdownで作成してください。少なくとも以下を含めてください。

1. **現行実装の調査結果**：該当ファイル／型／処理経路と既存機能の再利用案
2. **責務境界**：DAGQ内で扱う機能と、外部のEvaluation／Analysisに委ねる機能
3. **アーキテクチャ**：主要コンポーネントと既存フローへの組み込み位置、制御フロー
4. **設定仕様案**：Independent／Combination Routing、優先順位、デフォルト、バリデーション、移行
5. **データモデル／イベント／保存設計**：IDの関係、履歴、実験設定のスナップショット、欠損、バージョン
6. **割当アルゴリズム**：実験単位、Sticky Assignment、再現性、リトライ、Fallback、設定変更時の扱い
7. **観測・エクスポート仕様**：最小スキーマ、Event/Evidence/Measurementの境界、出力例
8. **テスト方針**：重み付け、割当の固定性、並列実行、再起動、データの整合性、実験汚染
9. **段階的実装計画**：MVPと後続フェーズ、既存実装への変更箇所、技術的リスク
10. **未決事項・代替案**：判断が必要な論点と推奨案、その理由

### MVPの初期候補

- Actor別Weighted Routing
- Worker×ReviewerなどのCombination Routing
- 適切な割当単位でのSticky Assignment
- 実験ID／Variant／Agent割当／実際の起動Agent／実行結果の保存
- 基本的な構造化エクスポート

これらも必ず実装すると決めつけず、既存DAGQとの整合性を踏まえて最小範囲を提案してください。

## 進め方

1. まず最新mainの実装・設計文書を調べ、現状の制約と利用可能な仕組みを整理する。
2. 次に責務境界とMVPを提案する。
3. 割当のタイミング、ID、永続化、Supervisorとの整合性など実装に影響の大きい論点について代替案を比較する。
4. 設計文書をまとめ、既存機能との差分、実装順序、検証方法を明示する。
5. **この段階ではアプリケーションコードを変更しない。** 実装へ進むために必要な判断事項を列挙する。

目標は、特定モデルの優劣をDAGQが判定することではなく、**DAGQがAgentの配置実験を安全・再現可能に実施し、将来変化する評価観点でも再利用できる観測事実を残せること**です。
