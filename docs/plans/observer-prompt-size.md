# 上限を入れた後の本番のobserverのpromptのbyte数と節ごとの大きさ

[observer](../design/supervisor-lifecycle/observer.md)の「promptの入力の上限と選ぶ順」の上限（[ADR-t1566-1](../adr/2026-10-03-t1566-1-headless-job-prompts-carry-decision-material-within-limits.md)、task 1567）を入れた後の本番の測定（task 1575）。上限は1回の本番の入力からの推定（約127,273 byte）で決めたので、着地後の実測と比べて上限を見直すかを決める。読むだけの測定で、コードも上限の値も変えない。

## 要点

- **実測は推定の1.02〜1.14倍。** 標本10件のprompt_bytesは130,376〜145,357 byte（平均137,837）で、推定127,273に対して1.024〜1.142倍。1567の後の全87件でも120,536〜158,456（中央値138,124）。
- **全体の上限160,000 byteの余裕は標本で9.2%、全87件では1.0%。** 標本の最大はdailyの145,357（90.8%）。全87件の最大は2026-10-05T12:45Zの158,456（99.0%）で、必須の`open_asks`が40件・27,963 byteに膨らみ、全体の上限で`notes`が20件とも落ちた（87件中この1件だけ）。150,000を超えたのは87件中5件。
- **省かれる節は`findings`・`stats`・`notes`の3つで、どれも節の上限に張り付いている。** 標本10件で`findings`は10回（最大22件）、`stats`は10回（最大13 key）、`notes`は9回（最大3件）。`kpi`・`improvements`・`graph`は一度も省かれず、最大でも上限の56%未満。
- **結論は全ての節で据え置き。** ただしdailyでは`stats`の1 keyの上限8,000 byteを`overall`・`failed_tests`が超えて、選ぶ順の先頭近くのkeyが省かれる。これはfollow_upに出す（下の「結論」）。

## 読んだコマンドと時刻

- 2026-10-07T12:07:30Z（UTC）に`dagq observe --history --limit 200`（固定バイナリ`~/.local/bin/dagq`）。返った200件のうち`prompt_bytes`が記録されたのは2026-10-03T08:40:47Z以降の87件（hourly 83・daily 4、outcomeは全てsucceeded）。それより前は`prompt_bytes`の無いerror・succeededで、1567の後に`skipped`のobservationは0件。
- 省いたkeyの名前は各observationの`<queue dir>/observer/<dir>/prompt.md`の`Left out`の行、keyの大きさは`dagq observe --input 1791374535`と`dagq observe --input 1791297305`の`sections`。
- 省いたものを読んだかは`<queue dir>/observer/<dir>/output.out`のcommandの行（Codexのobserverのjsonlだけがcommandを残す）。
- 集計はjqで`prompt_sections`から取った（節のbytesは見出しと省いた注記を含むので、上限を少し超える）。

- 推定（1567のreceipt）との比較: 推定では`findings`は52件中38件、`stats`は40 key中33 key。実測の`findings`は46〜60件中38〜43件、`stats`は42 key中29〜39 key（hourlyは34〜39）で、推定とほぼ同じ件数が残る。全体が推定より大きいのは、推定に無かった`kpi.breaches`（6.6KB）と、`stats`・`notes`が節の上限まで埋まることによる。
- `notes`の全87件の最大の省略20件は、上の2026-10-05T12:45Z（全体の上限で後ろの節から落ちた）の1件だけで、それ以外は1〜3件。
- hourlyの`stats`が省くkeyは`runs`・`goals`・`versions`・`areas`・`changes`・`sessions`など1 keyで8,000 byteを超えるもの（1791374535で`versions` 24,925・`runs` 15,914・`areas` 15,394）で、節の上限ではなく1 keyの上限で外れる。
- dailyの`stats`は4件とも`failed_tests`を省き、2026-10-06T14:35Zは`overall`（8,197 byte）・`failed_tests`（8,844）・`review_reasons`（8,922）も省いた。どれも選ぶ順の先頭近くのkeyで、24時間分で1 keyの上限8,000を少し超える。
- 省いたものを読むか: Codexのobserverの出力（87件中32件）は32件とも`dagq observe --input`を打ち、うち30件が`--section findings`で省いたfindingを読んだ。Claudeのobserverの出力は最後の文だけでcommandを残さないので数えられない。

## 結論

標本は10件（全体では87件）で、3件に満たない場合には当たらない。

| 節 | 結論 | 理由 |
| --- | --- | --- |
| 全体160,000 | 据え置き | 標本の余裕は9.2%で、160,000を超えたpromptは無い。全体の上限で節が削られたのは、必須の`open_asks`が40件に膨らんだ87件中1件（158,456 byte）だけで、そのときも上限の規則どおり後ろの節（`notes`）を落とし、読む方法を書いた。上限はagentの文脈のための値で、推定より1割大きいのは`kpi.breaches`と節が埋まることで説明がつき、上げる理由にならない。 |
| `findings` 48,000 | 据え置き | 毎回省くが、選ぶ順（impact・occurrences・新しい順）で38〜43件が残り、Codexのobserverは毎回`observe --input`で残りを読んでいる。上げると全体の余裕（標本で約15〜30KB）を食い、`open_asks`が膨らんだときに後ろの`notes`・`graph`が落ちやすくなる。 |
| `stats` 40,000（1 key 8,000） | 節は据え置き、dailyの1 keyの上限は確かめ直す | hourlyで省くのは1 keyで8,000を大きく超えるkey（`versions`・`runs`など）で、節の上限を上げても入らない。dailyでは選ぶ順の先頭近くの`overall`・`failed_tests`が1 keyの上限をわずかに超えて省かれており、順の意図と合わない。直し方（dailyの1 keyの上限、先頭のkeyを要約するなど）はコードの変更なのでfollow_upに出す。 |
| `kpi` 32,000（1 key 16,000） | 据え置き | 最大55%で省いたことが無い。節の上限は空きを他の節に回さないので、下げても他の節は増えない。 |
| `notes` 12,000 | 据え置き | 省くのは直近20件のうち古い1〜3件で、`dagq notes`で読める。上げても1件あたり約600 byteで得るものが小さい。 |
| `improvements` 4,000・`graph.critical` 2,000・`graph.candidates` 4,000 | 据え置き | 最大でも上限の38%未満（標本では29%以下）で省いたことが無い。下げても他の節は増えない。 |
| 必須の資料（`kpi.breaches`・`open_asks`・`stats.alerts`・`stats.running_alerts`） | 据え置き | 自分の上限を持たない決定（ADR-t1566-1）どおりで、`open_asks`が膨らんだ1件も全体の上限の中に収まった。 |
