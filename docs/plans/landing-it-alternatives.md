# 着地の絞った IT の全部流す条件の代替案の比較

[着地の検証の切り替えの前後比較](landing-verify-switch.md)の結論 1 は、切り替えの後の窓で `sh scripts/landing-it.sh` の 183 回のうち 170 回（93%）が IT を全部流したことだった。
ここでは、全部流す条件の代替案を同じ 183 回と、その窓の着地の見逃しに当てて比べ、1 つを選んだ。
あわせて、全部流した回が前の窓の `cargo llvm-cov nextest` より長い理由を、検証のログの段ごとの時間から読んだ。
選んだ案は [ADR-t2892-1](../adr/2026-10-20-t2892-1-landing-it-leaves-added-sources-and-broad-entries-to-ci.md) と `scripts/landing-it.py` に入れ、値の根拠は[着地の IT の絞り込みの測定](landing-it-selection.md)の「決めたこと」の 2 と 4 に書いた。

## 要点

- **新しく足した src のファイルの扱いを変えるだけ（案 ii・iii）では、全部流す割合は 93% から 90〜92% にしか減らない。**
  足したファイルで全部流した 81 回の差分は、ほかに多くの IT に当たる表の項目にも触れていて、理由が閾値超えに移るだけだった。
- **効くのは広い表の項目の扱い（案 iv）。** 表の src・crates のファイルの 58〜65% は IT の 25% より多くに当たり、45〜54% は半分より多くに当たる（使った 8 本の表）。
  ファイルの粒度の表では、多くのファイルが IT のほとんどに当たる。
- **選んだ案は iii と iv（IT の 25%）の組み合わせ**: 表の tree に無い src のファイルは表から何も選ばず、表が IT の 25% より多くに当てるファイルも表から何も選ばない。どちらも差分のテストと表に無い IT は流し、残りは CI に任せる。
  全部流す割合は 92.9% → 21.9%（共通のファイル 28 回・閾値超え 12 回）、IT の見込みの壁時計の中央値は 462 秒 → 31 秒。
- **見逃しの数え方では差が分からない。** 窓で新たに赤くなった IT は 2 本の `planner_headless` のテストが 21 の CI の run で赤と緑を繰り返したものだけで、着地の変更でなく不安定なテストの赤である。
  選んだ案の見逃し 5 件（範囲が 1 件の着地 3 件）はどれもこの 2 本で、今の規則は 0 件。
  代わりに、差分が表で当たる IT のうち案が流さない本数を数えた。絞った回では中央値 806 本（当たりの 97%）を CI に任せる。
- **全部流した回が旧 llvm-cov の回より長い（中央値 714 秒 対 569 秒）のは、テストの本数の増加では説明できない。**
  IT の本数は 1,127 → 1,145（+1.6%）、unit test は 1,551 → 1,999 本（+29%）だが unit test の直列の和は 126 → 202 秒しかない。
  伸びたのは同じ IT 1 本あたりの時間で、両方の窓で流れた 1,137 本の中央値の和は 2,319 → 3,253 秒（×1.40）。
  段ごとでは、build は 91 → 50 秒、テスト（nextest）は 424 → 630 秒、残り（llvm-cov の coverage の表・landing-it の表の取得）は 33 → 6 秒。

## 窓と入力

- **後の窓**: `2026-10-07T10:27:40.972Z` 以上 `2026-10-14T10:27:40.972Z` 未満（印 123128 の前後比較と同じ）。前の窓はその前の 168 時間。
- **landing-it の回**: 後の窓の `verification_command`（`command` が `sh scripts/landing-it.sh`）183 回。各回の差分は同じ run のその回の `integration_started` の `main` から `integration_rebased` の `head_after` まで、表はその回より前に終わった `IT coverage map` の成功した run の最新（[landing-verify-switch/replay_choice.py](landing-verify-switch/replay_choice.py) と同じ）。使った表は 8 本（run 37543663080〜38482877733、IT 1,110〜1,223 本）。
  今の規則の再現は [landing-verify-switch/choice.csv](landing-verify-switch/choice.csv) と 183 回とも一致し、選んだ案を入れた `scripts/landing-it.py` の `choose` を同じ 183 回に当てた全部か絞ったかも、`replay.py` の選んだ案と 183 回とも一致した。
- **着地**: 2026-10-06 からの `run_integrated` 345 件（範囲が窓の前に始まる CI の run のため）。後の窓の 254 件のうち landing-it を流したのは 161 件、93 件は IT を流さない（docs・config など）。
  llvm-cov か全体の `cargo test --locked` を流した着地は全部のテストを流したとし、IT を流さない着地は何も選ばないとした。
- **CI**: `landing-verify-switch/ci_main_runs.csv` の 2026-10-06 以降の main の push の run 333 件（cancel 85 件を除く）。job ごとのテストの step の結論と、failure の run 134 件の `gh run view --log-failed` から落ちたテストを、[landing-it-selection/collect.sh](landing-it-selection/collect.sh) の手順 3・6 と同じ規則で読んだ。
- **検証のログ**: 各 `verification_command` の `log_path`（host の run の directory）。前の窓の llvm-cov 313 回・後の窓の landing-it 183 回のログが全部残っていた。
- 読んだ時刻は 2026-10-20T01:40Z〜02:10Z（UTC）。状態を変えないコマンド（`events`）だけを worker のクライアントモードで読んだ。
- **周回しない理由**: 入力は queue の event・git・CI の記録・表・検証のログで、値はそれらから計算するだけで決まる。host の上で build や test を流す測定でないので揺れの源が無く、周回数は 1。

## 比べた案

どの案も、差分で足した・変えたテストのファイルが定める IT、テストが repository から読むファイルの IT、表に無い IT を必ず流し、共通のファイル・表の古さで全部流し、既に落ちているテストを外す（どれも今の規則のまま）。
閾値は今のまま（絞った IT の見込みの壁時計が IT 全部の見込みの半分を超えたら全部）で、案ごとに選んだ IT に当てた。

- **(i) 今の規則**: 表の tree に無い src・crates の `.rs`（unit test の module を除く）に触れたら全部流す。
- **(ii) 親の module で選ぶ**: 表の tree に無い src のファイルは、その module を `mod` で宣言する親の module のファイル（`src/a/b.rs` なら `src/a.rs` か `src/a/mod.rs`）の表の項目で選ぶ。親に項目が無ければさらに上へ辿り、crate の root まで無ければ全部流す（`ii_parent`）。同じ directory のファイルの項目の和で選び、無ければ上の directory へ辿る形も比べた（`ii_dir`）。
- **(iii) CI に任せる**: 表の tree に無い src のファイルは表から何も選ばない（差分のテストと表に無い IT だけが流れ、残りは CI に任せる）。
- **(iv) 広い項目を選ばない**: 表がそのファイルを IT の本数の B（50%・25%）より多くに当てているなら、そのファイルの項目からは何も選ばない（`iv_broad50`・`iv_broad25`）。(ii)・(iii) との組み合わせと、(iii) と B = 10% も比べた。

## 値の式

- **全部流す割合** = 全部流した回 ÷ 183。
- **IT の見込みの壁時計** = max(選んだ表の IT の所要時間の和 ÷ 6, 最長の IT)。6 は `NEXTEST_TEST_THREADS`、秒は表の値（CI の coverage の計測つきの runner）で、着地の host の秒と違う。全部流した回は、その表の IT 全部の見込み（419〜527 秒）で数える。表に無い IT は表に秒が無いので入れない。
- **中央値・p90**: 中央値は件数が偶数なら中の 2 つの平均、p90 は最近順位法（昇順の ceil(0.9×n) 番目）。183 回全部と、絞れた回だけの値を出す。
- **見逃し**（[landing-it-selection](landing-it-selection.md)の「値の式」と同じ数え方）: job ごとにテストの結果がある run を順に並べ、前の結果のある run では落ちておらずその run で落ちたテストを「新たに赤」とする（FLKY-FL は数えない）。範囲は前の run の `headSha`（含まない）からその run の `headSha`（含む）までの main の first-parent の commit。新たに赤の IT のうち、範囲のどの着地も案のもとで流さなかったものを見逃しとし、範囲が 1 件の着地のものを別に数える。着地がその表に無い IT は必ず流すので見逃しにならない。範囲の着地がどれも IT を流さないもの（2 件）と、dagq を通らない commit を含む範囲（0 件）は見逃しと別にした。
- **任せた本数**: 案が全部流さなかった回について、差分のファイルに表が当てる IT（広い項目を含む）のうち、案が選ばなかった本数。見逃しの代わりの、CI に任せる量の目安。

## 選んだ案と理由

**(iii) と (iv) の 25% の組み合わせ**を選んだ。

- 全部流す割合と見込みは、比べた案のうち (iii) + (iv) 10% の次に小さい。93% から 22% に減り、残る全部流す回の 7 割は共通のファイル（`Cargo.lock`・`migrations/**`・`tests/common/**` など）で、表が判断できないので今のまま全部流す。
- (ii) は (iii) と結果がほとんど変わらない。足したファイルの親の module もたいてい広い項目で、(iv) と組むと何も選ばないか閾値を超える。親を辿る規則を足しても得が無いので、単純な (iii) にした。
- 25% と 50% の比較: 50% では 61% がまだ全部流し、そのほとんどが閾値超え（83 回）で、IT の 25〜50% に当たる項目の和が半分を超えている。25% にすると閾値超えは 12 回に減り、絞った回で任せる割合（約 97%）は 50% と変わらない。
- 25% と 10% の比較: 全部流す回は 40 → 28 回で、減るのは閾値超えの 12 回だけ。10% では IT の 10〜25% に当たる、まだ選び方の手がかりになる項目（表の src のファイルの 7〜10%）も捨てる。
- 見逃しの釣り合い: 見逃しを CI に任せ事故を許容するのは goal 157 の人の決定（ADR-t1925-1 決定 5）で、選んだ案はそれに乗る。記録の上の見逃し 5 件はどれも上の不安定な 2 本で、変更による壊れの見逃しは記録からは 0 件。任せる量（絞った回で中央値 806 本）が大きいことは、見逃しが CI の後で見つかる遅れとして残る。事故は CI の見張りの修正 task で直す前提なので、その経路が修正 task を作れていない問題（前後比較の結論 3）は別に残る。
- 絞った回の時間の見込み: 後の窓で実際に絞れた 13 回のコマンドは中央値 149 秒（build 79 秒・nextest 59 秒）で、選んだ案で絞れる回もこれに近いと見込む（unit test 全件の約 200 秒の直列の和は変わらない）。測っていない。

閾値（IT 全部の見込みの半分）・共通のファイル・表の古さの上限は変えない。表の作り方も変えないので、夜間の job（`.github/workflows/it-coverage-map.yml`）は直さない。

## 全部流した run の段

後の窓の全部流した 170 回（通った 152 回）と、前の窓の通った llvm-cov の 276 回のログから読んだ（`landing-it-alternatives/stages.csv`・`stage-summary.json`）。

- **build** = ログの cargo の `Finished ... in` の秒の和（landing-it は `cargo nextest list` と `cargo nextest run` の 2 回、llvm-cov は計測つきの build）。
- **テスト** = nextest の `Summary` の秒。unit test と IT は 1 回の nextest で同時に流れるので、壁時計を段に分けられない。代わりに PASS・FAIL の行の秒を binary id で分けた直列の和を出す（`dagq`・`dagq-broker` などの lib と `::bin/` は unit test、`dagq::it`・`dagq::plugin` などは IT）。
- **残り** = コマンドの時間 − build − テスト（llvm-cov は coverage の表の出力、landing-it は表の取得と選択）。

| 値（中央値） | 前: llvm-cov（通った 276 回） | 後: landing-it を全部（170 回） | 後: 同、通った 152 回 |
|---|---|---|---|
| コマンドの時間 | 568.5 | 713.8 | 710.5 |
| build | 91.0 | 50.3 | 50.3 |
| テスト（nextest の壁時計） | 423.6 | 629.9 | 628.8 |
| 残り | 33.0 | 6.2 | 6.0 |
| テストの本数 | 2,722.5 | 3,148 | 3,148 |
| unit test の本数 / 直列の和 | 1,551 / 125.5 | 1,998.5 / 202.3 | 1,999.5 / 201.4 |
| IT の本数 / 直列の和 | 1,126.5 / 2,358.9 | 1,144.5 / 3,578.7 | 1,145 / 3,583.8 |
| IT 1 本あたりの秒 | 2.12 | 3.16 | 3.17 |
| load の平均 | 12.8 | 12.5 | 12.4 |

- テストの本数の伸び（3,095 → 3,584 は後の窓の日ごとの中央値。前後の窓の中央値では 2,723 → 3,148）の大半は unit test で、unit test の直列の和は IT の 1 割に満たない。IT の本数は 1.6% しか増えていない。
- 両方の窓で流れた IT 1,137 本の 1 本ごとの中央値は、和で 2,318.7 → 3,252.5 秒（×1.40）、1 本ごとの比の中央値は 1.47。前の窓は coverage の計測つき（ふつうは遅くなる）で、後の窓は計測なしなのに遅い。
  伸びの大きい module は `runtime_resume`・`runtime_integrate`・`runtime_recheck`・`runtime_handoff`・`runtime_headless`（`stage-summary.json` の `modules_grown_most`）。
- IT 1 本あたりの秒は日ごとに、10-07 の 2.16 から 10-08 に 2.71、10-09 以降 3.3〜3.4 に上がった（前の窓は 1.9〜2.4。`it_by_day`）。load の平均はほぼ同じなので、host の混み具合では説明できない。
- **結論**: 714 秒と 569 秒の差（145 秒）は、テストの段の伸び（+206 秒）から build（−41 秒）と残り（−27 秒）の縮みを引いたもので、テストの段の伸びは本数でなく同じ IT が 1 本ずつ遅くなったことによる。何が IT を遅くしたか（テストの待ち・runtime の処理・環境）はここでは分けていない。

## 限界

- `replay.py` は選び方を案ごとに書き直したもので、差分のテストのファイルの IT を見込みに入れ、`tests/it/<m>/…` を第 1 階層の module で選び、テストが repository から読むファイルを見ない。見込みと閾値超えの回はやや多め（上限）で、見逃しの数はやや少なめに出る。
- 新たに赤の IT が不安定な 2 本だけなので、見逃しの数では案の危険を比べられない。任せた本数は表のファイルの粒度での上限で、その IT が実際に変更で落ちうるかは分からない。
- 表のファイルの粒度は粗く、どの案も「差分が IT のどの行を通るか」は見ない。行の粒度の表は夜間の job の形を変える別の変更になる。
- 見込みの秒は表の値で、着地の host の秒ではない。選んだ案での verify の実測は、入った後の窓で測り直す。
- 前の窓の llvm-cov は計測つきの build とテストなので、段の秒は計測の重さを含む（それでも後の窓の IT のほうが遅い）。

## 実行のコマンドとファイル

repository の root で（DATA は repository の外の dir）:

```sh
sh docs/plans/landing-it-alternatives/collect.sh "$DATA"
```

- `collect.sh`: 窓の event・着地・夜間の表・main の CI の job と落ちたテストを DATA に読み、下の 3 本を流して DATA/out に書く。
- `replay.py`: 案ごとに選び方を 183 回と着地に当て、見逃しと任せた本数を数える → `attempts.csv`・`new-failures.csv`・`summary.json`。閾値・共通のファイル・古さの上限は当てる時点の `scripts/landing-it.py` から読む。
- `stages.py`: 検証のログから段ごとの時間 → `stages.csv`。
- `stage_summary.py`: 段の中央値と p90、IT 1 本あたりの秒の日ごとの値、両方の窓の IT の比較 → `stage-summary.json`。

区分: CSV と JSON は queue の event・git・CI の記録・表・検証のログから上のコマンドで作り直せるビューで、DATA に集めたものは消えてよい材料。表の artifact の保持（30 日）と host の run の directory が消えると作り直せないので、CSV と JSON を正として残す。
