# スパイク：空き容量の新しい claim の規則の当て直し

問いは「goal の案の規則（最低ライン max(5 GiB, 5%)、想定は直近 20 件のうち 14 日以内の p90・5 件未満は最大、係数なし、走っている run 0 本なら 1 本通す、着地優先）を固定の期間の記録に当て直すと、今の規則より claim と着地の控えの時間が減り、かつ容量不足が claim の 1% を超えないか」。
runtime は変えていない。[ADR-0047](../adr/0047-irregularities-in-three-layers-recovery-job-ask-reasons-and-goal-review.md) 決定 44 もこの Spike では保つ。

**判定: does_not_hold。** 今の規則の再現は合い、既定の行の容量不足は 0 区間だが、控えの和集合は記録の 147.6 時間に対して案の規則が 489.9 時間で、3.3 倍に増える。
11/03 の外れ値で閾値が跳ねることは案の想定（p90）で無くなる（想定 10.7 GiB、今の閾値 91.3 GiB）。
ただし既定の行は、その止まりの 12.4 h の中でも 12.2 h 控える（仮想の run は 0 本）。走っている run の数え方で規則 4 が発火せず、本数 × 想定を足すからである（線形の行なら 0.0 h）。
増えるのは、式が足す量（走っている run の残り + 着地の想定 + 最低ライン）が、この host の空きの水準を恒常的に超えるからである。

## 問いごとの判定と根拠

受け入れ条件の読み方のとおり、表 B の案の規則の既定の行（reserve max(5 GiB, 5%)・今の大きさの仮定は想定そのまま）で読む。想定の標本は説明の (1) の大きさのとおり全 run である。

| 条件 | 値 | 満たすか |
|---|---|---|
| 再現: 記録の和集合のうち再現と重なる割合 ≥ 80% | 91.7%（135.4 h / 147.6 h） | はい |
| 再現: 再現の合計が記録の ±20% 以内 | 157.4 h / 147.6 h = 1.07 倍 | はい |
| CSV の 5 分を超える間の合計 ≤ 期間の 20% | 84.9 h / 588 h = 14.4%（346 か所、最長 7.6 h） | はい |
| CSV と events を読める | 読めた | はい |
| 控えの和集合の合計 ≤ 今の規則 | **489.9 h > 147.6 h** | **いいえ** |
| 比（容量不足の区間数 ÷ claim の数）≤ 1% | 0 / 1008 = 0.0% | はい（ただし下の注意） |

**判定: does_not_hold**（控えの時間が超える）。

- **比の 0% は安全の証拠にならない。** 既定の行の仮想の run は 0 本である。説明の (1) の run の期間は人の答え待ちや着地待ちを含むので、走っている run の本数が中央値 8・最大 30 で、99.4% の sample が parallel（3）以上になり、仮想の run が足されない。式も本数 × 想定（中央値 10.8 GiB）を足すので、判断の必要量の中央値は 105.3 GiB になり、期間中の空きの最大（90.0 GiB）を超える。
- **今の規則を上回る控えの主因は 2 つある。** 1 つは走っている run の数え方で、11/03 の止まりの間も説明の期間では中央値 4 本で 0 本の sample が無く、規則 4（0 本なら 1 本通す）は期間全体で発火しない。もう 1 つは式の総量で、数え方を動いている run に直しても（下の感度 S1〜S3）必要量の中央値は 38.5〜59.5 GiB で、観測の空きの中央値 30.9 GiB を超える。
- **控えの絶対値は多めに出る。** 観測の空きは今の規則の掃除の結果で、案の規則で閾値が上がれば掃除は早く走って空きも増えるはずだが、記録からは作れない（「この当て直しの限界」）。ただし既定の行の必要量の中央値は観測の空きの最大も超えるので、この偏りで判定が変わるとは読まない。
- **標本を変えても判定は同じである。** `build_outputs_removed` の記録のある run だけを標本にした追加の比較（表 B の 2 つ目の表）でも、既定の行は 501.9 h・比 0.0% である。
- **成り立つ値の組は見つからなかった。** 感度の 22 行と分位点・件数の 24 行（どちらも 2 つの標本）のどれも、和集合が 147.6 h 以下で比が 1% 以下を同時に満たさない。同じ sample の判定どうしで比べる今の規則の再現（157.4 h）を基準にしても同じである。
  - 全 run の標本で比が 1% 以下の行のうち、控えが最も短いのは S4 の 272.0 h である。
  - 控えが 157.4 h 以下の行は S11 だけで（124.9 h）、比は 2.4% である。
  - 最も近いのは S5（165.1 h・比 1.1%）だが、build の記録のある run の標本では 223.4 h・比 3.8% に開く。全 run の標本は測っていない 0 に近い値で想定が下がる分だけ有利に出るので、この近さは割り引いて読む。

## 仮定

- **run の期間**: `run_claimed` から、その run の最後の `session_closed` か `run_integrated` の遅い方まで（期間の中央値 1.07 h）。どちらも無い run は長さ 0。待ちと着地待ちの時間を含む。
- **想定の標本**: どれかの記録のある全 run（説明の (1)）。`build_outputs_removed` の記録のある run に絞った表は追加の比較である。時刻 t の run の大きさは t までの記録だけで作り、最後の記録の順で件数と期間の窓を取る。5 件未満は最大、0 件は想定なし。分位点は最近順位法（昇順の ceil(q × n) 番目）。
- **案の規則の判断**: claim は `仮想の空き − reserve ≥ 想定 + Σ 走っている run の max(0, 想定 − 今の大きさ) + 着地待ちの想定`、着地は `仮想の空き − reserve ≥ 想定`。走っている run が 0 本で仮想の空き ≥ reserve ならどちらも通す。想定は判断の時刻の 1 つの値を全 run に使う。線形の仮定の今の大きさは、claim からの経過 ÷ 仮想の run の期間（1 まで）× 想定。
- **仮想の run**: `claim_held`（reason `disk_space`）の区間の中の sample で、案の規則が通し、走っている run（実際 + 仮想）が parallel 未満なら 1 本足す。着地の控えだけの区間は claim を止めていないので足さない。claim できる候補はいつもあるとする。大きさはその時点の想定、期間は想定と同じ窓の run のうちその時点で終わっていた run の期間の中央値（無ければ期間全体の中央値 1.07 h）。仮想の run の記録は想定に入れない。
- **仮想の空き**: 観測の空きから、仮想の run の大きさを、足した sample からその期間のあいだ丸ごと引く（線形の仮定でも引く量は丸ごとで、容量不足を多めに数える側）。実際の run を案の規則が控えても、その run の分は空きに足し戻さない（控えを多めに数える側）。
- **着地待ちの想定**: `landing_runs` が 1 以上なら想定 1 本分、列の無い日は常に 1 本分。列のある日の空のセルは 30 分以内の直前の値を使い、無ければ 1 本分とする（この列は既定で 10 分に 1 度しか書かれない）。着地の控えの時間も同じ想定で数える。
- **期間の終わり**: 11/03 の止まりは人の応急の未 commit の `sample_runs = 5` と起動し直しで解けた。期間の最後の約 10 分はその設定の下にあるが、再現は 20 件のまま計算していて、影響は最大 0.17 h である。
- **控えの時間**: 各 sample は次の sample までを代表し、間が 5 分を超えれば数えない（補わない）。

## この当て直しの限界

- **空きは今の規則の結果である。** 空きの掃除は閾値を下回ったときだけ走るので（期間中の `disk_cleanup` は 540 回、1 回の中央値 2.8 GiB、p90 10.4 GiB、合計 2,423 GiB）、空きは今の閾値の周りに張りつく。sample の 36.2% が閾値の下、21.3% が閾値の 25% 以内の上にあり、空き ÷ 閾値の中央値は 1.15 倍である。案の規則の下で掃除がどれだけ空けるかは記録に無いので、案の規則の控えは多めに、仮想の run の容量不足も多めに出る。
- **今の大きさの記録が無い。** 判断の Σ の項は実際には測った値で減るが、その値は過去に無いので 0 と線形の 2 つで挟むだけである。
- **着地した run の大きさが無い。** 1008 run のうち build の大きさが分かるのは 298 本で、待ちか掃除か run の終わりで消された run に偏る。
- **`disk_full` は着地の検証の分類だけ** で、worker の session の中の容量不足は数えていない。

## 後続の計画への推奨

値はどれもこの PJ の大きさに固定しない。GiB の値はこの host の結果で、runtime に持ち込むのは割合と順位と件数と下限の 5 GiB だけにする。

判定は does_not_hold なので、案の式をそのまま実装しない。足りないものは次の 3 つで、再計画は値より先にこれらを決める。

1. **走っている run を「動いている run」にする。** 待ちと着地待ちの run は書き足さないので Σ から外す。人の答え待ちの長さは PJ と人に依るので、含めると規則が人の応答の速さに左右される。規則 4 も、この数え方でないと発火しない（説明の期間では期間全体で 0 本の sample が無い）。
2. **今の大きさを測るか、Σ の項を外す。** 測らずに想定を足すと（S1〜S3）、parallel × 想定が空きの水準を超えて並列が事実上消える。Σ を外した S5 は控えが 165.1 h で、11/03 の中の控えは 1.0 h に縮むが、比は 1.1% である（build の記録のある run の標本では 223.4 h・3.8%）。これは容量不足を多めに数える仮定の下の値なので、人の許容（1 本が落ちてやり直す）と合わせて再計画か人が決める。着地待ちの想定を claim の判断に足すのも同じ理由で再考する（S3 と S4 の差は 102.9 h、容量不足の区間の差は 5）。
3. **掃除の閾値を判断の必要量と別に考える。** 空きが閾値に張りつくのは閾値を下回るまで掃除しないからである。必要量を上げるなら、掃除で空く量（`held_target_bytes` の列など）を判断に入れないと控えだけが伸びる。

| 5 件未満 | 最大 | 変えない。この期間では効く場面が無く、確かめていない | 少ない記録の分位点は最大とほぼ同じで、控えめに倒す方が 1 本落ちるより安い |

他に実装の計画に入れるもの:

- **想定の標本**: 全 run の標本は測っていない 0 に近い値が混ざり、想定の中央値は 10.8 GiB である（build の記録のある run だけなら 13.2 GiB）。build を持たない PJ で標本が空にならないよう、終わった run すべての大きさを worktree を消す前に記録するのが汎用である。
- **外れ値**: 超えた量の最大は全 run の組で 30〜36 GiB、build の記録のある run の組で 25〜32 GiB で、分位点と件数では防げない。45.6 GiB の型は 24 日で 2 run で、容量不足で落ちたら環境の失敗としてやり直す規則（goal の案）で受ける。原因を知るには transcript か run のログを読む別の調べが要る。
- **着地の後の測定**: 案を入れた後の控えと容量不足は、この当て直しでは掃除の反応を作れないので、実際の控えの時間・`disk_full`・worker の容量不足の失敗を前後の窓で比べる。

## 実績

- 使った時間: 約 40 分（host の時計で `dagq events` の最初の読み取りから review の 3 回の直しまで。限度 2 時間）。
- script の書き直し: 4 回（限度 3 回を 1 回超えた）。1 回目は動いている run と感度の行を足し、2 回目は最低ライン 5 GiB の行と 11/03 の中の値を足し、3 回目は review の指摘で容量不足をその sample で足した仮想の run の後の空きで数えるように直し、表 B の主な標本を説明の (1) の全 run に戻した。4 回目は review の指摘で大きさの分布の集計だけを claim の集合に直した。当て直しの計算は変えておらず、`summary.json` で変わったのは分布の値だけである。
