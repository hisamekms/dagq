# スパイク：着地待ちの想定の足し方の当て直し

問いは「claim の必要量に、動いている run があり着地待ちがあるとき想定をもう 1 本分足す今の足し方（[ADR-t4473-1](../adr/2026-11-08-t4473-1-disk-needs-follow-a-reserve-and-recent-runs-with-no-factor.md) 決定6 の後半、`domain::disk::DiskState::needs`）が過大でないか（前提: 過大でない）」。
runtime は変えていない。

**判定: holds（過大でない）。** F =（a の控えの時間 − d の控えの時間）÷ a の控えの時間 = **0.003**（35.79 h に対して 35.66 h）で 0.5 以下である。
着地待ちの想定を外しても、記録の控えの中で claim を通す標本はほとんど増えない。
控えを決めているのは最低ライン・想定・動いている run の残りの和で、T2 の後の控え 41 件のうち着地待ちの想定を足したのは 3 件だけである。
人が問うた 2026-11-10T06:37:31Z の控え（空き 35.4 GiB・必要量 48.7 GiB）は、最低ライン 11.4・想定 16.6・2 本の残り 20.7 GiB で、着地待ちの想定を足していない。
そのとき着地を待つ 6 本は人の `approve_landing` の答えを待つ run（phase `landing_answer`。`summary.json` には無く、同じ data の `run_phase_changed` をその時刻で数えた）で、着地待ちにも動いている run にも数えない。

## 求め方

- **最低ライン**: その時刻以前の最後の行の `disk_total_bytes` の 5%（切り上げ）と 5 GiB の大きい方。
- **想定**: 時刻 t 以前の大きさの event から `run_samples` と同じ規則で run ごとの標本を作り（build と worktree の大きい方 + scratchpad + TMPDIR、測れない記録を含む run と build の記録の無い run は除く、`worktree_missing` は読み飛ばす）、t から 14 日以内の新しい 20 件の、5 件未満なら最大、以上なら ceil(0.9n) 番目。
- **run の phase**: `run_phase_changed` の t 以前の最後の `phase` と `holds`。
  - 動いている run: `holds` が `worker_slot` か `landing_slot` で、phase が `awaiting_slot`・`review_held`・`waiting` でない run（supervisor の `in_flight` と同じ形、ADR-t4473-1 決定4）。
  - 着地待ち: phase が `awaiting_slot` か `landing_queue` の run。
  - 着地の検証中: phase が `landing` の run。
- **Q1 の残り**: 動いている run があり想定があれば 必要量 − 最低ライン − 想定 − 着地待ちの想定、無ければ 必要量 − 最低ライン。T2 より前は 0 のはずの値で、再現の確かめになる。
- **Q4**: description の形のとおり。判断は `needs` と同じで、動いている run が 0 本なら最低ラインだけ、0 本で着地待ちがあれば claim は控えの event なしに待ち（控えの時間にも仮想の run にも数えない）、動いている run があり想定が無ければ待つ。足し方は a: 着地待ちがあれば想定、b: a のうち着地の検証中の run が着地 slot の数（1）未満のときだけ、c: 着地待ちの run ごとの max(0, 想定 − 今の大きさ) の最大、d: 足さない。

## Q2: 着地の検証は想定 1 本分を使うか

着地の区間は phase `landing` の始まりから次の phase の始まりまでとした。`landing` の次の phase は、終わり（`push`・`needs_session` など）か、復旧（cause `run_recovered`）で `landing_queue` に戻ったとき（読んだ phase の記録の中で 3 回）で、どちらもその検証の終わりとする。復旧の後の検証は次の `landing` の区間に入る。
[T, E) に始まった着地の区間は 70 で、区間の中に `verification_command` がある 62 を検証した着地として数える（2 分未満でも検証したものが 5、検証の無い 8 はどれも 2 分未満）。
検証が作った build の大きさは、区間の終わりから次の build する phase（worker・resume・revise・recovery・landing・e2e・verifying）の始まりまでの最初の掃除（`build_outputs_removed` か `worktree_removed`）の bytes だけをその検証に帰属させ、その間に掃除が無いか bytes が測れていなければ不明とした。
「前に消された」は、着地の前の最後の build する phase の終わりから着地の始まりまでに `build_outputs_removed` がある検証（検証は空の target から build する）。

| 組 | 検証 | 想定の中央値（GiB） | 空きの減りの中央値（GiB、件数） | 減り ÷ 想定の中央値（最大） | 減りが想定以上 | 帰属した掃除の大きさの中央値（GiB、件数） | それ ÷ 想定の中央値（最大） | それが想定以上 | 不明 |

| すべて | 62 | 14.5 | 2.9（56） | 0.19（1.09） | 2 | 7.7（52） | 0.54（1.50） | 1 | 10 |
| build 出力を前に消された | 42 | 14.5 | 1.9（40） | 0.14（1.09） | 2 | 7.7（36） | 0.53（0.73） | 0 | 6 |
| 消されていない | 20 | 15.3 | 6.2（16） | 0.38（0.99） | 0 | 9.1（16） | 0.56（1.50） | 1 | 4 |

- **答え**: 検証の間に空きが想定 1 本分以上減ったのは、空きの標本のある 56 件のうち 2 件（11/09 23:13Z と 11/10 00:33Z、減りは 16.7・18.0 GiB で、同じ時間に worker が動いていたので検証だけの分ではない）。
- build 出力を前に消された run の検証は空の target から作り直し、帰属できた 36 件の大きさは想定の中央値 0.53 倍・最大 0.73 倍で、想定 1 本分より小さい。想定は worker の build・review の手直し・scratchpad・TMPDIR を含む run の全体の大きさで、検証の build はその一部である。
- 消されていない run の掃除の大きさは検証の前からあった build を含む上限で、1 件（71105c2a、20.4 GiB = 想定の 1.50 倍）が想定を超えた。検証だけの分は分けられない。

- 不明の 10 件は、検証の後に resume などの build する phase が先に始まった（例: f05833b1 の 02:39Z の検証は 02:49Z に落ち、02:49Z からの resume の後の 02:59Z の掃除 12.4 GiB は検証と resume の分を分けられない）か、掃除の記録が期間の後まで無い検証である。
- 着地待ちの想定 1 本分は、消された run の検証の実際の大きさより大きく、同じ桁である。

## 判定

- **unresolved に当たらない**: 記録の disk_space の claim_held の区間の中の欠測は 4.27 / 40.10 時間 = 10.6%（20% 以下）、a の控えの時間と記録の hold_spans の和の差は −10.8%（25% 以下）、T は `update_installed` から求まった。
- **F** = (35.79 − 35.66) ÷ 35.79 = **0.003**（0.0035、0.5 以下）。参考の感度でも 0.036。
- **R**: b 4.5%（3 区間 ÷ 67）、c 0.0%（0 ÷ 58）、d 4.5%（3 ÷ 67）。
- **判定は holds（過大でない）**: F が 0.5 以下なので、description の 1 つ目の holds の場合に当たる。着地待ちの想定は記録の控えのほぼどの時間でも控えの決め手でなく、外しても控えは 0.35% しか縮まない。外す形（b・d）は当て直しの仮定の下で容量不足の区間を 3 つ生み、比が 3% を超える。
- Q2・Q3 から、足す 1 本分は build 出力を消された run の着地の検証の実際の大きさ（中央値で想定の 0.53 倍、最大 0.73 倍）より大きく、着地の検証中の run の残りとの 2 重の数えも 12.8 時間のうち 8.8 時間ある。ただしそれは控えの長さを決めておらず、控えを決めているのは最低ライン（11.4 GiB）・想定（13.6〜16.6 GiB）・動いている 2〜3 本の残り（T2 の後の中央値 23.5 GiB）の和と、空き 35〜50 GiB の差である。

## 仮定

- **動いている run と着地待ち**: supervisor の slot の状態は event に残らないので `run_phase_changed` から作った。`waiting` は slot に残る形（`in_slot`）も数えない（決定4の人の答え）。着地待ちは `awaiting_slot` と `landing_queue` で、`landing_goes_but_for_disk` の他の控え（CI・container・landing branch）は見ていない（T2 より前の 38 件中 1 件だけがこれでずれた）。T の 2 日前より前の phase は読んでいないが、その頃 claim して T に動いていた run は無い。
- **数え方が runtime より控えに寄る点**: `landing_queue` には slot の外で lease の無い承認済みの run も入るので、runtime（slot の `AwaitingSlot` だけ）より着地待ちを多く数えうる。phase の記録が途切れた run を動いているまま数えうる（期間の後まで記録を読んだので終わりの phase は概ね残る）。仮想の run の上限は着地の検証中の run も 3 本に数え、動いていない slot の run は数えない（description の形どおり）。前の 2 つは a を d より多く控えさせる側で F を上げ、後の 1 つは d の仮想の run を増やして F を下げる側である。仮想の run を足さない上限でも、着地待ちの項だけが控えを決めた時間は a の 12% で、F は 0.5 に届かない。
- **今の大きさ**: events に残らないので、claim から run の終わり（claim の後の最後の `session_closed` か `run_integrated`）まで 0 から実際の大きさ（`run_samples` の値、無い run はその時刻の想定）へ線形に増えるとした。実際の大きさは期間の後の記録まで使う（description の形）。終わりの無い run は実際の大きさの半分とした。着地待ちの run の今の大きさ（c）は、t より前に `build_outputs_removed` がある run は 0、それ以外は同じ線形の値。
- **T2 より前の残り**: description の形どおり対象の commit の式（残りを数える）で流した。その頃の固定バイナリは残りを 0 と数えていた（決定7）ので、それに合わせた形を参考の感度として別に出した。
- **仮想の run**: 記録の disk_space の控えの区間の中で、その足し方が claim を通す標本ごとに 1 本、動いている run と仮想の run の和が 3 本未満のときだけ足した。大きさはその時刻の想定、期間は t の前 14 日に終わった run の claim から終わりまでの中央値（無ければ 1 時間）で、0 から想定へ線形に増え、期間の終わりで 0 に戻る。仮想の run は大きさの標本を作らず、着地もしない（着地待ちに数えない）。実際の run を控えても、その分を空きに足し戻さない。
- **控えの時間**: 標本の代表の区間（次の標本まで、300 秒を超えるか空きが空なら欠測）と記録の控えの区間の積集合の和。代表の区間が欠測の標本（[T, E) に空きの値を持つものが 18 件、空きが空の行は 0 件）は判断せず、控えにも容量不足にも数えず、仮想の run も足さない。欠測の標本を挟む容量不足は別の区間に分かれる。仮想の run を足すかは標本の時刻が記録の控えの中かで決めた。動いている run が 0 本で着地待ちがある標本は、控えの event の無い 1 pass の待ちなので控えに数えない。
- **標本の上限**: runtime は kind ごとに最新 500 件（`SAMPLE_EVENT_LIMIT`）から標本を作り、読み直しの間隔の間は前の標本を使う。当て直しは期間の event をすべて読み、標本ごとに読み直した。20 件の窓に対して 500 件は十分なので結果は変わらないとみる（Q1 の T2 より前の想定は記録とすべて合った）。
- **容量不足**: 仮想の空き（実の空き − 仮想の run の今の大きさの和）が 0 以下の標本の連続を 1 区間とした。worker の session の中の容量不足は `auto_repaired` の `full_disk_resume` だけで数え、その記録の無い失敗は数えていない。
- **着地の検証の空きの減り**: 着地の始まりの直前の標本の空きと、検証の間の最小の空きの差。同じ時間の worker の build と掃除が混ざる。区間の中に空きの標本が無い着地は減りを不明とした。
- **着地の検証中**: Q3・Q4 の「着地の検証中」は phase `landing` の run だけで、復旧で `landing_queue` に戻った run は着地待ちに数える（Q2 の区間と同じ境界）。

## 推奨

- **判定の後続: 算出方法を維持する。** ADR-t4473-1 決定6 の後半（動いている run があり着地待ちがあるとき想定を 1 本分足す）は変えない。足し方を変える実装の task は要らない。
- Q2・Q3 の重なり（着地の検証中の run の残りと着地待ちの 1 本分）は実在するが、控えの時間を決めていないので、それだけを直しても控えは縮まない。控えを短くしたいときに見るのは、動いている run の残り（T2 の後の控えで中央値 23.5 GiB、動いている run が 2 本の控え 34 件で想定の 1.0〜2.0 本分）と想定の項か、task 4727 の上書きの運用である（goal 279 の制約のとおり、割合・分位点・窓はこの goal で変えない）。
- **goal 260 の task 4475 への渡し方**: 4475 は置き換えない。4475 は T±5 日の窓で着地待ちと重なる控えの時間を出すが、この Spike は、重なる時間（[T, E) で 12.8 時間）と控えの原因（着地待ちの想定を外して通る時間 4.46 時間、外しても縮む控え 0.13 時間）が別であることを示した。4475 の結果を読むときは、重なる時間を着地待ちの想定の効きと読まず、この文書の F と内訳の表（T と T2 も）と合わせて読むよう、再計画の planner に渡す。4475 の窓が T2 の後の控え（残りを量った値）を多く含むなら、残りの項の大きさも並べると、どの項が控えを決めたかが比べられる。
