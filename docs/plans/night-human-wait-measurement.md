# 夜の人の答え待ちが着地を遅らせた量

goal 62 の材料（task 919）。2026-09-27〜28 の夜に、人の答えを待つ run の答えが朝 07:02〜07:05 にまとめて返り、その間の着地が減った。この文書は、夜（JST 22〜07 時）の人の答え待ちが着地をどれだけ遅らせたかを測り、次の打ち手の候補を挙げる。決定はしない（人と planner が決める）。

## 要点

- **4 夜とも、夜に開いた ask の答えは朝 07:00〜07:20 にまとめて返っている。** 期間中にこの 20 分で返った答えは 25 件（09-25 に 8 件、09-26 に 12 件、09-28 に 5 件）。夜に開いて着地を遅らせた ask は 28 件で、答えまでの中央値は 177 分、合計は 89.8 時間。昼（07〜22 時）に開いた同じ種類の ask は 44 件で、中央値は 3 分、合計は 21.6 時間だった。
- **09-27→28 の夜の着地は 40 件（4.4 件/時）で、前の昼（6.3 件/時）より約 17 件少ない。** 見立てでは、人の答え待ちが 55〜70%（朝に押し出された着地 5 件と、task 438 の run が ask の答えを待つあいだ slot に居た 3.9 slot 時間）、task 438 の run が ask より前に居座った分（runtime の不具合で、task 918 が扱う）が 10〜15%、runtime の task の 1 件あたりの時間が長かった分が 10〜30%、load による claim の保留は 5% 以下。
- **worker_question の待ちは slot を空けており、空いた slot はすぐ埋まっていた。** task 770 の 392 分の待ちのあいだ、supervisor は 39 件を claim し、空き slot は合計 3 分だけで、candidates は常に 74 件以上あった（ADR-0071 の待ちが効いている）。この種類の待ちが遅らせたのは、その task 自身の着地だけで、夜の処理量は減らしていない。
- **夜の処理量を落としたのは、slot を持ったまま人を待つ run だった。** 09-24→25 と 09-25→26 の夜は、stuck_exit と observer の blocked の ask で待つ run が slot を 21.8 slot 時間・15.1 slot 時間持っていた（夜の容量 27 slot 時間（3 slot × 9 時間）の 81%・56%）。runtime が既知のダイアログと `/exit` を直すようになった（ADR-0047）後の 09-26→27 の夜は、着地を遅らせた ask が 4 件（30 分を超えるのは 2 件）だけで、着地は期間中で最も速かった（8.6 件/時）。09-27→28 の夜は task 438 の 5.6 slot 時間（そのうち ask が開いていたのは 3.9 時間）が同じ型だった。

## 期間とコマンド

期間は 2026-09-24 13:00 JST（observer の最初の ask_opened）から 2026-09-28 17:45 JST まで。4.2 日で、夜は 4 回（09-24→25、09-25→26、09-26→27、09-27→28）。使ったのは読み取り専用のコマンドだけで、固定バイナリの `~/.local/bin/dagq` で打った。queue の状態を変えるコマンドは打っていない。

```sh
dagq events --all --full --kind ask_opened --kind ask_answered --kind ask_closed --since 2026-09-21T00:00:00Z --limit 5000
dagq events --all --full --since 2026-09-24T00:00:00Z --limit 100000   # run_integrated・run_claimed・claim_held / claim_resumed・candidates_sampled・run_waiting_* を読む
dagq stats --since 2026-09-24T00:00:00Z --full                          # runs（kind・work・land_phases）と waiting・asks・claim_holds
dagq timeline 2503af69-bf4c-49fd-94af-a7b5c138ab84                     # task 438 の run の after_receipt の区間
```

集計の定義:

- **ask の待ち**: `ask_opened` から、同じ ask の最初の `ask_answered` か `ask_closed` まで。期間の終わりに開いていた 3 件（176・177・178）は表の件数に入れ、時間には入れない。
- **着地を遅らせた ask**: run を止める種類（`worker_question`・`stalled`・`stuck_exit`・`answer_prompt`・`decide`・`approve_landing`・run か task に紐づく `blocked`）で、task の次の `run_integrated` が答えの後に来たもの。遅れはその ask の待ちの時間とする（同じ task の重なる ask は、task ごとの遅れの合計で重ねて数えない）。`planner_question`・`approve_update`・`update_failed`・`approve_goal`・task の無い `blocked` は run を止めないので数えない。observer の blocked のうち、run が答えより前に着地していたものも数えない。
- **slot を持つ待ち**: `stuck_exit`・`answer_prompt` と、run か task に紐づく着地を遅らせた `blocked`。blocked の run が実際に slot を持っていたかは確かめておらず（task 205・225・292・361 は答えの数時間〜数日後に着地した）、09-24〜26 の夜の slot 時間は上限の見積もり。`worker_question`・`stalled` の待ちは 09-26 以降 ADR-0071 で slot を空け、`approve_landing`・`decide` の run は lease を持たないので slot を持たない。
- **slot が埋まったか**: `candidates_sampled` の `free_slots` を次の標本まで続く値とみなし、時間で積んだ（標本は 09-27 08:31 JST 以降だけにある）。

## 次の打ち手の候補

決定はしない。数字は 4 夜の実績から、そのまま当てはめた見込み。

1. **worker が scope の問いの前に自分で決めてよい範囲を広げる**。夜に開いた worker_question は 4 夜で 5 件 8.9 時間、09-27→28 の夜だけで 2 件 8.5 時間（770・816）。worker_question の待ちは slot を空けて処理量を落とさないので、効くのはその task の着地の前倒しで、09-27→28 型の夜で 1〜2 件を夜のうちに着地させ、1 件あたり 4 時間ほど早める見込み。夜の処理量（件/時）はほぼ変わらない。
2. **夜の待ちに上限を付け、過ぎたら既定の答えか復旧 job に回す**。夜に開いて着地を遅らせた 28 件のうち 21 件が 60 分を超え、上限 60 分なら 68.1 時間、30 分なら 78.6 時間の待ちが縮む。うち approve_landing（12 件 35.5 時間）は slot を持たないので効くのは着地の前倒し、slot を持つ blocked と stuck_exit（10 件 41.7 時間）は夜の処理量にも効く。approve_landing の既定の答え（`land` か `send_back` か）は人の判断が要る。
3. **slot を持ったまま人を待つ run を無くす**。夜の処理量に最も効くのはここで、09-24→25 は 21.8 slot 時間（夜の容量の 81%）、09-25→26 は 15.1 slot 時間（56%）、09-27→28 は 438 の 5.6 slot 時間（21%。着地にして 5〜10 件）。stuck_exit は ADR-0047 の自動の修復の後の夜には出ておらず、receipt の後の居座りは task 918 が扱う。918 の着地の後、夜の slot を持つ待ちが 0 に近いかを次の数夜の `stats` で確かめる。
4. **寝る前と朝の答え方を決める**。22〜24 時に開いた着地を遅らせた ask は 8 件で、そのうち 2 件（41・43）が寝る前に開いて朝まで 7.7 時間ずつ待った。寝る前に open な ask を一度片付けると 4 夜で約 15 時間（1 夜あたり 1 件・4 時間程度）の待ちが縮む。夜の 28 件のうち 20 件は 00〜07 時に開くので、それ以上は候補 2 か 3 が要る。朝は 07:00〜07:20 に 25 件をまとめて答えており、slot を持つ run（stuck_exit・blocked）から先に答えれば、その run の slot が数分早く空く程度の効果にとどまる。
