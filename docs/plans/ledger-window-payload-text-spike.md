# スパイク：台帳の窓の records の payload を text で持つ形のピーク

問いは「今の形（lean）の窓の読み 1 件のピークのうち、`records` の `RunEvent` の payload を `serde_json::Value` の木でなく JSON の text で持ち、読むところで解く形（候補 (1)）にすると、どこまで下がるか。本番の規模（event 約 120 万件）の外挿で読み 1 件 1,000,000,000 bytes 以下にできるか」。
台帳の行の形と `ledger_v` は変えない。queue 行の読みを要る列に絞る候補 (2) と (1)+(2) は、queue 行の量が変わる後の Spike が測る（下の「入口」）。本番の queue は開いていない。

## 判定

**does_not_hold**。根拠は、どの形の (1) でも通る text で読む段のピークの実測で、120 万件の外挿は 1,122,554,454（kpi（既定））〜1,123,742,551 bytes（他の 4 つ、傾き 936 bytes/event、線形）と、この段だけで 1 GB を超える。

依頼の形（窓が payload を text で持ち、畳み方の読み手が読むところで 1 件ずつ解いて使った後に捨てる形）は測らなかった。読み手の書き換え（畳み方が辿る module の `.payload` 335 か所・`&[RunEvent]` を受ける関数 288・窓の fold method 十数か所）が要り、この Spike の上限（3 時間・試作 3 回）の内では作れないため（人の決定 2026-11-09）。この形の全体のピークと答えの digest、lean からの削減量は未決で、下の推計は測っていない値として別の欄に置き、判定にも推奨の根拠にも使わない。

測った 2 つの形（どちらも依頼の形ではなく、解いた木を畳む間ずっと持つ）:

- kind で解く形（窓は payload を text で持ち、畳み方が payload を読む kind の payload を窓 1 つ分まとめて解いて渡す）: process の数えた使用中の bytes の最大は lean の 99.5〜100.9% で、120 万件の外挿は kpi（既定）2,093,214,866、kpi --since 2,162,567,015、ObserverKpi 2,147,919,119、stats 3,422,842,110、stats --since 3,107,664,392 bytes。kind の粒度で前もって解く形の削減は 1% 未満で、この形を配線する価値は無い。下がらないのは、畳み方が合成の台帳の 30 の kind のうち 29 の payload を読むから（下の「kind ごとの読み手」）。読まないと言えたのは `first_commit_observed`（event の 1.0%）だけで、`supervisor_of` は kind に依らず全ての event の payload の `supervisor` を読み（`heartbeats` が呼ぶ `Lives::new` など）、`run_phase_changed`・`stall_config_loaded`・`session_turns` なども名指しの読み手がある。合成の台帳で答えが変わらない kind（16）にも読み手があり、合成の答えの一致は読まない証拠にならない。
- 参考に、合成の台帳で答えが変わらない 16 の kind を全部解かない形（runtime がしてよい読みではない）は、40 万件で lean の 59.5〜71.2%、120 万件の外挿は kpi（既定）1,476,527,030、kpi --since 1,525,370,425、ObserverKpi 1,510,722,528、stats 2,149,163,442、stats --since 1,833,985,724 bytes（線形でないので上限）。
- 全部を解く形（読む間だけ text、畳む前に全部を解く）は lean の 100.0〜101.2% で、120 万件に 2.10〜3.44 GB。
- 答えの digest は、測った全ての組で今の形と同じ。外挿は全て線形（傾きの差 9.5% 以下）で、参考の形の stats --since だけ線形でない。

推計（測っていない）: 依頼の形で、畳む間に解いた木が同時に残らないとしたときの全体のピークを、全部を解く形で測った段の値から max(読みのピーク, 読みの後に持つ量 + 畳む層のピーク) と組むと、120 万件で kpi（既定）1,151,636,172、kpi --since 1,203,054,558、ObserverKpi 1,210,321,569、stats 2,500,906,880 bytes（下の「依頼の形（測らなかった）」）。lean からの差は約 0.92〜0.94 GB になるが、畳む層が event を参照で集める所はその形では解いた値を持ち直すので上に振れ、読み手が同じ event を何度も解く分の時間も入っていない。この推計がどこまで当たるかは、読み手を書き換えて測るまで分からない。

決定を変える必要は見つかっていない。ADR-t1662-2 決定 1・7・8（event が SSOT、台帳はビュー）は (1) も下の推奨も保つ（台帳の行の形と `ledger_v` を変えず、読みの中のメモリの形だけを変える）。

測った内訳（40 万件、下の「内訳」）:

- 読みの後に持つ量 334,505,028 bytes（kpi（既定）は範囲の読みで 320,529,596）。うち records（text）155,144,229（event 1 件あたり 388。別の process で複製して数えた）、records 以外（行の `totals`・`intervals`・`attributes`・`detail`、node 行の sample、`Vec` の容量の余りなど）179,360,799（448）。records は全部を解くと event 1 件あたり 1,169 bytes（Spike 4246 の 1,180 bytes の見立てと合う）、kind で解いても 1,162 bytes。
- 読みのピークが持つ量を超える分は 40,223,784 bytes（event 1 件あたり約 100 で event の数とともに増える）。中身は分けていない（読み終える前の `Vec` の容量の余りと、1 頁の行の text と木が候補）。queue 行は 50 行ずつ読んで records を移し行を捨てるので、queue 行の text が同時にあるのは 1 頁分。
- 畳む層（解いた窓の上の確保のピーク）は kpi（既定）70,105,767（175）、kpi --since 71,879,736（180）、ObserverKpi 77,856,960（195）、stats 499,164,552（1,248）。stats は畳む層だけで 120 万件に約 1.5 GB（線形）。参考の 16 の kind を解かない形では stats の畳む層は 284,397,852 に下がる（畳む層が解いた payload の一部を写して持つ）が、中身は分けていない。

## 試作

置き場と入口:

| 名 | 置き場 | 中身 |
| --- | --- | --- |
| `TextEvent`・`TextWindow`・`WindowRows::payload_text`・`WindowRows::into_text_window` | `src/domain/ledger/window/payload_text.rs`（`#[doc(hidden)]`、module doc に使い方） | 行を取るたびに、その行の `records` を `TextEvent`（payload は `Box<str>` の JSON の text）に移す。`TextWindow::into_window_of_kinds` が、渡した kind の payload だけを解き、他の kind の record は payload 無し（`Value::Null`）で今の `LedgerWindow` にする（text は record を作るたびに捨てる）。`TextWindow::into_window` は全ての kind を解く。 |
| `ledger_window_payload_text` | `src/application/ports/observation.rs`（`#[doc(hidden)]`） | `LedgerStore::ledger_window` と同じ読み（同じ行・同じ順・`read_from_ms` の snapshot の読み）で `TextWindow` を返す。読みの流れは `ledger_window` と 1 つの関数（`window_rows`）を共有する。 |
| `whole <dir> <read> text`・`text-kinds`・`text-kinds-synthetic`・`text-without:<kind>`・`text-parts` | `examples/kpi_read_memory.rs` | 下の「測り方」。解かない kind は `UNREAD_KINDS`（コードと合成の両方で読まない）と `SYNTHETIC_UNREAD_KINDS`（合成だけ）。 |

kpi・stats・report の呼び出しは変えていない（`ledger_window` は `WindowRows::new` で同じ読みをする）。答えの一致は合成の台帳の 5 つの読み（表の digest）と、unit test の `domain::ledger::window::payload_text::tests::a_kind_not_read_keeps_its_record_without_a_payload`・ `domain::ledger::window::tests::a_read_of_the_payloads_as_text_decodes_to_the_window_of_values`（窓の cursor ごと）・`infrastructure::runtime_store::ledger::read_from_tests::the_read_of_the_payloads_as_text_decodes_to_the_stores_window`（SQLite の store で、`read_from_ms` の有無）で確かめた。

### 後の Spike の入口（(1)+(2)）

`dagq::application::ledger_window_payload_text(&store, &query)` は store の `ledger_rows_after`・`ledger_rows_from`・`ledger_row` が返す行を取るので、queue 行の読みを要る列に絞った store（か、その読みを試作した `LedgerStore` の実装）を渡せば、そのまま (1)+(2) になる。example の `whole <dir> <read> text` がその読みを測り、`lean` と同じ表の列と段ごとの値を出す。試作の読みは 1 頁（`ROWS_PER_PAGE` の 50 行）の行の木を同時に持ち、`TextWindow::into_window_of_kinds` は解いた kind の木を畳む間ずっと持つ。

### 打ったもの

```sh
cargo build --release --locked --example kpi_read_memory
E=target/release/examples/kpi_read_memory
K=$TMPDIR/k
for n in 20000 100000 400000; do $E prepare $K/q$n $n; done
# kind ごとの確かめ（2 万件）: 1 つの kind の payload を解かずに、どの読みの答えが変わるか
for kind in $(合成の台帳の 30 の kind); do
  for read in kpi kpi-since observer stats stats-since; do $E whole $K/q20000 $read text-without:$kind; done
done
# 1 process に 1 読み、同時に 1 process だけ
for q in q20000 q100000 q400000; do
  for read in kpi kpi-since observer stats stats-since; do
    for candidate in lean text text-kinds text-kinds-synthetic text-parts; do
      $E whole $K/$q $read $candidate
    done
  done
done
# 確かめ: 2 万件の 2 回目
for read in kpi kpi-since observer stats stats-since; do
  for candidate in lean text text-kinds text-kinds-synthetic; do $E whole $K/q20000 $read $candidate; done
done
rm -rf $K
```

kind の読み手を数えたコマンドは下の「kind ごとの読み手」。合成の queue は `$TMPDIR` に置いた（40 万件で 703 MB、event 400,026 件・`ledger_rows` 242,650 行、payload の平均 154 bytes。列は前例と同じ固定の値）。

## 測り方

[kpi-read-memory-spike.md](kpi-read-memory-spike.md) の「測り方」の数え方（example だけの `#[global_allocator]` で `Layout::size` の和とピーク）・基準点（queue を開いた直後を 0）・1 process に 1 読み・3 GiB の上限・合成の列・外挿の式・線形性の基準（15%）をそのまま継承した。差分:

- 読み: kpi（`KpiQuery::default()`）・kpi --since・ObserverKpi・stats（`StatsQuery::default()`）・stats --since。since は合成の台帳の最後の event の時刻の 7 日前（`Cursor::Time`、kpi・stats とも同じ値）。kpi（既定）は今の `kpi::kpi` のとおり `read_from_ms` の範囲を読む（40 万件で窓は 14 日分なので一部の行を読まない）。kpi --since は全件を読む。
- lean は runtime の読みをそのまま測る（`kpi::kpi`、`stats::stats`、`report::window` と `observer_kpi_read` と同じ畳み方）。
- (1) は `ledger_window_payload_text` で読み、`text-kinds` は `TextWindow::into_window_of_kinds` で payload を読む kind だけを解き、`text` は全部を解いて、今の畳み方で答えを出す。全体のピークは、その process の全ての段（読み・解く・畳む）を通した数えた使用中の bytes の最大（実測）。段ごとに、読みのピーク・読みの後に持つ量・解くまでのピーク・解いた窓が持つ量・畳む層のピーク（解いた後で基準を取り直した確保のピーク）を出す。process の最大 = max(解くまでのピーク, 解いた窓が持つ量 + 畳む層のピーク)。
- 解く kind の選び方: 合成の台帳の 30 の kind ごとに、その kind の payload だけを解かずに 5 つの読みを 2 万件で流し、答えの digest を lean と比べた（`text-without:<kind>`）。答えが変わらない 16 の kind について、畳み方のコードに payload の読み手があるかを下の「kind ごとの読み手」で確かめた。両方で読まないと言えた kind だけを `UNREAD_KINDS` にした。合成で変わらないだけの 16 を全部解かない `text-kinds-synthetic` は参考（runtime がしてよい読みではない）。
- records の text の bytes は、`text-parts` が別の process で読みの後に `records` を複製して割り当てた量（読みの後に持つ量は `text` の process と同じ値）。複製は他の process の値に入らない。
- 周回: 組ごとに 1 回。2 万件の全ての組を 2 回ずつ流した差は全て 0 bytes（0.00%）で、1% を超えないので 3 回の周回はしていない。
- 上限: 3 GiB を超えて止まった組は無い（最大は 40 万件の stats の 1,146,209,193 bytes）。20 万件の代わりは要らなかった。
- event 1 件あたりの bytes = 全体のピーク ÷ 合成の event の件数（20,064・100,006・400,026）。

## RunEvent.payload の読み手と配線の大きさ

数えたコマンド（test の file と `tests` の directory を除く）:

```sh
rg -c '\.payload\b' src --type rust -g '!*test*' -g '!**/tests/**' | awk -F: '{s+=$2} END {print s, NR}'
# 1471 209
rg -c 'restore_payload' src --type rust -g '!*test*' -g '!**/tests/**' | awk -F: '{s+=$2} END {print s, NR}'
# 124 37
rg -c '\.payload\b' src/domain/stats src/domain/stats.rs src/domain/kpi src/domain/kpi.rs src/domain/ledger src/domain/ledger.rs \
  src/domain/live_alerts* src/domain/supervisor_life* src/domain/sessions* src/domain/areas* \
  src/application/stats.rs src/application/kpi.rs src/application/report.rs src/application/report \
  --type rust -g '!*test*' -g '!**/tests/**' | awk -F: '{s+=$2} END {print s, NR}'
# 335 51
rg -n 'fn [a-z_]+\([^)]*&\[RunEvent\]' src -g '!*test*' -g '!**/tests/**' | wc -l
# 288
```

`.payload` の 1,471 件（209 file）は `RunEvent` 以外の payload の欄も含む上限で、窓の畳み方が辿る module（stats・kpi・ledger・live_alerts・supervisor_life・sessions・areas と application の stats・kpi・report）に 335 件（51 file）。`&[RunEvent]` を受ける関数は 288（1 行の signature のもの）。

見積もり:

- `RunEvent.payload` の型を変える形は、窓の外（EventStore の読み、supervisor、headless session など）の読み手まで全部に当たり（1,471 件の大半）、この goal の範囲を超える。採らない。
- 窓だけを text にする形（試作の `into_window_of_kinds` は、この形の窓 1 つ分の粒度）: `LedgerWindow` が `TextEvent` を持ち、`events()` の代わりに kind の組を受けて解いた `RunEvent` を返す読み（例: `events_of(&[EventKind])`）を足し、畳み方の入口（`kpi::of_window` の `run_areas`・`heartbeats`・`derive`、`stats::of_window` の `stall_config`・`aggregate`・`run_areas`・`breakdown`、窓の `attributes`・`main_log`・`judgments`・`post_landing_book`・`executions`・`context_records` など十数か所）を、読む kind の分だけ解いた slice で呼ぶ。読み手の多く（335 件）は `&[RunEvent]` を受けたまま変えずに済むが、各入口が読む kind を漏れなく挙げる要があり、漏れは答えの違いになる（合成の台帳で答えが同じでも、読まない kind の証拠にならない。Spike 4246 の注意と同じ）。入口ごとに今の形と答えを比べる unit test（`application::window_read_tests` の形）が要る。入口ごとに読む kind をまとめて解いて渡す形は、解いた木をその入口の間ずっと持つので、読むところで 1 件ずつ解く形とはメモリの寿命が違う（その全体のピークは測っていない）。
- 解く kind を挙げずに済む形は、解いた窓を入口ごとに作って捨てる形だが、全体のピークは lean に戻る（全部を同時に解くため）。採らない。

## 後続の計画への推奨

1. kind の粒度で前もって解く形と、畳む前に全部を解く形は配線しない。実測で lean から 1% も下がらない（99.5〜101.2%）。
2. 読み手が読むところで 1 件ずつ解く形の配線の価値は未決。決めるには、読み手を書き換えて全体のピークと答えの digest を測る別の Spike か、測定を受け入れに持つ配線の task が要る。書き換えの大きさは上の「RunEvent.payload の読み手と配線の大きさ」（窓だけを text にする形で、畳み方の入口と `.payload` の読み手 335 か所）。推計（測っていない）の上限は 120 万件で約 0.92〜0.94 GB の削減で、その形だけでは text で読む段のピーク（約 1.12 GB、実測の外挿）があるので 1 GB に届かない。
3. 1 GB に近づけるには (1) の外も要る: 読みの段（読みのピークが持つ量を超える約 100 bytes/event と、records 以外の行の 448 bytes/event）、records の本体（解いても解かなくても 1 件ごとに `RunEvent` の本体と `created_at`・`run_id` の text を持つ）、stats の畳む層（1,248 bytes/event、120 万件に約 1.5 GB。合成の 16 の kind を解かない参考の形で 284,397,852 に下がるので、畳む層が payload の写しを持つ所がある）。(2) の Spike は `ledger_window_payload_text` を入口に読みのピークと全体のピークの両方を測ることを勧め、stats は畳む層の中身（`aggregate` などの層ごとのピーク）を分ける測定を先に置くことを勧める。
4. goal 271 の範囲の読みの draft（4122・4132〜4134）とは: 範囲の決まる問いはそちらで読む量自体が減り、(1) は範囲の決まらない問いだけに効く。読み手を書き換える Spike か配線の task を足すなら、触る所が `src/domain/ledger/window.rs`（`WindowRows`・`of_records`・窓の fold method）と `src/application/ports/observation.rs` で重なるので、範囲の読みの配線を先に着地させてから置くことを勧める。
5. 試作の `payload_text` と `ledger_window_payload_text` は、(1)+(2) の Spike と読み手を書き換えて測る Spike か配線の task が使った後、そのどれかが消す。

## 使った時間と試作の回数

- 時間: 約 2 時間（上限 3 時間）。build と合成の queue の用意と全ての組の測定、2 回の review の後の測り直しと、依頼の形を測るかの人の決定を待つ間の文書の直しを含む。
