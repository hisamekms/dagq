# design 文書の削減の前後比較の指標（M7）

goal 194（request 103）の A（書かないものの一括削除）と C（review の差し戻しの範囲）の前後で、run の review の差し戻しの回数・待ち・review の回数・worker の作業時間を同じ取り方で比べるための定義。
M7 は `scripts/docs-metrics.py` が数え、`scripts/docs-metrics-test.py` が fixture で確かめる。
M1〜M6 の定義と基準値は [docs/design の4指標](docs-slim.md) が持ち、この文書は変えない。

## 測り方

```sh
dagq events --full --kind review_finished --kind review_started --kind run_integrated \
  --since <since> --until <until> --limit 1000 --after <cursor> > events-run-<頁>.json
dagq stats --full --since <since> --until <until> > stats.json
python3 scripts/docs-metrics.py --since <since> --until <until> --metrics m7 \
  --run-events events-run-*.json --stats stats.json --format json
```

- `--run-events` は `dagq events` の JSON を保存したファイル（複数可。頁送りの各頁）。全てのファイルを通して event ID が同じものは1件（最初に読んだもの）で、`created_at`（UTC）が `[since, until)` に入るものだけを数える。
- `--stats` は M3 と同じ渡し方で、M7 は worker の作業時間だけをそこから読む。省くと `worker_work` は `null`。
- `--ask-events` は (h) の入力で、渡し方は下の (h)。
- `--run-events` を省くと M7 は `null`。script は queue を読まない。

## M7 の定義

規則は planner が request 103 の測定の要求から決めたもの（task 1689 と 2289 の定義を元にした）で、下の参考の値に合わせて調整しない。

- **(a) review の回数**: 期間の `review_finished` の event の数（`attempt` を問わない）と、その `run_id` の異なる数。
- **(b) 差し戻し**: `review_finished` のうち、payload に `route` があれば `route.destination` が `send_back` のもの、`route` が無ければ `verdict` が `revise` のもの。
  `route` のある event は `verdict` によらず `route` で決める（`revise` でも `route` が `ask` なら差し戻しではない）。
  `verdict` が `concern` で `route` の無いものは差し戻しに数えず、件数を `concern_without_route` に出す。
  `route` で決まったものと `verdict` で決まったものの件数も別に出す。
- **(c) ドキュメントの理由**: 差し戻しの `reasons`（理由の文の配列）の添字 i の理由は、`reason_codes[i]`（同じ添字の理由の code の配列）が配列で `docs_drift` を含むか、文 `reasons[i]` が次の path を名指せばドキュメントの理由。
  - 名指しの path: `docs/` の下の path、`plugins/` の下の `.md`、root の `AGENTS.md`・`README.md`。語の始まりで始まるもの（前が ASCII の英数字・`_`・`.`・`-`・`/` でない。日本語の文字は前後に接してよい。先頭の `./` は許す）だけで、`src/docs/...` や `foo/README.md` は名指しに数えない。
  - code の欠け: `reason_codes` が無いか配列でない event は、どの理由も code を持たないとして文の名指しだけで決める。`reason_codes` が `reasons` より短く添字 i の code が無い理由と、`reason_codes[i]` が配列でない理由も、文の名指しだけで決める。`reason_codes` が `reasons` より長いときの余りの code は理由に数えない。
  - 形の崩れの件数: 差し戻しのうち `reason_codes` が無い（配列でない）event・`reasons` より短い event・長い event の数と、配列でない `reason_codes[i]` の理由の数を、それぞれ別の欄（`reason_codes`）に出す。
  - ドキュメントを含む差し戻し（`docs_any`）: ドキュメントの理由を1つ以上持つ差し戻し。
  - ドキュメントだけの差し戻し（`docs_only`）: 理由が1つ以上で、全部がドキュメントの理由の差し戻し。`reasons` が無いか空の差し戻しはどちらにも数えず、件数を `without_reasons` に出す。
- **(d) 差し戻しの待ち**: 差し戻しの `review_finished` の `created_at` から、同じ run の次の `review_started`（`created_at`、同じ時刻なら event ID の順で後のもの）の `created_at` まで。
  期間の中に次の `review_started` が無ければ期間の終わりで打ち切り、打ち切りの件数を `cut` に出して合計と中央値に含めない。
  全体・ドキュメントを含む・ドキュメントだけの3つについて、合計（秒と時間）・中央値（秒）・件数。
- **(e) 着地の数**: 期間の `run_integrated` の event の数。
- **(f) worker の作業時間**: `dagq stats --full` の JSON の `runs[].work`（`run_claimed` から最初の `receipt_observed` までの秒。2026-10-13 の `src/domain/stats.rs` の `RunStats` で確かめた）の、`null` を除いた中央値と件数。
  run を選ぶのは `dagq stats` の `--since`・`--until`（run の終わりの時刻で選ぶ。`--since` は含まず `--until` は含む）で、events の `[since, until)` と境界が違う。
- **(g) 比**: review あたり（差し戻し・ドキュメントを含む・ドキュメントだけの回数 ÷ review の回数）、着地あたり（review の回数 ÷ 着地の数、待ちの合計の時間 ÷ 着地の数）、1日あたり（review・差し戻し・ドキュメントを含む・ドキュメントだけ・待ちの時間・着地 ÷ 期間の日数）。
- **(h) 人の答え待ちを引いた値**: (d) の待ちと (f) の作業時間から、run を止める ask の待ちを引いた値。
  - 入力: `--ask-events`（複数可）に `dagq events --full --kind ask_opened --kind ask_answered --kind ask_closed --kind run_claimed --kind receipt_observed` の JSON の頁を渡す。全てのファイルを通して event ID が同じものは1件で、`[since, until)` で絞らない（区間の前に開いた ask と、区間の前に claim した run を読むため）。省くと (h) の欄（`ask_waits`・`waits_without_asks`・`worker_work_without_asks`）は `null`、`--stats` を省くと `worker_work_without_asks` は `null` で、(a)〜(g) の値は `--ask-events` の有無で変わらない。
  - 対象の ask: `ask_opened` のうち event の `run_id` があり、payload の `kind` が `blocked`・`planner_question` でないもの（run を止める ask。`dagq timeline` の `waiting_ask` と同じ規則）。`run_id` の無い ask は引かない。
  - 待ちの始まりと終わり: 始まりは `ask_opened` の `created_at`。終わりは同じ payload の `ask_id` の最初の `ask_answered` と最初の `ask_closed` の早い方の `created_at`。
  - runtime が閉じた ask と ask_opened の無い終わり: 終わりの event の payload が `runtime_closed: true` の ask は人の待ちでないので除き、件数を出す（`dagq stats` の人の待ちと同じ）。`ask_opened` が入力に無い `ask_answered`・`ask_closed` は数えず、その `ask_id` の数を出す。
  - 未回答: 入力に終わりの無い ask は終わり無し（区間の終わりを越えて続く）として扱い、件数を出す。
  - 重なり: 同じ run の対象の ask の区間は和集合にし、重なった時間を 2 度引かない。
  - 測る区間との交差: 引くのは、測る区間とその run の和集合の交わりの長さだけ。
  - 差し戻しの待ち: (d) と同じ端の待ち（打ち切りは (d) と同じく除く）ごとに、[差し戻しの `review_finished`, 次の `review_started`) とその run の和集合の交わりを引く。全体・ドキュメントを含む・ドキュメントだけの3つについて、引いた後の合計（秒と時間）・中央値（秒）・件数・打ち切りの件数と、引いた時間の合計（秒）。
  - worker の作業時間: (f) と同じ `runs[].work` が `null` でない run ごとに、`--ask-events` の同じ `run_id` の最初の `run_claimed` から最初の `receipt_observed` までを測る区間とする（`[since, until)` で切らない）。区間の長さが `runs[].work` と 1 秒より大きく違う run と、入力に `run_claimed` か `receipt_observed` の無い run は除いてその件数を出し、残りの run の `runs[].work` から交わりを引いた値の中央値（秒）・件数と、引いた時間の合計（秒）。
  - (h) は JSON だけに出し、Markdown の表には足さない。

## 比べる区間

期間の長さが違うので、回数と待ちは1日あたり・review あたり・着地あたりの値を並べて比べる。
着地の時刻は、その task の run の `run_integrated` の event の `created_at`。

| --- | --- | --- |
| 基準 | 2026-10-05T15:03:00Z | 2026-10-12T00:38:00Z |
| A の前 | A の task（2335〜2351）の最初の着地の 6.4 日前 | その着地 |
| A の後 | A の task の最後の着地 | C の task 2353 の着地 |

| C の後（全体） | 2353 の着地 | 2353 の着地の 6.4 日後 |

基準の区間は request 103 の人の分析と同じ期間で、script で数え直した値を基準にする。

- **A の前は F・D の効果を含む**: request 103 の F・D の着地は A の前の区間に入る。A の前と A の後の差は A だけの効果ではなく、F・D の後に A を足した差。基準と A の前の差は F・D とその間の他の変化を含み、A の効果ではない。

- **別の run の重複（104 件、58%）は畳まず、今のまま draft の planner が閉じる**: 重複先の 83 件（80%）は登録の 1 日以上前に登録された task か draft（閉じた時点で `ready` 52・`completed` 21・`in_progress` 6・別の run の draft 4）で、65 件は着地した 2164・2165 の 2 task に集まった一過性のもの。runtime が別の run の同じ文書・節の draft や task に寄せるのは、重複の判定を draft の planner に置く ADR-0063 から外れる。ADR-0063 は決定7で follow_up の planner が候補を `related` で取り出して LLM で重複を判じ、決定5の形（`cancel --duplicate-of`）で記録して閉じると決め、[Draft planners](../design/supervisor-lifecycle/draft-planners.md) はそれを draft の planner の役目とする。登録の前に runtime が機械の鍵で別の run の draft や task に寄せると、cancel の記録は要らなくなるが、決定7の LLM の判断を通らずに重複を決めるので、選ぶなら ADR を書く task が要る。同じ文書の別の節や同じ節の別の食い違いを機械の鍵で落とす恐れもあり、得るのは 6.4 日で約 1.3 時間（重複の draft の分の時間 2.7 時間から同じ run の分 1.4 時間を引いた算術、1 件あたり約 45 秒）の planner の時間だけ。review の材料に差分が触った文書の開いている docs_drift の draft と task を載せる案は、全ての review の prompt を大きくして、planner が `related` で引いている突き合わせを review に移すだけで、手間の総量は減らない。
- **同じ run の前の回の review の重複（58 件、32%）は登録の前に畳む**: 同じ run の中で同じ食い違いを重ねて作らないことは既に runtime の受け持ち（ADR-t2352-1 決定3・4）で、今の (path, 節) の鍵が review の節の書き方の揺れで外れている。runtime が review の材料にその run の前の回の review が返した follow_up（path・節・理由）を載せ、review がそれと同じ食い違いを返さない（返すなら同じ path と節の文字列で返す）ようにする。重複を runtime の機械の鍵で決めず review（LLM）の判断に置き、別の run の task との重複はこれまでどおり draft の planner が判じて決定5の形で閉じるので、ADR-0063 決定5・7 と食い違わない。ADR-t947-3 決定2 は重複を follow_up の種類のコードに入れないこと（重複は結末として記録する）で、この案は種類のコードも結末の記録も変えないので当たらない。減る見込みは重複の 32%（58 件）・planner の時間 1.02 時間 / 6.4 日・束の全部が重複の planner の起動 27 回で、材料は run ごとの数件で済む。
- **同じ run の同じ回の review の重複（16 件）と receipt の follow_up との重複（1 件）は畳まず、今のまま draft の planner が閉じる**: 前の回の follow_up を材料に載せる案では減らない（同じ回の job は並んで走り互いの follow_up を見ず、receipt の follow_up は review の follow_up の材料に無い）。どれも重複先と同じ束に入り、16 件中 14 件と receipt の 1 件は重複先と同じ planner が 1 つの束で採用と重複を決めたので、束の全部が重複の planner は 0 回で、手間は 6.4 日で 0.38 時間。同じ回の job の follow_up を runtime が path だけで 1 つにするのは、同じ文書の別の食い違いを落としうるうえ ADR-t2352-1 決定3 の (path, 節) の鍵を変えるので、この手間に見合わない。

#### 経路（reasons が空になる理由）

- **全体の review が `pass` で subagent が `revise` の review（107 / 107）**: run の review は全体の review の job と、paths で選ばれた subagent ごとの job を並列に流す。`src/application/supervise/execution/landing.rs` の `judge_review` は、`src/domain/review_jobs.rs` の `assemble`（全体の review の verdict に agents の結果を足すだけ）の verdict の `reasons`・`reason_codes`・`primary_code` を `review_finished` に書き、agents の結果は `agents` に、行き先は `src/domain/review_subagents.rs` の `route`（親と各 agent の行き先の最も重いもの）の `VerdictRoute::event_value` で `route` に書く。全体の review が `pass` で `reasons` を返さないと、`review_finished` の `reasons` は空で、差し戻した理由は `agents[].reasons` にだけある。
- **worker には理由が届く**: 差し戻す先は `act_on_verdict` → `act_on_agents` で、`combined_verdict`（同じ file）が `src/domain/mod.rs` の `ReviewVerdict::sent_back_findings` で、`route.parent` が `route.destination` と同じときだけ親の `reasons` を、`route.deciding()` の agent の `reasons`（無ければ `summary`）を agent の名を付けて並べ、`send_revise` がそれを revise の依頼と `revise_requested` の `reasons` に載せる。理由なしの差し戻しは worker が理由なしで直されたのではなく、M7 (c) が `review_finished` の `reasons`（全体の review のものだけ）しか読まないことによる。
- **review の上限の後の判定**: `send_revise` は上限を使い切った run を `past_revise_limit` → `judge_past_revise_limit` に回し、同じ `sent_back_findings` の理由で着地か `approve_landing` かを決める。`review_finished` はその前に `judge_review` が書くので、上限の後でも `reasons` の形は変わらず、空になる経路を足さない。ただし上限の後に着地した review も `route.destination` は `send_back` のままで、M7 (b) は差し戻しに数える。
- **プログラムの review**: `go_on_with_programs`（`landing.rs`）は、プログラムが変更を拒んだとき `review_programs_finished` に理由を書いて `send_revise` で返し、`review_finished` を書かない。M7 の入力（`review_finished`）に入らないので、理由なしにもどの差し戻しにも数えない。

#### 判断

- **増えの出どころ**: 理由なしの差し戻しは全て「全体の review が `pass`、subagent が `revise`」の review で、`reasons` が空なのは review の形（task 1903 の並列の job）と M7 (c) の読む欄の組み合わせによる。基準 4.0%→C の後 28.0% の増えは、基準の大半が task 1903 の前の形だったことと、subagent だけが差し戻す review の割合（差し戻しのうち、task 1903 の後の基準 15 / 100・A の前 58 / 219・C の後 110 / 382 の 15.0%・26.5%・28.8%）の増えによる。後者の理由は測っていないが、C（全体の review が差分の触っていない文書の指摘を差し戻さない）の後に全体の review が `pass` を返す review が増えた向きと合う。理由なしの中身は `receipt-evidence`（93 / 107）の手元の検証・stress・E2E の根拠の指摘が主で、そこは「C の後のドキュメント以外の理由だけの差し戻しの内訳」の「既にあるものが持つ分」（task 3240・3241・3257・3258）が減らす向き。
- **runtime の直し: 不要**: worker には `sent_back_findings` で subagent の理由が届き、上限の後の判定も同じ理由を読む。`review_finished` は全体の review の `reasons` と `agents[].reasons` を分けて残していて、情報は欠けていない。
- **M7 の定義の直し: 要る（follow_up）**: M7 (c) が `review_finished` の `reasons` だけを読むので、task 1903 の後の区間では subagent だけの差し戻しの理由を数えず（107 回）、`concern` で着地に回った親の `reasons` を差し戻した理由に数える（3 回）。この 107 だけを `agents[].reasons` で読み直すとドキュメントを含むは 11・だけは 10 増える（両方・親だけの差し戻しの読み直しで変わる分は数えていない）。定義を `sent_back_findings` と同じ組み立て（`route.parent` = `route.destination` のときだけ親の `reasons`、`route` で `send_back` の agent の `agents[].reasons`）に直し、基準・A の前・C の前・C の後の区間を同じ入力で流し直す。上限の後に着地した review を差し戻しに数えること（入力に `revise_limit_judged` が要る）と、プログラムの review の差し戻しを数えないことを定義に書くかも、そこで決める。
- **次の打ち手の対象選び**: 理由なしは独立の出どころではなく subagent（主に `receipt-evidence`）の差し戻しなので、差し戻しを減らす打ち手の対象は「C の後のドキュメント以外の理由だけの差し戻しの内訳」の subagent の行に足して読む。理由なしだけを減らす runtime の打ち手は足さない。

## 区分

- SSOT: queue の EventStore（run の event）。M7 は git の履歴も会話記録も読まない。
- 入力: `dagq events --full` と `dagq stats --full` の JSON は EventStore から作り直せるビュー。EventStore の該当の期間の event が残る限り同じ入力を作り直せる。
- 出力: script の JSON の `m7` と Markdown の表は、入力から `scripts/docs-metrics.py` で作り直せるビュー。
- 人の分析の参考の値は材料で、取り方が残っていないので作り直せない。
- 保存する JSON の置き場は [docs/design の4指標](docs-slim.md) の「保存」と同じ dir（`~/.local/share/dagq-hostmetrics/docs-slim/`）に、入力を `events-run-<since>_<until>-<頁>.json`、出力を `m7-<since>_<until>.json` として置く。
